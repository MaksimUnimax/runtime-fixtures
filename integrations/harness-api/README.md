# Octoport: DeepSeek API + матрица Алисы

Задание владельца от 18 ноября 2026: перейти с браузерного DeepSeek Web на API DeepSeek, использовать действующий рабочий ключ Алисы, сохранить её фильтр выбора шаблонов и кэширование, отдавать готовый ответ обработчика в чат без финальной LLM.

## Рабочая схема

`аккаунт Алисы → Octoport UI → Harness 0.2.2-rc.1 → octoport-templates → штатный selector DeepSeek → матрица/шаблон → API магазина → штатный обработчик → прямой ответ → Harness history → браузерное озвучивание`

Вход и магазины принадлежат существующему аккаунту Алисы. Канонический адрес — `https://alisa.octoport.ru/harness/`. Сохраняется штатная `__Host-alisa_session`; ключ модели не заменяет пользовательскую авторизацию. Переход через `/harness/login` использует существующую страницу входа и возвращает в фиксированный адрес чата после обычного `/app` callback. Маркер возврата не предоставляет доступ.

## Компоненты

| Каталог | Назначение |
| --- | --- |
| `engine/` | Настоящий Harness AgentLoop, provider, история и идемпотентность |
| `backend/` | Авторизация, владелец запроса, импорт живого ядра Алисы, прямой вывод |
| `static/` | Интерфейс, разговоры, безопасное отображение, диктовка и озвучивание |
| `deploy/` | Службы, nginx и изоляция метаданных запросов от обычной очереди Алисы |
| `tests/` | Синтетические браузерные проверки и проверки расчётного вывода |

Engine слушает `127.0.0.1:18132`, gateway — `127.0.0.1:18131`. Внешний nginx публикует только `/harness/`; внутренний execution endpoint не публикуется. Родительские сервисы Алисы и её голосовой канал продолжают использовать свою очередь.

## Ключ и модель

Рабочий DeepSeek API key читается через systemd `LoadCredential` из существующего файла `/var/lib/alice-lab/secrets/deepseek.key`. Его значение не записывается в репозиторий, фронтенд, метаданные диалогов или отчёт. Пользователь не вводит API key.

Официальный provider `deepseek-official` настроен тем же серверным credential. Основная модель Harness — `octoport-templates/alisa-matrix`: она вызывает уже существующий DeepSeek selector Алисы, который сохраняет свой Chat Completions transport и порядок префикса. Это исключает дополнительный агентный вызов перед selector.

Финальная формулировка создаётся из проверенных обработчиков и расчётных контрактов. Запросы к операциям финального model answer блокируются в отдельном transport этого процесса. Текст и расчётные строки не оцениваются как платные выходные токены модели. Реальные token usage и cache hit/miss берутся из квитанций selector.

## Сохранение доступа и результатов

На каждом API-запросе проверяется актуальная сессия. Chat ownership включает customer и tenant. Внутренний adapter получает только binding, созданный после входа; произвольный actor из browser payload или текста не принимается. Магазины проверяются по штатной authority; их ключи остаются в Алисе.

Для расчётов с коэффициентами создаются настоящие WEB Query metadata receipts с прежним подтверждением пользователя. Marker `harness_runtime_v1` отделяет их от обычной истории и диспетчера Алисы. Guarded patch сохраняет порядок проверки owner, TTL и principal и запрещает отправку такой записи в другой runtime. Схема БД и формат подтверждения не меняются.

`request_id` защищает от повторного исполнения после двойного клика и потери ответа. Неизвестный исход не запускает автоматический повтор. Незавершённые jobs после перезапуска становятся interrupted; новая явная реплика получает новый идентификатор. История Harness сохраняется отдельно от секретов авторизации.

## Проверки и пределы доказательств

Тесты engine должны выполняться с установленным точным Harness без пропусков. Fixture pipeline не доказывает фактические данные маркетплейса. Браузерные тесты используют синтетический аккаунт и отдельный временный Chrome; мобильный viewport не является физическим телефоном владельца.

Финальные результаты установки, вызовов рабочего API, сохранности native service и конкретные хеши публикуются в `DEPLOYMENT.md` после проверки. Результаты не подменяются статусом запущенного процесса.

## Обслуживание

Пути исходного ядра и платформы фиксируются в gateway unit для проверенного релиза. После смены ядра, матрицы или настроек selector обновить эти привязки и перезапустить gateway; его systemd credentials загружаются при старте. Поддерживать совместимость native QueryService isolation patch при следующем выпуске платформы. Текущие настройки API ключа меняются только в исходном защищённом файле с последующим перезапуском обоих Harness сервисов.

Озвучивание выполняется SpeechSynthesis браузера, без вызова модели. Наличие русского голоса и поддержка диктовки зависят от браузера; текстовый чат остаётся основным доступным каналом.
