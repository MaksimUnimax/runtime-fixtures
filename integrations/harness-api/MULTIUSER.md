# Многопользовательская схема Harness

## Вход и владение

1. Пользователь открывает `/harness/` и проходит обычный вход Octoport. Harness не заводит отдельную базу паролей и не выдаёт общую owner-ссылку native Host.
2. Gateway проверяет актуальную сессию и получает `customer_id`, `tenant_id`, состояние аккаунта и действующие полномочия из штатной системы авторизации.
3. Engine получает доверенные actor/tenant только от gateway по закрытому loopback API. Cookie, DeepSeek key и ключи магазинов в engine history не записываются.
4. Чат, job, настройки плагинов и выдача квитанций привязаны к точной паре actor/tenant. Даже два пользователя одного tenant имеют отдельные чаты и настройки. Доступ к магазину определяется действующим членством и authority, а не знанием его ID.

Клиент не может указать другой actor/tenant в JSON или сообщении. Чужие chat/job/report IDs не предоставляют доступ. На чтении и записи проверяется актуальная сессия; отзыв сессии прекращает новые обращения. Выход очищает отображённые сообщения и панели; запоздавшие ответы предыдущей сессии отбрасываются. Локальные указатели последнего чата и незавершённого запроса разделены по actor/tenant и не являются разрешением на сервере.

## Магазины и данные

Для вопроса gateway создаёт binding со своим request ID, actor/tenant, chat, хешем вопроса, разрешёнными магазинами и исходной сессией. Перед исполнением и доступом к отчёту штатная authority повторно проверяет доступ. Привязку уже принятого запроса нельзя заменить токеном другого входа.

DeepSeek key общий серверный рабочий ключ. Он оплачивает запросы всех пользователей, но не даёт им доступ к аккаунтам, истории и магазинам друг друга. Provider credentials магазинов остаются в существующей системе Алисы. Формат входа в matrix и её tenant-aware cache сохранён; общая очередь Harness не является общим диалогом.

## Плагины

Общий процесс содержит только доверенные модули из выпуска. Пользовательские переключатели меняют сохранённые feature preferences, а не устанавливают npm-пакеты и не выгружают общий Cordis модуль.

| Настройка | Кто видит изменение | Приоритет |
| --- | --- | --- |
| Значение по умолчанию манифеста | Пользователь без собственных настроек | Базовый |
| Настройка аккаунта | Только данный actor/tenant | Выше манифеста |
| Настройка чата | Только данный чат этого actor/tenant | Выше аккаунта |
| Обязательный `plugin-manager` | Всегда включён | Не отключается |
| Серверное разрешение плагина | Только явно разрешённые пользователи | Проверяется до настроек |

`включи плагин матрица` действует в текущем чате. `/plugins account enable matrix` меняет значение по умолчанию для своего аккаунта, сохраняя явные исключения отдельных чатов. Эти команды работают без подключённых магазинов и без вызова DeepSeek. Неизвестная явная команда переключения возвращает подсказку, не отправляется платному selector.

При приёме сообщения сохраняется снимок возможностей и ревизия настроек. Последующее переключение не меняет выполняющийся запрос. После перезапуска настройки и история сохраняются; сомнительные незавершённые вызовы не повторяются автоматически.

## Плагин разработчика

Серверный файл `/etc/octoport-harness/developer-principals.json` имеет формат:

```json
{
  "schema": "octoport-developer-principals/v1",
  "principals": [
    {
      "actor_id": "VERIFIED_CUSTOMER_UUID",
      "tenant_id": "VERIFIED_TENANT_UUID",
      "permissions": ["developer_meter"]
    }
  ]
}
```

Это пример структуры; реальные идентификаторы не входят в исходники. Пары должны быть подтверждены из действующего identity/account linkage. Совпадение имени или роль `OWNER_CLIENT` не являются основанием для выдачи разрешения.

Gateway получает файл как `LoadCredential=developer_principals`, а engine — только вычисленную capability текущего пользователя. Отсутствие, неверный формат или небезопасные права означают отсутствие доступа. Значения browser JSON и модели не могут добавить capability. В production systemd credentials являются снимком на запуске: после изменения файла нужно перезапустить gateway.

Доступ к каталогу, действиям, per-request meter и истории проверяется повторно engine. Если право отозвано или плагин выключен, старый текст частной команды расхода тоже скрывается, включая сбой между native commit и сохранением job receipt. Gateway дополнительно выдаёт только разрешённые поля ответа. Пользователь без developer grant не получает usage, meter и цены.

Разработчик видит собственные запросы. Глобальная сводка всех клиентов не включена. Добавить второго разработчика можно отдельной проверенной парой в приватном allowlist; общую роль владельца магазина использовать нельзя.

## Ограничения текущего выпуска

Это несколько пользователей на общем сервере с проверяемым логическим разделением. Отдельные контейнеры, процессы и DeepSeek API keys для каждого клиента не создаются. Новые плагины — доверенный код сервера; выполнение произвольного пользовательского кода не разрешено. Новый плагин обязан использовать переданный trusted scope и проверять свои ресурсы.

Существующие общие ограничения ресурса engine и gateway сохранены. Индивидуальные коммерческие тарифы, клиентские бюджеты, выставление счетов и отдельный платёжный баланс в этом выпуске не реализованы. Счётчик разработки отражает API-квитанции и датированные оценки рублей, не является биллингом клиентов.

## Проверка

Actual-runtime engine tests проверяют двух владельцев, разные tenant и чаты одного аккаунта, отсутствие чужой истории и переключателей, независимые overrides, запрет developer actions обычному пользователю и сохранение предпочтений после рестарта. Backend tests проверяют сессию, Origin/Host, caller-derived scope, магазины, отчёты, no replay и фильтрацию developer metadata. UI tests проверяют поздние ответы после выхода/перехода и разделённые страницы плагинов/расхода.

Эти проверки используют синтетические пользователи и не создают фиктивные живые login sessions. Production readiness services/маршрутов и private allowlist проверяется отдельно; фактические магазинные ответы требуют настоящей пользовательской сессии.
