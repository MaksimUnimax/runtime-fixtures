# Аккаунты и два чата в общем Harness

Эта поставка добавляет локальный HTTP-вход в платформу. Пользователь создаёт аккаунт в браузере, входит с паролем и продолжает чат с другого клиента. Оператор также может создать аккаунт через CLI. Приёмка использует штатные Session, Agent и MCP-клиент Harness 0.2.2-rc.1. Для ответа модели в этой проверке оператор явно включает детерминированный тестовый провайдер. Ответы воспроизводимы и внешние ключи для них не нужны.

Режим обработки сообщений через модельный шлюз и связь ответа с расходом описаны в [учёте вызовов из чата](METERED_CHAT.md).

## Запуск

Из каталога `products/harness-platform` с Python 3.12 и Node 24:

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
mkdir -m 700 -p .local
npm install --prefix .local/harness --ignore-scripts --no-audit --no-fund @deepseek-ai/dsh@0.2.2-rc.1
export HARNESS_NODE_MODULES="$PWD/.local/harness/node_modules"
export HARNESS_OFFLINE_MODEL=1
python -m platform_core.chat_service --db .local/platform.sqlite3 create-account seller-a
python -m platform_core.chat_service --db .local/platform.sqlite3 create-account seller-b
python -m platform_core.chat_service --db .local/platform.sqlite3 serve --chats .local/chats --composition examples.reference_plugin
```

Оператор вводит пароль в скрытом приглашении и передаёт владельцу показанный один раз код восстановления. Команда запускает один процесс API на `127.0.0.1:8765`. Без подключения эталонного модуля можно опустить `--composition`. Если убрать `HARNESS_OFFLINE_MODEL`, сохраняются вход, работа с историей и разрешёнными инструментами. Платный провайдер модели к этому входу ещё не подключён.

## Вход через браузер

После запуска откройте `http://127.0.0.1:8765/login`. Войдите под первым аккаунтом, нажмите кнопку создания сессии и отправьте короткую фразу. Откройте второй профиль браузера и войдите под вторым аккаунтом. Ссылка на чужой чат возвращает 404. После обновления своей страницы отправьте второе сообщение. В тестовом режиме ответ содержит предыдущую фразу именно этого пользователя. Переключение на «Траекторию» показывает события тех же ходов. «Выйти» отзывает сессию текущего профиля.

В продукте две страницы. На `/` для гостя и владельца аккаунта загружается штатный веб-клиент Harness 0.2.2-rc.1. Окно разговора, боковая панель, редактор и история принадлежат штатным плагинам. Плагин аккаунта размещает вход, регистрацию и баланс в слотах того же клиента. Адреса отдельных бесед открывают этот же клиент. На `/admin` администратор начисляет монеты и смотрит расходы. Сервер проверяет роль при открытии страницы и при каждом административном запросе.

Браузер передаёт запросы через транспорт платформы. Сервер проверяет cookie, Origin для изменяющих запросов и права на конкретный чат. Гостевой обработчик читает только публичную справку. При входе с другого устройства история загружается из серверного журнала.

При загрузке сервер сверяет SHA-256 входного скрипта веб-клиента с закреплённым выпуском. В этом выпуске Cordis создаёт интерпретатор JavaScript-выражений из YAML через `new Function` даже при статическом списке модулей. Для сборки кабинета сервер отключает только эту фабрику при выдаче скрипта. Страница работает с политикой `script-src 'self'`. При обновлении Harness нужно сверить новый файл и повторить браузерную приёмку. Локальные пакеты и компоненты представлений используются из установленного выпуска.

## Из гостя в свой аккаунт

1. Откройте `/` в новом профиле браузера. Отправьте «Как сохранить историю?». В гостевой беседе отвечает локальная справка о сервисе. Запомните адрес чата.
2. Нажмите «Создать аккаунт и сохранить чат». Выберите логин и пароль длиной от 15 до 256 символов. Сохраните показанный код восстановления и отправьте форму. Сервис выдаст сессию владельца и откроет тот же адрес в штатном представлении Harness. Кнопка «Создать аккаунт» на странице входа также позволяет начать с пустого чата.
3. Продолжите переписку. В тестовом режиме ответ на следующий ход содержит предыдущую гостевую фразу. Войдите в другом профиле под созданным логином и откройте чат из списка. Оба устройства видят одну историю.

Все посетители получают ответы из одной базы публичной справки о сервисе. У гостевого консультанта нет ключей и доступа к API, моделям и данным магазина. Число уже полученных ответов не ограничивает дальнейшую переписку. [Устройство и проверка справки](GUEST_ASSISTANT.md). Срок жизни текущего черновика — 24 часа с момента создания. Просроченные черновики недоступны сразу, физическая очистка происходит при запуске сервиса и создании нового гостевого чата.

Форма регистрации привязывает существующий идентификатор разговора к новому владельцу в одной транзакции с созданием аккаунта и сессии. После этого прежняя гостевая cookie теряет доступ к переписке. Если ответ сервера потерялся, повтор исходной формы возвращает тот же чат и действующую сессию. Занятый логин можно сменить с сохранением черновика. Выход или восстановление пароля отзывает прежнюю сессию. Сохранённая форма её не возобновляет.

Сервис хранит исходные гостевые реплики в базе платформы. При первом обращении владельца нативный процесс записывает их в журнал Session одной транзакцией, с исходным порядком и временем. Чтение, запись и повтор после перезапуска используют одинаковый механизм. Доступ к инструментам определяется текущими правами владельца.

## Договор HTTP

Клиенты с явным bearer-токеном продолжают использовать тот же контракт. JSON-запросы используют `Content-Type: application/json`. После входа клиент передаёт заголовок `Authorization: Bearer <token>`. Сервер определяет пользователя и кабинет по сессии. Клиент выбирает чат по возвращённому идентификатору. Ответ на обращение к неизвестному или чужому чату — HTTP 404. После истечения или отзыва сессии нужен новый вход.

| Метод и путь | Тело | Успешный ответ |
| --- | --- | --- |
| POST /api/login | `{"login":"…","password":"…"}` | Токен устройства в поле `token` |
| POST /api/logout | — | 204, сессия этого устройства отозвана |
| POST /api/recover | `{"login":"…","recovery":"…","password":"новый пароль"}` | Новый одноразовый код в поле `recovery`, предыдущие сессии отозваны |
| POST /api/chats | — | 201, новый `chatId` |
| GET /api/chats | — | Массив идентификаторов своих чатов |
| POST /api/chats/{id}/turns | `{"requestId":"t1","text":"…"}` | Реплика ассистента после штатного хода |
| POST /api/chats/{id}/messages | Те же поля | Одна пользовательская реплика без запуска агента |
| GET /api/chats/{id}/messages | — | Упорядоченные реплики с полями `requestId`, `role`, `text` |
| GET /api/chats/{id}/events | — | Одна страница видимых событий и реплик, курсор более ранних ходов в `nextBefore` |
| GET /api/chats/{id}/tools | — | Доступные имена инструментов |
| POST /api/chats/{id}/tools/{name} | `{"arguments":{…}}` | JSON-результат инструмента |

При повторной отправке хода клиент передаёт тот же `requestId`. Совпадающие запросы в пределах одного чата возвращают записанную реплику. Другое действие или текст под тем же ключом даёт 409. История по умолчанию охватывает последние 30 записанных ходов. `?limit=10&offset=10` возвращает предыдущие десять в хронологическом порядке. В одном ходе может быть несколько реплик. Максимальное окно — 50 ходов.

Страница событий возвращает последние 20 ходов. Для продолжения клиент передаёт полученный курсор через `?before=…`. Сервер выбирает строки по неизменяемому номеру ревизии, поэтому новые реплики не сдвигают более раннюю страницу. Браузер получает текст пользователя и ответа и события начала и завершения ходов и шагов. Системные инструкции и внутренние запросы модели остаются в журнале сервера.

## Как проверить

```bash
export HARNESS_TEST_PYTHON="$PWD/.venv/bin/python"
python -m unittest discover -s tests -p test_account_chat_e2e.py -v
python -m unittest discover -s tests -v
node --test native/*.test.mjs
```

Браузерная проверка запускает собственный сервер на свободном порту и использует временные аккаунты.

```bash
python -m pip install playwright==1.62.0
python -m playwright install --with-deps chromium
python -m unittest discover -s tests/browser -v
```

Сквозной тест создаёт две отдельные учётные записи, выдаёт право на тестовый инструмент только первой и запускает параллельные HTTP-запросы. Оба владельца могут использовать один и тот же ключ запроса в своих чатах. Тест проверяет ответы ассистента, отказы при обращении к чужому чату, сохранение после рестарта, вход с другого клиента, выход и восстановление по одноразовому коду.

## Хранение и границы поставки

В базе платформы находятся хеши паролей, дайджесты сессий и кодов восстановления, принадлежность чата и права на модули. Отдельная приватная база в каталоге `--chats` хранит события Session и ключи повтора. Для резервного копирования остановите локальный экземпляр и сохраните обе базы вместе. Права файловой системы на оба каталога должны быть у оператора сервиса.

Один сервер API обслуживает сессии в общем процессе Node. Для каждой операции он восстанавливает область по серверной сессии и передаёт её по приватному stdio. Нативные контексты инструментов разделены. Порядок команд внутри чата сохраняется. Пользователь может зарегистрироваться самостоятельно. Следующий шаг касается потоковой доставки событий своего чата и восстановления после обрыва. В текущей браузерной версии реплика появляется после завершения хода. Прямой вызов инструмента предназначен для проверенных расширений чтения текущего каркаса. Семантика повторов для платных и изменяющих операций относится к этапу 3.
