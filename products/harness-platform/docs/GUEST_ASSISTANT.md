# Гостевой помощник продавца

Предложение для реализации. Основания — GST-01…03, CACHE-01…02 исходного ТЗ, сценарий первого визита из концепции продукта и уточнение владельца о 12 обращениях мимо нашего кэша. Публичная база отвечает до обращения к модели. Предельное количество обращений к модели у одного гостя — 12. Срок хранения черновика и период обновления этого бюджета задаются раздельно. Правило автоматического обновления бюджета через 24 часа владельцем не утверждено.

Требования зафиксированы в документах. [ТЗ v0.2, стр. 3 и 8](https://chatgpt.com/library?file_id=libfile_34bed45f222881919695bbea277bdb8c&account_id=personal), [концепция, стр. 2](https://chatgpt.com/library?file_id=libfile_41f3cec98d708191aa0ab25f09f590c5&account_id=personal).

## Что увидит гость

| Слова гостя | Ответ и следующий шаг | Обращений к модели |
| --- | --- | --- |
| «Почему заказы те же, а денег меньше?» | Карточка «Демонстрационные данные». При продажах 100 000 ₽ удержания выросли с 20 000 до 25 000 ₽. Выплата уменьшилась на 5 000 ₽. Действия «Посмотреть разбивку» и «Проверить на моём магазине». | 0 |
| «А на WB?» после примера | Прочитать предыдущую тему и выбранную площадку. Открыть опубликованный пример WB либо уточнить, какой показатель интересует. | 0 |
| «Сколько удержали у меня вчера?» | Объяснить, какие данные потребуются. Предложить «Создать аккаунт и продолжить этот разбор». Сохранить вопрос и перейти к подключению через защищённую форму. | 0 |
| «Сколько стоит ваш сервис?» | Открыть действующую карточку тарифа и условий. Если сведений нет, сообщить об этом. | 0 |
| «Сколько стоит?» без контекста | Один вопрос «Вы про подписку или про расходы на площадке?» с двумя вариантами. Выбор продолжает исходный вопрос. | 0 |
| «Напиши стих про Ozon» | «Я могу помочь с работой на маркетплейсах и с нашим сервисом. Например, показать, из чего складывается выплата продавцу». | 0 |
| Разрешённый вопрос, для которого есть свежие материалы, но готового ответа нет | Предложить тематический пример или составить ответ по проверенным фрагментам через бюджетный модельный шлюз. | До 1 первичного вызова |
| Исчерпаны все 12 обращений | Для новых запросов по-прежнему доступны поиск по базе, демо, уточнения, регистрация и подключение. При нужде в новом разборе предложить наиболее близкую карточку и следующий шаг. | 0 |

Пример дан для обсуждения сценария продажи. Числа синтетические. Кнопка появляется только для доступного продолжения. На вопрос о подписке продавец получает условия, на вопрос о своём магазине — переход к подключению. Повтор уже отклонённого приглашения заменяется возможностью продолжать разговор по теме. Первые темы каталога стоит выбрать по подлинным вопросам посетителей. Публичные описания площадок, комиссий и цен публикуются с датой действия и источником.

## Путь запроса

1. Сервер определяет гостевую сессию и проверяет повтор по идентификатору хода. Кнопки содержат идентификатор опубликованного действия. Сервер проверяет его принадлежность действующей карточке. Короткие продолжения используют последнюю тему, площадку и предложение из этой беседы. Смена темы сбрасывает унаследованный контекст.
2. Использовать белый список публичных материалов из доверенного каталога функций. Модуль предоставляет варианты вопросов, предметные признаки, краткий ответ, связанные карточки, разрешённые действия, площадку, источник, дату действия и версию. Сведения о подключениях, частные отчёты и скрытые административные функции остаются вне индекса. Снятие карточки с публикации и изменение версии сразу исключают старый ответ.
3. Для свободного ввода точно искать нормализованные формулировки в БД. Ключ включает язык, версию каталога и значимый контекст. Сохранять исходные значимые слова, отрицания, числовые параметры, площадку и различие между «мои данные» и публичным примером. Настройка темы публикуется модулем. Совпавшее название площадки не даёт разрешения на произвольную задачу.
4. При отсутствии точного попадания искать варианты в SQLite FTS5. Сочетать слова, символьные триграммы, алиасы и признаки предмета. Учитывать качество первого кандидата, отрыв от второго и соответствие реального действия посетителя теме карточки. Общий поиск находит кандидатов, затем отдельная проверка выбирает публичный ответ, персональный переход, уточнение или тематическую заглушку. Смешанный запрос обслуживается только в выделенной разрешённой части. При неопределимой границе задать вопрос. После одного неудачного уточнения предложить выбор тем.
5. Дешёвый модельный вызов допускается при установленной теме, отсутствии готового ответа, наличии подходящих публичных источников и свободном бюджете. Подставить несколько свежих фрагментов и предыдущую тему, ограничить ввод и вывод, отключить рассуждения для этого маршрута. Доступ к кабинету, произвольному веб-поиску и приватным инструментам гостевому агенту не требуется. При отсутствии материала предложить смежный опубликованный пример. Актуальные тарифы берутся только из действующей карточки.
6. Записать реплики и источник ответа в канонический журнал чата. У ответа из БД есть идентификатор и версия материала. Учёт платного вызова привязан к фактической операции шлюза. При регистрации тот же вопрос и демо доступны владельцу, права следующего хода определяются актуальным статусом аккаунта. Полезные промахи без личных данных попадают в очередь редактора. Только после проверки публикуются новое объяснение или альтернативная формулировка.

Чистый локальный поиск и маршрутизация — первый вариант запуска. Если реальная разметка покажет много пропущенных перефразировок, сравнить с локальным классификатором по символьным n-граммам или компактными локальными эмбеддингами на той же отложенной выборке. Для семантического поиска сохраняются проверка тематики, срок действия, площадка и ограничения доступа. Внешний LLM-классификатор на каждом сообщении расходовал бы бюджет даже на отказы.

## Учёт расходов

Для гостевой сессии хранить бюджет из 12 обращений, а для оплачиваемого выполнения — отдельную запись операции с уникальным ключом сессии и хода. Считать реальный выход к провайдеру после промаха нашего публичного кэша. Обычные сообщения, поиск, уточнения, отказы, демо, регистрация и попадания в БД дают нулевой расход. Попадание во внутренний KV-кэш провайдера по-прежнему означает внешний вызов.

Перед отправкой к модели атомарно резервировать место в бюджете и проверять общий денежный предел гостевого канала. Повтор доставки хода присоединяется к существующей операции. Достоверный сбой до отправки освобождает резерв. Возможная доставка с потерей ответа оставляет операцию на сверку. Повтор внешнего вызова выполняется только с поддерживаемой поставщиком идемпотентностью либо как отдельно разрешённая попытка в рамках обоих бюджетов. При отключённом шлюзе, общем денежном пределе или исчерпанных 12 обращениях локальные ответы продолжают работать. Для анонимного трафика отдельное ограничение частоты и общий дневной бюджет защищают расходы при создании новых гостевых сессий.

## На чём основано предложение

- В открытом демоботе Sara от Rasa опубликованы FAQ и отдельные намерения для постороннего запроса, демо и обращения в продажи. Можно изучить маршруты и формулировки. [Конфигурация Sara](https://github.com/RasaHQ/rasa-demo/blob/main/domain.yml), [ответы](https://github.com/RasaHQ/rasa-demo/blob/main/data/nlu/responses/responses.yml).
- Dialogflow CX при уверенном совпадении возвращает опубликованный FAQ как есть. Microsoft описывает несколько формулировок на одну карточку и выбор порога по собственной выборке. [FAQ в Dialogflow CX](https://docs.cloud.google.com/dialogflow/cx/docs/concept/data-store), [практика Microsoft](https://learn.microsoft.com/en-us/azure/ai-services/language-service/question-answering/concepts/best-practices).
- В HubSpot готовые сценарии квалификации используют ответы посетителя для выбора следующего действия. У нас таким действием служит просмотр демонстрации, регистрация либо переход к подключению выбранной площадки. [Действия бота HubSpot](https://knowledge.hubspot.com/chatflows/a-guide-to-bot-actions).
- SQLite поддерживает FTS5 и ранжирование BM25. Это позволяет проверить полнотекстовый и символьный поиск в уже используемом хранилище. [Документация SQLite](https://www.sqlite.org/fts5.html).

## Проверка предложения и условия запуска

Воспроизводимый локальный эксперимент использует только Python и SQLite. Из каталога продукта выполнить `python acceptance/guest_faq/evaluate.py`. Пробный каталог, размеченные запросы и правила контекста находятся в [наборе примеров](../acceptance/guest_faq/catalog.json). [Скрипт сравнения](../acceptance/guest_faq/evaluate.py).

На 25 составленных запросах один лексический поиск выбрал ожидаемый маршрут 20 раз. После добавления явной проверки темы и намерения — 23 раза. В пяти отдельных проверках продолжения совпали все пять маршрутов. Внешних вызовов модели в эксперименте не было. Поиск потерял перефразировку про прежний оборот и меньшую сумму на счёте, а фразу с отрицанием «не надо про продажи напиши сказку» пометил как смешанную. Правила настраивались на этом наборе для разработки. Числа не измеряют точность для посетителей.

Для приёмки отдельно разметить реальные обезличенные запросы продавцов, посторонние темы, вопросы о сервисе, персональные, смешанные и короткие продолжения. Зафиксировать правила и применять их к отложенным целым диалогам. Проверять ошибочный ответ по теме на постороннюю просьбу, пропуск допустимой темы, устаревшую карточку, повторы, два одновременных последних резерва, регистрацию на середине беседы и бесплатный 13-й и последующие ответы из БД. Приёмка расходов включает сценарий из 12 реальных промахов с модельным вызовом и следующий промах при закрытом бюджете.

Цель CACHE-02 — верные применимые ответы из базы / все подходящие реальные запросы на независимой выборке. Целевое значение из ТЗ — 90%. Заглушки и приглашения войти учитывать отдельно. Дополнительно измерять долю внешних вызовов, стоимость на 100 гостевых диалогов и стоимость одного посетителя, который подключил магазин и получил первый ответ по своим данным. Измерять путь «получил полезный ответ → открыл демо → начал регистрацию → подключил магазин → получил первый ответ → оплатил». Сравнить варианты приглашения на реальном трафике с одинаковым бюджетом и одинаковой выдачей справки.

## Что изменить в текущем PR

В #481 `guest_turn` считает все строки `guest_turns`, а `_public_answer` выбирает один из трёх текстов, встроенных в Python. Эта временная реализация расходится с требованиями. Простое удаление проверки количества строк требует также пересмотреть чтение полного гостевого журнала. Сейчас он выводится целиком и передаётся нативному процессу при каждом обращении после регистрации. Первая поставка должна подключить опубликованный каталог к обычному гостевому входу, убрать квоту на локальные реплики, выдавать историю страницами и читать сохранённые ходы по устойчивому курсору. Следующая поставка добавляет учёт промахов и экономичный модельный маршрут через общий шлюз. Параллельные работы над пользовательскими ролями и учётом стоимости используют свои ветки.
