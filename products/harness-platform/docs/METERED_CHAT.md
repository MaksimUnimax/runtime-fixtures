# Учёт вызовов из чата

Администратор видит под ответом оценочную стоимость всех обращений к модели за этот ход. Например, вызов плагина между двумя обращениями к модели даёт одну строку «Оценка стоимости · 0,00144 ₽». История показывает ту же оценку после обновления страницы. При отсутствии курса интерфейс показывает сверенную сумму в USD. При неполной сумме в обеих валютах появляется «Оценка стоимости пока недоступна».

Обычный аккаунт получает текст ответа и историю. Сервер ведёт внутренний учёт вызовов для всех аккаунтов. Доступ к полям `modelCost` и `operationId` в ответе чата, истории, событиях и ответе о незавершённом ходе требует административной роли. Сохраняется проверка владельца чата. Оценка рассчитана по тарифу шлюза.

## Назначение роли

Существующие и новые аккаунты получают обычные права по умолчанию. На сервере оператор может назначить роль существующему логину или отозвать её. Из каталога `products/harness-platform` выполните нужную команду

```sh
python -m platform_core.chat_service --db .local/platform.sqlite3 set-role LOGIN admin
python -m platform_core.chat_service --db .local/platform.sqlite3 set-role LOGIN user
```

Изменение действует при следующем запросе, в том числе в уже открытой сессии. Обновление страницы сразу применяет новые права к видимой истории.

## Настройка

Потребуются Python 3.12, Node.js 24, установленный Harness 0.2.2-rc.1 и созданная база аккаунтов. Установка зависимостей и создание пользователя описаны в [запуске сервиса чатов](ACCOUNT_CHATS.md).

В процессе шлюза задайте путь к той же базе аккаунтов в `HARNESS_USAGE_PLATFORM_DB`, каталог журнала в `LAB_USAGE_DIR` и путь к операторскому ключу модели в `DEEPSEEK_KEY_FILE`. При необходимости задайте `LAB_FX_RUB_PER_USD` для рублёвой оценки. Инициализация реестра и команда запуска приведены в [инструкции шлюза](../usage-reconciliation/README.md).

Сервис чатов читает журнал по пути `HARNESS_USAGE_JOURNAL`. По умолчанию используется файл `model-attempts.jsonl` в каталоге `LAB_USAGE_DIR`, либо в `/var/lib/harness-native-lab/meter`. Для раздельного размещения сервису нужен доступ для чтения к журналу шлюза. Проверенные суммы кэшируются на время жизни процесса, при изменении журнала или тарифов создаётся новый снимок. Недоступность журнала меняет только подпись для администратора.

В процессе сервиса чатов выполните из `products/harness-platform`

```sh
unset HARNESS_OFFLINE_MODEL
export HARNESS_MODEL_GATEWAY_URL=http://127.0.0.1:18442
export HARNESS_CHAT_MODEL=deepseek-flash
python -m platform_core.chat_service --db .local/platform.sqlite3 serve --chats .local/chats --composition examples.reference_plugin
```

`HARNESS_NODE_MODULES` должен указывать на каталог модулей установленного Harness. Модель по умолчанию — `deepseek-flash`. Имя модели и адрес шлюза задаёт оператор. При удалённом подключении используется HTTPS, локальный шлюз допускает HTTP. Шлюз и сервис должны работать с одним реестром операций. Опция `HARNESS_OFFLINE_MODEL=1` включает тестовое эхо как отдельный режим.

## Повторная отправка

Клиент генерирует `requestId` один раз при отправке сообщения и сохраняет его для сетевых повторов. Завершённый ход возвращает прежнее сообщение, в том числе после перезапуска. Администратору также доступен прежний `operationId`. Изменённый текст с тем же ключом получает HTTP 409.

Перед обращением к модельному транспорту исполнитель сохраняет отметку о начале хода. При нескольких процессах активный ход занимает только свой чат. Код `busy` означает, что исходный запрос ещё может выполняться. Если исполнитель был прерван и ответ так и не сохранён, клиент получает HTTP 409 с `turn_unconfirmed`. Администратору также возвращается идентификатор исходной операции. Оператор сверяет допущенные попытки с журналом, а клиент показывает пользователю, что исход неизвестен. Для намеренно нового обращения клиент создаёт новый `requestId`. Окно исходного хода составляет до 120 секунд, включая ожидание в очереди.

## Воспроизведение

Команда запускает временную базу, штатный сервис и шлюз с локальным имитатором ответов модели. В качестве первой проверки один клиент вызывает тестовый плагин внутри хода, пока второй клиент использует такой же ключ запроса в другом рабочем пространстве. Тест сопоставляет идентификаторы из HTTP-ответов и истории с итогами реального журнала. Ещё две проверки воспроизводят ошибку провайдера и остановку исполнителя после допуска вызова.

```sh
python -m unittest discover -s tests -p test_metered_chat_e2e.py -v
```

В контрольном примере ход с плагином содержит две попытки и даёт 0,00144 ₽. Ответ второму клиенту содержит одну попытку и даёт 0,00072 ₽. Курс и число токенов задаёт тест. Проверка не расходует средства провайдера.

Для браузерной приёмки установите Chromium для Playwright и из каталога продукта выполните

```sh
PYTHONPATH=. python -m unittest discover -s tests/browser -p test_metered_browser.py -v
```

Браузерная проверка отправляет сообщения из двух независимых профилей. Под ответом администратора появляется сумма, подтверждённая журналом. В обычном профиле финансовая подпись отсутствует. После отзыва роли тест заново открывает историю и проверяет обычный ответ API и вид страницы.
