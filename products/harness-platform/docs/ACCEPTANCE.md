# Приёмка первой поставки и локальная эксплуатация

**Срез от 20 ноября 2026 года.** Основание — лабораторная ветка `feature/harness-native-mcp-lab-20261118`, коммит `68ee4735c825ae279b5e9ebbd29310cb0a767b16`. Поставка добавляет самостоятельное ядро в `products/harness-platform/`. Предыдущая лаборатория имеет собственные результаты и свой жизненный цикл. Ниже отдельно отмечены проверки именно этого каталога.

## Локальные результаты

Среда — изолированная Linux-среда, Python 3.12.14, MCP SDK 1.29.0, JSON Schema 4.26.0, Node 24.22.3. Источник данных — синтетические, заново созданные пространства. Платные вызовы модели и кабинеты магазинов для этих проверок не требуются.

| Граница | Как проверяется |
| --- | --- |
| Manifest v1 и расширяемость | Пустая и составная конфигурации, неизвестная версия, конфликт имён, схема и защита от изменения её после регистрации, явное включение независимого второго плагина |
| Привязка и сохранность прав | Два владельца, посторонний чат, сохранение после перезапуска, повторные и параллельные операции, отзыв и повторная выдача, rollback частичного создания. Случайная опечатка пути рабочего процесса не создаёт новую базу |
| Вызов | Актуальное право проверяется прежде схемы входа. Закрытые детали ошибки обработчика не передаются клиенту. Результаты, которые JSON не передаёт без потерь, возвращают ошибку исполнения |
| Настоящий протокол MCP | Официальный Python-клиент запускает CLI как дочерний процесс по stdio, выполняет initialize, tools/list, tools/call, повтор после отзыва и повторное обнаружение |
| Адаптер Harness | Проверены параметры записи официального MCP-клиента, ошибки конфигурации и монтирование в Cordis-контексте теста. Отдельная проверка с установленным официальным npm-пакетом запускается при заданном HARNESS_NODE_MODULES |

В первой локальной проверке с полным набором этого среза прошли 20 Python-тестов и 3 теста Node. Дополнительный тест Node с реальным нативным пакетом не запускался в этой локальной среде. В [изолированном задании CI](https://github.com/MaksimUnimax/runtime-fixtures/actions/runs/44667974173) установлен официальный пакет Harness 0.2.2-rc.1. Прошли 20 Python-тестов и все 4 теста Node. Настоящий клиент Harness обнаружил инструмент, вызвал его по stdio и получил отказ после отзыва права. Из архива поставки отдельно проверены CLI, второй владелец, отзыв и восстановление SQLite-копии. Сквозной разговор с реальной моделью через интерфейс нового продукта в эту поставку не входит.

## Как воспроизвести и принять

1. Выполнить быстрый старт в [README](../README.md). Пустой каталог успешно запускается без отраслевых модулей. После выдачи права и включения примера в чате вызов возвращает нормализованный текст и число слов.
2. В другом процессе с той же БД отозвать право. На уже открытом MCP-подключении штатный tools/call получает одинаковый отказ для старого и неизвестного имени. Это покрывает `tests/test_mcp.py`.
3. Запустить команды проверки из README. Для полного прогона с установленным релизом задать `HARNESS_NODE_MODULES` как абсолютный путь к node_modules, содержащему `@deepseek-ai/dsh@0.2.2-rc.1`, и `HARNESS_TEST_PYTHON` как абсолютный путь к Python с MCP SDK. Запустить `node --test native/platform-mcp.test.mjs`. Тест использует временную БД и собственный Cordis-контекст.
4. Для следующей приёмки открыть реальный продуктовый вход в двух независимых учётных записях, проверить диалог, поток ответов, переключение пользователя, выдачу инструмента и отзыв. Эту проверку можно провести после появления продуктовой авторизации и изолированного адаптера сессий.

## Обновление и восстановление

- **Локальные файлы.** В отдельном каталоге владельца хранится тестовая SQLite-БД. Синтетический `init` создаёт новый файл с правами 0600. Реальная identity не включена в CLI. Рабочим процессам передаётся существующий путь и доверенная привязка. CLI предназначен для оператора установки.
- **Копия и восстановление.** Для локальной БД создать копию SQLite Backup API или при остановленных тестовых процессах скопировать закрытый файл. Восстанавливать сначала под новым именем в закрытом каталоге. Проверить `PRAGMA integrity_check`, затем известный и недоступный чат. Оригинал и исходные привязки сохранять до проверки.
- **Изменение схемы.** Формат отмечен application_id и user_version. Неподдерживаемая версия открывается с ошибкой. При следующей версии схемы добавляются миграция, тест обновления реального предыдущего состояния и инструкция возврата совместимого релиза. Для изменения набора плагинов подготовить совместимую композицию и обновить подключение.
- **Выход на стенд.** Использовать отдельное окружение, собственную тестовую БД, закреплённые версии и разрешения. Проверить независимые чаты в одном пуле, следы доступа, восстановление и отсутствие повторов. Для выпуска с деньгами дополнительно проверять операции и сверку платежей. Операторский прототип на клиентский адрес не публикуется.
- **После выпуска.** Отдельное событие мониторинга для отказа входа, невозможности выполнить инструмент, задержки, неполных данных и неизвестного денежного исхода. В записи оставлять идентификатор операции, версию и безопасный класс сбоя. Подробные контекстные данные и журналы доступны по минимально необходимым правам.

**Продолжение этапа 2.** Серверный вход, проверка прав и восстановление двух чатов через общий процесс Harness описаны в [отдельной приёмке](ACCOUNT_CHATS.md). Браузерная проверка охватывает два изолированных профиля Chromium, официальный Chat/Trajectory, прямую ссылку и выход. Третий сценарий проходит от гостевой справки через самостоятельную регистрацию до следующего хода и входа с другого устройства. Серверные тесты повторяют регистрацию одновременно и после потери ответа.

## Гость, регистрация и оплаченный чат на одном стенде

Для проверки общей справки откройте форму входа и выберите «Попробовать без регистрации». Спросите «Что ты умеешь?», «Как зарегистрироваться?» и «Сколько стоит ваш сервис?». Проверьте ответ на посторонний вопрос. Каждый ответ поступает из локального справочника. На этом этапе отсутствуют вызовы модели и обращения к площадкам.

Нажмите «Создать аккаунт и сохранить чат». После регистрации сохраняются адрес и порядок реплик. Попросите процитировать первый гостевой вопрос. Новый аккаунт на стенде с модельным шлюзом получает HTTP 402. Администратор начисляет 3 монеты в меню «Монеты» либо оператор выполняет `python -m platform_core.chat_service --db "$STATE/identity.sqlite3" grant-coins LOGIN 3 --key first-credit --reason pilot`. Отправьте вопрос повторно. Проверьте ответ, остаток и одно списание по рублёвой себестоимости. После входа через второй браузер история сохраняется. Внутренняя себестоимость видна при административной роли.

Для приёмки из каталога продукта установите зависимости проекта и Chromium для Playwright, укажите `HARNESS_NODE_MODULES` с закреплённым выпуском Harness и запустите

```sh
python -m unittest discover -s tests/browser -p test_guest_paid_journey.py -v
```

По умолчанию тест использует локальный ответчик модели. Для прогона с реальным DeepSeek Flash установите `HARNESS_LIVE_GUEST_ACCEPTANCE=1`, `HARNESS_ACCEPTANCE_GATEWAY` и `HARNESS_ACCEPTANCE_KEY_FILE` по инструкции [проверки реальной модели](METERED_CHAT.md). Тест создаёт отдельный кабинет и проверяет число вызовов модели по журналу шлюза. Каталог бизнес-плагинов пуст.

Для ручного просмотра гостевой части на свободном порту задайте отдельный пустой каталог в `STATE` и выполните команду из каталога продукта.

```sh
python -m acceptance.guest_paid.stage --state "$STATE" --port 18761 --model off
```

Откройте `http://127.0.0.1:18761/` на той же машине. Для отображения чата гостя и пользователя требуется установленный веб-клиент Harness закреплённой версии. Регистрация сохраняет чат. Для работы штатного интерфейса личного кабинета нужен установленный пакет Harness. При заданных оператором настройках реального шлюза можно выбрать `--model live`. При запуске без параметра режима стенд использует настроенный оператором шлюз, а в чистом окружении запускает веб-сервис без модели. Стенд слушает loopback и хранит данные в указанном каталоге.


## Переключение провайдера в существующем диалоге

Автоматический сценарий tests/test_service_plugins.py создаёт изолированные кошельки, выбирает альтернативную модель одного аккаунта, проводит платный ход штатным агентом Harness и проверяет повтор того же запроса. После перезапуска с выключенным расширением он открывает прежний чат и выполняет второй ход через прямой шлюз DeepSeek. Две тестовые службы провайдера возвращают фиксированные ответы. Сверяются ответ, историческая квитанция, баланс, выбранный маршрут и единственный вызов альтернативной модели.

На боевом ключе отдельно проверить одну небольшую генерацию у выбранного производителя, сумму usage.cost и факт списания по ID провайдера. Для проверки подключения магазина войти в обычный аккаунт, открыть Настройки → Интеграции, выбрать сервис, сохранить реквизиты и нажать «Проверить». В другом аккаунте список должен оставаться собственным. Вставка реквизитов в чат вызывает защищённый ввод, открытие истории после входа не раскрывает значений.


### Поток ответа и подключения разговора

1. Войти, открыть чат и открыть настройки интеграций. Прикрепить существующий Ozon Seller. Обновить страницу и проверить отметку.
2. Спросить «Сколько товаров заказали вчера на Ozon и на какую сумму?». Убедиться, что отправка подтверждается до завершения хода, видны этап обращения к сервису и поступающий текст. Сверить дату, количество и сумму с аналитикой заказов. После завершения в истории остаётся один ответ.
3. Открыть другой чат. Подключение можно выбрать в списке, но доступ к данным появляется только после прикрепления. Снять отметку в первом чате и проверить, что инструмент недоступен для нового запроса.
4. Добавить реквизиты через защищённую форму по команде в диалоге. Проверить наличие имени в списке этого чата и отсутствие ключа в истории. Для гостя доступен справочный чат.
