# Сверка оценочной стоимости вызовов модели

Утилита отвечает на вопрос «какую часть оценочных расходов можно подтвердить по журналу шлюза?». Она объединяет начало и завершение попытки, пересчитывает сумму по таблице тарифов и показывает, по каким причинам общий итог нельзя вывести. Это часть этапа 4 дорожной карты Harness. В режиме учёта по операциям отчёт также показывает расходы конкретного запуска чата или плагина. Она работает на копии журнала, которой можно пользоваться и после остановки сервиса.

## Запуск за минуту

Нужен Python 3.10 или новее. Из этого каталога выполните

```sh
python3 reconcile.py example.jsonl --tariffs tariffs.json
```

В примере есть начало одной попытки и два одинаковых сообщения о завершении. Получатся `unique_attempts=1`, `duplicate_events=1`, `total_usd="0.000038814"` и `total_rub="0.00310512"`. Числа синтетические. Для проверки своей выгрузки укажите путь к снимку JSONL вместо `example.jsonl`. Берите один согласованный снимок, который охватывает обе фазы нужных попыток. При разрезании файла по полуночи попытка может начаться в предыдущем дне. Дата файла сама по себе не определяет отчётный период.

## Что означает результат

| Поле | Как читать |
| --- | --- |
| `basis` | `conservative_peak_estimate` означает расчёт по пиковым ставкам тарифа. Фактический счёт провайдера и списание с кошелька клиента сверяются по другим источникам. |
| `unique_attempts` и `duplicate_events` | Число разных идентификаторов попыток и число повторно прочитанных экземпляров одного события. Новая попытка после ошибки получает собственный ID. |
| `verified_usd_attempts` и `verified_rub_attempts` | Число попыток, для которых удалось подтвердить сумму в соответствующей валюте. |
| `known_usd` и `known_rub` | Сумма проверенных вкладов отдельно для каждой валюты. При нулевом числе проверенных попыток подытог равен строке `"0"`. |
| `total_usd` и `total_rub` | Полная сумма по непустому снимку, если подтверждены все попытки для этой валюты. В остальных случаях поле содержит `null`. |
| `issues` | Счётчики причин. Для каждой неполной попытки показывается первая причина в порядке проверок. Пустая выгрузка получает причину `empty_journal`. |

Денежные значения возвращаются десятичными строками. При полном успехе процесс завершается с кодом **0**. При неполной сверке код **1** сопровождается JSON с известными суммами и причинами. Код **2** означает ошибку входных данных или чтения, JSON-отчёт в этом случае не выдаётся. Ошибка JSONL указывает номер строки. В сообщениях и отчёте отсутствуют содержимое событий и идентификаторы сессий.

## Правила сверки

1. Формат журнала — `harness-lab-model-attempt/v1`, по одному JSON-объекту в строке. Каждому `attempt_id` соответствует пара `admitted` и `finished`. Порядок строк произвольный. Перестановка полей и эквивалентная запись JSON-числа сохраняют равенство событий. Разные варианты одной фазы, расхождение метаданных между фазами, отсутствие начала или конца делают обе суммы неизвестными.
2. Подтверждение расхода требует завершения `completed` с HTTP 2xx и четырёх целочисленных счётчиков. Учитывается отдельно обычный вход, чтение из кеша и выход. В версии шлюза v1 нет ставки за создание кеша. Ненулевой счётчик создания, частичные данные и ошибки оставляют сумму попытки неизвестной. Полная попытка с четырьмя нулями даёт подтверждённый ноль.
3. Версия берётся из котировки, модель — из ответа провайдера. При отсутствии имени в ответе используется запрошенная модель. Пара версия/модель должна присутствовать в отдельном манифесте. Ставки котировки сравниваются с манифестом до расчёта. Тариф в этом каталоге воспроизводит версию `deepseek-2026-11-18-peak-cap` из `integrations/harness-native-lab/gateway/server.mjs` на коммите `3c435746aaeeeef5d8b47c75332328d519b764a4`. Новый тариф получает новую версию в манифесте.
4. Сумма в USD равна сумме трёх произведений «число токенов × ставка за миллион», делённой на миллион. RUB рассчитывается по положительному курсу из той же записи. Источник для проверки самого валютного курса потребуется отдельно. Десятичный расчёт сверяется с котировкой шлюза с относительным допуском `2e-15` на округление JavaScript. Для нулевой суммы сравнение точное.
5. При отсутствии курса или расхождении только в RUB подтверждённый USD сохраняется. При несовпадении USD обе общие суммы становятся неизвестными. Событие со спорной суммой не увеличивает соответствующий подытог.

Записи целиком индексируются в памяти по попыткам, одинаковые варианты фаз учитываются по отпечатку. Время и память зависят от размера снимка. Исторические записи лаборатории одного владельца подходят для общей сверки. Операционный режим шлюза дополнительно пишет выданную сервером привязку к рабочему пространству и операции.

## Приёмка

Из каталога компонента запустите

```sh
python3 -B -m unittest discover -s . -p 'test_*.py' -v
```

В полном репозитории дополнительно запустите из корня

```sh
node --test products/harness-platform/usage-reconciliation/test_gateway.mjs
```

Для второй проверки нужен Node.js 22+ и Python. Тест поднимает штатный шлюз и имитатор провайдера на временных портах localhost, делает запрос, передаёт фактический журнал в утилиту, затем повторно добавляет финальную запись и сверяет обе суммы. Все данные тестовые.

## Сверка по поручениям

Из каталога компонента выполните

```sh
python3 reconcile.py example-operations.jsonl --tariffs tariffs.json --by-operation
```

Синтетический пример содержит три обращения к модели. Первые два относятся к одному запуску поручения и дают **0,00144 ₽** вместе. Третье относится к отдельной операции другого рабочего пространства и даёт **0,00336 ₽**. Общая сумма составляет **0,0048 ₽**. Одинаковая метка сессии в трёх попытках не влияет на принадлежность.

В дополнительном разделе `attribution.operations` каждая строка содержит рабочее пространство, операцию, источник, число попыток и результаты сверки по валютам. `assigned_attempts` и `unassigned_attempts` показывают охват распределения. Строка только с началом попытки может иметь известного владельца и неизвестную стоимость. Старые записи без привязки входят в подтверждённый общий расход, если прошли денежную сверку. Расхождение рабочих пространств или источников у одного идентификатора операции выводится в `attribution.issues.operation_binding_conflict`. Открытие этого отчёта даёт оператору сведения обо всех клиентах в снимке. Для клиентского экрана потребуется отдельная выборка с проверкой доступа.

## Подключение источника операций

Платформенный сервер уже знает владельца и рабочее пространство после проверки входа. В чате в функцию выдачи передаётся `Scope`, возвращённый `IdentityStore.resolve_chat`. Для фонового задания исполнитель берёт сохранённое сервером рабочее пространство владельца и использует `OperationScope(actor_id, workspace_id)`. Плагин задаёт постоянное имя `source` и уникальный ключ **конкретного запуска** `run_key`. Например, ключ для проверки по расписанию включает ID поручения и плановый момент срабатывания. Повтор той же проверки использует тот же ключ, завтрашняя проверка получает новый. Повторная выдача в том же рабочем пространстве, чате и источнике сохраняет `operation_id` после перезапуска. За сохранение результата операции и повторное выполнение бизнес-действий отвечает исполнитель.

Пример в коде обработчика. Здесь `scope` уже проверен сервером, а `run_turn` обозначает модельный транспорт одного хода. Он получает отдельный ключ на этот ход. Параллельные ходы используют свои экземпляры транспорта.

```python
from platform_core.operation_grants import model_operation

with model_operation(db_path, scope, source="chat.turn", run_key=request_id) as grant:
    result = await run_turn(gateway_url=gateway_url, api_key=grant.token)
```

В доверенном процессе вызов `initialize_grants(db_path)` устанавливает две таблицы в уже созданной базе продукта. Шлюз открывает эту базу только для чтения. Для локального запуска операционного шлюза нужны Node.js 24, инициализированная база, заданный `HARNESS_USAGE_PLATFORM_DB` и штатный файл ключа провайдера `DEEPSEEK_KEY_FILE`. Для запуска из корня репозитория выполните

```sh
PYTHONPATH=products/harness-platform python3 -c 'import os; from platform_core.operation_grants import initialize_grants; initialize_grants(os.environ["HARNESS_USAGE_PLATFORM_DB"])'
node integrations/harness-native-lab/gateway/server.mjs
```

Переменная `LAB_USAGE_DIR` указывает каталог журнала, `LAB_FX_RUB_PER_USD` задаёт курс для рублёвой оценки. Сервер по умолчанию слушает `127.0.0.1:18442`. Ключ операции действует 15 минут по умолчанию. При выходе из `model_operation` сервер отзывает этот ключ, в том числе при ошибке транспорта. Уже допущенные обращения завершают запись с исходной привязкой. Для длинного запуска исполнитель может выдать новый ключ с прежним `run_key`. Публичный клиент получает результат поручения через свой сервер.

Шлюз ищет хеш предъявленного ключа в реестре, проверяет срок и текущую принадлежность рабочего пространства и чата. Он записывает `workspace_id`, `operation_id` и `source` в обе фазы попытки. Ключ, внутренние идентификаторы и ключ повтора из реестра провайдеру не передаются. Шлюз в режиме операций закрывает общий лабораторный маршрут `/lab-meter`.

Сквозная проверка на локальном имитаторе, из корня репозитория или архива выполняется так

```sh
python3 -B -m unittest discover -s products/harness-platform/usage-reconciliation -v
node --test integrations/harness-native-lab/gateway/server.test.mjs products/harness-platform/usage-reconciliation/test_*.mjs
```

В режиме шлюза сервер передаёт ключ операции нативному адаптеру каждого хода. Для администратора успешный ответ и история чата содержат оценку и идентификатор операции. Обычный аккаунт получает сообщение без финансовых полей. [Подключение и приёмка учёта вызовов из чата](../docs/METERED_CHAT.md).
