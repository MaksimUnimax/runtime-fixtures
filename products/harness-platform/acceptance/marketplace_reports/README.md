# Сверка дневного отчёта Ozon и WB

Перед подключением источника разработчик может проверить, совпадают ли агрегаты коннектора с ранее собранным дневным отчётом. `replay.py` пересчитывает шесть показателей на каждую площадку и на обе вместе. Работает локально с Python 3.12 и стандартной библиотекой. Тестовый пример содержит вымышленные значения.

## Запуск

Из `products/harness-platform/` в Linux или macOS можно собрать пример и получить эталонный JSON.

```sh
case_dir=acceptance/marketplace_reports
python -m zipfile -c /tmp/harness-sample-day.zip "$case_dir"/fixtures/sample_day/*
python "$case_dir/replay.py" /tmp/harness-sample-day.zip --actual "$case_dir/fixtures/sample_result.json"
python -m unittest discover -s tests -p test_marketplace_report_replay.py -v
```

В примере заказано 4 штуки на 1 200,00 ₽. Расход на рекламу составляет 84,37 ₽, общий ДРР — 7,03%. У WB списано 30,00 ₽ при оперативной оценке 31,17 ₽. Сверка возвращает разницу −1,17 ₽.

Для проверки своего источника подготовьте суточный ZIP и полученный от коннектора JSON за тот же день. Первый аргумент задаёт архив. Параметр `--actual` включает сравнение с ответом коннектора.

```sh
python acceptance/marketplace_reports/replay.py daily-report.zip --actual connector-result.json
```

Код завершения 0 означает совпадение по всем проверенным полям. При расхождении команда возвращает 1 и указывает проблемное поле в stderr. Частный ZIP и ответ коннектора храните локально.

## Из чего складывается эталон

В корне архива формата `joint-marketplace-statistics/v2` нужны четыре файла.

| Файл | Что проверяется |
| --- | --- |
| `OZON_PHYSICAL_UNIT_LEDGER.csv`, `WB_PHYSICAL_UNIT_LEDGER.csv` | Одна строка на заказанную физическую единицу, `original_quantity = 1`. Исходный оборот из `revenue_without`, распределённый расход на рекламу из `advertising_with`, расчётные остатки с коэффициентом и без него из `profit_with` и `profit_without`. |
| `SUMMARY.json` | Формат, дата отчёта, способ подсчёта количества, по одной записи на площадку и сводный итог. Все шесть показателей сверяются с суммами по строкам. |
| `ADVERTISING_SOURCE_RECONCILIATION.json` | Дата и сумма списаний WB. Оперативная оценка и разница «списано минус оперативно» выводятся отдельно. При неизвестной оценке оба этих поля содержат `null`. |

`wb_advertising.operational_coverage` описывает охват оперативной статистики WB в архиве. Если в выгрузке перечислены отсутствующие кампании, возвращаются `partial` и их число в `missing_campaign_count`. Явно пустой список даёт `reported_complete`, отсутствие сведений о списке — `unknown`. При отсутствии самой оперативной суммы возвращается `unavailable`. Списания сохраняют своё значение при любом охвате оперативного источника.

ДРР считают как 100 × реклама / исходный оборот. В сводном итоге числитель и знаменатель сначала суммируются по обеим площадкам. При нулевом обороте ДРР равен `null`. Деньги и проценты округляются до сотых после сложения строк, половина округляется от нуля. Денежный остаток в этом отчёте означает расчётную сумму с учётом выбранного сценария затрат.

Выход содержит `date`, объекты `ozon`, `wb`, `combined` и `wb_advertising`. Количество имеет тип integer, деньги и проценты представлены десятичными строками с двумя знаками. Пример запуска выше показывает точные имена полей. В ответе коннектора допускаются дополнительные метаданные. Сверка требует все эталонные поля, включая явно заданный `null` для неизвестного значения.

Проверка подтверждает согласованность сохранённых поштучных строк, итогов отчёта и переданных агрегатов коннектора. Если в день без заказанных единиц площадка списала деньги за рекламу, в ведомости отсутствуют строки для сверки этого расхода. Команда завершится ошибкой `unallocated advertising`. Для такого дня требуется самостоятельный источник нераспределённых расходов. Достоверность сбора из API, расчёт исходных строк из тарифов и полнота выгрузки требуют отдельной проверки по источнику.
