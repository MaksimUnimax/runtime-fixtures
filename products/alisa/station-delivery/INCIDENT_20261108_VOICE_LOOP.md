# Incident: Station voice callback loop, 2026-11-08

## Corrected root-cause analysis (11:09 UTC; read-only investigation)

The first user question at 10:58:08 UTC, about products participating in promotions, ran a universal-read planner. Two DeepSeek calls returned HTTP 200. The second planner decision could not be parsed as JSON, so the job became `FAILED / INVALID_JSON` at about 10:58:12. The Station poller silently changes any state outside `READY/QUEUED/RUNNING` to `stopped`; it does not announce the failure or recover that planner step. The exact model output was not retained, so the precise malformed characters cannot be established from existing logs. This explains the first silent ending; it is separate from the callback loop.

At 10:59–11:01 UTC the smart-home scenario sent the full phrase `спроси октопорт маркет доставка <nonce>` through a Quasar `text_action`. All webhook events from message IDs 1–15 had **the same hashed session ID**. The lab handler always built its marketplace reply with `end_session=false`, including the initial asynchronous acceptance. The skill therefore remained open; the scenario phrase was delivered inside that existing session as the entire `request.command`, not parsed as a fresh skill activation. The handler forwarded it unchanged to Station ingress and, before the r5 guard, to the analytics gateway. Each READY answer started another scenario, creating a loop. This same-session lifecycle is the underlying cause of the full-command shape. The model calls in the loop returned HTTP 200, not 429.

The r5 change below recognizes the full phrase and blocks the runaway loop. **It is a containment guard, not a complete lifecycle fix.** The proper next implementation must explicitly end the skill session after accepting an asynchronous job, then verify on the physical Station that the subsequent smart-home `text_action` actually opens a new skill session and yields only the suffix in `request.command`. The official Dialogs contract defines `end_session=true` as closing the session and strips activation text from a newly activated skill's command; the private Quasar text-action behavior still requires physical verification. The failed model-decision path must also recover a known malformed JSON response or at least announce a failure, never silently stop. No further production change was made during this correction.

The automatic Station sidecar was stopped at 11:01 UTC; the analytics worker remained active. In release `station-auto-r5-voice-route`, ingress recognizes the exact full skill invocation, routes the nonce to the bound job, and returns the existing READY answer without creating an analytics job. Unbound/invalid internal commands return a direct denial. Ingress exceptions for an internal voice command fail closed with a reply, not a gateway command. The admin form explains `{remaining}` and gives an example. No user QR reauthorization or account rebinding was performed.

Verification: 29 Station unit tests passed, including the skill adapter through Station callback with an assertion that DeepSeek is never called, the full Quasar phrase, unbound command, and Unix socket failure; the 10-second ETA test passed. The service was restarted at 11:05:48 UTC and the admin page returned its expected login redirect. At 11:06:40 UTC there had been no new jobs since reactivation. The r5 tests do not cover ending and reopening a real Alice session. A physical Station end-to-end acceptance is still required: speak one analytical request, hear initial ETA and periodic remaining-time phrase if running, then hear the exact final report once. The configured interval at verification was 25 seconds (owner setting); we did not overwrite it.

Related 429 handling in the currently active runtime `alisa-runtime-method-semantics-r1-20261108`: all Worker provider/model calls route through `_call`, which records calls, preserves provider `Retry-After`, and reschedules the same job for known HTTP 429 with increasing pause up to 900 seconds. There is no local daily quota in the active Worker path. HTTP 401/403 deny the affected source, known other errors fail the job, and unknown transport outcomes do not retry blindly. Store credential checks use a separate rate-limited status path. The Station callback loop above produced HTTP 200 model calls and was unrelated to 429.

User check: [admin settings](https://alisa-admin.octoport.ru/admin/station/) and [customer Station connection](https://alisa.octoport.ru/app/station/). Confirm the current interval and `{remaining}` help, then make one physical voice request. Do not infer physical speech from Quasar action acceptance alone.

## Root-cause correction installed at 11:23 UTC

The Station sidecar release `station-auto-r6-session` returns `end_session=true` only for an accepted asynchronous job with automatic delivery. The `station_client.handle_turn` bridge propagates this structured decision to the new lab webhook target, loaded through an unchanged no-quota adapter copied to `20261108-station-session-r1`. The lab now sends the actual Dialogs `response.end_session=true` instead of always using `false`. This closes the old session before the scenario tries to reopen the skill. The r5 full-command guard remains as defense in case a Quasar action still arrives before the close completes. A terminal `FAILED` or `UNKNOWN` job now speaks the runtime's failure explanation once rather than disappearing silently. QR session and customer binding were not reset.

The active marketplace runtime was independently advanced by the code stream to `alisa-runtime-method-semantics-r4-20261108`. Its `model_decision` catches malformed JSON after a received DeepSeek response, stores a bounded diagnostic (size, parser position, hash; not raw content), and retries the model decision in the same job without replaying provider reads. A focused 15-test suite passed. New backend probes at 11:19:58 UTC for current Ozon and Wildberries promotion participation both reached `READY` after actual marketplace API calls. These are new requests; they do not reconstruct the original malformed second response.

The original 10:58:08 request received: (1) a valid `discover` decision for Ozon `prices_promotions`, query «акции промо участие товаров», which exposed 11 methods and made no Ozon API call; (2) an HTTP-200 model decision with `finish_reason=stop` whose content failed strict JSON parsing. Its bytes were not retained by the older runtime, so the exact response cannot be recovered. The job's two model call records are HTTP 200; it contains no provider call. This explains precisely why no participation list was returned on that attempt.

Offline validation: 31 Station tests, ETA delivery, synthetic lab webhook `end_session` true/false, and no-quota wrapper pin check passed. Both production services restarted cleanly; the admin/customer Station routes returned their expected login redirects. Physical acceptance remains open: confirm a fresh skill session ID and final audible answer once on the paired Station, including a slower query and a real `READY` callback. Do not label it physically verified from server acceptance alone.
