# Автоматическое подключение магазинов

Подтверждённый магазин из личного кабинета становится доступен общему исполнителю
запросов без ручной записи магазина и ключей в конфигурацию ядра. Для Ozon
достаточно Seller API; Performance API добавляет рекламные методы после отдельной
проверки. Для WB используется проверенный ключ WB. Возможность включается
`ALISA_RUNTIME_AUTO_BINDINGS_ENABLED=1` вместе с действующей runtime authority.

После успешной штатной проверки идентификатора площадки `stores.finish` в той же
транзакции создаёт две служебные ссылки: владельца и магазина. Это случайные
серверные идентификаторы, а не UUID из браузера. Для уже настроенного магазина
сохраняются идентификаторы из защищённой операторской привязки. Две новые таблицы
`stores.0002_runtime_bindings` содержат только ссылки и подтверждённый идентификатор
кабинета; ключи остаются в прежнем зашифрованном хранилище.

На каждом запросе действующие ключи и их версии определяются заново. Подготовленный
или отклонённый ключ не заменяет работающий. Успешная замена сохраняет ссылку на
магазин, отзывает прежний ключ и уничтожает его шифротекст штатным механизмом.
Добавление другого магазина не меняет область уже выбранного магазина. Отключённый
или отозванный магазин не возвращается к старой файловой привязке.

Исполнитель получает ключи непосредственно перед одним обращением к площадке через
существующее закрытое Unix-соединение authority, операцию `credentials`. Проверяются
права владельца, период доступа, магазин, версия ключа и принятая область задания.
Права повторно проверяются перед фактической отправкой HTTP. Ключи не записываются
в файл ядра, задание, журнал, ответ кабинета или контекст модели; контекст выдачи
сбрасывается даже при ошибке. Ответ RPC защищён прежним служебным токеном, HMAC и
одноразовым идентификатором запроса. Публичного маршрута для выдачи ключей нет.

`build_overlay.py` создаёт отдельную копию проверенного выпуска ядра: изменяет
только три функции интеграции и добавляет модуль `platform_store_credentials.py`.
Замороженный исходник и параллельные изменения не переписываются. При изменении
ожидаемого контекста или несовпадении хешей сборка прекращается. Кандидат получает
полный обновлённый `CURRENT_CORE_MANIFEST.json`; обычная сверка версии платформы
остаётся обязательной. Нового сервиса, таймера и отдельного хранилища ключей нет.

Проверки источников данных сохраняются. Персональные доказательства доступа к
особым типам таблиц/событий не переносятся с чужого магазина. Ключ WB для обычного
API не заменяет отдельный сервисный токен WB. Рекламный запрос без проверенного
Performance API завершается штатным отказом до отправки API. Лимит этого реестра —
1000 доступных ссылок на владельца; это техническое ограничение, не тарифная квота.

Выбор пользователем последнего магазина сохраняется по прежнему правилу до явной
смены. Архив документов по шаблонам сохраняет прежние 48 часов от создания;
скачивание не продлевает срок. Эта доработка не создаёт новые расчёты при чтении
или повторном скачивании.

Проверки: `runtime/tests/test_platform_store_overlay.py` защищает неизменность базы,
контекст параллельных правок и хеши; `tests/runtime_authority/store_enrollment.py`
проходит реальную PostgreSQL, vault, RPC по Unix и штатный HTTPTransport с подменой
только внешней HTTPS-границы. Квалификация запускается через
`qualify_runtime_authority.py --current-core-source ... --platform-stores-overlay`.
Синтетические проверки не являются ручной приёмкой на магазине владельца.

При откате приложение может вернуться к прежнему выпуску с выключенным флагом.
Добавочные таблицы в живой БД сохраняются; их удаление не нужно для отката кода.
Миграция вниз/вверх проверяется только на собственной одноразовой БД. До установки
необходимо сверить текущие параллельные изменения и привязку native-owner к новой
генерации процесса, сохранить версии для отката и проверить запас диска.
