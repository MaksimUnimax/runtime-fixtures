## 1. [P2] Материальное изменение подписанного профиля ИИ не отзывает захваченный контекст команды

Основное место: [client.js:253–262](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/packages/control-client/src/client.js#L253-L262). Связанные места: [живой контекст runtime](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/apps/extension/src/application/runtime.js#L816-L827), [profile_changed не вызывает обычную invalidation](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/apps/extension/src/application/runtime.js#L1265-L1268), [поля execution context](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/packages/bridge-core/src/execution/context.js#L3-L16).

`grantRights()` удаляет из сравниваемого payload не только временные поля, но и весь `ai.profile`. Поэтому замена `profileKey`, revision, content SHA или данных профиля не меняет `makeGrant().changed` при остальных неизменных правах. `grantEpoch` остаётся прежним. Scope identity также не включает профиль.

Контекст уже захваченной команды связывает её с `scopeKey`, `principalEpoch`, `accessEpoch`, `grantEpoch` и `workGeneration`, но не с идентичностью профиля. `saReadContext()` получает новые полномочия с тем же поколением. Отдельная реакция на `profile_changed` обновляет content profile, однако явно пропускает обычную `saInvalidateAuthority()`; при этом старый execution context остаётся допустимым. Это нарушает описанное в [PAR-20](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/docs/development/Octoport_R3_personal_implementation.md#L60-L61) разделение обычного refresh и материального изменения профиля.

**Воспроизведение на итоговых собранных продуктовых байтах (`a939c07d` и `d5549e9e` побайтово совпадают):** неизменённый worker в существующем `worker-harness`; настоящие client, bootstrap signature verifier, Work Start/identity acknowledgement, `captureBatchContext()`, `saReadContext()` и `SellerAgentsExecutionContext.assertSame()`. Управляемый bootstrap endpoint выдаёт криптографически подписанные синтетические snapshots. После обычного refresh выполнен Start, создана действующая привязка магазина и захвачен контекст. Следующий snapshot меняет revision `1 → 2` и `content.observation.intervalMs`, с пересчитанным canonical SHA256 профиля. Account/device/session/права сохраняются. Ни подпись, ни проверки доступа не выключались.

```json
{"ordinaryRefreshEpochUnchanged":true,"nativeWorkActive":true,"profileRevisionBefore":1,"profileRevisionAfter":2,"profileHashChanged":true,"grantEpochBefore":1,"grantEpochAfter":1,"capturedExecutionRejected":false,"bootstrapCalls":3}
```

**Положительные контроли:** refresh без изменения профиля сохраняет epoch; до замены профиля настоящий живой Work-контекст успешно проходит guard. **Падающая проверка:** изменение профиля должно повысить epoch и отклонить прежний контекст, но это не происходит. Оба результата повторены на итоговом runtime после merge ACK UI.

**Последствие:** опубликованное изменение профиля не создаёт предусмотренную R3 границу отзыва для уже захваченной команды. Старый контекст продолжает проходить проверенный runtime guard после получения нового подписанного профиля. Реальный неверно адресованный provider-вызов или повторный Send этим воспроизведением не утверждается: браузер и transport синтетические, проверена граница допуска контекста.

**Рекомендация:** включить устойчивую идентичность профиля (`profileKey`, revision, scope variant, content SHA и существенную compatibility) в сравнение материальных прав либо отдельно закрепить её в execution context и проверке живого контекста. Изменять поколение только затронутого AI grant, сохраняя независимость другого ИИ. Обычный refresh с тем же профилем должен сохранить epoch. Добавить регрессии на смену профиля при захваченной команде, поздний результат, predispatch и copy/retry; новый профиль не должен незаметно обновлять контекст прежней команды.

## 2. [P2] Лимит command ledger не восстанавливается через предлагаемый новый Start

Основное место: [command-ledger.js:26–28](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/packages/bridge-core/src/execution/command-ledger.js#L26-L28). Связанные места: [сохранение всего журнала при замене owner](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/apps/extension/src/background/compat/mutateManualOperation.js#L15-L18), [reservation и capacity](https://github.com/MaksimUnimax/runtime-fixtures/blob/d5549e9e52e84fa887c8ded1e8e423faff23f85e/packages/bridge-core/src/execution/command-ledger.js#L105-L118).

`capacity()` считает все receipts, deliveries и approvals карточки диалога, независимо от `context.workSessionId`, завершения прежней Work и возраста записи. После 2000 markers он выдаёт `WORK_MARKER_CAPACITY_START_REQUIRED`. Finish и новый Start меняют Work identity/generation, но прежний `r3_commands` сохраняется целиком, и механизм ledger не освобождает бюджет для нового Work. Поэтому выполнение предлагаемого восстановительного действия не устраняет причину отказа.

**Воспроизведение на итоговых собранных продуктовых байтах (`a939c07d` и `d5549e9e` побайтово совпадают):** настоящие popup Start → identity acknowledgement, захват контекста, существующий `manualOperationRecords` writer с readback, popup Finish, второй Start и `saR3Ledger().reserveCommand()`. Для проверки точной границы через собственный storage writer внесены синтетические корректно сформированные receipts **предыдущего Work**: все в `RESULT`, payload TTL истёк, неизвестных provider intent нет. Это подготовка состояния на границе, а не выполнение 2000 API-запросов. Новая команда перед внешними эффектами проходит обычную проверку актуального native Work-контекста.

Контроль непосредственно ниже лимита:

```json
{"markerCount":1999,"oldReceiptsRetained":1999,"newWorkCreated":true,"reserveFailure":null}
```

На границе:

```json
{"markerCount":2000,"oldReceiptsRetained":2000,"newWorkCreated":true,"reserveFailure":"WORK_MARKER_CAPACITY_START_REQUIRED"}
```

Новый Start действительно успешен и создаёт другой `workSessionId`; ошибка возникает при первой reservation в новой Work. Оба сценария повторены на итоговом runtime. Assertion ожидает, что корректно завершённый новый Start восстанавливает допуск команды, и падает на том же `START_REQUIRED`.

**Последствие:** накопленный бюджет журнала блокирует новые команды в диалоге и после явного Finish → Start. Receipts обычных команд, previews повторов и copy approvals расходуют один общий бюджет, поэтому достаточно истории разных Work; активные UNKNOWN для этой проблемы не нужны. Сам лимит полезен, но предложенный пользователю способ восстановления не работает.

**Рекомендация:** согласовать бюджет с областью Work и безопасной стратегией хранения истории: новый Work должен иметь доступный ограниченный бюджет либо завершённая история должна переходить в проверяемое компактное представление/отдельный bounded archive. Сохранять запреты повторного выполнения и UNKNOWN текущей Work; не очищать весь журнал без анализа этих инвариантов. Добавить полный сценарий достижения лимита, Finish, нового Start, первой команды и рестарта worker; отдельно проверить сохранение старых запретов и ограничения storage.
