**Условие возникновения.** Официальные операции одной семьи распределены по нескольким документам. При обработке каждого документа `persistProductCrosswalk` извлекает реестр всей семьи `WILDBERRIES`, но передаёт в `buildProductCrosswalk` inventory только этого документа. Операции остальных документов ошибочно считаются отсутствующими в источнике.

**Последствие.** Crosswalk сохраняет ложные `RUNTIME_ONLY/BLOCKING_RISK`, а вычисление инцидентов открывает по ним инциденты даже при `NO_CHANGE`. Корректное присутствие операции в другом документе не устраняет такую запись: строки имеют разную область документа. Это искажает мониторинг и увеличивает очередь блокирующих замечаний. Автоматическая блокировка выполнения API этим воспроизведением не установлена.

**Воспроизведение на проверенном снимке.** Настоящий extractor прочитал 187 записей реестра WB. Они были полностью распределены между двумя контрольными inventories. Для каждого вызван настоящий `buildProductCrosswalk`; результаты сохранены в `InMemoryProductCrosswalkStore`. Затем настоящий `evaluateApiWatchIncidents` обработал отчёт, в котором оба источника приняты и имеют `NO_CHANGE`. Получено **171 ложное блокирующее сопоставление** для операций, одновременно присутствующих в здоровых `MAPPED_ENABLED` строках других документов; открытие соответствующих инцидентов подтверждено проверкой.

Это локальный контролируемый сценарий с реальным кодом реестра, crosswalk и инцидентов. Число 171 относится к этому сценарию и не является измерением живого мониторинга WB.

**Рекомендация.** Определять отсутствие runtime-операции после объединения всех inventories семьи либо ограничивать сравнение реестром операций, относящихся к конкретному документу. Добавить регрессию: два неизменившихся документа полностью покрывают реестр семьи, и обработка не создаёт ложных `RUNTIME_ONLY/BLOCKING_RISK` и инцидентов.

## 2. P2 — запоздавший ответ подменяет данные выбранной карточки исправления

Статус: **повторно подтверждено; исправление отсутствует**.

Основное место: [`apps/admin/app/admin-ui.tsx`, строки 564–588](https://github.com/MaksimUnimax/runtime-fixtures/blob/6cf99dd3e30da387f1add343a10fc3192e5831d2/apps/admin/app/admin-ui.tsx#L564).

Потребитель: [`apps/admin/app/health/repairs/page.tsx:62`](https://github.com/MaksimUnimax/runtime-fixtures/blob/6cf99dd3e30da387f1add343a10fc3192e5831d2/apps/admin/app/health/repairs/page.tsx#L62), отображение [`page.tsx:187`](https://github.com/MaksimUnimax/runtime-fixtures/blob/6cf99dd3e30da387f1add343a10fc3192e5831d2/apps/admin/app/health/repairs/page.tsx#L187).

**Условие возникновения.** Оператор открывает случай A и до завершения его запроса выбирает B. Ответ B приходит первым, затем завершается более старый запрос A.

**Причина.** Общий hook `useData` выполняет `setData(await controlPlane(path))` без проверки актуальности запроса. Смена `path` запускает новую загрузку, но не отменяет предыдущую и не запрещает ей записать результат. Старый `finally` также меняет общий `busy`. Страница отображает `detail.data` без сверки с выбранным идентификатором и ревизией.

**Последствие.** При выбранном B интерфейс может показать статус и доказательства случая A, уже без индикатора загрузки. Оператор получает неверные сведения о текущем выборе. Выполнение исправления или обход полномочий этим сценарием не доказаны.

**Воспроизведение на проверенном снимке.** Из исходника извлечена настоящая функция `useData`, транспилирована и выполнена с контролируемыми состояниями hooks и отложенными ответами `controlPlane`. После ответа B данные содержат `repairCaseId: B`; после позднего ответа A при неизменном пути B данные становятся `repairCaseId: A`, а `busy` равен `false`. Обе проверки выполнены успешно.

Это проверка настоящего hook с контролируемым порядком ответов; полноценный сценарий в установленном браузере не запускался.

**Рекомендация.** Привязать изменения `data`, `error` и `busy` к поколению актуального запроса и отменять предыдущий запрос при смене пути. При смене выбора очищать старые данные; перед отображением карточки дополнительно сверять её идентификатор и ревизию. Регрессия должна разрешать ответы в порядке B → A и сохранять данные B.
