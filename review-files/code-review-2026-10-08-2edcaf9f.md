## 1. P2 — временная потеря DOM-идентификатора меняет адрес активной привязки

Статус: **новое подтверждённое замечание**.

Основное место: [`packages/bridge-core/src/work/conversation-identity.js:125–139`](https://github.com/MaksimUnimax/runtime-fixtures/blob/2edcaf9f1739eac1562470ec9096987462fd0c7d/packages/bridge-core/src/work/conversation-identity.js#L125).

Связанные места:

- [`conversation-identity.js:45–50`](https://github.com/MaksimUnimax/runtime-fixtures/blob/2edcaf9f1739eac1562470ec9096987462fd0c7d/packages/bridge-core/src/work/conversation-identity.js#L45) выбирает внешний ID либо `local:<surface_id>`.
- [`apps/extension/src/content/conversation-surface.js:36–46`](https://github.com/MaksimUnimax/runtime-fixtures/blob/2edcaf9f1739eac1562470ec9096987462fd0c7d/apps/extension/src/content/conversation-surface.js#L36) читает внешний ID из DOM; для Алисы также используется активный пункт списка чатов.
- [`apps/extension/src/application/runtime.js:1420–1433`](https://github.com/MaksimUnimax/runtime-fixtures/blob/2edcaf9f1739eac1562470ec9096987462fd0c7d/apps/extension/src/application/runtime.js#L1420) ищет Work, контекст магазина и ручную операцию по полученному ключу.

**Условие возникновения.** Диалог уже подтверждён внешним идентификатором. При изменении DOM атрибут или активный пункт списка временно отсутствует. Origin, provider, URL, root, `surface_id` и идентификаторы сообщений остаются теми же; переписка по-прежнему видима и подтверждена.

**Причина.** Следующий `resolveEvidence` возвращает новую подтверждённую идентичность `local:<surface_id>`. `observe` сохраняет её вместо предыдущего внешнего ID, хотя признаков нового диалога нет. После возвращения внешнего ID ветка `state.identity.identity_scope === "document"` закрепляет уже полученный локальный адрес. Исходный ключ не восстанавливается.

**Последствие.** Существующая активная Work остаётся под старым внешним ключом, а popup и связанные потребители обращаются к новому локальному ключу. Прежняя работа и подключённый магазин перестают находиться. Возвращение DOM-идентификатора не исправляет это состояние. Автоматический повтор отправки инструкции, утечка данных или обход полномочий этим воспроизведением не установлены.

**Воспроизведение на свежей сборке 0.2.13.** Настоящий shared tracker получил три наблюдения синтетического диалога Алисы: внешний ID присутствует → отсутствует → снова присутствует. Всё остальное, включая два якоря сообщений, оставалось неизменным. Настоящий worker вычислил ключи `conversationKeyFromIdentity`. Затем настоящая функция `saPopupState` выполнена с контролируемым хранилищем, содержащим одну активную Work под исходным ключом.

Результат:

```json
{"originalScope":"conversation","missingScope":"document","returnedScope":"document","surfaceUnchanged":true,"keyChanged":true,"originalKeyRestored":false,"popupWorkFound":[true,false,false]}
```

Регрессия сохранения ключа падает. Это проверка реальных функций и собранного worker с контролируемыми данными; воспроизведение на установленной живой странице Алисы не запускалось.

**Рекомендация.** Различать временную потерю внешнего свидетельства и создание новой локальной привязки. При доказанной непрерывности сохранять прежний адрес; при недостаточных свидетельствах возвращать `unknown` без замены адреса активной Work. Не закреплять новый локальный ключ лишь из-за временного исчезновения атрибута. Добавить регрессии внешнего ID «есть → нет → есть», включая remount/виртуализацию и отрицательный случай настоящего перехода в другой диалог.

## 2. P2 — семейный инцидент API-watch остаётся OPEN после восстановления операции

Статус: **предыдущее замечание остаётся открытым; повторно подтверждено**.

Основное место: [`tooling/api-watch/src/incident.ts:311–330`](https://github.com/MaksimUnimax/runtime-fixtures/blob/2edcaf9f1739eac1562470ec9096987462fd0c7d/tooling/api-watch/src/incident.ts#L311).

Связанные места: [`run.ts:226–235`](https://github.com/MaksimUnimax/runtime-fixtures/blob/2edcaf9f1739eac1562470ec9096987462fd0c7d/tooling/api-watch/src/run.ts#L226), [`product-registry.ts:603–623`](https://github.com/MaksimUnimax/runtime-fixtures/blob/2edcaf9f1739eac1562470ec9096987462fd0c7d/tooling/api-watch/src/product-registry.ts#L603).

**Условие возникновения.** Включённая операция действительно отсутствует во всех принятых документах WB. Crosswalk открывает один `API_CHANGE_BLOCKING` на уровне семьи, с `documentKey: null`. Затем операция возвращается, а документы побайтно совпадают с принятой базой.

**Причина.** Логика закрытия продуктового инцидента требует непустого `matchingDocumentSources`, но для `documentKey: null` этот набор всегда пустой. Подтверждённое восстановление всей семьи не рассматривается.

**Последствие.** Уже неактуальная блокирующая тревога остаётся `OPEN`; уведомление `RESOLVED` не отправляется. Автоматическая блокировка бизнес-API этим сценарием не доказана.

**Повторное воспроизведение.** Выполнен настоящий `runApiWatchReport` с двумя loopback-документами WB и хранилищами in-memory. Контрольный реестр ограничен этой семьёй, поэтому итоговый отчёт имеет `COMPLETED`. После принятия базы одна включённая операция удалена, затем документ восстановлен. Оба источника имеют `NO_CHANGE`, ошибки и блокеры отсутствуют, SHA совпадают с SHA базы, операция снова `MAPPED_ENABLED`, блокирующих строк нет. Инцидент остаётся открытым:

```json
{"reportState":"COMPLETED","sourceModes":["NO_CHANGE","NO_CHANGE"],"problematicRows":0,"incidentState":"OPEN","documentKey":null}
```

Отдельная регрессия ожидаемого закрытия падает на `OPEN` вместо `RESOLVED`.

**Рекомендация.** Согласовать семейную область инцидента с проверкой восстановления. Для доказанного семейного отсутствия предусмотреть явное происхождение/область и закрытие после полного подтверждённого восстановления. Сохранить запрет на закрытие при неопределённом документе или неполной базе. Не закрывать безусловно все исторические записи с `documentKey: null`. Проверить последовательность «здоровая семья → исчезновение → возврат к принятой базе → RESOLVED» и отрицательный случай неопределённости одного документа.
