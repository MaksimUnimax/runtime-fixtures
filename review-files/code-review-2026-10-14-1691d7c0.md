## 1. [P2, впервые подтверждён] Завершённый WB operator request ломает следующий API Watch report

Основное место: [source-set.ts:174–186](https://github.com/MaksimUnimax/runtime-fixtures/blob/1691d7c0371a22d34126943248a937040e8e1dd1/tooling/api-watch/src/source-set.ts#L174-L186). При HTTP 403 официальных WB sources `runDocumentAuthorityPass()` находит только открытый запрос. Если открытого нет, он создаёт запрос с постоянным ID **`WILDBERRIES:WB_OPENAPI_BUNDLE`**. После перехода существующего запроса в `CANDIDATE_READY`, `CANCELLED` или `EXPIRED` open lookup его уже не возвращает, но durable запись с этим ID остаётся. Следующая попытка создания отклоняется как `SWAGGER_REQUEST_ALREADY_EXISTS`; весь report переводится в `FAILED` с кодом `API_WATCH_REPORT_FAILED`.

**Свежая проверка полного потока:** production WB registry с 13 documents, настоящий `createApiWatchRunner`, report store и handoff service. Transport синтетически возвращает HTTP 403 без внешней сети. Первые два прохода создают и корректно переиспользуют один открытый запрос. Затем выполнена настоящая загрузка полного 13-document бандла, созданного `createWbBundle()` и проверенного `validateWbBundleUpload()`. Она успешно создаёт один зарегистрированный artifact и переводит запрос в `CANDIDATE_READY`. На следующем проходе возникает описанный отказ. Отдельно проверены отменённый и истёкший запросы.

Все три сценария повторены с настоящим PostgreSQL request/artifact store в собственной disposable DB, а не только с memory implementation:

| Backend | Состояние запроса перед следующим report | Результат следующего report | Ошибка authority pass |
| --- | --- | --- | --- |
| memory | `CANDIDATE_READY`, artifact `1` | `FAILED` | `SWAGGER_REQUEST_ALREADY_EXISTS` |
| PostgreSQL | `CANDIDATE_READY`, artifact `1` | `FAILED` | `SWAGGER_REQUEST_ALREADY_EXISTS` |
| memory | `CANCELLED` | `FAILED` | `SWAGGER_REQUEST_ALREADY_EXISTS` |
| PostgreSQL | `CANCELLED` | `FAILED` | `SWAGGER_REQUEST_ALREADY_EXISTS` |
| memory | `EXPIRED` | `FAILED` | `SWAGGER_REQUEST_ALREADY_EXISTS` |
| PostgreSQL | `EXPIRED` | `FAILED` | `SWAGGER_REQUEST_ALREADY_EXISTS` |

Пример native observation:

```json
{"backend":"postgres","terminal":"CANDIDATE_READY","pendingRepeatStatus":"NOT_OBSERVABLE","afterTerminalStatus":"FAILED","afterTerminalCode":"API_WATCH_REPORT_FAILED","underlyingError":"SWAGGER_REQUEST_ALREADY_EXISTS","durableRequestStatus":"CANDIDATE_READY","artifacts":1}
```

Положительный контроль — повторный проход до завершения запроса: `NOT_OBSERVABLE`, один pending request, без ошибки ID. Шесть assertions исправного поведения после terminal transition падают. Подмена статуса на `CANDIDATE_READY` вручную не использовалась: в этом сценарии был реально проверен полный бандл и зарегистрирован artifact. Для `EXPIRED`/`CANCELLED` использована штатная операция store.

**Последствие:** обычное успешное действие оператора переводит последующие проверки lane в ошибку. Сам факт наличия пригодного operator candidate не позволяет проходу завершиться; отмена или истечение также не дают корректно продолжить мониторинг. Воспроизведение не утверждает автоматическое принятие candidate в authority или установленный Telegram сценарий.

**Рекомендация:** разделить identity семейства и identity конкретного operator request/поколения. До создания учитывать существующий candidate и terminal history; предусмотреть idempotent создание нового допустимого запроса там, где это разрешено продуктовым потоком. Не переоткрывать отмену молча, не перезаписывать прежний provenance и не удалять durable историю ради обхода unique constraint. Проверить два повторных прохода с открытым запросом, реальную успешную загрузку, следующий проход, отмену/истечение и конкурентное создание на native PostgreSQL.
