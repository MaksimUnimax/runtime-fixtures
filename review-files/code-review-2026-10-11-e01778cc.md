## 1. P2 — опубликованный DONE невозможно штатно вернуть на доработку

Основное место: [`tooling/coordination/work_queue.py:1435–1443`](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/coordination/work_queue.py#L1435).

Связанные места: [`валидатор DONE-only publication evidence:988–990`](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/coordination/work_queue.py#L988), [`resource callback:414–427`](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/coordination/control.py#L414).

### Причина и последствие

Для invalidated `DONE` код принимает отдельный task/candidate-bound отрицательный review и создаёт `completion_history`. Однако в активной строке остаются `completion_publication_registration` и `completion_publication_snapshot`. Эти поля допустимы только при `state == DONE`. После установки `IN_PROGRESS` собственный validator отвергает кандидат доски.

Новый resource callback удаляет только resource marker/snapshot и снимает seal после успешного queue commit. До commit дело не доходит: V1 выдаёт `WORK_QUEUE_INVALID: repair controllers/work-board.json; no waiting proof`, V2 — `WORK_QUEUE_INVALID: logical v2 candidate`. Durable board остаётся `DONE`, resource completion остаётся `SEALED`, обычное продолжение этой задачи с новыми allocations недоступно.

Ошибка проявляется на **same-role** задаче без foreign allocation. Она не является предусмотренным отказом в самостоятельном reopening делегированного CONTROLLER-ресурса. Задачи без publication snapshot проходят отрицательный rework через тот же настоящий control/queue/resource путь.

Неперенос publication metadata в history существовал и в базе `2d640ce7`. Это новое замечание данного ревью к действующему поведению, повторно проверенному через изменённый native resource callback; отчёт не утверждает, что причина впервые появилась в `e01778cc`.

### Воспроизведение

На собственной временной доске создана source-задача B с native-reader-valid CLOSED publication registration, exact candidate-bound PASS receipt и закрытым ресурсным inventory. Настоящий `control.advance_queue_task` фиксирует `DONE` и `SEALED`. Затем исходный completion receipt становится отрицательным, а отдельный корректный `REWORK_REQUIRED` receipt для текущего source HEAD передаётся обычному control reopening.

Использованы настоящий control, queue writer, resource registry, validators и V2 journals. Publication/migration authority — синтетические fixtures штатных source-тестов; реальный publisher, GitHub CI или живое разрешение ими не имитируются. Запись/валидация очереди не подменена.

```json

```

V2 после настоящей миграции собственной fixture:

```json
{"storageVersion":2,"publicationBacked":true,"failure":"WORK_QUEUE_INVALID: logical v2 candidate","boardState":"DONE","sealState":"SEALED","boardBytesUnchanged":true,"oldPublicationSnapshotStillPresent":true}
```

Две регрессии, ожидающие принятого `IN_PROGRESS`/`REOPENED`, падают. Два контроля без publication snapshot проходят для V1 и V2: board становится `IN_PROGRESS`, seal — `REOPENED`.

### Рекомендация

После принятия отрицательного review переносить прежнюю publication provenance в completion history и убирать DONE-only поля из активной `IN_PROGRESS` строки. Сохранять исходные publication/resource доказательства и снимать seal только после durable queue commit. Добавить native end-to-end reopening опубликованной same-role задачи для V1/V2; сохранить отдельный запрет foreign-resource reopening без journal authority.

## 2. P2 — FIFO в inventory блокирует resource lock до проверки типа файла

Основное место: [`tooling/coordination/disk_lifecycle.py:779–794`](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/coordination/disk_lifecycle.py#L779).

Связанное место: [`verified_receipt:700–718`](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/coordination/disk_lifecycle.py#L700).

### Причина и последствие

Новый inventory scanner открывает registration через `os.open(..., O_RDONLY | O_NOFOLLOW)`, затем вызывает `fstat` и проверяет `S_ISREG`. `O_NOFOLLOW` ограничивает symlink, но не делает открытие FIFO неблокирующим. Если запись `<64 hex>.json` является FIFO без writer, `open` ожидает writer и до проверки типа/лимита bytes код не доходит.

Проверяются все registration files, включая не относящиеся к текущей задаче. Один такой нештатный entry останавливает complete inventory, удерживая общий `resource-admission.lock`; другие операции, использующие этот lock, тоже ждут. В guarded queue completion этот же scanner вызывается при удержании role → coordination → resource locks. Внешний deadline или неблокирующее открытие здесь отсутствуют. Бounded size/JSON validation не ограничивают ожидание `open`.

Аналогичный порядок open-before-type-check используется в `verified_receipt`; непосредственно воспроизведено зависание на registration entry. Замечание требует нештатного типа файла в управляемом реестре и не утверждает наличие удалённого доступа к этому реестру.

### Воспроизведение

Один дочерний процесс создаёт собственную disposable fixture с корректным делегированным source inventory и native CLOSED publication chain. Контроль `Registry.status('A', task, complete=True)` успешно проходит. Затем в **этот собственный** registrations directory добавляется FIFO с допустимым именем; тот же настоящий locked reader запускается повторно.

```json
{"fixtureReady":true,"boundedTimeoutSeconds":2,"readerBlocked":true,"positiveControlPassed":true}
```

Ридер не возвращает предусмотренный отказ за 2 секунды. Родитель завершает только свой дочерний процесс и удаляет только подтверждённую собственную fixture; живые control paths не используются. Причина соответствует POSIX FIFO open без writer: обычный blocking open не достигает следующего `fstat`.

### Рекомендация

Открывать непроверенный leaf с `O_NONBLOCK | O_NOFOLLOW`, проверять regular-file type по открытому descriptor до чтения и сохранять существующие inode/size/hash проверки. Применить это к registration/receipt readers и проверить другие новые bounded readers. Добавить ограниченную по времени отрицательную проверку non-regular entry, включая unrelated registration, и контроль освобождения locks после отказа.
