## 1. [P2] Обработанная ошибка сохранения результата всё равно аварийно завершает процесс планировщика

Основное место: [scheduler.ts:124–126](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/packages/server/monitoring-control/src/scheduler.ts#L124-L126). Связанные места: [сохранение вне обработки ошибки runner](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/packages/server/monitoring-control/src/scheduler.ts#L130-L149), [необработанная ошибка периодического tick](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/packages/server/monitoring-control/src/scheduler.ts#L48-L51).

`begin()` запускает `execute()` и регистрирует `void work.finally(...)` для удаления задачи из `active`. `finally()` создаёт отдельный promise. Если `execute()` отклонён, этот отдельный promise также отклонён, но у него нет обработчика. Обработка ошибки исходного `work` через `runNowAndWait()` не обрабатывает promise, созданный `finally()`.

В `execute()` перехвачены только ошибки runner. Ошибки чтения/записи PostgreSQL после runner, потеря владельца запуска или ошибка записи состояния доставки выходят из функции. Node 24 при стандартной обработке необработанных rejection завершает процесс. Кроме того, периодический `setInterval(() => void this.tick())` имеет самостоятельную необработанную ветку ошибки чтения/старта.

**Воспроизведение:** в собственной disposable PostgreSQL выполнены настоящие миграции. Отдельный процесс Node 24 запускает неизменённые `IndependentMonitoringScheduler`, `createPostgresMonitoringScheduleStore` и `createDatabaseRuntime`. В собственной таблице установлен временный trigger, который отклоняет только изменение `last_result` для синтетического запуска LLM. Вызывающий код явно перехватывает ошибку `runNowAndWait()`; обработчики `unhandledRejection` и изменённый режим Node не устанавливаются.

Наблюдаемый результат:

```json
{"exitCode":1,"callerCaught":true,"survived":false,"databaseError":true,"durableResultAbsent":true,"restartStart":"ALREADY_RUNNING"}
```

Положительный контроль в том же отдельном процессе: исключение самого runner корректно сохраняется как `FAILED`, процесс завершается штатно с кодом `0` и достигает контрольной точки после закрытия БД. SQL, PostgreSQL, запуск Node и promise-цепочка настоящие; отказ записи управляемо внесён только в собственную БД.

**Последствие:** временная ошибка сохранения результата аварийно завершает процесс Telegram-оператора с обоими его расписаниями. [Шаблон systemd](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/infra/production/systemd/octoport-telegram-operator.service.in#L22-L25) предусматривает перезапуск через 5 секунд, поэтому постоянная остановка службы не утверждается. При этом неосвобождённая durable lease блокирует новый запуск того же направления до истечения срока; в воспроизведении сразу после падения получен `ALREADY_RUNNING`, а новый результат отсутствует. Срок lease по умолчанию — 15 минут.

**Рекомендация:** обработать обе ветки завершения фонового promise, не оставляя отклонённый promise от `finally()`; обработать ошибки периодического `tick()` и выполнения фоновой задачи. Ошибки persistence и stale-owner должны давать безопасный операционный результат и сохранять ограничения durable ownership. Нельзя записывать ложный `SUCCEEDED`, снимать чужую lease или повторно выполнять уже отправленное действие ради восстановления. Добавить отдельный процессный тест: runner failure, failure чтения/записи, stale owner, caller catch и продолжение работы другого направления.

## 2. [P2] Страница неподдерживаемых Telegram-сообщений блокирует последующие команды оператора

Основные места: [telegram-client.ts:95–99](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/apps/telegram-operator/src/telegram-client.ts#L95-L99), [telegram.ts:437–444](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/apps/telegram-operator/src/telegram.ts#L437-L444).

Транспорт запрашивает `message` и `callback_query`, но отображает в локальный список только текст, документы и поддержанные callback. Стикеры, фотографии и прочие неподдерживаемые сообщения отбрасываются. `nextOffset` вычисляется из последнего **отображённого** update; когда список пуст, остаётся прежний offset. Сервис дополнительно игнорирует возвращаемый `response.nextOffset` и продвигает свою позицию только при обходе отображённых сообщений.

**Триггер:** перед допустимой командой оператора накопилась полная страница из 100 неподдерживаемых update. Следующая команда находится за этой страницей. Telegram возвращает ту же неподтверждённую страницу, транспорт создаёт пустой список, а сервис снова обращается с прежним offset. Команда за страницей не достигает ни проверки авторизации, ни обработчика. Такая страница может состоять из обычных сообщений пользователя, который не включён в `operatorIds`: фильтрация происходит в транспорте до проверки actor ID.

**Воспроизведение:** использованы неизменённые `createTelegramTransport` и `TelegramOperatorService`, настоящий планировщик с локальным хранилищем и управляемый транспортный ответ. Синтетическая очередь содержит 100 стикеров с ID `1..100` от постороннего fixture-пользователя и `/llm_status` с ID `101` от разрешённого fixture-оператора. Ответ `getUpdates` соблюдает размер страницы 100 и правило отбора по offset. Реальных запросов Telegram и отправки сообщений не было. После трёх проходов собственный сервис корректно остановлен.

```json
{"offsets":[null,null,null],"deliveredStatusMessages":0}
```

Положительный контроль без неподдерживаемой страницы:

```json
{"offsets":[null,2,2],"deliveredStatusMessages":1}
```

Отдельный контроль контракта показал вторую половину дефекта: даже если транспорт явно возвращает `{updates: [], nextOffset: 101}`, сервис продолжает передавать старый offset. Исправления одного расчёта в транспорте недостаточно.

**Последствие:** бот не принимает команды `/llm_status`, `/swagger_run`, загрузку спецификации и другие команды за заблокированной страницей; проверка ID оператора не защищает обработку очереди от этого сценария. Сам таймер мониторинга продолжает работу, поэтому остановка всех мониторинговых задач не утверждается.

**Рекомендация:** транспорт должен вычислять прогресс по всем полученным raw update, включая неподдерживаемые, а сервис — применять `nextOffset` после обработки полученного пакета. Сохранить авторизацию команд и корректную границу подтверждения при ошибке обработки; неподдерживаемый update можно подтверждать без выполнения команды. Нужны регрессии для страницы из 100 неподдерживаемых update, смешанной страницы, посторонних actor ID и пустого локального списка с возвращённым прогрессом.

## 3. [P2] Документы Wildberries расходуют семейный лимит повторов внутри первого прохода

Основное место: [run.ts:631–639](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/api-watch/src/run.ts#L631-L639). Связанные места: [семейный счётчик и лимит](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/api-watch/src/retry.ts#L115-L135), [задержки 15/60 минут](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/api-watch/src/retry.ts#L138-L162), [13 документов production-реестра WB](https://github.com/MaksimUnimax/runtime-fixtures/blob/e01778cca4af25c366fd80acd55fca5349527052/tooling/api-watch/src/source-registry.ts#L15-L30).

`runApiWatchReport()` вызывает `applyRetryDecision()` отдельно для каждого результата документа. Retry state хранится по `sourceFamily`, без `documentKey` или идентификатора уже учтённого прохода. Поэтому несколько неудачных документов одного семейства считаются несколькими последовательными попытками повторного выполнения.

При HTTP 503 всех 13 документов WB первый документ устанавливает retry через 15 минут и `retryCount=1`; второй уже выставляет `retryCount=2` и следующий retry через 60 минут; третий обнуляет `nextRetryAt` как при исчерпанном лимите. Остальные продолжают сохранять исчерпанное состояние. В расписании остаётся ближайший запуск через 15 минут, но на нём состояние уже исчерпано и следующий ограниченный повтор не планируется. Отдельный успешный документ также может очистить состояние семейства, хотя другие его документы ещё недоступны; основной подтверждённый сценарий ниже не требует этой дополнительной ветки.

**Воспроизведение:** настоящий report pipeline, acquisition классификация, `applyRetryDecision()` и `IndependentMonitoringScheduler`; 13 документов взяты непосредственно из production-реестра WB. HTTP-транспорт управляемо отвечает `503` для каждого документа без внешней сети. Два семейства Ozon отключены в синтетической конфигурации, чтобы изолировать счётчик WB. Время продвигается по принятой последовательности повторов `0 → 15 → 75` минут. Сценарий выполнен сначала с локальными хранилищами, затем повторён с настоящими `createPostgresMonitoringScheduleStore` и `createPostgresApiWatchRetryStore` на мигрированной disposable PostgreSQL.

Одинаковый результат обоих вариантов:

| Момент | Выполнено проходов | HTTP-попыток WB | retryCount | nextRetryAt | Следующий запуск направления |
| --- | ---: | ---: | ---: | --- | --- |
| 00:00 | 1 | 13 | 2 | null | 00:15 |
| 00:15 | 2 | 26 | 2 | null | 06:15 |
| 01:15 | 2 | 26 | 2 | null | 06:15 |

Положительный контроль с одним документом того же семейства и теми же ошибками: **3 прохода / 3 HTTP-попытки**, запуск через 15 минут, затем ещё через 60 минут; состояние становится исчерпанным после второго фактического повторного прохода. С 13 документами фактически получены **2 прохода / 26 HTTP-попыток**, хотя при той же политике должны состояться 3 прохода / 39 попыток.

**Последствие:** кратковременный общий сбой WB преждевременно расходует бюджет повторов. Второй предусмотренный сетевой повтор исчезает; после первого повторного прохода проверка откладывается до обычного интервала, по умолчанию на 6 часов. Число документов меняет поведение политики повторов одного семейства. Потеря baseline или ложное объявление удаления endpoints в этом воспроизведении не обнаружены.

**Рекомендация:** применять семейное retry-решение один раз на законченный проход, агрегируя результаты его документов. Считать фактические попытки повторного прохода; не очищать семейный failure episode из-за частичного успеха. Если нужна политика на уровне документа, отдельно закрепить document identity и миграцию состояния. Сохранить ограниченные повторы, правила `Retry-After`, классификацию authority blocker и запрет обхода доступа. Добавить интеграционные сценарии для 13 одинаковых отказов, смешанного успеха/отказа и исчерпания после реальных повторных запусков.
