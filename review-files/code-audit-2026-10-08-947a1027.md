## 1. P1 — источник больше не может принять обычный запрос на перенос ключей

Статус: **новая регрессия**, введена коммитом [`47bdad9e`](https://github.com/MaksimUnimax/runtime-fixtures/commit/47bdad9e).

Основное место: [`packages/server/credential-transfer/src/index.ts:357–367`](https://github.com/MaksimUnimax/runtime-fixtures/blob/947a102789a0ab9d9952b37a1f05c29a54e4097a/packages/server/credential-transfer/src/index.ts#L357).

Связанные места:

- [`credential-transfer-repository.ts:153–163`](https://github.com/MaksimUnimax/runtime-fixtures/blob/947a102789a0ab9d9952b37a1f05c29a54e4097a/packages/server/db/src/credential-transfer-repository.ts#L153): production `read` разрешён получателю либо уже назначенному источнику.
- [`credential-transfer-repository.ts:166–178`](https://github.com/MaksimUnimax/runtime-fixtures/blob/947a102789a0ab9d9952b37a1f05c29a54e4097a/packages/server/db/src/credential-transfer-repository.ts#L166): обнаружение допускает запросы с `source_device_id IS NULL`.
- [`credential-transfer-repository.ts:181–205`](https://github.com/MaksimUnimax/runtime-fixtures/blob/947a102789a0ab9d9952b37a1f05c29a54e4097a/packages/server/db/src/credential-transfer-repository.ts#L181): `markSourceSeen` предусмотрен для назначения источника такому запросу.
- [`popup.js:270–272`](https://github.com/MaksimUnimax/runtime-fixtures/blob/947a102789a0ab9d9952b37a1f05c29a54e4097a/apps/extension/src/application/popup.js#L270): кнопка «Запросить ключи» создаёт запрос без `sourceDeviceId`.
- [`runtime.js:159–163`](https://github.com/MaksimUnimax/runtime-fixtures/blob/947a102789a0ab9d9952b37a1f05c29a54e4097a/apps/extension/src/application/runtime.js#L159): отправка источником начинается с `markCredentialTransferSourceSeen`.

### Причина и пользовательский эффект

Новый `sourceSeen` сначала вызывает общий `repository.read` от имени источника и отклоняет запрос, если результат отсутствует. В PostgreSQL неназначенный источник ещё не имеет права на это чтение: он отличается от получателя, а `source_device_id` равен `NULL`. Поэтому выполнение прекращается с `TRANSFER_ACCOUNT_MISMATCH` до предусмотренного назначения через `markSourceSeen`.

Именно такой запрос создаёт обычный popup. Источник в том же аккаунте видит его через `listForSource`, однако отправка заканчивается ошибкой; запрос остаётся `REQUESTED`, пакет не формируется. HTTP-обработчик переводит эту ошибку в 409. Повтор обнаружения не исправляет состояние. При заранее назначенном `sourceDeviceId` этот дефект не возникает.

Приоритет P1 обусловлен блокировкой штатного пользовательского сценария без дополнительной гонки или редкого состояния. Утечка ключей, переход между аккаунтами или обход полномочий этим воспроизведением не установлены.

### Независимое воспроизведение

На отдельном PostgreSQL применены настоящие миграции репозитория. Созданы синтетический аккаунт, пользователь и две активные установки с корректными client metadata. Использованы настоящий `createCredentialTransferRepository` и текущий `CredentialTransferService`:

1. Получатель создаёт запрос с `sourceDeviceId: null`, согласием и TTL 300 секунд.
2. `listForSource` от имени второй установки этого аккаунта возвращает запрос.
3. Вторая установка вызывает `sourceSeen`.
4. Запрос повторно читается получателем.

Фактический результат:

```json
{"discovered":true,"failure":"TRANSFER_ACCOUNT_MISMATCH","state":"REQUESTED","sourceDeviceId":null}
```

Регрессия ожидаемого назначения источника падает. Четыре контрольных сценария прошли:

- Текущий сервис с настоящим in-memory repository принимает такой же неназначенный запрос.
- Сервис из предыдущего проверенного снимка `2edcaf9f` с тем же настоящим PostgreSQL repository успешно назначает источник.
- Текущий сервис с заранее назначенным источником проходит submit → receive → ACK → `COMPLETED`. Замена уже доставленного пакета и повторный source-seen отклоняются; после ACK relay освобождается.
- Другой аккаунт не обнаруживает и не может принять неназначенный запрос.

Таким образом, воспроизведение отделяет новую регрессию от настройки среды, ошибочного аккаунта и поведения relay после доставки. Тестовый in-memory `read` допускает чтение при неназначенном источнике, поэтому его зелёные тесты не доказывают работоспособность production-пути.

### Рекомендация

Согласовать проверку перед `sourceSeen` с допустимым назначением активного источника своего аккаунта. Сохранить ограничения обычного чтения и защиту доставленного пакета от сброса до ACK; при необходимости использовать отдельный проверенный путь чтения/назначения для источника. Добавить регрессию полного неназначенного сценария именно с production PostgreSQL repository и сохранить отрицательные проверки другого аккаунта, другого назначенного источника, отозванного устройства и доставленного пакета.

### P2 — временная потеря DOM-ID меняла ключ активной Work: исправлено

Повторён прежний независимый сценарий на свежем composed runtime: внешний ID присутствует → отсутствует при тех же якорях сообщений → возвращается. Настоящий tracker сохраняет адрес; настоящий worker вычисляет тот же ключ; настоящая функция `saPopupState` находит Work во всех трёх наблюдениях.

```json
{"originalScope":"conversation","missingScope":"conversation","returnedScope":"conversation","surfaceUnchanged":true,"keyChanged":false,"originalKeyRestored":true,"popupWorkFound":[true,true,true]}
```

Существующие расширенные lifecycle-регрессии также прошли в исходной сборке и распакованном ZIP. Они проверяют приостановку без доказательства истории и ограничения при смене пути, аккаунта, origin/provider и внешнего ID. Исправление принимается на уровне SOURCE/PACKAGE/OFFLINE; установленная живая страница Алисы не проверялась.

### P2 — семейный инцидент API-watch не закрывался после восстановления: исправлено

Повторён прежний настоящий `runApiWatchReport` с двумя loopback-документами WB: принятая база → удаление включённой операции → побайтное восстановление базы. Отчёт `COMPLETED`, оба источника `NO_CHANGE`, блокирующих crosswalk-строк нет, инцидент `RESOLVED`.

Дополнительно тот же сценарий выполнен с настоящим PostgreSQL incident store, пересоздаваемым перед каждым обращением. Маркер происхождения семейного отсутствия имеет длину 78 и сохраняется в существующий `varchar(80)`. После восстановления повторный запуск не порождает второе уведомление о закрытии:

```json
{"markerLength":78,"state":"RESOLVED","notifications":["OPENED","RESOLVED"]}
```

Проверки неполной базы, ошибки источника, отсутствующего документа, неверного/устаревшего mapping и исторического неподтверждённого null-scope остаются в существующих наборах. Исправление не интерпретирует все старые записи с `documentKey: null` как доказанное семейное отсутствие.
