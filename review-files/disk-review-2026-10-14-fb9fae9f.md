# Дисковый аудит runtime-fixtures — 14 октября 2026

**Рабочие 50 ГБ пока не разложены по каталогам: файловая система рабочего сервера в этой сессии недоступна. Нельзя утверждать, что найдено 45 ГБ для удаления. В доступной облачной среде занято 2,8 ГБ; в исходниках подтверждены две ошибки, оставляющие ненужные файлы после сбоев, и обнаружены механизмы накопления релизов без встроенного ограничения числа копий.**

Это отчёт об измерениях и причинах роста, без удаления данных и без продуктовых исправлений. Основная незавершённая часть — актуальный размер каталогов, Docker, баз и журналов именно рабочего сервера.

## Где действительно удалось измерить

Доступна облачная среда Codex `/workspace`, а не `/root/octoport-*` рабочего сервера. Повторное упоминание Remote Desktop Commander не добавило его команд в доступный набор инструментов. В локальной CLI-конфигурации MCP servers отсутствуют; это отдельная проверка локального клиента, а не утверждение о настройках приложения пользователя. Настроенного SSH-подключения и SSH agent в среде нет. TCP-проверка SSH-порта 22 у адреса из deployment script завершилась `ConnectionRefusedError`, без попытки аутентификации. Это не доказывает недоступность всего сервера или другого SSH-порта.

Текущий исходник аудита: **`fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127`**. Он отличается от ранее проверенного `03740125` только двумя transfer-файлами; все рассматриваемые ниже storage/release реализации неизменны. Два воспроизведения повторены после перехода на точный `fb9fae9f`.

Облачный диск `/`: около **32 ГБ всего, 2,8 ГБ занято, 28 ГБ доступно**; свободно более 2 млн inode. `/tmp` — отдельный tmpfs, около **95 МиБ** занято; эти 95 МиБ не занимают тот же overlay-диск. По данной среде нехватка диска не подтверждается.

### Важная поправка: pnpm-store и node_modules нельзя считать дважды

Сопоставлены device/inode реальных файлов store и root `node_modules`, без перехода по symlinks:

| Физические файлы | Занятые блоки |
| --- | ---: |
| Общие между store и dependencies | **508,0 МиБ** |
| Встречающиеся только в store среди этих двух деревьев | **5,6 МиБ** |
| Встречающиеся только в root dependencies | **1,0 МиБ** |

Остальное в directory totals — directory/index overhead и способ обхода. Поэтому обещание «удалим store на 520 МиБ и освободим 520 МиБ» неверно: пока hardlinks из dependencies остаются, общие блоки не освобождаются. Даже 5,6 МиБ store-only не объявлены устаревшими без проверки потребителей.

Локальный Docker: **два образа общей уникальной величиной около 175 MB**, ноль контейнеров, ноль volumes, build cache `0 B`. Эти образы могут быть полезным offline test cache; автоматически мусором они не объявлены. Docker этой облачной среды также не объясняет 50 ГБ рабочего сервера.

## 1. [P2] Ошибка записи snapshot оставляет частичный временный файл

Место: [snapshot.ts:91–102](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/tooling/api-watch/src/snapshot.ts#L91-L102).

`promoteAcceptedSnapshot()` создаёт уникальный `.<sha>.<uuid>.tmp`, записывает bytes и выполняет sync. `finally` закрывает handle, но не удаляет temporary file при ошибке write/sync/rename. Следующая попытка использует новый UUID и оставляет ещё один файл. Поэтому сбой места может дополнительно удерживать уже записанные частичные данные.

**Воспроизведение:** настоящий product function и настоящий локальный filesystem. Только результат write инжектирован: после реальной записи 512 байт в собственный fixture file выбрасывается синтетический `ENOSPC`. Настоящий диск не заполнялся. После трёх отклонённых попыток:

```json
{"attempts":3,"orphanFiles":3,"orphanBytes":1536}
```

Assertion исправного поведения (`0` оставшихся partial files) падает. Положительный контроль трёх успешных сохранений одинакового snapshot оставляет **один** content-addressed файл — обычные успешные повторы не создают три полных копии.

**Что исправлять:** гарантированно удалять собственный незавершённый temporary path при неуспехе, не затрагивая опубликованный content-addressed файл. Для уже накопленного остатка — проверка возраста, активных writers и соответствия имени временной схеме перед отдельной очисткой. Влияние на конкретные серверные 50 ГБ не измерено.

## 2. [P2] Ошибка регистрации загрузки в БД оставляет quarantine-копию при каждом повторе

Места: [запись random-UUID файла до регистрации](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/packages/server/monitoring-control/src/swagger-handoff.ts#L595-L612), [последующий saveArtifact](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/packages/server/monitoring-control/src/swagger-handoff.ts#L680-L684).

Handoff сначала создаёт `quarantine/<uuid>.<extension>`, потом сохраняет artifact metadata. При отказе записи metadata файла rollback/reconciliation нет. Dedupe смотрит в store: если регистрация не состоялась, следующая попытка с теми же bytes создаёт новый UUID-файл.

**Воспроизведение:** настоящий handoff service, штатный memory store и настоящий локальный filesystem. `saveArtifact()` отклоняет запись до сохранения metadata. Три явных повтора одного и того же синтетического валидного документа:

```json
{"attempts":3,"orphanFiles":3,"orphanBytes":12552,"registeredArtifacts":0}
```

Все три файла физически существуют, ни один не зарегистрирован; assertion отсутствия неучтённых копий падает. Это не утверждение о штатной загрузке без ошибок или о реальном отказе серверной БД.

**Что исправлять:** связать staging-файл с устойчивой операцией и последующей регистрацией; обеспечить повторяемое восстановление и уборку подтверждённо неиспользуемых файлов. При неизвестном результате database commit нельзя безусловно удалять bytes: metadata могла сохраниться. Нужна сверка ссылок и защита активной загрузки. Проверить также отказ `setRequestStatus` и потерю ответа после commit.

## 3. Полные immutable ops releases накапливаются по SHA

Место: [prepare-octoport-ops-release.sh:42–66](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/infra/production/scripts/prepare-octoport-ops-release.sh#L42-L66), [публикация завершённого release](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/infra/production/scripts/prepare-octoport-ops-release.sh#L130-L138).

Каждый новый source SHA создаёт отдельный каталог. В него попадает `git archive` **всего workspace**, отдельная копия Node (`install ... .runtime/node`), затем workspace install и production install без ограничения одним package closure. Cleanup удаляет неуспешную подготовку, а успешные releases сохраняются. В самом preparer нет ограничения числа завершённых release directories или их размера.

Скопированный Node не является hardlink: `install` создаёт отдельный файл. При размере Node из текущей облачной среды десять releases означают около **1,18 ГиБ только копий Node**, ещё до исходников и зависимостей. Это расчёт механизма, а не измерение серверного каталога. PNPM dependencies могут разделять блоки через hardlinks, поэтому их нельзя просто умножать по `du` каждого release.

**Первый серверный кандидат для измерения:** `/opt/octoport/ops-releases`. Нужны общий занятый объём с учётом hardlinks, число SHA-каталогов, размер `.runtime/node`, набор releases, на которые ссылаются действующие unit/timer/maintenance/rollback consumers. Каталог без запущенного процесса ещё не означает ненужный release: на него может ссылаться таймер или процедура восстановления.

**Что менять после измерения:** собирать фактическую runtime closure нужной службы; содержать ограниченный проверенный набор развёртываний и rollback. Уникальные принятые архивы, manifests, Git/WIP и receipts сохранять. Снятие старого release с рабочего диска требует подтверждения отсутствия потребителей и сохранности нужного recovery artifact. Изменение immutable directory на месте не предлагается.

## 4. Статический сайт и локальные сборки тоже сохраняют копии

[Site deploy](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/infra/production/scripts/deploy-octoport-site.sh#L5-L22) создаёт `/var/www/octoport-site/releases/<sha>` и timestamped `/var/backups/octoport-site/<time>`. `stage_release()` копирует полный static-site payload; в этом deploy script нет удаления завершённых старых releases. Локальный static-site tree около 1,7 МиБ, поэтому единичный такой release небольшой; десятки гигабайт нельзя приписывать ему без реального списка каталогов.

Builder расширения намеренно сохраняет **ZIP + runtime + extracted** для проверки идентичности ([extension_composed.py](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/tooling/build/extension_composed.py#L370-L383)). Это три представления результата, а не три нужных production deployment. В облачной среде одна свежая development build занимает около 7,5 МиБ; весь `/tmp` со старыми проверками около 95 МиБ. Здесь это небольшой, явно измеренный расход. На сервере архивы candidates, распакованные рабочие копии и результаты тестов нужно измерить отдельно.

**Кандидаты на освобождение после проверки использования:** воспроизводимый `.next/cache`, промежуточные `dist/build/extracted` завершённых проверок, тестовые browser caches и доказанно завершённые disposable clusters. Активные Work, R3 browser profiles, незакоммиченные worktrees, незавершённые тестовые ресурсы и уникальное evidence не относятся к автоматическому списку удаления.

## 5. Данные мониторинга сохраняют историю, общего storage budget не обнаружено

Принятые snapshots расположены в `/var/lib/octoport/api-watch/snapshots/<family>/<sha>.<ext>` и дедуплицируются по содержимому. Одинаковый успешный ответ не означает новый полный файл — это проверено положительным контролем. Но новая версия документа создаёт новую запись/файл; в просмотренном snapshot/store API нет удаления старых versions по age/bytes/reference set.

Authority и report records создаются на проходах, inventories хранятся по snapshot SHA, semantic differences — по паре версий. Это другие данные, чем .tmp leak. Объём таблиц и объём файлов нужно учитывать раздельно. Retention для health/feedback/audit в репозитории есть, но нельзя автоматически считать, что он ограничивает API Watch snapshots/quarantine/reports.

**Нужное измерение:** `/var/lib/octoport/api-watch/{snapshots,quarantine}` с разделением опубликованных файлов, `.tmp`, неиспользуемого quarantine и реально referenced history; в PostgreSQL — размеры таблиц/индексов/TOAST, базы целиком, WAL, replication slots и archive backlog. `DELETE` сам по себе не гарантирует уменьшение файлов БД. Ручное удаление `pg_wal` недопустимо.

## Что не подтверждено как причина раздувания

- **«Git весит десятки гигабайт»** — в доступной копии packs 17,55 МиБ, tracked tree 31,6 МиБ. Серверные отдельные clones/worktrees и их ignored outputs не измерены.
- **«Все backups бесконечные»** — независимый PostgreSQL backup tool имеет `keep_successful=7`, [retention успешных проверенных backups](https://github.com/MaksimUnimax/runtime-fixtures/blob/fb9fae9f8a5e59a002fbaefb4f2be8dcc3b4d127/tooling/operations/backup_postgres_independent.py#L333-L349) и cleanup текущей incomplete directory в `finally`. Это не доказательство установки timer на сервере. Повреждённые/неучтённые backups и остатки после аварийного kill требуют отдельной инвентаризации, автоматическое удаление не предлагается.
- **«Всё занимают Docker images»** — локально только около 175 MB и нет containers/volumes/cache. Данные Docker рабочего сервера неизвестны.
- **«WAL — обязательно мусор»** — локально 880 МиБ при `max_wal_size=1GB`, `min_wal_size=80MB`; WAL может сохраняться как нормальный recycled journal и ограничивается не одним размером таблиц. На сервере рост могут удерживать slots/archive/backup consumers — это пока гипотезы, нужен read-only SQL.
- **«Нужно удалить `/opt/codex`»** — видимые инструменты облачной платформы не являются приложением и могут принадлежать read-only lower layers. У overlay `du` видимого дерева и `df` writable filesystem не обязаны совпадать. Этот путь не кандидат на очистку проекта.

## Порядок завершения аудита рабочего сервера

1. Получить рабочее подключение Commander/SSH к той машине, где наблюдаются 50 ГБ. Пользователю не требуется программировать; текущая проблема — отсутствующие команды подключения в этой сессии.
2. Read-only обход с низким I/O приоритетом: filesystem totals и inode; размеры первого уровня `/root`, `/var`, `/opt`, `/home`, затем крупнейших дочерних каталогов. Не уходить по чужим mounts. Дубли и hardlinks считать по device/inode.
3. Разложить фактический расход на runtime, development dependencies/worktrees, release copies, build/test/browser cache, PostgreSQL data/WAL, backup, container images/layers/volumes, system/application logs. Сверить deleted-but-open files и reserved filesystem space, если `df` и `du` расходятся.
4. Для крупных кандидатов установить владельца, реальных consumers, Git/WIP и уникальные данные. Не останавливать процессы и не удалять файлы ради самого измерения.
5. Выдать таблицу **путь → занято → причина → реально освобождаемый объём → условие безопасной очистки**. Сумма должна объяснять наблюдаемые 50 ГБ; до этого вывод «сервис можно уменьшить до 5 ГБ» не доказан.
6. После отдельно разрешённой очистки повторить те же измерения и проверить работу службы. Профили R3, активные тесты, live DB и чужие WIP сохраняются. Обязательный системный запас свободного места не уменьшается ради достижения цифры 5 ГБ.
