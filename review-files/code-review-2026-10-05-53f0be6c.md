## P2 — семейный инцидент API-watch не закрывается после восстановления операции

Основная граница изменения: [`tooling/api-watch/src/run.ts:226–235`](https://github.com/MaksimUnimax/runtime-fixtures/blob/53f0be6cfc9ab7e8d4ea268a25fb55608f216f41/tooling/api-watch/src/run.ts#L226).

Связанные места:

- [`product-registry.ts:603`](https://github.com/MaksimUnimax/runtime-fixtures/blob/53f0be6cfc9ab7e8d4ea268a25fb55608f216f41/tooling/api-watch/src/product-registry.ts#L603) сохраняет отсутствие операции с `documentKey: null`.
- [`incident.ts:311–330`](https://github.com/MaksimUnimax/runtime-fixtures/blob/53f0be6cfc9ab7e8d4ea268a25fb55608f216f41/tooling/api-watch/src/incident.ts#L311) допускает восстановление продуктового инцидента только при непустом наборе источников конкретного документа.

**Условие возникновения.** Включённая runtime-операция действительно исчезает из всех принятых документов WB. Исправленное построение crosswalk создаёт одну семейную `RUNTIME_ONLY/BLOCKING_RISK` запись, и по ней открывается `API_CHANGE_BLOCKING` с `documentKey: null`. Затем провайдер возвращает операцию, а документы снова совпадают с принятой базой.

**Причина.** Новая граница сопоставления намеренно сохраняет отсутствие на уровне семьи. Потребитель инцидентов продолжает требовать `open.documentKey !== null` для вычисления `matchingDocumentSources`. Для семейного инцидента этот набор всегда пустой; `productRecovered` никогда не становится истинным. При повторных здоровых отчётах инцидент остаётся открытым.

**Последствие.** Мониторинг сохраняет уже неактуальную блокирующую тревогу и не отправляет уведомление `RESOLVED`, хотя операция снова присутствует, а все проверенные документы совпадают с принятой базой. Это искажает состояние мониторинга и требует отдельного устранения зависшего инцидента. Блокировка выполнения бизнес-API этим воспроизведением не установлена.

**Подтверждение.** Выполнен отдельный сценарий над настоящими `runApiWatchReport`, extractor, crosswalk и `evaluateApiWatchIncidents`, с двумя HTTP-источниками на loopback и хранилищами in-memory. Контрольный реестр содержит только семью WB, поэтому завершающий отчёт имеет `COMPLETED`, а не `PARTIAL` из-за посторонних источников.

Последовательность:

1. Записи настоящего реестра WB распределены между двумя документами. Снимки приняты как продуктовая база; здоровый повторный проход не создаёт ложных блокирующих записей.
2. Одна включённая операция удалена из первого документа. Подтверждены ровно одна семейная `RUNTIME_ONLY` запись и один блокирующий инцидент.
3. Первый документ восстановлен побайтно до исходной принятой базы.
4. Новый отчёт имеет `COMPLETED`; оба источника имеют `NO_CHANGE`, `errorCode: null`, `blockerCode: null`, и их SHA совпадают с SHA базы. Операция снова `MAPPED_ENABLED`, блокирующих записей нет.
5. Проверка ожидаемого закрытия падает: получено `OPEN`, ожидалось `RESOLVED`.

Зафиксированный вывод:

```json
{"reportState":"COMPLETED","sourceModes":["NO_CHANGE","NO_CHANGE"],"problematicRows":0,"incidentState":"OPEN","documentKey":null}
```

Сценарий построен на [регрессии семейного сопоставления в report.test.ts:980](https://github.com/MaksimUnimax/runtime-fixtures/blob/53f0be6cfc9ab7e8d4ea268a25fb55608f216f41/tooling/api-watch/src/report.test.ts#L980) с дополнительным шагом восстановления сразу после проверки настоящего отсутствия. Временный тест находился вне продуктовых исходников; проверенный код не изменялся.

**Рекомендация.** Согласовать область семейного инцидента с логикой восстановления. Для доказанного семейного отсутствия предусмотреть явную область/происхождение и закрытие после полного подтверждённого восстановления семьи. Сохранить запрет на закрытие при неполной или неизвестной базе. Не применять безусловное закрытие ко всем историческим инцидентам с `documentKey: null`: среди них могут быть записи без достаточного происхождения. Добавить регрессию «здоровая семья → исчезновение → возврат к принятой базе → RESOLVED» и отрицательный сценарий с одним неопределённым документом.
