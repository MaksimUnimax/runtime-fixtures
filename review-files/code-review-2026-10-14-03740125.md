## 1. [P2] Ошибка финализации мониторинга завершает Node даже после обработки ошибки вызывающим кодом

Основное место: [scheduler.ts:124–126](https://github.com/MaksimUnimax/runtime-fixtures/blob/0374012512cf9cc7640a0583a107a3f6a37dd9d4/packages/server/monitoring-control/src/scheduler.ts#L124-L126). Связанные места: [интервальный запуск без обработчика rejection](https://github.com/MaksimUnimax/runtime-fixtures/blob/0374012512cf9cc7640a0583a107a3f6a37dd9d4/packages/server/monitoring-control/src/scheduler.ts#L48-L51), [запись результата вне обработки runner failure](https://github.com/MaksimUnimax/runtime-fixtures/blob/0374012512cf9cc7640a0583a107a3f6a37dd9d4/packages/server/monitoring-control/src/scheduler.ts#L143-L149).

`void work.finally(...)` создаёт отдельный promise, который повторяет rejection `work`. Для него нет обработчика. Поэтому `runNowAndWait()` может передать исходную ошибку ожидающему caller, caller её перехватит, но производный promise всё равно аварийно завершит процесс при стандартной обработке unhandled rejection в Node 24. В периодическом запуске также остаётся необработанный promise `tick()`.

**Свежая проверка:** настоящий PostgreSQL repository, собственный failure trigger на запись результата LLM и отдельный процесс Node без глобального подавления unhandled rejection. Runner успешно возвращает результат; триггер отклоняет его сохранение. Caller ловит ошибку, после чего Node всё равно завершается:

```json
{"exitCode":1,"callerCaught":true,"survived":false,"databaseError":true,"durableResultAbsent":true,"restartStart":"ALREADY_RUNNING"}
```

Положительный контроль с ошибкой самого runner проходит: записывается `FAILED`, процесс завершается штатно с кодом `0`. Таким образом, проблема находится на границе финализации/обработки promise, а не в обычной конвертации ошибки runner в результат.

**Последствие:** сбой БД одной monitoring lane может завершить весь Telegram operator/monitoring процесс. Durable lease остаётся активным до истечения; новый запуск сразу после сбоя отвечает `ALREADY_RUNNING`.

**Рекомендация:** обработать обе ветви завершения фонового `work` и rejection периодического `tick()`, сохранив исходную ошибку для явно ожидающего caller. Ошибки фиксировать безопасным ограниченным событием с lane/stage; обработчик диагностики тоже не должен создавать unhandled rejection. Не подменять несохранённый результат на `SUCCEEDED`, не снимать чужую lease и не добавлять автоматическое повторение внешнего действия. Проверить native Node child для awaited/background/timer failures и отдельное продолжение второй lane.

**Рекомендация:** включить устойчивую идентичность профиля в определение материального изменения grant либо закрепить её в execution context и сравнивать с актуальной authority. Изменение одного AI grant должно отзывать только его старые контексты; обычный refresh с тем же профилем сохраняет поколение. Добавить проверки позднего результата, predispatch и copy/retry после смены профиля.

## 4. [P2] Страница неподдерживаемых Telegram updates блокирует следующую команду оператора

Основные места: [telegram-client.ts:95–99](https://github.com/MaksimUnimax/runtime-fixtures/blob/0374012512cf9cc7640a0583a107a3f6a37dd9d4/apps/telegram-operator/src/telegram-client.ts#L95-L99), [telegram.ts:437–444](https://github.com/MaksimUnimax/runtime-fixtures/blob/0374012512cf9cc7640a0583a107a3f6a37dd9d4/apps/telegram-operator/src/telegram.ts#L437-L444).

Transport вычисляет `nextOffset` только по updates, преобразованным в текст/document/callback. Для sticker/service messages преобразованный список пуст, поэтому offset не сдвигается. Service дополнительно игнорирует `response.nextOffset` и обновляет offset лишь внутри цикла mapped updates.

**Свежая проверка:** настоящие transport/service и синтетическая Telegram очередь из 100 sticker updates, за которыми находится разрешённая операторская `/llm_status`. Получение ограничено обычной страницей из 100 updates. Повторяется одна и та же страница:

```json
{"offsets":[null,null,null],"deliveredStatusMessages":0}
```

Положительный контроль без неподдерживаемой страницы доставляет команду и продвигает offset: `[null,2,2]`, одна status message. Отдельный контроль контракта transport, который уже возвращает `nextOffset:101` при пустом mapped batch, также застревает в service: `[null,null,null]`. Поэтому исправить только один из двух слоёв недостаточно.

**Последствие:** бот продолжает polling без видимого исключения, но команды после такой страницы не обрабатываются.

**Рекомендация:** вычислять прогресс по всем raw `update_id`, а service должен принимать этот прогресс после обработки поддерживаемой части batch. Offset не должен уменьшаться или перескакивать через ещё не обработанные команды при исключении handler. Проверить пустой batch, полностью неподдерживаемый batch, смешанный batch и ошибку обработчика.

## 5. [P2] API Watch расходует retry budget семейства внутри одного прохода по документам

Основное место: [run.ts:631–639](https://github.com/MaksimUnimax/runtime-fixtures/blob/0374012512cf9cc7640a0583a107a3f6a37dd9d4/tooling/api-watch/src/run.ts#L631-L639). Retry state хранится по `sourceFamily`, но `applyRetryDecision()` вызывается отдельно для каждого document outcome. При временной недоступности 13 документов WB первый проход уже увеличивает общий `retryCount` до `2`, а последующие документы записывают `nextRetryAt:null`. Это расходует бюджет до реальных повторных проходов.

**Свежая проверка:** production source registry с 13 WB documents, настоящий acquisition/report/retry/scheduler pipeline, синтетические HTTP 503 без внешней сети. Проверено и с memory stores, и с настоящими PostgreSQL schedule/retry stores. Логическое время: минуты `0`, `15`, `75`.

| Состояние | Ожидаемое число проходов / загрузок | Фактическое число проходов / загрузок |
| --- | --- | --- |
| Одно-документный положительный контроль | 3 / 3 | **3 / 3** |
| 13 WB documents, memory | 3 / 39 | **2 / 26** |
| 13 WB documents, PostgreSQL | 3 / 39 | **2 / 26** |

Уже на минуте `0`: `retryCount=2`, `nextRetryAt=null`. После прохода на минуте `15` ближайший запуск переносится на регулярный шестичасовой интервал; на минуте `75` повтор не выполняется.

**Последствие:** два предусмотренных сетевых повтора фактически превращаются в один; время восстановления семейства зависит от количества документов.

**Рекомендация:** принимать одно retry-решение на семейство после полного acquisition pass. При нескольких 429 учитывать консервативный `Retry-After`; частичный успех не должен сбрасывать episode, пока другие документы семейства временно недоступны. Проверить независимость семейств, порядок mixed success/failure, лимиты 429 и интервалы 15/60 минут на реальном scheduler.
