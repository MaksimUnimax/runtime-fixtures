Новый `/swagger_new` решает восстановление после `CANDIDATE_READY`, `CANCELLED` и `EXPIRED`, но не после ошибки содержимого. Невалидный файл уже зарегистрирован как артефакт, а его запрос имеет статус `VALIDATION_FAILED`. `isOpenRequest()` включает этот статус; `renewRequest()` повторно выдаёт тот же ID. Другие bytes в этом запросе затем отклоняются с `REQUEST_ARTIFACT_ALREADY_RECEIVED`. Повтор того же невалидного файла даёт duplicate и также не исправляет источник.

Исходный запрос создаётся реальным acquisition/report path после синтетического 403. Первым загружен ошибочный JSON; затем через ту же поверхность бота отправлен полный валидный bundle 13/13:

{"backend":"postgres","firstStatus":"VALIDATION_FAILED","firstReply":"WB_BUNDLE_VERSION_INVALID","newRequestCreated":false,"nextStatus":"VALIDATION_FAILED","correctedUploadReply":"REQUEST_ARTIFACT_ALREADY_RECEIVED","oldArtifactCount":1}

Положительные контроли: такой же валидный bundle в свежем запросе проходит bot → authority → 13 snapshots/inventories; renewal после трёх прежних terminal statuses проходит. Дефект относится именно к recovery после validation failure.

**Последствие:** одна исправимая ошибка выбора/содержимого файла оставляет оператора без рабочего способа повторить загрузку. Новый запрос по кнопке фактически не создаётся. В автоматических запросах срок по умолчанию не задан; само ожидание не обеспечивает восстановление.

**Исправление:** по явному разрешённому действию создавать новую generation после зарегистрированного невалидного артефакта, сохраняя failed request/artifact и provenance. Альтернатива — явная безопасная финализация ошибочной попытки с последующим renewal. Продолжать переиспользовать реально ожидающий пустой запрос и сохранять конкурентную идемпотентность. Не перезаписывать старые bytes и не переоткрывать terminal history автоматически.

**Проверка исправления:** wrong bundle → понятная ошибка → `/swagger_new`/кнопка → новый ID → corrected bundle → принятые 13 документов; прежний артефакт остаётся неизменным. Повтор и конкурентные нажатия не должны создавать несколько активных поколений.

## 2. [P2] Не подменять все будущие проверки однажды обработанным WB-бандлом

Место: [runAuthorityPass:487–527](https://github.com/MaksimUnimax/runtime-fixtures/blob/299d611340703117a0292cce14a092870ace99cc/tooling/api-watch/src/authority.ts#L487-L527), [исторические ready requests остаются в выборке](https://github.com/MaksimUnimax/runtime-fixtures/blob/299d611340703117a0292cce14a092870ace99cc/packages/server/monitoring-control/src/swagger-handoff.ts#L609-L613). Связанный контракт: [API watcher проверяет официальную документацию](https://github.com/MaksimUnimax/runtime-fixtures/blob/299d611340703117a0292cce14a092870ace99cc/docs/operations/MONITORING.md#L20-L28).

Новый consumer правильно возобновляет обработку сохранённого upload после сбоя. Однако после успешного завершения request всё ещё `CANDIDATE_READY`. В каждом следующем `runAuthorityPass()` он снова выбирается, его старые bytes выдаются как `ACQUIRED_OFFICIAL_SOURCE_CANDIDATE`, а WILDBERRIES полностью исключается из registry automatic pass. Условие не различает первичное продолжение, восстановление незавершённого pipeline и новую проверку; forced run проходит ту же ветку.

Это позволяет одному старому bundle бессрочно замещать получение новой официальной документации. Успешно обработанный артефакт не перестаёт выбираться; наличие новых доступных документов на официальном URL не проверяется. Создание нового pending-запроса само по себе также не убирает старый ready candidate из выборки.

Независимое воспроизведение использует настоящий бот, scheduler, report runner, snapshot/inventory persistence, полный production registry 13 документов и собственные каталоги. Проверено в памяти и PostgreSQL:

1. Синтетический официальный источник сначала возвращает 403.
2. Оператор загружает валидный bundle версии содержимого 1; normal wake завершается успешно и сохраняет 13 snapshots.
3. Тот же synthetic transport переключён на корректные официальные YAML версии содержимого 2 с новой операцией в каждом из 13 документов.
4. Выполнен новый принудительный запуск scheduler. Он делает **0 fetch calls**, использует только 13 прежних snapshots и выдаёт `NO_CHANGE`, `addedCount=0`.
5. Положительный контроль настоящего `acquireOfficialSource()` на том же URL и transport успешно принимает изменённую спецификацию. Сетевых внешних запросов нет.

```json
{"backend":"memory","forcedFetches":0,"forcedStatus":"SUCCEEDED","snapshots":13,"addedCount":0,"comparisonState":"NOT_RUN","changeModes":["NO_CHANGE"],"directOfficialControl":"ACQUIRED_OFFICIAL_SOURCE_CANDIDATE"}
{"backend":"postgres","forcedFetches":0,"forcedStatus":"SUCCEEDED","snapshots":13,"addedCount":0,"comparisonState":"NOT_RUN","changeModes":["NO_CHANGE"],"directOfficialControl":"ACQUIRED_OFFICIAL_SOURCE_CANDIDATE"}
```

`comparisonState=NOT_RUN` здесь честно отражает отсутствие product baseline repository в независимом fixture. Этот результат не представлен как доказанная production coverage `COMPLETED`. Подтверждён другой дефект: новый forced acquisition вообще не обращается к уже восстановившемуся официальному источнику и не обнаруживает новые bytes; `NO_CHANGE` получено повторным чтением старого upload.

**Последствие:** WB watcher после первого успешного handoff может бесконечно проверять один и тот же локальный файл вместо обнаружения последующих изменений. Дополнительный ручной upload становится необходим даже тогда, когда официальный источник снова доступен, а обычный forced run не даёт его проверить.

**Исправление:** различать незавершённое продолжение/recovery конкретного артефакта и исторический уже обработанный источник. Сохранить идемпотентное восстановление после partial persistence, но не считать повторное чтение завершённого bundle новым наблюдением официального API. Предусмотреть разрешённую принудительную проверку восстановившегося official source. Пока источник действительно требует оператора, сохранять operator hold и явно показывать необходимость новых данных, без ложного вывода о свежести. Не удалять accepted baseline, provenance или защиту от повторов.

**Проверка исправления:** import v1 → завершённый pipeline → official v2 с новым методом → forced acquisition/report замечает v2; отдельно 403 по-прежнему удерживает семейство без автоматического retry storm, а restart во время неполной записи всё ещё возобновляет тот же bundle.
