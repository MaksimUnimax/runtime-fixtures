## 1. P2 — повтор источника сбрасывает состояние успешно отправляемого пакета

Основное место: [`packages/server/credential-transfer/src/index.ts:408–423`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/packages/server/credential-transfer/src/index.ts#L408).

Связанные места:

- [`sourceSeen:374–383`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/packages/server/credential-transfer/src/index.ts#L374) блокирует повтор после фиксации доставки, но допускает его при активной reservation первой отправки.
- [`credential-transfer-repository.ts:199–222`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/packages/server/db/src/credential-transfer-repository.ts#L199) переводит существующий запрос обратно в `SOURCE_SEEN`.
- [`credential-transfer-repository.ts:242–249`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/packages/server/db/src/credential-transfer-repository.ts#L242) допускает получение только из `PACKET_AVAILABLE_EPHEMERAL` либо `DELIVERED_TO_RECIPIENT`.
- [`runtime.js:157–183`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/apps/extension/src/application/runtime.js#L157) при каждой отправке сначала вызывает source-seen; успешный submit завершает отправку с `ok: true`.

### Причина и последствие

`submit` проверяет наличие `inFlightRequests`, но сам не регистрирует свою мутацию в этом наборе. Reservation защищает от второго submit, однако не защищает от конкурентного source-seen. Если первая отправка уже записала `PACKET_AVAILABLE_EPHEMERAL`, а её завершение ещё ожидается, повторный source-seen сбрасывает durable state в `SOURCE_SEEN`. Второй submit отклоняется из-за существующей reservation. Первая отправка затем успешно активирует свой пакет в relay и возвращает запрос со сброшенным состоянием.

После завершения обеих попыток пакет существует, но `receive` получает `TRANSFER_CONFLICT`, поскольку PostgreSQL state не допускает доставку. Источнику приходится отправлять новый пакет. Воспроизведение подтверждает нарушение завершения передачи; утечка ключей, переход между аккаунтами или обход ACK им не установлены.

### Независимое воспроизведение

Использованы настоящий `CredentialTransferService`, настоящий PostgreSQL repository и отдельная мигрированная база. Управляемый барьер задерживает возврат `markPacketAvailable` **после настоящего commit**, моделируя задержку завершения асинхронной операции. SQL и состояния базы не подменяются.

Последовательность: первый submit записывает доступность → повторный source-seen того же назначенного источника принимается → второй submit получает конфликт reservation → первый submit завершается → получатель пытается получить пакет.

```json
{"firstSubmissionAccepted":true,"firstReturnedState":"SOURCE_SEEN","sourceRetry":"ACCEPTED","replacementFailure":"TRANSFER_CONFLICT","relayPacketPresent":true,"durableState":"SOURCE_SEEN","receiveFailure":"TRANSFER_CONFLICT"}
```

Регрессия, ожидающая доступность единственного успешно отправленного пакета, падает. Контрольная последовательная передача проходит submit → receive → ACK → `COMPLETED`.

### Рекомендация

Учитывать активный submit в защите одного `requestId` и согласовать эту защиту с relay reservation. Source-seen не должен сбрасывать состояние при незавершённой отправке. Сохранить ограничения доставки/замены, отмену, TTL, квоты и независимость других запросов. Добавить регрессию данного порядка событий и обратного порядка конкурентных действий.

## 2. P2 — потеря памяти relay перед ACK удаляет сохранённый результат импорта

Основное место: [`apps/extension/src/application/runtime.js:1623–1629`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/apps/extension/src/application/runtime.js#L1623).

Связанные места:

- [`credential-transfer/src/index.ts:477–489`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/packages/server/credential-transfer/src/index.ts#L477) возвращает `TRANSFER_REPLAY`, если соответствующего пакета больше нет в process-memory relay.
- [`control-client/src/client.js:1255–1270`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/packages/control-client/src/client.js#L1255) восстанавливает ACK после ошибки только при наблюдаемом серверном `COMPLETED`.
- [`runtime.js:1614–1617`](https://github.com/MaksimUnimax/runtime-fixtures/blob/50bf143cfd7f3fa9bf58193ce5e33a9097a68b95/apps/extension/src/application/runtime.js#L1614) пытается повторить ACK для `IMPORTED_PENDING_ACK`.

### Причина и последствие

Получатель уже расшифровал пакет, импортировал ключи и записал безопасный результат в фазе `IMPORTED_PENDING_ACK`. До ACK сервер теряет process-memory relay; durable запрос в PostgreSQL остаётся `DELIVERED_TO_RECIPIENT`.

Следующая попытка через `SA_TRANSFER_RECEIVE_PENDING` получает от ACK `TRANSFER_REPLAY`. Client readback видит незавершённый серверный запрос и повторно выбрасывает эту ошибку. Dispatcher трактует её как основание удалить всю локальную запись через `discardCredentialTransfer`, затем возвращает `PENDING`.

Исчезают recipient private key и сохранённый безопасный результат уже выполненного импорта. Импортированные магазинные ключи остаются в каталоге. Пользователь видит ожидание вместо результата, а текущую передачу больше нельзя нормально восстановить из recipient vault. Воспроизведение не устанавливает удаление уже импортированных магазинных ключей или повторное применение импорта.

### Независимое воспроизведение

Проверка соединяет настоящий свежесобранный worker расширения, его crypto/import/vault/client/dispatcher и настоящий transfer service с PostgreSQL repository. HTTP-переходы worker направлены контролируемым fixture transport в реальные методы сервиса; production HTTP authentication этим стендом не проверяется. IndexedDB использует существующий fixture adapter регрессий; все данные синтетические.

После настоящего импорта и durable записи результата process-memory relay очищается и создаётся новый экземпляр сервиса с той же PostgreSQL. Это моделирует перезапуск сервиса без изменения базы и recipient state. Затем вызывается настоящий popup handler `SA_TRANSFER_RECEIVE_PENDING`.

```json
{"beforePhase":"IMPORTED_PENDING_ACK","beforeResult":"IMPORTED","afterRecordCount":0,"popupImportState":"PENDING","serverState":"DELIVERED_TO_RECIPIENT","storesUnchanged":true}
```

Регрессия сохранения результата падает: вместо одной локальной записи обнаруживается пустой vault. Сравнение каталога до/после подтверждает сохранение уже импортированных магазинов.

Отдельный положительный контроль с теми же функциями и PostgreSQL проходит: ACK действительно commit-ится, его ответ теряется, client читает `COMPLETED`, сохраняет `ACKED_RESULT`, popup возвращает `IMPORTED`. Таким образом, замечание относится к потере relay **до серверного ACK**, а не к уже реализованному восстановлению потерянного ответа после commit.

### Рекомендация

Различать отсутствие process-memory пакета и подтверждённое терминальное состояние запроса. Сохранять результат `IMPORTED_PENDING_ACK` при восстановимой потере relay; одна ошибка `TRANSFER_REPLAY` при серверном `DELIVERED_TO_RECIPIENT` не должна удалять результат. Предусмотреть согласованный путь завершения или явное восстановимое состояние, сохраняя account/device/request/packet binding и запрет повторного импорта. Не признавать ACK успешным без подтверждённого основания. Проверить совместный сценарий перезапуска сервера и recipient recovery.
