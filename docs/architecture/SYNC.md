# Автономность и редкое согласование

Основная норма: ноль обязательных обращений к Seller Agents на обычный пакет команд и его доставку.
Сервер не является посредником бизнес-запросов. Строгая глобальная блокировка диалога при сетевом разделении не требуется.

## В одной установке

Worker владеет локальной таблицей диалогов и очередями. Вкладки одного conversationKey используют одного исполнителя; повторный клик/перезагрузка не создаёт второй запрос.
Квоты разделяются по подтверждённому кабинету и семейству API, независимо от имени магазина и вкладки. Состояние хранится устойчиво к остановке worker.
Локальное межвкладочное согласование не обращается к серверу. Недостаточно одного in-memory mutex, теряемого при перезапуске.

## Между браузерами

Сервер хранит текущую bindingRevision: какой магазин выбран, явное изменение/завершение, предпочтительная установка. Он не хранит очередь команд, буфер или контекст ИИ.
При доступном сервере новая установка получает известную привязку. Если магазин тот же — принимает bindingId; если иной — показывает конфликт и предлагает явную смену.
Токен может отсутствовать локально: общая привязка не означает наличие ключа, нужен импорт/перенос.

При временной недоступности сервера установка может продолжать известную допустимую сессию. Попытка явной передачи/смены записывается как pending операция с baseRevision/requestId.
Две установки временно могут исполнять независимо. Возможны повтор одинаковой команды, двойное сообщение в ИИ, расход общей квоты площадки и устаревшие ответы. Это принятый предел автономности, а не exactly-once между браузерами.
Новый Start при неподтверждённой глобальной смене ясно показывает локальное состояние; после обнаруженного другого магазина конфликт разрешается для этого диалога, не для всего расширения.

## N2: общий wire для редкого чтения состояния

Остаётся один транспорт `POST /v1/sync`; отдельного read endpoint, heartbeat, lease, WebSocket или server poll не вводится. Для binding-состояния канонический server entity key — `conversation:<conversationKeyDigest>`, где digest — 64 hex SHA-256 подтверждённого conversation key. Для store metadata ключ — `store:<storeId>`. Сырые conversation ID, содержимое диалога, marketplace credentials и отчёты в этот wire не входят.

Совместимый V1 request получает необязательный `readEntityIds`. Это уникальные канонические IDs, максимум 32. `entries` по-прежнему максимум 32, но может быть пустым только когда есть хотя бы один read; `entries + unique readEntityIds <= 32`. Старые mutation-only клиенты продолжают посылать прежний shape. Во время server-first rollout legacy mutation `entityId` не становится canonical-only на wire: сервер обязан вывести канонический storage/lock key из binding payload и сохранить exact historical replay/fingerprint semantics. Новые `readEntityIds` принимают только канонические ключи.

Совместимый V1 response получает необязательный `snapshots`. Для каждого запрошенного ID сервер возвращает ровно один snapshot в порядке request: `entityId`, `serverRevision`, `serverState`. Неизвестная сущность — revision `0` и `null` state. Read-only вызов не создаёт entity, receipt и не меняет `updated_at`. Mixed call сначала завершает mutations, затем делает bounded read актуального committed состояния; это не обещание атомарности всего batch сверх уже существующей mutation semantics.

Каждый `serverState` ограничен существующим durable пределом 4096 UTF-8 bytes. `snapshots <= 32`, полный JSON response — не более 256 KiB. Сервер не обрезает state молча: нарушение границы fail closed. Новые request fields не отправляются клиентом до принятого server-first deployment; optional response snapshots должны оставаться совместимыми со старым response consumer.

## Восстановление связи

Расширение инициирует запросы. Сервер не опрашивает браузеры.
Пока есть pending операция, фоновые попытки: ориентировочно 5 с, 15 с, 30 с, 1 мин, 2 мин, далее максимум раз в 5 мин с jitter. Это технические стартовые значения, не гарантия точного времени браузерных alarms.
Событие восстановления сети/открытия браузера может ускорить одну попытку; нужен single-flight и общий лимит попыток на установку. Спящий браузер не удерживается искусственно.
Без pending задач отдельного частого таймера согласования нет. Плановое обновление лицензии целевым образом выполняется примерно раз в 24 часа при использовании по [согласованной политике](SUBSCRIPTION_ACCESS_POLICY.md); небольшие dirty metadata/маркеры следует объединять с уже необходимым служебным обращением. Это требование, не утверждение о текущей реализации отправки. Явные изменения привязки/магазина и ограниченный retry pending операций имеют отдельные события; не откладывать нужную сверку автоматически на сутки и не отправлять запрос на каждый отчёт.

Последняя успешная доставка записывает локально один компактный маркер для своей привязки; не вызывает немедленный сетевой запрос и не создаёт историю всех отчётов на сервере.
При обращении передаются только изменившиеся записи. Повторный requestId безопасен. Полученный ACK удаляет/уплотняет pending запись.
Размер очередей ограничен: изменения одной сущности сворачиваются по revision; устаревшие записи не вызывают бесконечные повторы.

## Что означает «последний отчёт»

Учитывается только доставка для той же актуальной bindingRevision и магазина. Явная смена/Finish имеют приоритет над поздними delivery markers.
Если AI даёт сопоставимый стабильный порядок сообщений, используем его. Иначе клиентские времена и локальная последовательность позволяют только приблизительный выбор; время получения сервером не равно времени доставки.
Детерминированное разрешение равенств стабилизирует preferredExecutor, но не доказывает истинный мировой порядок. Ошибка часов не меняет магазин и не перезапускает работу.
Сервер не может знать о доставке установки, которая ещё не обратилась. Результат согласования уточняется при следующих обращениях; это постепенное схождение, не мгновенная синхронизация.

Новая полученная revision прекращает будущие действия старой локальной сессии и запрещает позднюю доставку под новым магазином. Уже отправленные сообщения не удаляются.
Смена preferredExecutor не генерирует новый промпт, не очищает credentials/квоту и не перебрасывает управление от каждого нового отчёта. Оконченная pending передача не открывается вновь от старого маркера.

## Отказоизоляция

Bootstrap/auth и optional reconcile имеют независимые результаты. Ошибка одной привязки не блокирует другую и не отзывает аккаунт.
Транзакция согласования короткая, по конкретной account/conversation записи. Нельзя ждать браузер или сеть, удерживая блокировку PostgreSQL.
API имеет ограничение пачки/времени; health и relay не занимают рабочий пул API без лимитов.
Никаких серверных leases/heartbeat на каждый диалог; никаких постоянных WebSocket только ради исключительного сценария у всех пользователей.
Граница: свежий известный отзыв доступа и истёкший signed grace обрабатываются по auth-политике, не игнорируются ради автономности.

## Перенос ключей

1. Получатель вошёл в тот же аккаунт, выбирает источник и явно соглашается на проход ключей через сервер.
2. Создаётся expiring запрос с recipient public key; raw secrets отсутствуют.
3. Активный источник узнаёт запрос при старте/служебной проверке или уже выполняющемся ограниченном сеансе переноса. Постоянный глобальный канал не нужен.
4. Источник без дополнительного popup подтверждения шифрует выбранные магазины для получателя; сервер кратковременно пересылает пакет без постоянного хранения.
5. Получатель проверяет запрос/аккаунт/срок/целостность, показывает конфликты и сохраняет локально. ACK закрывает запрос.
6. При logout/revoke/expiry сеанс закрывается; неподтверждённые пакеты не импортируются.

Если источник выключен или не авторизован, ключи получить нельзя. Показываем инструкцию из [UX](../product/UX.md), а не сообщение «на сервере ничего не найдено».
Без фонового постоянного канала уже открытый источник может заметить запрос с задержкой. Открытие/пробуждение исходного расширения ускоряет обнаружение; это не второе подтверждение.
