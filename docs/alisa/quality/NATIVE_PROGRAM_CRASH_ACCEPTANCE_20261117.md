# Авария worker во время программного расчёта · 17.11.2026

Три сценария прошли на точной копии 210 файлов установленного R15. Это авторская синтетическая проверка настоящего Worker/SQLite/Unix-протокола с реальным SIGKILL и отдельным процессом восстановления. Независимое статическое review R2 — PASS для этих ограниченных утверждений. Весь R5 и настоящий executor outbox этим не приняты.

## Граница доказательства

Работающий native: `alisa-economics-r15-native-cafb743c94672104`, manifest SHA256 `4e49ab8da6f88fce1c5672d2960b536f5043d1e942c28ef3e18117c1f33c86d7`. На Alisa и в тестовой копии проверены все 210 хешей; digest отсортированной карты `path:sha256` — `38588f45b740b963459af93db04abb4d453021a260313011ef16499e82aeecba`. После прогона карта не изменилась. Python теста 3.12.13; идентичность всей среды серверу не заявляется.

[Конечный qualifier](scripts/qualify_native_program_crash_20261117.py) использует действующий `template_mode=True`, как runtime.py на сервере. Подготовка задания использует штатную template-fixture; только API_DATA заменены синтетическим документом 11000 символов для выбора program lane. Это не проверка сбора финансовых данных. Прежний запрос, program binding, SQLite ledger, claim/lease, model_answer и model_program остаются настоящими.

Синтетический Unix broker и loopback HTTP peer — управляемые источники исходов. HTTP-обработчик подтверждает приём запроса до SIGKILL; в другом случае broker подтверждает получение ответа до SIGKILL. Новый PID продолжает тот же job после продвижения часов теста за lease. Это не перезапуск рабочей службы и не ожидание реального срока lease. Разрешены только два адреса этой фикстуры; остальные соединения отклоняются audit hook.

| Место аварии / действие | Подтверждённый исход |
|---|---|
| HTTP принят, ledger ещё SENDING, broker не имеет результата | Первоначальный started/binding сохранён; новое соединение protocol3/resume_only содержит только job_id/fingerprint; тот же job становится UNKNOWN. Чтение статуса и следующий шаг Worker не создают запрос. |
| Ответ HTTP уже RECEIVED, ответ broker удержан до записи итогового результата | Новый процесс получает сохранённый ответ по прежнему binding и завершает тот же job READY. ACK наблюдался при уже записанном READY. |
| Отмена при HTTP в полёте, затем SIGKILL | Новый Worker не принимает отменённый job. Позднее complete со старым owner отклоняется; CANCELLED не получает результат. |

В каждом сценарии — один физический синтетический program-model HTTP и одна новая строка его ledger; при восстановлении нет новых ledger rows. Стартовавшие процессы завершены SIGKILL (-9), процессы восстановления — exit0. Реальных вызовов площадок/модели нет. Рабочие DB/config/credentials не использовались. При запуске заданы параметры отдельной cgroup: MemoryMax512MiB, MemorySwapMax0, RuntimeMaxSec180. Это параметры команды запуска, а не встроенные проверки qualifier: R2 не записывает наблюдаемый пик памяти или эти свойства. Завершение подтверждено сообщением systemd «Deactivated successfully»; unit после завершения выгружен, его собственная cgroup пуста. Review отдельно сохранило это ограничение ресурсных доказательств.

## Первый отказ сохранён

R1 использовал штатную старую AnswerFlow с `template_mode=False`. Собственно аварийное восстановление дало UNKNOWN и один model send, но дополнительная команда с префиксом «обнови» изменила original_question/answer key и создала отдельный legacy job. FAIL и точный исходный qualifier сохранены; это поведение не объявлено исправленным. На работающем пути runtime.py принудительно включает TEMPLATE_ONLY. R2 проверяет этот режим и восстановление прежнего принятого задания, не подменяет его новым переформулированным намерением. Обычные правила repeat_safe/retry и продуктовый код не менялись.

## Воспроизведение и остаток

Запускать qualifier штатным Python с `--native-root <точная code-only копия> --pins <JSON с картой native> --output <новый приватный каталог>`, в отдельной конечной cgroup по RESOURCE_POLICY. Не передавать рабочий config или DB; не повторять существующий output/unit. Скрипт сохраняет RESULT.json с тремя отдельными исходами, проверяет хеши до/после и завершает только собственные дочерние процессы/сокеты. Удаление тестовых данных выполняется автором после сохранения уникальных результатов.

Полные приватные доказательства: `/root/alisa-native-program-crash-20261117` на Easyscript, R1 сохранён отдельно. Следующий рубеж — настоящий установленный executor/outbox: долговечное сохранение и восстановление ответа на его стороне при потере соединения, без запуска платной модели. Эта проверка не заменяет его. Подтверждённый источник начала истории Ozon и полная R5-приёмка остаются открытыми; границы истории здесь не вычисляются.
