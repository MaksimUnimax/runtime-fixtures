# Устранение искусственной суточной квоты и цикла ожидания — 8 ноября 2026

## Факт и причина

После реального подключения колонки сообщения ожидания повторялись через 10 секунд. Задание оставалось в `QUEUED` с `due` примерно через 21 час. Причина была **наша**, а не внешняя квота DeepSeek: `resource_limits.json` задавал `daily_calls=20`; `Repository.reserve` считал все вызовы `model:deepseek-flash` за последние 24 часа и переносил следующее задание до выхода первого вызова из окна. На сервере было ровно 20 таких вызовов. Это не означало, что расчёт всё это время выполнялся.

## Что установлено

- На текущем runtime `alisa-runtime-read-surface-r3-20261108` построен отдельный слой `/opt/alice-market/releases/alisa-runtime-model-unlimited-r1-20261108`. `daily_calls=0` означает отсутствие нашей суточной квоты **только** для `model:deepseek-flash`. Ограничения конкретных API маркетплейсов не изменялись. Интервал не менее 2 секунд между модельными запросами оставлен для сериализации, это не суточная квота.
- Запись отложенного задания возвращена в очередь без создания второго запроса. Установка: `/run/alisa-model-unlimited-r1.json`, `INSTALLED`, 19 проверок, 91 тест каталога и отдельная проверка 25 модельных резервирований при сохранении лимита обычного источника.
- На колонке повторение реплики ожидания ограничено тремя отправками на одно задание. После этого сервис продолжает молча проверять готовность и при `READY` вызывает навык. Сохранившееся подключение и выбранное устройство не сбрасывались.
- При истечении короткого голосового access token сервис не передаёт текст отчёта до новой авторизации: вызывает навык только при наличии действующего refresh token в учётной записи, затем callback обязан предъявить новый access token. При отсутствии действующего гранта отправка блокируется.

## Наблюдение после исправления

Первое отложенное задание перешло в `READY` после снятия лимита: для него состоялись три модельных вызова. При повторе автоматической доставки сервис получил callback и зафиксировал `responded_to_skill`. Это подтверждает ответ навыка, но не факт слышимого звука на физической колонке. Позже появилось **другое** задание, завершившееся `FAILED/HTTP_400`; оно требует отдельной диагностики исполнителем runtime/read-surface.

## Оставшаяся работа по оценке времени

Цифровое время ответа нельзя честно вычислить из одного статуса `QUEUED/RUNNING`: серверный `station_status` не передаёт `due` или стадийный прогресс, а готовых запусков для статистики на момент проверки почти не было. Следующий шаг — добавить безопасные `due` и этап в IPC статуса, собрать реальные длительности по классам запросов, затем в пределах первых трёх реплик сообщать пересчитываемый диапазон. Если расчёт отложен за пределы окна доставки, нужно сказать об этом один раз и прекратить повтор. Не озвучивать выдуманное обещание «через N минут».

## Проверка владельца

1. [Кабинет колонки](https://alisa.octoport.ru/app/station/): подключение и привязка сохранены; обновление страницы не вызывает нового QR.
2. При новом долгом задании не более трёх реплик ожидания, затем тишина до готового ответа; колонка не должна бесконечно повторять фразу.
3. Готовый ответ озвучивается автоматически при успешном запросе. Если именно новый запрос вернул ошибку, сообщить его формулировку без ключей и кодов, чтобы проверить `HTTP_400`.

Следующий кодовый выпуск runtime обязан сохранить снятие искусственной квоты; при замене текущего слоя старой `resource_limits.json` ошибка вернётся.
