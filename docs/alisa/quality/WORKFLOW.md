# Регламент постоянной совместной работы

Версия QA-1, 04.11.2026. Применяется к матрице и её тестам, не меняет права платформы. Прототип инструмента/исследовательский Python — вход квалификации, не production-модуль.

## 1. Начало сеанса

Прочитать README/BOARD, последние реестры и связанные карточки. Установить точные active build, catalog/source/decoder версии и границы разрешённого стенда. Задачи в RUNS старой сборки не объявлять проверенными на новой. Выбрать один пакет сценариев по зависимости и приоритету; записать `run_id` и назначение. Различать engine offline, recorded API, live API, console и Station.

## 2. Подача тестером

В `inbox/<UTCYYYYMMDD>-TESTER-<8 hex>/` сохранить RUN_REPORT.json и при необходимости BUG_REPORT.md / TEMPLATE_CANDIDATE.json. Использовать формы, перечислять изменённые файлы и SHA. У каждой реплики: безопасный текст, ожидаемое определение, фактический безопасный ответ, начало/конец UTC, webhook/job/API/UI время раздельно (неизмеренное null), HTTP/LLM счётчики и result/job_ref при наличии без секретов. «Результат», повтор webhook и страницы не считаются новыми спросовыми эпизодами.

Новый баг: проверить реестр на тот же смысл/причину. Указать legacy ID либо создать `QA-YYYYMMDD-TESTER-<8hex>`; уникальный ID не требует изменения общего счётчика. Группы «заказы», «выкупы», «начисления» не объединять по сходству слов. Приложить минимальный пример и expected/actual. Неизвестная причина так и остаётся неизвестной.

## 3. Что считается багом

BUG — неверная работа реализованного контракта; CAPABILITY_GAP — отсутствующая функция; PROVIDER_ERROR/PROVIDER_FORMAT — доказанный ответ источника, не предположение о ключах; PREVENTED/ACCEPTANCE_RULE/LIMITATION — ограничение или предотвращённая ошибка; RESEARCH_FIX/RESEARCH_TOOLING — исправление исследования, не обязательно текущего сервиса. Source severity сохраняется, отсутствующая — UNSET. Технический HTTP200 не доказывает бизнес-смысл и правильную арифметику.

## 4. Приём автором ядра

Проверить import hash, отсутствие секретов, точную версию, полноту evidence и возможность воспроизведения. Обновить единственный реестр с текущим Git blob SHA; конфликт записи означает re-read/merge, никогда force overwrite. Записать тип изменения SYNONYM / FORMULA_FROM_EXISTING / SOURCE_BINDING / GENERAL_OPERATOR / BUG / PROVIDER_WAIT. Найти общий источник/операцию, объединить только доказанные дубли и оставить alias/ссылку. Нельзя делать отдельный обработчик под месяц, формулировку или площадку там, где работает общий DSL.

## 5. Статусы дефекта

NEW → TRIAGED → REPRODUCED → IN_DEVELOPMENT → READY_FOR_RETEST → VERIFIED → CLOSED. Альтернативы BLOCKED, DUPLICATE, NOT_A_BUG с reason и ссылкой. READY_FOR_RETEST требует fix_commit и конкретный regression/proof. VERIFIED требует отдельный retest_run_id, target build+catalog и результат тестера. CLOSED требует выполненный согласованный scope и release/readback, если заявлено исправление работающего сервиса. Историческое PREVENTED/FIXED_IN_RESEARCH хранится в reported_outcome; оно не даёт автоматического VERIFIED для production. Ненадёжный результат возвращается в TRIAGED/REPRODUCED, а не становится PASS.

## 6. Статусы шаблона

Использовать цепь v0.5: NEW → TRIAGED → CANDIDATE → SPECIFIED → IN_DEVELOPMENT → VALIDATING → RELEASED → MONITORING → CLOSED. BLOCKED/DECLINED — с причиной. SPECIFIED требует answer contract, axes/units/currency, scopes, source qualification, negatives, независимый numeric gold. Новая ревизия candidate SHA сбрасывает прежнее approved_hash. Само наличие JSON/Python/зелёных unit-тестов не даёт RELEASED.

Для VALIDATING: полный regression + доказательство «совместимая функция добавляется только матрицей» (контрольные SHA runtime Python до/после). Для RELEASED: approved_hash==content hash, approval_ref, proof IDs, отдельный test-tenant assignment, реальный runtime readback, исходная задача тестера и пострелизный контроль. Если live API/Dialogs требовались — fixture их не заменяет. Политика публикации и staff approval принадлежат платформе. LLM и пользовательский текст publish-права не получают.

## 7. Числовые эталоны и типовые запреты

`commission.sale_price` в источнике начислений — сумма строки; среднее = SUM(line amounts)/SUM(quantity). Не умножать её второй раз. Заказной unit price и начисленный line amount — разные определения. Сохранить реальные различия цен одного SKU; возвраты отдельно по квалифицированному знаку; отсутствие денег не ноль. Цена конкретной сделки не текущая цена карточки. Payment unknown отдельной группой; bank_coinvestment не является доказательством карты. Признак «Ozon Банк» не превращает остальные метки в «карты других банков». Средние по дням не усреднять вместо взвешенного общего среднего. Сезонность/порог — описательная связь, не доказанный эффект цены. Эти правила взяты из приложенных CASE и должны присутствовать в отрицательных тестах.

## 8. Доказательства и приватность

В Git только очищенные сценарии, схемы, synthetic fixtures, хеши и минимальная metadata. Не сохранять полный Request Алисы с access_token, cookies, Authorization, execution_ticket, реальные store/posting/order IDs, персональные сведения и финансовую выборку. Секрет обнаружен — карантин локально, metadata-only, не пересылать его в новый отчёт. Numeric gold для публикации должен быть synthetic; приватная сверка — закрытая evidence_ref с hash/TTL и фактом наличия. Сканер — дополнительный контроль, не гарантия анонимности.

Source-исследование на имеющихся закрытых страницах не является использованием старых финансовых отчётов рабочим exact-кэшем. Не повторять вызовы только ради переноса документа. Исходники/происхождение остаются в Git; raw evidence — по действующему серверному TTL. Runtime conversation TTL и публикационная история — разные виды данных.

## 9. Конец сеанса и передача

Сохранить RUN_REPORT и карточки, выполнить qa_check --check, обновить BOARD через --render, опубликовать с readback SHA. Отчёт владельцу: что сделано; что воспроизведено/не проверено; что реально установлено; явные блокеры; один конкретный следующий шаг. При обрыве возобновлять по run/status, не повторять весь сетевой пакет. История инструментальных отказов — TOOL_FAILURE_RUNBOOK; неизвестный исход не повторять вслепую.

## 10. Нет незаявленного фонового тестирования

Этот комплект задаёт процесс для агента при его фактических запусках. Он сам не создаёт автоматизацию, не запускает фоновый сбор и не даёт агенту новые права. Если агенту разрешены API, он соблюдает общий ledger/квоты, locks и область работ. В installer/platform/рабочий каталог он не пишет. Интегратор не изменяет чужую platform STATUS и не принимает шаги вместо второго исполнителя.
