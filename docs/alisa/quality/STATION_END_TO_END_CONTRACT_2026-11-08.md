# Голосовой путь без ручных сценариев — уточнение 8 ноября 2026

Статус: RESEARCH_COMPLETE / TRANSPORT_NOT_VERIFIED / NOT_DEPLOYED.
Это уточнение заменяет прежнее предложение обязательного ручного сценария как пользовательского подключения. Рабочие службы, привязки, голос, приветствие и настройки пользователя этим исследованием не менялись.

## Обязательные требования владельца
- При входе без вопроса: только «Привет, {имя из профиля сайта}». Источник — текущий связанный профиль сервиса, не имя Яндекса, email или догадка. Если имя отсутствует/пользователь не связан — «Привет», без выдуманного имени.
- Возможности — по отдельному запросу «Что умеет навык?», «Что ты умеешь?» и уже существующему H00. Не смешивать помощь с приветствием.
- При запуске с аналитическим вопросом сразу обрабатывать вопрос; не подменять его приветствием.
- Один запрос → расчёт → автоматическое произнесение готового ответа. Никаких обязательных команд опроса готовности.
- Пользователь не должен вручную конструировать сценарии умного дома. Согласие на доступ и выбор колонки допустимы как необходимые этапы подключения; технический сценарий должна обслуживать система.

Справка H00 уже описана в BASE_BATCH_01_PLAN_2026-11-04.md, п.4. Новый текст помощи не придумывать отдельно от реально включённых возможностей.

## Что подтверждено
1. Публичный IoT API перечисляет чтение устройств/сценариев, действия над устройствами/группами, запуск существующего сценария, удаление устройства. Метод создания/редактирования сценария в опубликованном контракте отсутствует.
2. Запуск POST /v1.0/scenarios/{scenario_id}/actions принимает существующий ID; динамический текст ответа в теле не предусмотрен.
3. Официальный путь старого плана поэтому включает разовую ручную настройку сценария. Это реальное ограничение подключения, а не обязательное действие перед каждым отчётом. Оно не соответствует новому требованию без ручного конструирования.
4. Обычный webhook должен полностью ответить за 4,5 секунды. Музыка/рассказ в tts могут заполнить паузу, но не предоставляют новый серверный канал и не вызывают документированный автоматический запрос за готовым ответом.
5. В актуальном открытом коде AlexxIT/YandexStation обнаружен другой, неофициальный путь: load_speakers автоматически вызывает add_scenario; add_scenario создаёт служебный сценарий через внутренний Quasar API; send обновляет действие с текстом/командой и запускает сценарий. README описывает QR-авторизацию и автоматическое создание служебного сценария на каждую колонку.
6. Этот код — доказательство существующей реализации механизма, не доказательство его работоспособности с нашим аккаунтом, моделью колонки и текущими токенами. Облачный режим не подтверждает фактически услышанный звук.
7. Публичный контракт AudioPlayer, гарантирующий переход от ожидания к ответу для нашего обычного навыка, не установлен. Наличие audio_player в meta.interfaces не доказывает доступность произвольного streaming/push API.

## Полный целевой пользовательский путь
Это спецификация для реализации и приёмки, не инструкция к уже готовым кнопкам.

1. Пользователь регистрируется на https://alisa.octoport.ru/, задаёт имя, подключает свои магазины. Этот путь не требует доступа в админку.
2. Связывает аккаунт сервиса с голосовым навыком Яндекса. Так аналитический вопрос и ответ получают правильного владельца/права.
3. Для автоматической речи подключает колонку: проходит отдельное разрешённое подтверждение Яндекса, выбирает устройство и включает автоответ. Разрешение обычного навыка и управление колонкой — разные полномочия; не заменять одно другим.
4. При выбранном Quasar-варианте система сама создаёт/проверяет ровно один свой технический сценарий на выбранную колонку. Пользователь не вводит команды/ID/JSON и не редактирует сценарии. Это требует нашей реализации и испытания, простого OAuth iot:control недостаточно.
5. Подключение завершается контрольной безопасной репликой на выбранной колонке и подтверждением пользователя. До этого функция не показывается как рабочая.
6. При обычном открытии навыка звучит только «Привет, {имя}». На вопрос о возможностях отвечает H00. На аналитический вопрос создаётся одно задание существующей очереди.
7. Быстрый расчёт выдаётся сразу. Для долгого расчёта короткая честная реплика, например «Считаю», затем фоновая обработка. Никакого обещания готовности до READY.
8. Когда расчёт завершён и ответ сохранён, событие READY запускает доставку на связанную колонку. Пользователь ничего не нажимает и не произносит.
9. Предпочтительный для единообразия голоса вариант: техническая команда вызывает наш навык, новый запрос читает конкретный разрешённый готовый отчёт; повторный LLM/API расчёт не производится. Прямой Quasar TTS — отдельная ветка: она умеет произносить переданный текст, но не обязана использовать выбранный в Диалогах голос и не равна полноценному продолжению разговора.
10. Колонка сама произносит готовую короткую сводку. Пользователь может задать уточнение, если проверенный вариант доставки оставляет диалог открытым. Полный текст сохраняется на сайте.
11. Отмена/отзыв доступа запрещают последующую речь. Оффлайн/занятость/неопределённый исход доставки не превращаются в успех. Нет слепых повторов, чужих ответов, глобального «последнего отчёта», одновременной перезаписи сценария двумя заданиями.
12. Несколько колонок требуют явной привязки источника запроса к разрешённому устройству. Пока она не доказана, допустим только явно выбранный пользователем канал автоответа, без заявления «ответит именно та, которой задали вопрос».

## Рассказ во время ожидания
Короткую заранее сформированную реплику или полезную вставку обычный навык воспроизвести может. Она не превращается в живую трансляцию этапов worker и не освобождает от отдельного механизма доставки. Непрерывное ожидание с автоматическим прерыванием рассказа готовым ответом пока НЕ ПОДТВЕРЖДЕНО. Нельзя делать длинный рассказ и объявлять этим требование закрытым. Базовая приёмка: краткое «Считаю» → автоматический готовый ответ.

## Почему сейчас иначе
Действующий голосовой путь долгого отчёта реализует сохранение результата и чтение по новой пользовательской реплике. Обработчик приветствия в legacy webhook объединён со справкой. В документации от3ноября автоматическая доставка была предложенной непроверенной архитектурой; поздний v0.5 S18 отложил её. Описание проекта ошибочно использовалось как доказательство готового транспорта. Этот разрыв нужно закрыть отдельной сквозной поставкой, а не изменением одной фразы.
