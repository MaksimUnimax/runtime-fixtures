## 4. Архитектура: что сохранить и что улучшить

**Основное направление правильное.** Ядро считает детерминированно, а LLM используется для понимания запроса. Семантика показателя, временная ось, валюта, источник и полнота должны быть явными. Это существенно надёжнее свободного вычисления финансов через текстовую модель.

Полезные реализованные границы: отдельные идентификация и продуктовые права; изоляция клиентов; шифрованное хранилище ключей; привязка проверок к ревизии магазина; фиксированные направления внешних запросов; журнал физических вызовов и квот; отсутствие слепого повтора неизвестного HTTP-исхода; повторная проверка прав при выдаче результата. Новый граф использует прежние Repository/Worker, а не создаёт параллельный расчётчик.

| Граница | Оценка | Изменение |
|---|---|---|
| Платформа ↔ аналитическое ядро | Главная незавершённая связь. Работоспособность каждого процесса отдельно не даёт сквозного отчёта | Один ответственный за адаптер: права, ревизии, submit/status/cancel/result, TTL и отзыв доступа |
| Матрица ↔ универсальный код | Верное направление; есть общие примитивы, фиксированные рецепты и квалификация | Новые совместимые показатели — через матрицу; новый оператор допускается только как общая возможность с регрессией |
| Очередь ↔ несколько пользователей | Текущая очередь сохраняет состояние, но не обеспечивает справедливое чередование задач | Исправить выбор следующей задачи и ограничить длительность внешнего вызова в существующем Worker |
| Сайт / identity / admin | Разделение оправдано; повторная проверка должна соответствовать цели операции | Один проверяемый сценарий входа для клиента и отдельный для staff; не смешивать код письма, TOTP и резервный код в пояснениях |
| Релиз ↔ воспроизводимость | Компонентные выпуски и точные SHA есть; восстановление полного runtime требует архива и нескольких патчей | Принятый runtime хранить как цельный исходный пакет с tests/lock/manifest в каноническом дереве; docs оставить для спецификаций и receipts |
| Эксплуатация ↔ ресурсы | Текущая установка помещается почти ровно в дисковый резерв | Рассчитать одновременно рабочий выпуск, rollback и пик новой сборки; не считать сохранённые файлы «освобождённым местом» |

Добавлять сейчас Kubernetes, Kafka, новый контроллер работы агентов или вторую очередь оснований нет. Сложность нужно уменьшать в передаче состояния и выпуске, а не расширять инфраструктурой. Модульное разделение оставлять внутри существующих сервисов, пока нет измеренной причины выделять новый процесс.

Две дополнительные меры до расширения аудитории: задать квоты числа незавершённых магазинов/ключей и срок хранения истории, а также сохранить протокольную регрессию native allauth при обновлении зависимостей. В проверенном `stores/service.py` есть ограничение скорости создания, но оно не ограничивает накопленное количество непроверенных магазинов с ключами PENDING; нагрузочный эффект не измерялся. Identity использует внутренние hooks/cache native-библиотеки: это осознанная зависимость, которую нельзя обновлять только по успешной сборке интерфейса.

## 5. Находки кода и эксплуатации

Приоритет P1 здесь означает блокер ближайшей безопасной поставки или многопользовательского пилота; P2 — исправляемый дефект/риск с конкретным условием. Отсутствующая запланированная функция отделена от ошибки реализованной функции.

### A01. P1: платформа ещё не подключена к runtime

**Подтверждено кодом и живым readback.** API платформы возвращает `RUNTIME_NOT_CONNECTED`. В установленном адаптере используется DisconnectedRuntime; foundation worker обслуживает инженерный probe, а не полноценные отчёты клиентов. Это незавершённость S06/S07, не внезапная поломка ранее принятого полного продукта.

Речь о выполнении аналитических задач и отчётов из новой платформы. Отдельный setup-check IPC магазинов этим статусом не оценивается. Значение readiness задано в коде и не является самостоятельной живой проверкой всех соединений; вывод основан также на адаптере и доступных маршрутах. Существующий лабораторный голосовой runtime и его прежние успешные ответы этим выводом не отрицаются.

Нельзя объявлять услугу готовой только по READY четырёх процессов. Критерий закрытия: новый клиент штатно входит, получает доступ, подключает проверенный магазин, связывает Яндекс, задаёт запрос, получает независимо сверенный отчёт; повтор не создаёт лишний внешний вызов, отзыв прав прекращает новые вызовы и выдачу недопустимого результата.

### A02. P1: практически исчерпан запас места для следующего выпуска

**Измерено 8 ноября в 02:16 UTC:** свободно 3087,74 МиБ, резерв по действующей политике 3072 МиБ, остаток сверх резерва **15,74 МиБ**. Свободных inode 524847 — inode не являются текущим ограничением. Эта разница ещё не учитывает размер следующей установки и возможные дополнительные резервы. Ранее в том же аудите доступная RAM составляла около 5901 МиБ; первичный наблюдаемый дефицит — диск.

Службы продолжают работать; это не сообщение о случившемся падении. Но следующий deploy с полноценной копией зависимостей нельзя считать обеспеченным. Последние установки уже требовали объединения одинаковых зависимостей hardlink, поэтому проблема повторяется.

Закрытие: инвентаризация сохраняемых выпусков и уникальных данных, доказуемо безопасное освобождение либо увеличение диска, затем расчёт пикового места для выпуска и отката. Резерв не снижать. В этом аудите ничего не удалено.

### A03. P1 перед многопользовательским пилотом: длинная задача вытесняет новые

**Воспроизведено на действующем коде.** `repository.py:178–186` выбирает `QUEUED` по `ORDER BY created,id`. `reschedule():210–214` возвращает задачу в очередь, сохраняя её исходный `created`. `runtime.py:74–83` запускает один рабочий поток.

Две искусственные задачи разных клиентов — старая длинная и новая короткая. После каждого шага старая снова готова к работе. Пять последовательных claim дали:

```json
{"selected":["old-long","old-long","old-long","old-long","old-long"],"other_tenant_selected":false,"temporary_only":true,"external_calls":0}
```

Это доказательство несправедливого планирования при указанном условии, а не измерение текущей пользовательской задержки. Пока старая задача готова без rate-limit-паузы, новая ждёт её завершения. Та же сортировка сохранена в `candidates/20261106-cue01-queue-r1/runtime/repository.py:182`.

Исправление: справедливое чередование клиентов/готовых задач с ограниченным числом шагов подряд, сохраняя единую очередь и журнал квот. Регрессия: длинная пагинация клиента A не блокирует короткий запрос B; рестарт не теряет очередь; паузы API и отзыв прав сохраняются.

### A04. P2: выдача доступа в админке зависает при недоступном localStorage

**Подтверждено точным исходником и изолированным воспроизведением ревьюера.** Admin `731801…`, `products/alisa/apps/admin/src/app/admin/access.tsx:39–43`: после `setBusy(true)` и `setPending(operation)` вызывается `localStorage.setItem` вне `try/finally`.

Если браузер запрещает storage или запись превышает квоту, возникает исключение до запроса API. Состояние остаётся `busy=true`, кнопка повторения тоже заблокирована. В проверке для SecurityError и QuotaExceededError: `apiCalls=0`, `busy=true`, `pending=true`. В error-cleanup есть также незащищённый `removeItem`.

Исправление: безопасный storage-adapter и обработка ошибки внутри общего finally; сохранить идентификатор операции в памяти, объяснить возможность восстановления после перезагрузки, не терять идемпотентность. Проверить запрет storage, заполненную квоту и потерю сетевого ответа после успешной выдачи.

### A05. P2: неизвестный результат создания магазина не сохраняет идентичность операции

**Статически подтверждённый сценарий отказа; реальный магазин не создавался.** Web `7afa…`, `products/alisa/apps/web/src/app/app/stores/view.tsx`: `send()` каждый раз генерирует новый `command_id`. После ошибки `perform()` пытается обновить список, но при неудаче readback сохраняет старый список и снимает `busy`.

Если сервер успел создать магазин, ответ потерян, а последующее чтение также недоступно, пользователь может повторно заполнить форму и создать новую команду. Идемпотентность backend по UUID не связывает её с первой. Для ещё не проверенного кабинета уникальность verified identity не устраняет этот случай. Последствие — дополнительная незавершённая карточка/ключ, а не доказанный доступ к чужому магазину.

Исправление: отдельно хранить безопасный идентификатор незавершённой команды и получать её итог до нового create; не сохранять секреты в localStorage. При неизвестном исходе показать состояние восстановления и блокировать случайное повторное создание. Проверить потерю ACK после commit вместе с неуспешным refresh, затем восстановление связи. Уже реализованная обработка неизвестного сохранения Performance после успешного create этот более ранний случай не закрывает.

### A06. P2: socket timeout не ограничивает полное время получения ответа

**Подтверждено чтением кода; медленный реальный источник не вызывался.** `http_transport.py:116` вызывает `read_response(timeout=25, limit=12000000)` без абсолютного deadline. В `shared_http.py:26–27` выполняется одно `response.read(limit+1)`. Timeout сокета не гарантирует общий предел времени при продолжающейся медленной передаче.

Один worker может долго удерживать задачу; при выходе за lease последующая запись может быть отвергнута. Это риск доступности и UNKNOWN, а не доказательство ложного финансового результата. Даже deadline-ветку общего helper нужно проверять на медленное заполнение отдельного блока чтения.

Исправление: общий бюджет вызова, согласованный с lease, и контролируемое чтение с оставшимся временем; тест на локальном медленном источнике без реальных API. Сохранить отсутствие автоматического повтора неизвестного физического вызова.

## 6. Ход работы: где теряется результат

### A07. P1 для управляемости: актуальные доказательства и общая доска расходятся

В `quality/README.md` и `CATALOG_PROGRESS_CURRENT.json` уже отражены 82/78/4 и QUEUE-R01/1670. Но генерируемая BOARD и её источники ещё показывают 27 записей разных типов в TRIAGED, шесть импортированных кандидатов и восемь исторических прогонов. Например, OZCP-001 имеет позднее независимое подтверждение на конкретной версии, а общая строка остаётся TRIAGED/NOT_RUN.

Это **не 27 подтверждённых текущих багов** и **не весь каталог из шести шаблонов**. Проблема — устаревшее представление, с которого регламент требует начинать работу. Документы S04/S05 и окончательный отчёт о парольном входе находятся в feature-ветках, отсутствуя в проверенной точке общей ветки `alisa`.

Frozen v0.5 roadmap со всеми NOT_STARTED — исходная спецификация, не текущий счётчик прогресса. Его не следует переписывать ради видимости завершения. Нужно поддерживать текущие execution-статусы и связи с доказательствами.

Исправление: обновить существующие BUGS/TEMPLATES/RUNS адресными ссылками на фактические build/retest; сгенерировать BOARD штатным инструментом; свести текущие платформенные статусы и состав выпуска в существующую рабочую документацию. Новую параллельную очередь или автоматический реестр ошибок не создавать. Сохранять исторические FAIL и не ставить VERIFIED без независимого retest.

### A08. P1 перед обещанием точных денег: остаётся долг независимой числовой приёмки

Независимый safety-retest зафиксировал 18 PASS, 2 PARTIAL, 1 FAIL и 3 SKIP на своей сборке. Для DS03 затем внесено исправление, но независимый повтор не наблюдается: это READY_FOR_RETEST, а не доказанная текущая поломка и не закрытый PASS. Прежние числовые PARTIAL/SKIP не закрываются успешной проверкой очереди.

Нужны эталоны с одинаковыми периодом, магазином, валютой, временной осью и смыслом показателя. Заказы, фактический выкуп, начисления и возвраты — разные события. Арифметическое совпадение двух обработчиков одного ответа API не заменяет сверку бизнес-смысла с независимым источником. Неизвестное значение не превращается в ноль.

### Оценка организации

Сильная сторона процесса — сохранение точных SHA, исходных неудачных попыток, независимых review и ограничений приёмки. За 4–6 ноября поставлены существенные платформенные функции; считать всё «не сделанным» неверно.

Слабая сторона — задача дробится на технические части, которые получают локальную проверку, тогда как окончательный путь владельца остаётся NOT_RUN. Много зелёных проверок не ответило на его практический вопрос «я вошёл — где моя админка и отчёт?». Это вывод о границе приёмки по имеющимся материалам, не утверждение, что последние исправления отсутствуют.

Последний код уже разделяет ordinary customer и staff: клиенту положены пароль и свежий email-code, staff сохраняет TOTP. Исторические скриншоты нельзя использовать как доказательство, что текущая версия по-прежнему требует TOTP от обычного клиента. Но и просмотр новой формы не заменяет конечный вход и возврат в нужный кабинет.

## 7. Как изменить работу без нового слоя бюрократии

1. **Единицей результата сделать пользовательский сценарий.** Одна задача заканчивается наблюдаемым эффектом: вход → нужный кабинет; сохранение двух ключей → одна карточка с отдельными статусами; вопрос → правильные числа. API, кнопка и установка — части этого результата.
2. **Сохранить двух предметных исполнителей и независимого тестера.** Платформа/identity/store UI и ядро/матрица могут работать отдельно. На общей границе нужен один владелец адаптера; результат принимается совместно. Тестер получает готовый пакет, точную версию, ожидаемый ответ и разрешённый стенд.
3. **До изменения фиксировать затрагиваемые сценарии.** Для входа: новый/старый пользователь, отсутствие пароля, установленный staff TOTP, logout/login, истечение сессии, возврат из MFA, запрет storage. Для магазинов: оба ключа, частичный успех, неизвестный исход, смена ключа и отзыв доступа.
4. **Не накапливать принятые изменения только в длинной цепочке feature-веток.** Объединять проверенные зависимости в согласованную интеграционную точку и поддерживать короткий состав текущего выпуска. Не сливать вслепую только ради зелёного статуса PR.
5. **Привязывать каждый PASS к exact build и уровню проверки.** Offline, recorded API, live API, browser, Яндекс Диалоги и настоящая Станция — отдельные уровни. Не складывать пересекающиеся тестовые наборы и повторные запуски.
6. **Закрывать результат перед расширением соседних функций.** На ближайшем пути важнее S05→S06→S07 и свежий C-UE01 через общий Worker, чем дальнейшее увеличение счётчика шаблонов. Независимая работа матрицы при этом не останавливается.
7. **Измерять ожидание и переделки.** В существующем checkpoint записывать дату готовности к тестеру, причину ожидания, время разблокировки, версию и следующий наблюдаемый результат. Не вводить новый контроллер допуска.
