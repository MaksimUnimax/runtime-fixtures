# Коэффициенты: один текущий результат и дата последней сборки

14 ноября 2026. **Первый серверный блок реализован и проверен в изолированном окружении. В рабочие ЛК, колонку и ядро он пока не установлен.**

[Обязательный контракт владельца](../architecture/CURRENT_PARAMETERS_CONTRACT_20261114.md) имеет приоритет над прежними архитектурными предложениями хранить историю числовых значений. Нет отдельного сервиса коэффициентов или новой очереди.

## Что реализовано

В существующем модуле owner_data подготовлены:

- `CurrentParameter`: одна текущая запись на tenant/store/parameter/scope/SKU. Успешная замена перезаписывает value и весь паспорт расчёта; старые значения не остаются в отдельной таблице истории.
- `parameter_catalog.json` и `parameter_contract.py`: общие типы, единицы, области, периоды, проверяемые формулы. Значения конкретного магазина не зашиты в исполнитель. Первые определения — потери заказов и средняя объединённая доставка.
- `parameter_service.py`: чтение актуального значения, ручная установка, использование общего вместо SKU-исключения, атомарная запись рассчитанного результата. Проверяются права владельца, магазин, принадлежность SKU, ожидаемая техническая ревизия.
- `parameter_resolution.py`: use/status/preview/recalculate. Существующее число, включая ноль и старую дату, не инициирует сбор. Чтение даты никогда не вызывает producer. Первичный недостающий общий параметр рассчитывается для всего магазина, даже если отчёт запрошен для одного SKU.
- Совместимая миграция, закрытый по умолчанию флаг и существующая account/service boundary для API. Внешний клиент не может прислать команду сохранения произвольного рассчитанного результата: это внутренний вызов доверенного job-адаптера с проверкой источников.

## Даты без путаницы

В текущем паспорте различаются:

| Поле | Значение |
|---|---|
| `calculated_at` | Когда успешно завершили последнюю сборку/расчёт текущего коэффициента. Это дата для вопроса «когда пересчитывали коэффициент?» |
| `collected_at` | Когда наблюдались исходные данные. Если источники получены в разное время, консервативно показывает наиболее раннюю дату; текущий паспорт содержит даты компонентов |
| `updated_at` | Когда сохранено текущее значение, включая ручной ввод |
| `actual_period` | За какой статистический диапазон рассчитано число; это не дата сборки |

Ручное число имеет `origin=manual`, дату ручной записи и пустые поля сбора/расчёта/статистического периода. При замене рассчитанного коэффициента ручным старые даты и основание очищаются. Расчёт по повторно используемым данным не выдаётся за новый сбор свежих данных.

Заполненный коэффициент действует до прямой команды пользователя. Нет автоматического обновления при новом дне, возрасте значения, очередном отчёте или изменении шаблона. По умолчанию новый расчёт запрашивает календарный год до вчерашнего дня; подтверждённая короткая история допускается. Явно указанный период не сокращается без согласия.

## Защита от потери текущего значения

Пока новый сбор не завершён, единственное рабочее значение остаётся на месте. Ошибка API, неполнота, отмена или конфликт не меняют число и даты. Успешная запись заменяет их одной транзакцией.

Ревизия — техническая защита от конкурирующих записей, не история коэффициентов. При снятии SKU-исключения состояние INHERIT содержит ревизию, но не старое число или паспорт. Это не позволяет поздней команде незаметно восстановить удалённое исключение.

Квитанции OwnerCommand содержат только метаданные операции/исхода/ревизии. Прежний value, числитель, знаменатель, даты и период не дублируются в receipt. Повтор прежней команды подтверждает её исход и возвращает актуальную запись, а не прежнее число. Удаление просроченных технических квитанций не разрешает исполнить старую команду заново.

Запрет истории не означает удаление независимой исходной статистики blood_sand, чужих финансовых отчётов, Git-истории программы или общих резервных копий. Новая функция не создаёт из них альтернативное хранилище коэффициентов. Автоматическое восстановление старого параметра из старого отчёта запрещено.
