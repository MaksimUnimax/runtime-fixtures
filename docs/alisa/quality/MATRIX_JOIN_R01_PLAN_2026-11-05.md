## Что отсутствует

Текущие metadata-строки содержат список SKU и общее quantity отправления; для надёжного join нужна quantity каждого SKU. Товарные начисления не несут нормализованный posting key. Источник метаданных в исходном периоде не гарантирует попадание отправлений, созданных раньше начисления. Обычный inner join теряет строки, many-to-many умножает суммы. Нужен общий конечный контракт, не ozon_payment_handler.

## Реализация этого среза

Отдельная копия hotfix плюс адресно объединённые B05/B13 JSON и общий availability-error fix. Прежние каталоги/тесты сохраняются; не переписывать активный hotfix или прежний candidate.

Общий pure join по декларативным composite keys: many-left-to-one-right; отказ на повторном правом ключе, конфликте SKU и нарушении количественной границы; защита от перезаписи левых денежных полей; сохранение всех целевых строк и независимая сверка сумм/количеств. Нет eval/HTTP/секретов. Используются существующие decoder и decimal primitives.

Join выполняется отдельно внутри проверенного store block после завершения всех страниц нужных stage. Поддерживается только bounded left enrichment, не произвольный SQL. Метрики остаются левыми; правая сторона добавляет только объявленные поля. Missing posting и missing/неизвестная метка видны отдельно; unknown не «без карты». Если posting найден, но SKU не совпал, это ошибка, не unknown. В зависимости от политики допускается явный unmatched либо fail-closed. Все enrichment coverage counts и суммы выводятся/сохраняются отдельно от source completeness.

Общий stage-window описывается данными: смещения начала/конца и размер непересекающихся calendar chunks. Для candidate метаданные запрашиваются с ограниченным lookback до периода начисления; это НЕ обещание полноты всей истории. Если нужного отправления нет, целевая строка остаётся unmatched, сумма не теряется. Будущие даты, чрезмерные окна/задачи и неразрешённый scope отклоняются. Квалификация проверяет фактические окна, не только исходный период.

В JSON добавить отдельные нормализованные источники per-posting-product и positive realization rows (не изменять прежние B05-отчёты). Поля берутся из уже описанных источников; production допуска нет до отдельной проверки наличия unit_number/product quantity. Выборка positive sales закреплена смыслом нового шаблона, обратные начисления не скрываются в net и не объявляются квалифицированными для payment-report.

На одном join — четыре отображения: строки, способ оплаты, день+оплата, товар+оплата. Суммы/взвешенные средние должны сходиться. Разность средних не скидка одинаковой покупки, никакой вывод о карте по bank_coinvestment. Составной C-UE01 этим не закрывается.
