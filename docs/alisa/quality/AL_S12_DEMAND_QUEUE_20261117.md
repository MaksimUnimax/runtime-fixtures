# AL-S12 · очередь потребностей в шаблонах

Продолжение roadmap после установленного AL-S11. База исходника — `485a2034ac0dc36fea2590666075b54c24b12174`; отдельная ветка `feat/alisa-demand-s12-20261117`. Приёмку коэффициента на физической колонке выполняет владелец. Её ожидание не задерживает этот этап.

**Уровень результата: установлено, техническая готовность подтверждена 17.11.2026.** На существующем сервере выполнена миграция шести новых таблиц, включены platform/admin/authority. Три readiness отвечают 200 с точными release ID. Native, Station, web, identity, store checker и SMTP сохранили поколения; коэффициенты и разрешение голосовой записи не менялись. Ручную приёмку выполняет владелец; её результат не заявляется.

## Что получает владелец сервиса

В существующей странице «Журнал вопросов» появляется раздел «Запросы на новые шаблоны». Он показывает очищенные формулировки, число эпизодов, вклад после дневного ограничения, уникальных клиентов, динамику по дням и карточку кандидата.

При достижении обычного или альтернативного порога создаётся одна карточка. Можно назначить ответственного, указать состояние и приоритет. Подтверждённый дефект или финансовая ошибка создаёт срочную карточку без ожидания порога; зависимость от провайдера — карточку в состоянии WAITING_FOR_PROVIDER. Новые события не сбрасывают это решение.

Совместимые группы можно объединить, выбранные эпизоды — выделить в отдельную группу. При объединении двух существующих карточек сохраняются состояние и ответственный целевой карточки, максимальный срочный приоритет и снимки обоих прежних решений в истории. Исходная карточка получает MERGED и остаётся связанной с историей. При разделении сохраняется первоначальное происхождение эпизода; вклад пересчитывается по всему составу группы, а не складывается из прежних итогов.

## Подсчёт и границы

| Правило | Значение по умолчанию |
| --- | --- |
| Обычный спрос | 20 вкладов, 5 клиентов, 30 суток |
| Оплаченный доступ на момент события | 5 вкладов, 3 клиента, 14 суток |
| Максимальный вклад клиента за день UTC | 1 |
| Внутренние проверки | исключены |
| Повторная доставка того же эпизода | не создаёт новый вклад |

Пороги настраиваются владельцем. Вклады считаются в PostgreSQL по парам «псевдоним клиента / день UTC», с ограничением каждого дневного вклада. Raw count остаётся количеством разных логических эпизодов. Общая сумма и число клиентов считаются по исходным группам в БД; в браузер не выгружается неограниченный список клиентов.

PAYMENT берётся из первого принятого снимка `access_basis_at_event`. Текущая подписка не запрашивается; последующая ревизия не превращает прежний UNKNOWN/GIFT в оплаченное событие и не отменяет прежний PAYMENT. Для нового поведения платного порога используются маркированные синтетические события в disposable БД; реальная оплата этим этапом не заявляется.

Признак внутренней проверки сохраняется при последующих ревизиях. Автоматический спрос учитывает только неподдержанный смысл/оператор, успешный ответ второго пути после промаха шаблона, неверный смысл и ошибку разбора/выполнения. Сбои доступа, безопасности или провайдера не становятся автоматическим доказательством отсутствующего шаблона. Ручная карточка не запускает runtime и не даёт дополнительных прав на данные.

Словарь объединяет только явно перечисленные лексические формы. Ось даты, площадка, исключения, остальные слова/условия и версия ключа псевдонимизации входят в смысловую сигнатуру. «Заказы» и «выкупы», «все» и «кроме» не смешиваются. Разные версии псевдонимизации не объединяются, чтобы смена ключа не создавала несколько кажущихся клиентов. METADATA_ONLY не даёт текстового кластера.

Кандидат закрепляет конфигурацию/версию порогов, интервал и агрегированные основания первого создания. Он не удаляется и не открывается заново автоматически при снижении спроса. Повтор создания возвращает прежнюю карточку; редактирование требует её актуальной ревизии. Запись decisions хранит управленческую историю этого продукта, без сырых вопросов, секретов или клиентских идентификаторов.

## Интеграция

- `query_insights.service.save_event` подключает захват после существующей дедупликации Inbox, только при включённой возможности. На фактической установке `gap_ingest` выполняется через `authority_rpc` в отдельном `alisa-runtime-authority-stage.service`; поэтому этот authority получает тот же backend overlay и флаг. Одной замены HTTP-platform недостаточно для автоматического появления карточек.
- Управляющие действия используют существующий PostgreSQL advisory transaction lock журнала. Порядок блокировок совпадает с ingestion; нового исполнителя/таймера нет.
- Новые таблицы: DemandPolicy, DemandCluster, DemandContribution, DemandReceipt, DemandCandidate, DemandDecision. Старые таблицы эпизодов не изменяются. Миграция — `query_insights.0002_demand_queue`.
- Чтение проходит по существующему `insights.read`. Изменения доступны только владельцу через существующее `staff.manage`; новый набор делегируемых полномочий не вводится. После операции полномочия проверяются повторно, отказ откатывает всю транзакцию.
- Используется прежний защищённый BFF и staff endpoint; действия `demand.list`, `demand.refresh`, `demand.policy`, `demand.create`, `demand.update`, `demand.merge`, `demand.split` сохраняют форму `action/filters`.
- Список ограничен 20 группами с cursor. Детали содержат до 30 эпизодов и 20 решений. Разделение ограничено 30 эпизодами и укладывается в прежний лимит запроса. Обработка старого журнала включает до 200 эпизодов за одно явное обновление и сообщает оставшийся объём. Новые события обрабатываются при штатной доставке.

## Поставка и откат

`ALISA_QUERY_DEMAND_ENABLED=0` — исходное состояние. После квалифицированной поставки флаг включён (`1`) в фактических процессах platform, admin и отдельного authority. Platform требует уже включённого query journal.

Три согласованных кандидата (platform/admin/authority) поставлены поверх фактической R15/Station-сборки с сохранением прежних дополнений. Конечные операции подготовки, включения и восстановления находятся в PR468. См. [порядок включения](AL_S12_ACTIVATION_20261117.md) и [фактическое чтение установки](AL_S12_INSTALLED_READBACK_20261117.json).

Откат доступности — выключение нового флага и возврат совместимого кода с сохранением добавленных таблиц/решений. Обратную миграцию с удалением истории проверять только в disposable среде; не выполнять её над пользовательскими данными. Текущие значения коэффициентов и Station consent не относятся к данным AL-S12.

## Проверка и приёмка

В существующий source-CI launcher добавлен `tests/runtime_authority/query_demand.py`: 12 контрактных сценариев в прежней disposable PostgreSQL/Unix fixture. Они проверяют оба порога, 100 эпизодов одного клиента за день, исключение внутренних проверок, лексическую дедупликацию, несовместимые оси/исключения, split→merge, срочный дефект/провайдера, повтор создания после изменения решения, запрет записи для read-only staff, rollback при окончательном отказе полномочий и невалидные входы. Это не тесты рабочей колонки и не вызовы маркетплейса.

Python-синтаксис проверен. Независимое статическое ревью текущих backend/migration/frontend не обнаружило блокирующих замечаний; это не проверка исполнения. Исходник `13f01118c7402814ba96cf42e8a75635220fbb45` прошёл source CI `44080835358` и documentation CI `44080835409`. Все 12 новых сценариев в disposable PostgreSQL прошли без ошибок; сборка admin и прежние проверки также успешны. После проверки плана выполнена `query_insights.0002_demand_queue`. Независимое от установщика read-only чтение подтвердило одну запись миграции, шесть таблиц, существующие runtime-права и флаг `1` в трёх процессах. Все девять служб активны. AL-S12 установлен; пользовательская приёмка не выполнялась.

Ручная приёмка AL-S12: в изолированной сборке воспроизвести пять сценариев TEST_PLAN AL-T11-01…05, открыть очередь владельцем и сотрудником без прав изменения, проверить назначение/историю и сохранность ранее поставленных функций. Следующий roadmap после этой функции — AL-S13, управляемая публикация проверенного шаблона; карточка кандидата сама по себе production-код не создаёт.
