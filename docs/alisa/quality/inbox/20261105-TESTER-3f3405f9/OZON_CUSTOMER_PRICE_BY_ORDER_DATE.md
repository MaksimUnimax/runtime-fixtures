# Цена реализации для покупателя по дате заказа

ID: ozon_customer_price_by_order_date_v1. Статус: **CANDIDATE**, спецификация добавлена по прямому поручению владельца 5 ноября 2026 года. В работающий голосовой навык не установлена. Используется общий оператор выбора когорты и соединения источников; отдельный обработчик под дату/месяц не создавать.

## Запрос и определение

«Стоимость реализации для покупателя товаров, заказанных на Озоне 1 ноября 2026 года». Допустим диапазон дат. Параметры: магазин, order_date_from/order_date_to, календарь Europe/Moscow и as_of_utc — до какого фактического момента собраны начисления. Относительные даты разрешать в явные даты. При неуказанном годе использовать общий проверенный календарный разбор с уточнением неоднозначности.

Основная ось — **дата заказа**, а цена берётся из финансовых данных этих же товаров. Дата начисления может быть позже даты заказа. Старый снимок публичной карточки не требуется. Историческая цена конкретной покупки не восстанавливает историческую витрину и не доказывает способ оплаты или использование Ozon Карты. as_of_utc фиксирует фактический текущий момент сбора; произвольное прошлое состояние знаний источника без сохранённого снимка не обещается. Поздние начисления могут уточнять ответ о старых заказах.

## Получение на сервере Alisa через API

1. В существующей привязке магазина получить POST /v1/analytics/data: date_from/date_to, metrics=[ordered_units,revenue], dimension=[sku,day], limit/offset. Пройти всю пагинацию. Это независимый контроль состава заказов и суммы продавца, а не источник фактической оплаты покупателя.
2. Получить отправления POST /v3/posting/fbo/list и POST /v4/posting/fbs/list с переводом границ московского дня в UTC, обязательной пагинацией и достаточным охватом пограничных состояний. FBO: проверенное поле created_at. FBS v4: в проверенном ответе есть in_process_at, **начало обработки**, не автоматически дата создания заказа; не сочинять created_at. Требуется подтверждённая семантика даты конкретного отправления либо иной надёжный источник его order_date. Дополнительно сверить SKU × день × количество и деньги с аналитикой. Агрегатное совпадение необходимо, но само по себе не доказывает точный состав отправлений: перестановка одинаковых SKU/цен через границу дня может сохранить суммы. Пока posting-level дата не квалифицирована, сохранять AXIS_NOT_QUALIFIED даже при равных агрегатах. При расхождении состава дополнительно вернуть COHORT_INCOMPLETE; не утверждать точную когорту по дате заказа.
3. Составить набор магазин + posting_number + SKU, сохранить physical quantity, цену продавца и дату заказа отдельно. Отменённые и ещё не реализованные позиции остаются в исходном количестве заказанных товаров.
4. Запросить POST /v1/finance/accrual/postings по этим posting_numbers для привязанных начислений и расходов. Этот ответ сам по себе не объявлять источником цены покупателя, если нужное поле не квалифицировано.
5. Для покупательской цены читать POST /v1/finance/accrual/by-day: {date: YYYY-MM-DD, last_id: ...}. Искать начисления от начала выбранного периода до as_of, включая даты ПОСЛЕ даты заказа; пройти last_id каждой даты до подтверждённого окончания, обнаруживать повтор курсора и лимит страниц. Большой диапазон выполнять через общий worker/квоты и разбиение; не обещать неограниченную историю или мгновенный полный ответ. Не ограничивать поиск финансовым днём самого заказа.
6. В проверенной структуре положительной реализации брать posting.products[].commission.sale_price.amount, валюту и products[].quantity. **sale_price — сумма товарной строки, не цена одной штуки.** Не умножать её повторно на quantity. Соединять unit_number/идентификатор отправления начисления с posting_number исходной когорты и SKU внутри того же магазина. Для безопасного экспорта использовать существующие стабильные псевдонимы; не публиковать исходные идентификаторы и данные покупателей.
7. Различать положительную реализацию, сторно и возврат по квалифицированному виду/знаку начисления; неизвестный тип не превращать в продажу. Положительные цены покупок и возвратные суммы показывать отдельно. Удалять только доказанные дубли по ключу начисления + товарной строки + потоку. Повторная реализация, частичная поставка и несколько строк одного SKU требуют сверки количества; конфликт или превышение покрытия не разрешать произвольным выбором строки.
8. Для каждой источниковой страницы сохранить запрос без секретов, ответ/контрольную сумму, начало/конец UTC и HTTP. Опираться на действующий общий rate ledger, не менять ограничения. 429, UNKNOWN, незавершённая пагинация и недоступная история означают неполное покрытие с причиной, а не нулевую цену.

## Формулы и ответ

- ordered_units — все физические единицы выбранной исходной когорты.
- matched_positive_units — уникальные единицы этой когорты с квалифицированной положительной реализацией; не сумма повторных наблюдений одной продажи.
- buyer_sale_amount — сумма квалифицированных положительных sale_price строк этой когорты в одной валюте.
- observed_average_buyer_price = buyer_sale_amount / matched_positive_units. При нуле — NULL.
- whole_cohort_average_buyer_price — значение разрешено только при полном однозначном покрытии всех исходных заказанных единиц и полном просмотре источников; иначе NULL. Отменённые/невыкупленные товары не получают фиктивную цену 0. Для частичного набора показывать среднее наблюдаемой части с явной подписью.
- coverage_pct = matched_positive_units / ordered_units × 100; при ordered_units=0 — NULL. Противоречивое или превышающее 100% покрытие — ошибка квалификации, не результат.

В ответе обязательны: выбранные даты заказа и календарь; as_of и интервал поиска начислений; исходное количество; количество подтверждённых, отменённых, ожидающих и неизвестных единиц; покрытие; сумма и средняя цена только подтверждённых покупок; средняя всей когорты либо NULL; возвраты/сторно отдельно; SKU-таблица и источник каждого значения. Неподтверждённую причину пропуска обозначать «нет квалифицированного начисления», не угадывать физический статус.

Группировка ответа: дата заказа по возрастанию, внутри даты SKU; история снимков — дата статистики, затем время сбора. Среднее по периоду вычислять как сумму денег / сумму физических единиц, не как среднее дневных средних. Разные валюты не складывать. Платёжный способ unknown остаётся unknown; разность цены не доказывает Ozon Карту.

## Контрольный синтетический пример и границы готовности

Синтетически заказаны 3 единицы в дату D. По 2 единицам одного SKU начисление D+2 содержит sale_price.amount=1000 RUB и quantity=2. Третья единица без начисления. Средняя подтверждённых покупок **500 RUB/шт.**, покрытие **2/3**, средняя всей исходной когорты **NULL**. Если подтверждена третья единица с суммой 700 RUB, общая средняя 1700/3=566,67 RUB/шт. Дополнительное возвратное начисление не превращать во вторую положительную продажу.

Нужны отдельные проверки: quantity>1; одинаковый SKU в разных отправлениях/магазинах; полночь Москвы и FBS-дата; позднее начисление; неполный/повторный курсор; отмена и возврат; несколько валют; отсутствующее Money; конфликт количества; UNKNOWN/429. До квалификации источников, общего runtime binding, независимого numeric gold и реального Яндекс-retest статус не повышать до RELEASED.
