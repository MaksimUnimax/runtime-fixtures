# Юнитэкономика Ozon по дате заказа · спецификация для исполнителя

Статус: CANDIDATE. Это описание будущего шаблона C-UE01; в Алису не установлен. Другой исполнитель реализует общий оператор и привязки данных, затем тестер проверит точную сборку. Не создавать отдельный Python-обработчик под каждую дату или фразу.

## Запрос и ввод
«Юнитэкономика на Озоне за 4 ноября 2026, себестоимость 250 рублей, без налога». Дата — параметр, относительная дата разрешается явно; календарь Europe/Moscow выводится в отчёте. Себестоимость и налог задаёт пользователь. Если они не заданы, расчёт продолжается без них с явной подписью; результат не называется чистой прибылью. 250 ₽ не становится общей настройкой для любых пользователей.

## База и две таблицы
Берём товары, заказанные в выбранную дату, со всеми отменами; количество — сумма штук, а не количество финансовых реализаций и не корзин. Состояние отмен/возвратов фиксируется на момент расчёта. Таблица A — условие «все исходные заказанные товары получены»; таблица B — прогноз по тому же набору заказов с известными отменами/возвратами. Суммы, на единицу, процент от цены продавца этого же сценария, источник каждой статьи и признак факта/оценки обязательны. В таблице B основная товарная единица — оставшаяся неотменённая заказанная штука, не уже реализованная штука. Дополнительное распределение результата на все исходные заказы подписывается отдельно.

Себестоимость 250 ₽ остаётся 250 ₽ на применимую штуку. По отменам выручка и себестоимость 0 ₽; понесённые реклама и прочие расходы остаются. Возвраты после получения выделяются отдельно: восстановленный товар на складе и утраченный/повреждённый товар имеют разную себестоимость потерь.

## Отмена с неизвестной стадией — точная инструкция
1. Прочитать POST /v5/product/info/prices для товара.
2. Для FBO взять items[].commissions.fbo_return_flow_amount; для FBS — items[].commissions.fbs_return_flow_amount.
3. Умножить сумму на количество отменённых штук соответствующей схемы и добавить в расходы строкой «Оценка обратной логистики по тарифу API».
4. Для того же события найдено фактическое начисление/сторно — использовать его вместо оценки, не добавлять тариф второй раз.
5. Не требовать ручного подтверждения физической сдачи. Один cancelled_after_ship=true не доказывает сдачу, но неизвестная стадия не блокирует эту оценку.
6. Остальную перевозку неизвестной отмены показывать консервативным сценарием полного маршрута: середина прямого тарифа + поле доставки до выдачи + середина first-mile для FBS. Эти суммы подписывать оценками, не понесёнными списаниями. При надёжном доказательстве несдачи неоказанную перевозку не прогнозировать; реальные противоречивые списания показывать отдельно.

Числа из конкретного магазина в публичной спецификации не закрепляются. Тарифы получают при выполнении; текущий тариф не объявляется историческим фактом. Если ни API, ни официальный тариф не дали значения — назвать отсутствующее поле и причину, показать неполноту; не сочинять ноль.

## Расходы и проценты
Комиссия — явная ставка API для товара и схемы × цена продавца; не цена покупателя после скидки Ozon Карты. Эквайринг — фактическое начисление либо денежное поле acquiring, не выведенный процент. Прямая логистика и FBS first-mile — фактическая сумма либо (min+max)/2 реального тарифного диапазона. Последняя миля — фактическая сумма либо поле API. Обратный тариф-комплекс не дополняется той же включённой обработкой второй раз.

Обязательны обе рекламы, хранение, приёмка, перевозки, обработка, эквайринг, платные услуги, штрафы и корректировки. Неизвестный тип расхода не отбрасывать. Реклама/хранение всего магазина — распределение расхода дня, не точная привязка к каждому заказу. Реклама из финансов и Performance сверяется, а не складывается дважды. Без источника рекламы нельзя принимать шаблон как полный. Возврат CPO не выдумывать: учитывать найденное сторно/подтверждённое правило.

Процент статьи = её сумма / стоимость товаров того же сценария × 100. Ставка комиссии и доля всех расходов — разные значения. Нельзя закреплять итоговые проценты нашего разового отчёта как тарифы. Нет выручки — процент не определён.

## Приёмка и передача
JSON содержит поля API, формулы, ошибки и отрицательные сценарии. SYNTHETIC_GOLD.json — проверяемый числовой пример без данных магазина. Перед установкой нужны общий оператор, квалификация всех источников/соединений, отсутствие двойного счёта, сравнение по одному и тому же набору заказов и внешний тест в Яндекс Диалогах. У каждого запроса сохранить запрос → безопасный ответ → начало/конец UTC → время API/очереди/Алисы отдельно. 429 не превращать в пустой успех или нулевые расходы.
