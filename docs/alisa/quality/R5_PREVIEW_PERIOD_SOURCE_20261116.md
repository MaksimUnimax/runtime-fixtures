## Проблема и изменение

При запуске «Рассчитать без сохранения» клиент сообщал, что текущее число будет заменено после завершения. Исправлен только текст принятого preview; сообщение о замене сохраняется для отправленного режима replace. Сообщение относится к отправленной команде, даже когда пользователь успел переключить select до ответа.

Подготовка получала requested и actual, но показывала только requested. Теперь показывается фактический период; при отличии рядом остаётся запрошенный. Клиент не вычисляет начало истории и не сокращает диапазон сам. Справка больше не обещает автоматическое сокращение истории, которого действующий протокол пока не обеспечивает.

Единственный продуктовый файл: products/alisa/apps/web/src/app/app/parameters/view.tsx, три изменённые строки. Backend, права, правила сохранения и API-команды не меняются. Чужие R15 source.py/service.py/settings/suite_routing/shared workflow не редактировались.

## Воспроизведение и проверка

Оба дефекта воспроизведены на прежнем компоненте из 3ba145d2: запрос годового периода с подтверждённым коротким actual показывал только год, принятый preview обещал замену. BEFORE_V3_period_PRIVATE.log и BEFORE_V3_preview_PRIVATE.log содержат отдельные AssertionError и фактический текст элемента.

Новый тест компилирует настоящий React-компонент и model.ts через установленные версии Next SWC/webpack из lockfile. Запускается существующий managed Chromium headless shell 1234; браузеры и зависимости не скачивались. Синтетический HTTP-сервер доступен только на loopback, внешние browser requests запрещены. Это проверка компонента, без Next BFF, Django, PostgreSQL, runtime, модели и маркетплейса; её нельзя считать installed/live приёмкой или доказательством доступности истории.

Итоговый FINAL_GUARDED_UI.json: 8 проверок UI PASS и 3 проверки файловых границ PASS:

- справка не обещает неподключённое автоматическое определение короткой истории;

- полный год не получает ложное сокращение;

- сообщение после переключения остаётся связано с отправленным режимом;
- replace отправляет одну команду своего режима, без ручной записи и немедленной замены показанного числа.

## Следующий шаг и незакрытая короткая история

parameter_contract.resolve_period уже принимает available_from/short_history_confirmed. parameter_service.execute при prepare_calculation и parameter_collection.start вызывают его только с сегодняшней датой и period. В существующем протоколе приёма нет подтверждённой границы истории, которую можно передать этим вызывающим путям. Простая подстановка первого найденного заказа, пустого ответа, ошибки API либо даты регистрации Store в платформе не даёт такого подтверждения.

Следующий шаг — определить авторитетное подтверждение доступного интервала обязательных источников с существующей привязкой к магазину/ревизии и провести его через подготовку и приём расчёта одним согласованным контрактом. Затем проверить настоящий short-history сценарий и точную поставку. Эта работа остаётся открытой; текущее исправление закрывает только две ошибки интерфейса. Новый UI проверен в реальном облачном кабинете: один preview завершён без сохранения, значение повторно прочитано и не изменилось. Физическая колонка и подтверждённая короткая история остаются открытыми. Native WB-поставка PR449/451/452 сохранена; поверх прежней веб-базы установлен только новый UI.
