# DeepSeek: ревью плана кэша и параллельная работа с шаблонами

Дата: 10 ноября 2026. Статус: оценка предложения и порядок совместной работы; кэш этой работой не устанавливался. Основание: приложенная оценка второго агента, чтение действующего ядра и документации DeepSeek. Готовый патч второго агента для ревью не представлен.

## Вывод

Штатный кэш входного префикса DeepSeek подходит. Основной ход предложен правильно: стабильные сведения для выбора шаблона перед вопросом, магазинами и текущей доступностью; измерения отдельно по этапам. Разработка этого изменения совместима с продолжением обкатки шаблонов. Установки на общий сервер должны выполняться последовательно между полностью завершёнными запросами.

Кэширование уже включено на стороне DeepSeek. Работа агента — улучшить повторяемость начала отправляемого запроса и измерить результат. Полное актуальное описание всё равно передаётся при каждом вызове. Ответ генерируется заново; отсутствие попадания в кэш не является ошибкой и не должно вызывать дополнительный запрос к модели.

## Проверенная исходная версия

Действующее ядро: `/opt/alice-market/releases/alisa-selector-terminology-r1-20261110`, исходный коммит `7f5af81dc6567f2ad30fb319adf4a528ad31eaad`. Station и web используют `raw-template-flow-r1`, исходный коммит `6ae53c9d84e34faec0f2d39ff19d83f84a5067e0`.

Приложенная оценка сделана по более раннему `alisa-template-basis-r1-20261110`. Для разработки следует перенести её решения на нынешнюю базу. Перед установкой базу нужно проверить ещё раз: указанный здесь коммит не разрешает перезаписать более поздние изменения других исполнителей.

В новой базе уже исправлены передача исходного вопроса, старые проверки по ключевым словам, различение отсутствующего шаблона и ошибки исполнения, доставка ответа. Последнее изменение B08.finance_sales разместило пояснение в `purpose`, очистило `notes`. Перенос целых старых файлов способен откатить эти исправления.

## Что в предложении сохранить

- Отделить общее описание шаблонов от `available_stores`; доступность и разрешённые магазины вычислять по текущему запросу. Сохранить серверную проверку выбранного плана и прав.
- Оставить действующие правила и их роли, все необходимые определения каталога и контракты. Не добавлять описания всей матрицы API ради длины кэшируемого текста.
- Использовать один сборщик запроса для снимка и HTTP-отправки. Снимок должен позволять восстановить реально отправленный вход, с действующей политикой доступа и хранения.
- Сохранять реальную квитанцию каждого вызова, добавить признак этапа и идентификаторы версии представления. Обычный успешный простой вопрос сохраняет два модельных вызова; дополнительная модельная проверка не возвращается.
- Первое переключение выполнять после завершения работы старых заданий. Поддержку нескольких одновременно исполняемых версий каталога рассматривать отдельной доработкой жизненного цикла.

## Поправки к предложению

### 1. Хеш каталога не должен ломать начало промпта

В предлагаемом порядке перед каталогом стоит версия представления, включающая хеш содержимого. Хеш меняется даже при маленьком изменении и прерывает совпадение до большого общего блока. Версию формата можно оставить стабильной; изменяемые хеши хранить в служебных метаданных снимка/учёта, вне текста модели. Если модели нужен такой идентификатор, размещать его после общего блока.

Хеш представления модели вычислять по реально отправляемым полям. Не включать в него `notes`, версию шаблона, изменившуюся только из-за `notes`, либо полный хеш исполнения, если эти данные не относятся к выбору. При изменении `purpose` модель должна сразу получать новый текст; старое представление ради попаданий сохранять нельзя.

Проверка в памяти действующего ядра на 85 определениях: изменение только `notes` и номера версии сохранило представление выбора, но изменило общий хеш каталога. Изменение `purpose` изменило представление. В диагностической сериализации совпадающее начало при изменении B08 составило 8789 символов без предваряющего хеша и 2104 с ним. Это символы, не токены и не измеренная экономия. Живых вызовов не было; файлы и службы не менялись. Результат: [PREFIX_EXPERIMENT.json](DEEPSEEK_CACHE_PREFIX_EXPERIMENT_2026-11-10.json).

Стабилизировать порядок определений и сериализацию, но не переставлять значимые шаги составных шаблонов. Не добавлять время сборки, путь релиза или случайный идентификатор перед каталогом. Новые шаблоны должны попадать в представление из активного каталога автоматически, без второго списка, редактируемого вручную.

### 2. Комментарии имеют разные назначения

По [правилу владельца](../OWNER_TERMINOLOGY.md), `purpose` — для выбора моделью; `notes` — для итогового ответа Алисы. В составном запросе итоговая модель получает примечания явно выбранного составного шаблона, а не примечания всех базовых зависимостей. Оптимизация кэша не меняет эту границу.

Изменение примечаний для озвучки может требовать обновления исполняемой версии по действующим правилам, но не должно менять общий текст выбора. Изменение пояснения для выбора закономерно меняет соответствующий участок входа и может временно уменьшить попадания. Это не повод прекращать настройку шаблонов.

### 3. Завершение расчёта ещё не означает завершение голосового сценария

Перед переключением недостаточно проверить отсутствие QUEUED/RUNNING: READY может ждать callback, передачи ответа или следующей части. Для пилота установку делать после завершения расчёта и доставки, без ожидающего продолжения. Проверка текущего глобального хеша пока не обеспечивает бесшовное продолжение старых заданий после смены каталога. Не отключать её ради установки.

### 4. Измерять пользу, не обещать процент

72–78% из предложения остаются гипотезой. Проверить фактические hit/miss/output, цену принятого плана со всеми попытками, общую цену вопроса, задержки и ошибки выбора. В недельной статистике считать `sum(hit) / sum(prompt)`; показывать полноту квитанций, неизвестную стоимость не считать нулевой. Признак этапа привязать к записи фактической попытки, чтобы он сохранился при ошибке и перезапуске.

А/B проводить на одном снимке каталога с одинаковыми моделью, инструкциями и профилем изоляции; учитывать тарифное окно и курс. Тестовые вызовы измерять отдельно от пользовательского среднего количества вызовов на запрос. Сравнивать несколько разных вопросов с общим каталогом, включая холодные и последующие обращения. Не добавлять платный периодический прогрев.

Стабильный непрозрачный `user_id` формировать из серверной области клиента, не из ответа модели и не заново на каждый вопрос. DeepSeek использует его для изоляции кэша; общий кэш между различными клиентскими областями обещать нельзя. Политика изоляции дополняет текущие проверки доступа.

## Разделение работ

| Работа | Ответственный и граница |
|---|---|
| Шаблоны | Наш поток: содержание `template_catalog.json`, новые определения по результатам тестов, `purpose`, `notes`, порядок приёмки и журнал результатов. |
| Кэш | Второй агент: сборка представления и запроса, снимки, измерения по этапам, собственные проверки. Не редактирует смысл шаблонов в рамках оптимизации. |
| Общие файлы ядра | Если изменение шаблона действительно требует кода, отдельно фиксировать пересечение и переносить оба изменения на свежую базу. Не заменять файл старой копией. |
| Установка | Один исполнитель в каждый момент, существующий `/run/lock/alisa-market-config.lock`, проверка актуальной базы и полного завершения голосового сценария. |

## Порядок внедрения без остановки разработки шаблонов

1. Второй агент готовит патч в отдельной рабочей копии/ветке от актуальной версии. Производственная версия продолжает обслуживать обычные проверки шаблонов. Мы сохраняем каждое принятое изменение каталога отдельно от кода кэша.
2. Агент фиксирует снимок только для своего сравнительного прогона. На нём проверяет корректность выбора, разные магазины и ограничения, простые и составные вопросы, повторы и отсутствие утечки `notes` в выбор. Сравнение с живой моделью выполняет без озвучки и без запуска запросов к маркетплейсам; ожидаемый выбор задаётся смыслом сценария, а не прежним ответом модели.
3. Перед установкой переносит только свои изменения поверх последнего ядра и каталога. Если каталог изменился после сравнительного прогона, проверяет затронутые сценарии на итоговой версии. В пакет включаются текущие шаблоны и их пояснения, а не замороженная копия из начала разработки.
4. Между завершёнными голосовыми сценариями выполняется короткое переключение. База проверяется под общей блокировкой; при расхождении собирается новый пакет. Если есть незавершённый запрос или доставка, установка ожидает их завершения.
5. Продолжаем тот же список запросов на новой версии. В отчёте остаются вопрос, полный ответ, время, число DeepSeek-вызовов, стоимость и точные изменения шаблона; добавляется фактический результат кэша выбора, когда есть квитанция. При регрессии откатывается код оптимизации с сохранением последних совместимых изменений шаблонов. Полный откат на старый каталог не использовать как автоматическое действие.

Полностью одновременная замена работающего ядра и выполнение запроса без поддержки закреплённых версий сейчас не обещается. Требуется небольшой промежуток между запросами для установки, а не прекращение всей обкатки на время разработки.

## Источники и границы проверки

- [DeepSeek Context Caching](https://api-docs.deepseek.com/guides/kv_cache/): автоматический кэш префиксов, счётчики usage, best effort. Для разных продолжений общая часть может стать доступной только на следующем обращении после обнаружения совпадения.
- [DeepSeek Rate Limit & Isolation](https://api-docs.deepseek.com/quick_start/rate_limit/): `user_id` и изоляция KVCache.
- [DeepSeek Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/): ставки необходимо привязывать к модели и тарифному окну фактического вызова.
- Приложенный текст второго агента: анализ по `alisa-template-basis-r1-20261110`. Его исторические агрегаты 240/31 и прогноз экономии здесь не выдаются за заново измеренные результаты.

В рамках этой оценки новые голосовые и платные запросы не запускались. Действующая остановка голосовых тестов сохранена; этот документ задаёт порядок для их продолжения. Продуктовый код кэша не изменён.
