## Итоговое поведение

Обычный вход не содержит двух повторных checkbox service/privacy. Native signup по-прежнему получает настоящие согласия. IdP передаёт подписанные версии и исходное время native receipts; BFF проверяет их после подписи/issuer/audience/nonce/PKCE. Платформа не выдумывает согласия и не переписывает существующие записи при входе. Новый локальный аккаунт без подтверждённой регистрации не создаётся. Старый открытый login-form с парой on/on совместим, но эта пара не превращается в фиктивные записи.

Правильный клиентский вход владельца по паролю и email-коду прошёл без аутентификатора. Прежний запрос TOTP был следствием перехода исполнителя в общий IdP-вход без клиентского next. Админский TOTP не меняется. Причина отказа доставки email устранена отдельно: правильный SMTP certificate и deploy-hook только для соответствующего lineage.

Авторизованный клиент со своим ACTIVE-магазином и без истории выдачи доступа получает опубликованный каталог для предварительного просмотра. Все карточки UNAVAILABLE, preview_only=true. Поиск, вид отчёта, пагинация и перенос вопроса в форму работают без отправки расчёта. Staff sources/metrics в ответ не входят. Интерфейс показывает фактический режим, без ложной фразы о проверенном допуске.

Любая история гранта — будущего, истёкшего или отозванного — сохраняет прежний контроль доступа. Чужой/отключённый магазин, отзыв сессии и изменение магазина во время чтения продолжают отказывать. Рабочие RPC, execution ticket, Query/Worker и доступ к данным не ослаблены. Grants и задания просмотром не создаются. Фильтр parameter совместим с R5.

## Разовая установка и откат

[Установщик](scripts/install_customer_catalog_20261115.py) меняет согласованную тройку web / platform HTTP / identity. R5, native runtime, authority, admin, environment, grants, security revisions и живые сессии сохраняются; миграций нет. Native-архив из CI ZIP не устанавливается.

Проверяется SHA256 tar, затем manifest читается непосредственно из этого архива с пределом 2 МиБ и сравнивается с распаковкой. Все metadata reads ограничены. Файлы и ссылки сверяются с этим manifest. Перед apply выполняется полный ограниченный обход кандидатов без следования symlink: лишние файлы, пустые каталоги и специальные объекты запрещены. Дополнительно разрешены только проверенный .venv и ownership-marker, связанный с PLAN.

Существующий identity3a имеет старый authenticated overlay: ссылки files объявлены в overlay_references, а исходный base manifest закреплён своим SHA256. До копирования сверяются pins обоих manifests, точные link targets и file digests из base. В новом кандидате они материализуются обычными hardlinked файлами; устаревшие reference metadata убраны. Первая prepare остановилась на различии формата до создания кандидатов или изменения служб; слепого повтора не было.

Новые releases создаются без перезаписи базовых файлов. Неизменённые байты разделяются hardlink; новые копируются буфером 1 МиБ и добавляются в pool, чтобы один новый digest физически записывался один раз. Бюджет сохраняет минимум 3 ГиБ и 200000 inode. Распаковка находится в собственном tmpfs.

Общий lock: `/run/lock/alisa-stage-rollout.lock`. Его уже используют [поставка R5](../runtime/v0.11/current_parameters_release/activate.py), [AL-S11](scripts/install_question_catalog_20261114.py) и остальные штатные поставщики Алисы. Это общий lock, а не частный lock нового установщика. Действующая запись scope в controller-notices закрепляет customer web/platform HTTP/identity за этой поставкой; все исполнители, включая ручные service-control действия, должны брать тот же lock и не менять чужой активный scope. До освобождения окна параллельная смена этих selectors/масок запрещена действующим ownership protocol. Перед переключением проверяются pins, неизменность конфигурации и отсутствие QUEUED/RUNNING native jobs. Собственные временные runtime masks запрещают перезапуск всех трёх изменяемых служб во время смены selectors. Web дренируется первым; cgroup должна завершиться. После смены обоих backend selectors снимаются только их собственные masks, запускается и проверяется совместимая пара. Mask web снимается и web запускается последним. Rollback использует тот же порядок. Чужие masks и selectors не перезаписываются.

Каждая смена selector проверяет точное состояние после drain и использует Linux RENAME_NOREPLACE. Staged-объект проверяется по inode/содержимому перед переносом и ещё раз в установленном имени до освобождения прежнего объекта. Прежний объект временно удерживается в `.customer-catalog-held`; при конкурентной записи он сохраняется для разбора. PLAN, PREPARING и три FENCE receipts фиксируют конкретную попытку. Это разовая поставка, без нового фонового контроллера.

Ресурсный envelope: tests 512 МиБ / 90 секунд, prepare 512 МиБ / 180 секунд, apply или rollback 512 МиБ / 720 секунд, независимый review 1024 МиБ / 300 секунд. Все запуски — конечные transient systemd service с MemorySwapMax=0, TasksMax=1024, MemoryAccounting=yes, KillMode=control-group, TimeoutStopSec=5s, SendSIGKILL=yes, OOMPolicy=stop. До запуска проверяются свободная память сверх ожидаемого расхода и резерв 1024 МиБ, pressure и диск. После запуска исполнитель проверяет действительные свойства unit, исход и завершение всей cgroup.

[Тесты](scripts/test_install_customer_catalog_20261115.py) проверяют обе гонки selectors, отсутствие перезаписи базы, общий dedup новых байтов, потоковое копирование, ограничение metadata, связь распаковки с tar, полный состав кандидата, fences трёх служб, чужую mask и восстановление старой пары до открытия web. Проверки выполняются только на временных файлах и подменённых service-control вызовах.

## Восстановление конкретной прерванной попытки

Сначала установить исход собственного unit и завершение cgroup. Не повторять prepare/apply по одному факту таймаута. При существующем PLAN проверить его hash, кандидатов и фактические selectors: это ветка apply/rollback, а не очистка подготовки.

При отсутствии PLAN сверить PREPARING ownership (source, hash установщика, nonce, два точных target path) с marker незавершённых releases, прежними manifests, environment hashes, selectors и unit definitions. Убедиться, что ни одна служба и ни один selector не используют кандидатов. Только собственные совпавшие незавершённые каталоги и PREPARING можно переместить без перезаписи в отдельный каталог текущей попытки внутри install root. Каталог без marker допускается так переместить только если он пуст: окно между mkdir и marker. Иное содержимое требует разбора. Чужие и исторические releases не удаляются. После карантина заново проверить резерв.

После прерывания переключения сохранить masks. Проверить PLAN/PREPARING и каждый WEB_FENCE, PLATFORM_FENCE, IDENTITY_FENCE: source, hash установщика, inode/ctime mask и фазу. Не снимать чужую mask. Собственные `.customer-catalog-held`/`.customer-catalog-new` сверяются с конкретной попыткой. Удержанный объект возвращается только на отсутствующее имя через rename_no_replace; занятое имя не затирать. Затем выполняется согласованный rollback с проверенной старой парой и web последним. Необъявленные runtime-cache entries нового кандидата сохраняются для разбора: rollback его не запускает, admitted files продолжают проверяться.

## Сохранение сессии и объёма диалога

Использовать тот же Cloud Browser profile; номер вкладки после восстановления может измениться. Сначала найти вкладку, при отсутствии открыть кабинет в том же браузере. Не выходить, не очищать профиль и не подменять owner сессией другого кабинета. После работы закрепить вкладку. Cookie/session не экспортировать в Git или отчёт.

Бинарные пакеты передавать файловыми ссылками, не Base64 в диалоге. Вывод инструментов ограничивать: по умолчанию до 8 КиБ на вызов, максимум 16 КиБ; читать нужный фрагмент вместо всего лога/документа/каталога. Не печатать весь registry, JSON артефактов или длинный DOM карточек. Checkpoint держать коротким и актуальным: source, CI, установленная версия, живая сессия, незаконченный шаг. Исторические доказательства хранить отдельно. Пользовательский сценарий считается принятым только после проверки настоящего пути, а не по зелёному build или metadata count.
