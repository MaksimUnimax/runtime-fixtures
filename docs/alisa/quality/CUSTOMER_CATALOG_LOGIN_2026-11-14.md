## Изменение поведения

Обычный вход больше не содержит двух повторных checkbox service/privacy. Native signup по-прежнему получает настоящие согласия. IDP передаёт подписанные версии и исходное время native receipts; BFF проверяет их после проверки подписи/issuer/audience/nonce/PKCE. Платформа не выдумывает согласия и не переписывает существующие записи при входе. Новый локальный аккаунт без подтверждённой регистрации не создаётся. Старый открытый login-form с настоящей парой on/on принимается для совместимости, но эта пара не превращается в фиктивные записи.

Клиент с действующей сессией и своим ACTIVE-магазином, которому ещё ни разу не выдавался доступ, получает опубликованный каталог для предварительного просмотра. Все карточки помечены UNAVAILABLE; ответ имеет preview_only=true. Поиск и страницы используют те же published description/id/kind/platform. Метрики и технические источники staff metadata в ответ не переходят. Можно подготовить вопрос в форме; это не отправляет расчёт.

История любого гранта — будущего, истёкшего или отозванного — сохраняет прежний контроль доступа. Revoked scoped reads, чужой/отключённый магазин, отзыв сессии или изменение магазина во время чтения продолжают отказывать. Рабочие RPC, выдача execution ticket, Query/Worker и права на данные не ослабляются. Новые grants, счета и задания при просмотре не создаются. Неподдержанная конфигурация/версия не превращается в пустой успешный каталог.

Фильтр parameter принимается backend так же, как существующим кабинетом и ядром R5. Ложная постоянная фраза о проверенном допуске убрана; интерфейс показывает фактический режим.

## Проверка и поставка

Проверки покрывают native metadata без jobs/model/provider calls, только собственный магазин, NOT_PROVISIONED без выдачи гранта, отзыв сессии во время preview, прежний отказ после отзыва гранта, поиск/пустой результат/пагинацию и отсутствие staff sources/metrics. Дополнительно — настоящий IDP/BFF/PG путь в изолированном GitHub root job, реальные native signup receipts и их исходное время. Локальный полный qualifier отказал в запуске на постоянном сервере по GITHUB_ACTIONS guard; guard не обходили. Синтетические БД и процессы удалены. Полный прогон назначен CI.

Поставка изменяет согласованную тройку web/platform HTTP/identity. Перед сменой platform/identity customer web останавливается и дренируется; запускается только после проверки совместимой тройки. Rollback использует тот же порядок. Это закрывает замечание независимого review о mixed-version sign-ins. Ключи, accounts/security revisions, живые сессии, R5-параметры, native runtime и его authority остаются в своих действующих границах. Миграций у изменения нет.

Независимый source/installer review, точные CI и owner browser checks должны быть завершены до объявления установленного результата. Сессия владельца закреплена в Cloud Browser; не заменять её сохранённой серверной сессией другого кабинета.

### Исправления независимого review установщика

Первое installer-review запросило защиту от записи вне общего lock и восстановление после прерванной подготовки. Файлы теперь копируются потоком с буфером 1 МиБ; весь файл в память не читается. Перед записью каждого selector проверяется точное состояние после drain. Смена использует Linux `renameat2(RENAME_NOREPLACE)`: прежний объект временно удерживается под собственным `.customer-catalog-held`, его inode/content сверяется, новый устанавливается только на свободное имя. Конкурентное значение не затирается. Если оно появилось, прежний объект сохраняется для разбора. В это время web и обе изменяемые службы остановлены. Тесты воспроизводят обе гонки: замену перед перемещением и создание в промежутке. Всего восемь disposable проверок PASS.

Восстановление незавершённой подготовки выполняет исполнитель. Сначала установить исход конечного prepare unit и завершение всей его cgroup. Не повторять prepare/apply вслепую. Если PLAN уже существует, сначала проверить его hash, кандидатов и фактический выбор служб; это ветка apply/rollback, а не очистка подготовки. Если PLAN отсутствует, PREPARING содержит source, hash установщика, nonce и два точных target path. Сверить его ownership с `.customer-catalog-preparation.json` каждого незавершённого release, исходные manifests, protected environment hashes, старые selectors и unit definitions. Убедиться, что ни служба, ни selector не используют кандидатов. Только собственные совпавшие незавершённые каталоги и PREPARING допускается переместить без перезаписи в отдельный каталог этой попытки внутри собственного install root. Существующую директорию без ownership разрешено так переместить только если она пуста: это окно между mkdir и marker. Иное содержимое — остановка зависимого шага для разбора; чужие/исторические releases не удаляются. Исходные releases и hardlinked файлы не переписываются. После карантина и повторной проверки дискового резерва можно заново подготовить поставку.

Если процесс оборван во время смены selectors, сначала остановить customer web и проверить базовые pins и оставшиеся `.customer-catalog-held`/`.customer-catalog-new`. Сверить тип, цель и собственность по PLAN/PREPARING и текущей попытке. Удержанный объект можно вернуть на отсутствующее живое имя только через `rename_no_replace`; занятое имя никогда не затирать. Если живой selector уже свой и корректен, удержанный объект сохраняется до окончания разбора. Затем выполнить согласованный rollback с проверенной парой и web последним. При чужом selector восстановление останавливается без его перезаписи. Это ручной разбор конкретной поставки, без фонового восстановителя и без смены авторизации.

Повторное review потребовало проверять полный состав кандидата. Перед apply теперь выполняется ограниченный обход без следования symlink: любые лишние файлы, пустые каталоги, ссылки или специальные объекты запрещены. Разрешены только manifest, его files/links, проверенный .venv и ownership-marker, связанный с PLAN. Тест добавляет посторонний файл, пустой каталог и внешнюю ссылку; все блокируются. Всего девять проверок PASS. Для rollback лишние runtime-cache entries кандидата сохраняются для разбора: он не запускается, admitted files продолжают сверяться, а восстанавливаются закреплённые старые версии.

Связь распаковки с пакетом проверяется самим установщиком: после SHA256 tar он читает manifest из этого же архива с пределом 2 МиБ, сравнивает его байты с распаковкой, затем проверяет весь объявленный состав и source. Подменённые после распаковки файлы вместе с новым согласованным manifest больше не проходят. Добавлен такой отрицательный тест; всего десять проверок PASS.
