По последнему уточнению владельца сервер не выводит предполагаемый тип параметра из текста ошибки и не исправляет значения. В R4 удалён предыдущий expected_type-парсер; планировщику возвращаются исходный код и отклонённая попытка. Это изменение не откатывать при миграции шаблонов.

Документ нового ответа: `docs/alisa/architecture/ANSWER_MODEL_CONTRACT_20261109.md` в указанном source commit. Итоговая модель получает исходный вопрос, разрешённые данные API и непустую дополнительную инструкцию администратора. Выход — обычный текст без обязательных JSON/DSL/facts. Промпты и пользовательский вопрос не являются частью шаблона данных.

## Фактические обработчики

1. `local_gateway.Handler`/`dialogue`/`Engine.submit`: доверенный вход, исходный вопрос, владелец,магазин,беседа,request_id. Отдельный IPC `read_method` существует, `execute_template` или batch-команда спискаsteps не найдены.
2. `Engine._submit_standard`: пока сохраняет старые ускоренные пути dataset/table/semantics и подбор по речевым фразам. Нельзя объявлять всю цепочку model-first. Если однозначный план уже есть, лишняя модель для выбора не вызывается.
3. `query_program`/`program_providers`/`scalar_runtime`: старые типизированные расчётные планы, группировка запросов к источникам, source mapping и отчётные состояния.
4. `dataset_pipeline`/`matrix_sources`: табличные планы, зависимости стадий, штатная пагинация, декодирование и соединения. `dataset_pipeline.validate_catalog` сейчас требует полеphrases.
5. `universal_reads`: общий сбор через зарегистрированные read-операции; действияdiscover/read/data_ready. При сложном запросе, не покрытом типизированным словарём, переход сюда возможен в том же задании. Зависимые параметры уже поддержаны черезparams_expr.
6. `read_surface.build`/`read_contracts`/исходные request builders: alias→разрешённые метод/URL/контракт, проверка фактическихparams. Произвольный URL и ключ от модели не принимаются.
7. `Worker._call`/`HTTPTransport.prepare,execute`/`shared_http`: единственная сеть, штатные токены, очередь,права,ledger; не HTTP-код внутри шаблонов.
8. `request_recovery`/`model_recovery`/`provider_failure`/`provider_access_result`: технические повторы, обратная связь параметров и безопасный отрицательныйmodel_result. Подписка/403 не жёстко вшиваются в шаблон.
9. `model_answer`: исходный вопрос+API-данные+настройки ответа→обычный текст; повтор генерации не повторяет успешно завершённые API-чтения. Station доставляет ответ отдельно.

## Требование к новому шаблону

**Шаблон описывает, какие зарегистрированные команды нужно выполнить и откуда взять параметры.** Он не распознаёт голос и не пишет аналитический ответ.

Внутри: устойчивыйid/version,площадка,краткое назначение данных,шаги с alias операций/вложенных шаблонов,постоянные параметры,ссылки на входные значения и результаты предыдущих шагов.

Снаружи: original_question,речевыеphrases/синонимы/regex,пользователь/магазин/ключи,текущее время,админскиеprompts,текст/TTSответа,тарифныйresolver,повторы,HTTP-клиент.

`purpose` — описание назначения для выбора моделью/матрицей, не пример реплики пользователя и не жёсткое правило совпадения текста.

Не дублировать контракт каждого API:operation ссылается на имеющийся реестр. Не копироватьURL,Authorization,схемутиповилиподписку во все85записей. Методы Ozon и WB могут требовать разные шаги, поэтому platform-specific recipes не заменяются выдуманной общей схемой ответа.

## Предлагаемый единый формат хранения

Это **оболочка для миграции**, не текущий IPC payload. `$path` — уже существующее безопасное выражение. Контекстinput и разворачиваниеsteps/template нужно добавить одним общим адаптером; такой адаптер пока не установлен.

### Простой рецепт

```json
{
  "id": "ozon.orders_data",
  "version": 1,
  "platform": "ozon",
  "purpose": "Количество и сумма заказов за период",
  "steps": [
    {
      "id": "orders",
      "operation": "analytics_data",
      "params": {
        "date_from": {"$path": ["input", "date_from"]},
        "date_to": {"$path": ["input", "date_to"]},
        "metrics": ["ordered_units", "revenue"],
        "dimension": ["day"],
        "filters": [],
        "limit": 1000,
        "offset": 0
      }
    }
  ]
}
```

date_from/date_to определяются из контекста вопроса до исполнения рецепта. Это не требование к владельцу вручную заполнять даты себестоимости. metrics/dimension/constants выбирают API-данные, а не формат итогового текста.

После подстановки сервер добавляет разрешённыйstore_id и выдаёт существующему исполнителю:

```json
{
  "action": "read",
  "store_id": "<проверенный сервером магазин>",
  "operation": "analytics_data",
  "params": {
    "date_from": "2026-11-08",
    "date_to": "2026-11-08",
    "metrics": ["ordered_units", "revenue"],
    "dimension": ["day"],
    "filters": [],
    "limit": 1000,
    "offset": 0
  }
}
```

Это именно формат универсального действия; полноценный локальныйIPC `read_method` дополнительно требуетtenant/request_id/conversation_id. Не отправлять действие `read` напрямую как полный IPC-запрос и не создавать отдельное пользовательское задание на каждый шаг составного рецепта.

### Составной рецепт: данные для ДРР

```json
{
  "id": "ozon.drr_data",
  "version": 1,
  "platform": "ozon",
  "purpose": "Заказы и рекламный расход за одинаковый период",
  "steps": [
    {"id": "orders", "template": "ozon.orders_data"},
    {
      "id": "advertising",
      "operation": "performance_daily_csv",
      "params": {
        "dateFrom": {"$path": ["input", "date_from"]},
        "dateTo": {"$path": ["input", "date_to"]}
      }
    }
  ]
}
```

Вложенный рецепт наследует тот же проверенныйinput и магазин. Он разворачивается в обычныеread-команды в одном задании. Рекламный источник использует Performance-подключение, которое выбирает транспорт, не шаблон и не модель.

Этот рецепт собирает основы ответа, а не требует от модели вернуть DSL `percent` или текст заранее заданного вида. Старые проверенные расчётные операции остаются отдельным вычислительным компонентом, не превращаются в обязательную схему итогового ответа. Какой расчёт нужен, следует из оригинального вопроса; данные источников не теряют названий/периодов/валют.

## Зависимые шаги

Составной рецепт может содержать независимые чтения либо зависимость «список→детали». В текущем универсальном пути уже существует:

```json
{
  "action": "read",
  "store_id": "<тот же проверенный магазин>",
  "operation": "ozon_action_products",
  "params_expr": {
    "action_id": {"$path": ["calls", 0, "data", "result", 0, "id"]},
    "limit": 100
  }
}
```

Пример — одна выбранная акция из уже полученного списка, **не все акции**. У будущего каталога зависимость лучше хранить поименованным результатом шага, а адаптер связывает его с конкретным сохранённым вызовом. Не хардкодить произвольныеcalls[0]в сложных вложенных рецептах, где индекс может измениться.

Для всех объектов нужны подтверждённые правила обхода и пагинации. В старом SourceMatrix автоматическая пагинация/workflow есть; в универсальном сборе последующие страницы сейчас запрашивает планировщик. Поэтому нельзя объявить общий автосбор всех страниц уже решённым флагомcomplete:true. При миграции цикл исполнения должен опираться на конкретные cursor/has_next/total и условия законченности источника. Пустые/неполные данные и отказ одного обязательного шага не превращаются в полный результат.

Асинхронный источник: создание отчёта→проверка статуса→получениефайла — транспортныйworkflow, не отдельная речевая функция. Зависимости такогоworkflow не должны смешиваться с голосовым вопросом.

## Что возвращается модели

Успех: сохранённые разрешённые ответы с различимостьюoperation/store/params/периода и полноты. Исходный вопрос добавляется отдельно вmodel_answer. Нельзя заменить всё заранее написанной фразой сервера или незаметно передать образец15строк как полный набор.

Нерешаемый отказ: тот же отрицательныйmodel_result с конкретным подтверждённымPremium-требованием,HTTP/provider-code,data:null. Временный429/5xx/истёкший предусмотренный временныйтокен сначала обрабатывает существующее ядро. Никаких отдельных покупок/таймеров/retry-циклов в шаблонах.
