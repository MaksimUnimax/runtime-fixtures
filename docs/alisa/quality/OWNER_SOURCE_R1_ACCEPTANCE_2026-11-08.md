## Выполненная реализация

В отдельной копии платформенного source добавлено приложение owner_data: сохранение, чтение и отзыв текущей версии параметров, миграция, внутренний endpoint и DjangoOwnerSource. Использованы существующие session/membership/customer-security, ownership магазина, AccessLedger/grants и nonsecret CredentialRevision. Новая авторизация, MFA, расшифровка ключей или второй аналитический Worker не создавались.

Два хранилища имеют разное назначение: OwnerDataset содержит текущие утверждённые значения одного магазина; OwnerCommand — ограниченные metadata-only квитанции идемпотентности без денежных строк. Отзыв очищает текущие факты. Явное подтверждение требует literal confirmed=true и ожидаемой ревизии. Повтор одной команды не создаёт второго эффекта; конкурентные разные изменения одного исходного revision не перезаписывают друг друга.

Producer выдаёт существующий S03 snapshot/owner_bundle. Проверка актуальности перечитывает PostgreSQL: владелец, магазин, доступ, security/store/credential revisions, одобренные значения, их версия и среда должны совпадать. Snapshot/hash/issuer сами по себе не дают разрешения. Session token не сериализуется в граф. Отзыв после READY, смена данных или отключение credential не выдают прежние суммы.

C-UE01 требует независимо квалифицированные SELLER и PERFORMANCE. AUTHENTICATED_UNLINKED не трактуется как подтверждение того же кабинета. Попытка понизить required-credential policy до SELLER-only не разрешает этот граф. VaultSecret не расшифровывается и provider HTTP в producer отсутствует.

Сопоставление данного producer ограничено точным числовым SKU→sku:<SKU> одного магазина. Это указание владельца, к какому товару относится стоимость; существование SKU дополнительно проверяет прежний source-normalizer по данным заказов/товаров. Cross-market aliases не объявлены реализованными.

Денежная семантика прежняя: разные unit costs и интервалы действия; налог/собственные расходы за точный период; десятичные строки; явный ноль, пропуск и разрешённое исключение различны. Нет r9/default250, автоматического определения налоговой ставки или распределения месячного расхода на день.

Новый внутренний endpoint использует прежний service-authenticated POST boundary. Включение feature flag по умолчанию запрещено. Browser BFF/Origin/CSRF и межсервисное размещение source/verifier должны подключаться штатно, а не публикацией внутреннего endpoint наружу.

## Сохранённые неуспешные этапы и исправления

Первоначальная попытка миграции на SQLite остановилась на требовании PostgreSQL, затем disposable PostgreSQL потребовал штатную runtime-role. Требования не отключались: тестовое окружение создало роль и сохранило исходные ограничения прав.

Первый интеграционный набор обнаружил несогласованные даты искусственных API-ответов и неполную synthetic setting RELEASE. Исправлены только часы/настройки фикстуры, не денежные ожидания и не проверки периода.

Следующий набор выявил реальный дефект стыка: после отзыва source.Rejected не переводился в runtime.Rejected. Финансовые суммы не выдавались, но наружу выходило внутреннее исключение. Преобразование исправлено в source.scope_for; добавлены отрицательные проверки. Runtime.auth не ослаблен.

После импортирования общего HTTP с read1 четыре прежние заглушки read были адаптированы к ограниченному потоковому ответу, две по точной upstream-версии. Денежные assertions, проверки полноты и запрет внешних вызовов сохранены. Все промежуточные FAIL и итоговые PASS оставлены в evidence; принудительного PASS нет.
