## 2. Контракт `model_result`

Нормализованный отрицательный ответ сохраняется целиком, а не теряется при превращении HTTP-ошибки в состояние задания:

```json
{
  "schema": "alice-provider-access-result/v1",
  "ok": false,
  "provider": "ozon",
  "operation": "marketplace_search_queries_text",
  "status": "SUBSCRIPTION_REQUIRED",
  "http_status": 403,
  "provider_code": 7,
  "required_subscriptions": [
    {"id": "PREMIUM_PRO", "name": "Premium Pro"}
  ],
  "subscription_relation": "SINGLE",
  "requirement_source": "provider_response",
  "data": null,
  "retryable": false,
  "message": "Для этого запроса Ozon требует подписку «Premium Pro». Данные по запросу не получены."
}
```

Это сокращённый вид реально проверенного объекта. Полная версия также содержит digest полученного ответа, признак конфликта с документацией и безопасную инструкцию модели: объяснить требование, не повторять отвергнутый запрос, не менять ключи, не выдавать неполученные данные за ноль и не придумывать название подписки.

Обычный отказ доступа даёт `ACCESS_DENIED` с пустым списком подписок. Недостаточные права метода отделены от тарифного ограничения. Упоминание действующей подписки и фраза «подписка не требуется» не превращаются в просьбу купить. Неизвестные будущие формулировки не обещаны автоматически распознанными: отсутствие подтверждения остаётся отсутствием подтверждения.

## 3. Передача через действующую архитектуру

Параллельная разработка изменила формирование итогового ответа: обычная модель получает исходный вопрос, данные API и настраиваемые владельцем промпты. Изолированный прежний кандидат с дополнительным вызовом модели только для подтверждения JSON-ошибки **не устанавливался**. Его роль перенесена в существующий основной этап ответа.

Общая цепочка теперь:

```
ответ Ozon → классификатор фактического отказа
→ полный отрицательный model_result
→ общий результат шаблона/инструмента
→ текущая итоговая модель
→ текст/TTS и серверный интерфейс Station
```

`provider_failure.detail` больше не отрезает источник требования, code7, признак отсутствия данных, hash и инструкцию. В обычном модельном пути объект присутствует в `_answer_api_data` и `_answer_pending`, затем в сохранённом результате. Модель получает полный объект, а не один строковый код ошибки.

Для точного `read_method` без итоговой модели задание остаётся **FAILED**, и вызывающий компонент получает `model_result`. Для обычного вопроса задание получает **READY только после подготовки объяснения моделью**, при этом `error=HTTP_403_OZON_PREMIUM_PRO_REQUIRED`, `ok=false` и `data=null` сохраняются. READY здесь означает готовность объяснения, **не успешное получение поисковых данных**.

Повтор генерации ответа при временной ошибке модели использует тот же сохранённый объект, не повторяет запрещённое чтение Ozon. Другая беседа, отзыв прав, истёкший результат и чужой магазин не получают объяснение/объект. Предыдущие данные источников не пересылаются модели после отказа доступа. Denied ledger не очищается.

## 4. Первый неуспешный сквозной прогон и дополнительное исправление

После первоначальной установки новый отрицательный ответ уже работал в локальных сценариях. Но первый живой вопрос о поисковых запросах завершился **READ_NO_PROGRESS**:5вызовов модели,0вызовов Ozon. Этот прогон не засчитан как успех.

Причина установлена по точному исходному валидатору Octoport: `limit` и `offset` у поискового endpoint должны быть **числовыми строками**, а модель передавала числа. JS-контракт возвращал `params.limit`, но Python оставлял только `INVALID_OPERATION_PARAMS`; полезная причина терялась до модели.

Исправлена общая граница валидации: разрешённое имя поля и ожидаемый JSON-тип передаются в существующую обратную связь планировщика. Сырые значения, произвольные сообщения и инструкции провайдера не передаются. Оригинальная строгая схема, допустимые значения и ограничения метода не ослаблены; значения не приводятся к другому смыслу автоматически. Не добавлен частный обработчик под поисковый вопрос.

Шесть отдельных тестов подтвердили: корректное сообщение о string, неизменность уже правильных параметров, запрет неизвестных полей, отсутствие личных значений в подсказке, отказ от произвольного типа и ремонт в том же задании с единственным HTTP к площадке.

В исходном receipt первого прогонa скрипт ошибочно записывал постоянный boolean `actual_provider_and_model_used=true`. Массив calls и счётчики при этом правильно показывали0API. Оригинал сохранён, отдельная поправка `FIRST_LIVE_STATUS_CORRECTION.json` явно фиксирует **false**. В окончательном runner этот флаг вычисляется из фактических вызовов.
