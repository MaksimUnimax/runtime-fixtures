Новые задания используют `catalog_prefix_v2`. Общие описания 85 шаблонов и входная схема стоят перед индивидуальным вопросом, датой, магазинами и доступностью. Кэшируется обработка повторяемого входа провайдером, а не разрешение на магазин или итоговая аналитика.

## 2. Активная настройка и поведение

Единственное дополнение рабочего config:

```json
{
  "selector_prompt": {
    "layout": "catalog_prefix_v2",
    "isolation": "tenant_v1"
  }
}
```

`tenant_v1` передаёт стабильный непрозрачный user_id, сформированный из серверной авторизованной области клиента. Он находится вне messages. Это изоляция кэша выбора; политика user_id итогового model_answer не менялась. Одинаковый user_id использовался внутри каждой пары старого/нового варианта A/B. Текущие права магазина по-прежнему проверяются сервером до исполнения и выдачи.

Новая policy записывается в draft при приёме задания. Уже подготовленный payload сохраняется с hash и повторяется побайтово при предусмотренном техническом retry. Смена default не переписывает принятые задания. Старые задания без policy интерпретируются как legacy_v1.

Поддержка двух layout внутри одной сборки НЕ является поддержкой одновременно работающих разных версий каталога. Для смены самого runtime/catalogue по-прежнему нужна безопасная граница и согласованные RuntimePort-версии.

Включение выполнено в два шага: запуск новой сборки с прежней отсутствующей policy, то есть legacy-совместимым default; проверка готовности и версий; затем атомарное добавление policy для новых заданий без второго restart. Возврат возможен заменой только layout на legacy_v1 при сохранении tenant_v1, без отката каталога и без повторного исполнения принятых задач.

## 6. Что получает тестер и учёт

Существующие семидневные calls-квитанции дополнены `model_context`:stage,layout,requestedmodel,хешselector-view,prefix,инструкционного профиля и точногоpayload. В messages эти хеши не вставляются; тексты запросов,tenant ID и секреты в метаданные не добавляются.

`model_usage.job_attempts()` возвращает отдельно context и receipt. Для отчёта случая использовать:

- context.stage и context.prompt_layout;
- receipt.usage.prompt_tokens,prompt_cache_hit_tokens,prompt_cache_miss_tokens,completion_tokens;
- все реальные попытки, а не только успешную;
- рассчитанную стоимость по ставкам нужной модели/времени, с отдельной отметкой неизвестной квитанции.

`model_usage.summary()` дополнен cache_by_stage; `stage_summary(..., rates_by_model=...)` считает weighted-hit=sum(hit)/sum(prompt), полнотуusage и стоимость по переданным ставкам. Автоматическое получение/вечная фиксация цен не добавлены. Готового нового frontend-экрана этой поставкой не создавалось: доступны backend-метрики и данные отчётов.

Колонка nullable: старые вызовы без контекста остаются unknown, их этап не восстанавливается догадкой. Строки имеют прежний срок604800секунд. Архив TEMPLATE_NOT_FOUND и пользовательские48-часовые отчёты не изменены.
