# Колонка: запрос Ozon и ответ после 429 — 8 ноября 2026

## Что увидели на установленной системе

Запрос колонки `ea2cb8312b1f40e2828af2c8e51c2297` запросил `analytics_data`, показатель `ordered_units` за 08.11.2026. Планировщик DeepSeek ответил успешно; Ozon на чтение дал три HTTP 429. Старая версия делала два повтора через 90 и 180 секунд, затем ставила `FAILED/HTTP_429_RETRY_EXHAUSTED`. Служба колонки после трёх сообщений ожидания останавливалась на ошибке, а также имела отдельный предел ожидания 900 секунд. Поэтому прозвучало ожидание и затем вернулась обычная Алиса без результата. Точные данные Ozon на момент проверки не получены.

## Исправлено и установлено

- Runtime `/opt/alice-market/releases/alisa-runtime-429-wait-r2-20261108` основан на **новой** версии `alisa-runtime-no-app-quotas-r1-20261108`, в которой `max_model_steps` и `max_provider_calls` уже равны `null`, а модельная суточная квота и пауза отсутствуют. На HTTP 429 он сохраняет исходный job ID и делает повтор с растущим интервалом (90, 180, 360, 720, до 900 секунд; если Ozon прислал Retry-After, соблюдается и он), не обрывая запрос после третьей попытки. Это ожидание отказа внешнего API, не внутренняя квота DeepSeek.
- Служба колонки `/opt/alisa-station/releases/station-auto-r3` продолжает отслеживание до 24 часов, максимум три раза озвучивает ожидание и затем молча следит за готовностью. Команда «результат» во время ожидания теперь сообщает текущий статус, сохраняя автоматическую доставку. Готовый ответ запускается через сценарий умного дома; факт звука на физической колонке требует проверки владельца.
- Тот же job ID возвращён в `QUEUED` с сохранённым планом и привязкой колонки. После установки gateway вернул `QUEUED`, а служба колонки показала `waiting`, `connected=true`, `uncertain=false`.
- При установке обнаружено совместное изменение конфигурации другого исполнителя: прежний runtime отвергал новую политику `null` как `SOURCE_ACCESS`. Выпуск r2 собран поверх `no-app-quotas`; gateway повторно подтвердил доступ к конкретному заданию.

## Проверки

- 103 теста runtime: PASS.
- Изолированная проверка службы колонки: после прежней границы 15 минут ожидание не обрывается, READY запускает сценарий; ручной запрос статуса не отключает автоответ: PASS.
- Оба systemd-сервиса активны. Реальный API Ozon на момент отчёта ещё возвращал 429; готовый голосовой ответ **не подтверждён**.

## Проверка владельца

1. Открыть [админку](https://alisa-admin.octoport.ru/admin) и [кабинет колонки](https://alisa.octoport.ru/app/station/).
2. Дождаться завершения запроса на колонке: после трёх реплик ожидания она должна молчать до появления данных, затем сама произнести результат. Новую голосовую команду для старого запроса произносить не нужно.
3. Если нужен статус во время ожидания, спросить у навыка «результат»; эта проверка больше не отменяет будущий автоответ.
4. Сообщить время и точную произнесённую фразу, если физическая колонка не разбудилась при READY.

## Следующий шаг исполнителя

Наблюдать этот же job ID до первого удачного ответа Ozon, проверить `READY →` сценарий → обратный вызов навыка и реальный звук на колонке; если 429 сохраняется, найти разрешённый точный источник `ordered_units` без подмены метрики. Затем добавить честную оценку времени ожидания из фактического состояния провайдера.
