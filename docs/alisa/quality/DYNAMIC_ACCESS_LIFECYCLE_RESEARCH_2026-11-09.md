# Постоянная проверка платности и доступности: исследование и обязательный контракт

9 ноября 2026. Статус: **источники проверены, дефекты воспроизведены, архитектурный контракт зафиксирован; новая сквозная автоматическая цепочка ещё НЕ установлена**.

## 1. Исправление постановки

Разовая таблица Premium/Plus/Pro, даже с датой и тестами, не выполняет требование владельца: механизм должен сопровождать проект весь срок жизни. Предыдущая поставка `alisa-ozon-subscription-access-r1-20261109` добавила статические метки и точные объяснения отказов, но не связала постоянное обновление правил, действующую подписку аккаунта, права ключа и пересмотр уже сохранённых отказов. Нельзя объявлять эту поставку завершённым динамическим entitlement-механизмом.

Продолжать ручное закрытие отдельных UNKNOWN без исправления жизненного цикла — не основной путь. Названия тарифов, альтернативные подписки, условия параметров и тип подключения должны быть изменяемыми данными, а не ветками кода под текущие Premium-названия.

### Бессрочные отказы текущего исполнителя

Текущий `Repository.deny(source,revision)` сохраняет только пару source/access_revision; `denied()` проверяет её наличие. В записи отсутствуют причина, срок действия и версия подписки. Если тариф изменится без смены access_revision, отказ может продолжить запрещать запрос. Исправление текста ошибки в предыдущем проходе это не устраняет.

Нельзя решать это безусловным удалением denied или подменой ключа. Требуется разделить security-revocation и временное/подписочное наблюдение, с отдельными основаниями пересмотра.

## 3. Надёжная модель: два разных вопроса вместо is_paid

Механизм обязан отдельно возвращать:

1. **Что требуется для конкретного запроса?** Базовый доступ, определённые продукты/возможности, OR/AND сочетания, платный параметр/период/поле, исключение по типу приложения, либо неизвестное правило.
2. **Разрешён ли этот запрос этому подключению сейчас?** Учитываются владелец, ключ/роль, срок ключа, подписка/дополнения, источник данных, тип авторизации, актуальность знаний и последний конкретный ответ провайдера.

Успешный HTTP200 у Premium-пользователя не доказывает, что метод бесплатен. Generic403 не доказывает платность. SellerInfo не заменяет roles; roles не заменяет тарифные требования; документация не доказывает купленный тариф; тип приложения нельзя угадывать по bearer/API-key или названию продукта.

Проверенного универсального официального endpoint `isPaid(method,params,account)` в исследованных источниках не найдено. Это не утверждение о принципиальной невозможности появления такого endpoint. Пока основание — композиция проверенных источников и строго ограниченные выводы.

## 4. Один AccessResolver в существующем исполнителе

Вход: нормализованный фактический запрос после existing read-контракта, а не свободная фраза модели:

```
provider + method/version + actual semantic params
+ tenant/store + credential/access revision
+ verified authentication/application type
```

Выход содержит раздельно `requirement`, `account_evidence`, `key_permission`, `decision`, `reason`, `source_revision`, `observed_at`, `valid_until`, `response_scope`. Решение не является разрешением обойти текущую авторизацию или write-запрет.

Основные состояния: подтверждено для данного запроса; ограниченный базовый ответ; подтверждённая нехватка подписки; нехватка прав ключа; истёкший/отозванный ключ; неподтверждённое/устаревшее правило; конфликт источников; недоступность конкретного ресурса; временная ошибка площадки. Это не один boolean.

Обязательная интеграция в **общую границу перед HTTP**: готовые шаблоны, типизированные расчёты, точные read_method и универсальный планировщик должны проходить одинаковую проверку. Метки только в discovery универсального планировщика недостаточны.

## 5. Два обновляемых потока доказательств

### A. Требования площадки — общие для всех магазинов

Использовать существующий Swagger-watch, без второго независимого таймера. Официальный документ, request/response schema, descriptions и датированные изменения сохраняются с hash, временем получения, датой вступления в силу, статусом свежести и точным method/path.

Извлечение отделено от публикации. Структурированные подтверждённые правила можно публиковать после валидации. Свободный новый текст или нераспознанный продукт создаёт candidate/UNKNOWN, а не новую «бесплатную» запись. Модель может предлагать интерпретацию для ревью, но не становится источником истины о правах.

Правило применимо только к совместимому отпечатку описания/схемы метода. Новый метод, изменённый параметр, новый продукт или удаление старой фразы не должны наследовать разрешение автоматически. Исключения тоже имеют источник, срок, тип подключения и проверку устаревания, а не вечный hardcode.

Публикация набора правил атомарна и версионирована; откат доступен. Неактивированный кандидат не влияет на выполнение. Повторное получение тех же bytes не продлевает срок доверия к заведомо старой публикации. Дата fetch и дата актуальности правила различаются.

Если Ozon не отдаёт схему: существующий last-known-good сохраняется с пометкой STALE; отсутствующий файл не заменяется `{}` и не делает все методы бесплатными. Для затронутых неизвестных правил — наблюдение провайдера/обработка неопределённости и внутренняя задача обновления источника. Официальный файл можно принять через существующий карантинный handoff с проверкой происхождения. **Требовать от владельца вручную исправлять тарифы каждого нового метода не является штатным сценарием.**

### B. Текущее подключение магазина

`/v1/seller/info` даёт подтверждённые поля подписки; `/v1/roles` — методы ключа и срок действия. Собирать это при подключении/изменении ключа, по сроку свежести и после противоречащего ответа провайдера. Не делать эти два вызова заново на каждый пользовательский вопрос; использовать общий cache и single-flight для одновременных запросов.

Срок свежести — характеристика доказательства, не лимит количества запросов или месячный бюджет. Интервалы конфигурируются и не вводят usage-квот. Инвалидация включает смену key/access revision, профиля подписки, type приложения, явный отказ, истечение ключа, ручное обновление подключения и новую версию применимого правила.

Молчание seller/info об addon не означает addon отсутствует. Новая неизвестная строка тарифа сохраняется как UNKNOWN вместе с исходным кодом в защищённом контексте, а не принудительно преобразуется в «без подписки».

## 6. Перед запросом и после ответа

До HTTP проверяется текущая авторизация и read-only; затем конкретные параметры сопоставляются с доступными доказательствами. При подтверждённом актуальном запрете возвращается точная причина без бесполезных повторов. При неполном знании допустимое read-действие может выполнить сам провайдер как авторитетную проверку: **не обход текущего запрета безопасности**, а отсутствие локального выдуманного тарифного запрета.

Используется сам полезный запрос, не отдельный массовый обход сотен endpoint. Не вызываются методы записи для диагностики. Повтор после обновления доказательств допустим только по существующей политике повторно-безопасного чтения; при неизменившемся основании повторный403 не порождает цикл.

После HTTP200 подтверждается доступность только этого feature-набора, диапазона/ресурса и подключения на момент наблюдения. Платность вообще из этого не выводится. Отдельно проверяется полнота обязательных полей: HTTP200 с урезанным ответом не становится полным финансовым отчётом.

После401/403 различаются expiration/revocation, роль ключа, явное требование подписки, доступ конкретного файла/объекта и неизвестная причина. Подписочный отказ расширенной метрики нельзя превращать в запрет всех бесплатных параметров того же endpoint. Наблюдение связано с нормализованным feature-signature, а ресурсный отказ — с конкретным ресурсом.

Cache отказа имеет observed_at, cause, affected_features, connection/access revision, account-evidence revision, rule revision и valid_until. Новая подтверждённая подписка делает старое подписочное наблюдение неприменимым, но не снимает отзыв ключа/владельца. Старые записи без причины не стираются массово: переоценка с явным состоянием legacy-unknown и новой проверкой. Это часть обязательной миграции, не ручная очистка SQL.

## 7. Что значит «на весь срок жизни проекта»

Это не обещание неизменности Ozon и не автоматическая догадка по любому новому тексту. Это контролируемый жизненный цикл:

- новый тариф/метод не ломает исполнение и не получает бесплатность по умолчанию;
- изменённые условия замечаются и имеют прозрачный срок актуальности;
- смена подписки или ключа пересматривает только соответствующие наблюдения;
- сбой документации не превращается в ложное разрешение или вечную остановку всех запросов;
- у каждого ответа «нужен тариф» есть конкретное проверяемое основание;
- постоянная механика не требует нового обработчика/релиза для простой замены данных о тарифе; новая семантика может потребовать ревью, и это видно, а не скрыто.

Админке нужны время последнего успешного обновления источника, версия правил, число устаревших/неразобранных изменений, возраст account evidence и конкретный blocker. Конечному клиенту — понятная причина и только реально необходимое действие, не обязательная ручная обработка наших UNKNOWN.

## 8. Приёмка, без которой нельзя говорить «готово»

1. Новый endpoint и новый платный продукт: UNKNOWN, не ALL_ACCOUNTS; изменение формулировки не означает бесплатность.
2. Premium появился/истёк без изменения ключа: обновление profile revision меняет решение, security revocation не снимается.
3. Ключ поменялся/истёк: кэш старого ключа не применяется, другой магазин изолирован.
4. Бесплатная и платная метрика одного endpoint: разные решения; один отказ не блокирует другой запрос.
5. Старый период и новый период: правила пересчитываются, диапазон не урезается незаметно.
6. HTTP200 на платном аккаунте не делает метод общедоступным; missing required fields не превращаются в нули.
7. Generic403 не порождает просьбу купить; файловый403 не блокирует Seller API целиком.
8. Документация307/403/timeout/невалидная/неполная: прежняя версия не повреждается, видны возраст и blocker; отсутствие документа не равнозначно отсутствию правил.
9. Одновременные одинаковые запросы используют общий refresh, без дополнительных платных LLM-вызовов и probe-storm.
10. Правило опубликовано/откачено во время выполнения: job фиксирует применённую ревизию, текущие права повторно проверяются перед выдачей.
11. Public OAuth, private OAuth и API key не смешиваются; временное исключение не становится вечным.
12. Обновление проходит через тот же executor/ledger/retention и сохраняет автоматическую Station-выдачу, учёт LLM и отсутствие внутренних квот.

## 9. Фактический статус этого исследования

Выполнено: изучены официальные источники, живые seller/info и roles, донорский compiler/refresh, существующий watcher; воспроизведены пять случаев парсера; проверена модель сохранения denial. Нового production runtime/config/timer не ставилось. Подписки/ключи/настройки пользователя не изменялись. Два служебных read-запроса записаны штатным ledger; результаты без идентификаторов и сырого содержимого сохранены в `/dev/shm/alisa-access-lifecycle-audit-20261109/` и в этом документе.

**Нельзя выдавать прошлые1620тестов статической разметки за приёмку указанного жизненного цикла.** Следующий кодовый блок — интеграция evidence cache + общего resolver + безопасного rule publication с существующим watcher, затем миграция причин/сроков отказов. Просто ещё раз заполнить31UNKNOWN недостаточно.
