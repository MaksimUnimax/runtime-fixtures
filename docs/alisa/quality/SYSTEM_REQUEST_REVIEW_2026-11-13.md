## Что организовано правильно

Модель выбирает зарегистрированные шаблоны. Сервер выполняет их обращения к API, собирает страницы и составные зависимости. Затем исходный вопрос и полученные данные получает итоговая модель. Для большого документа модель читает файл и выполняет написанный ею расчёт в отдельном окружении. Окончательный текст остаётся ответом модели; доставка не вычисляет финансовые показатели.

Сохранены единая очередь и единый журнал фактических отправок. Внутренние обращения Harness проходят существующий `Worker._call`; промах кэша не вызывает дополнительную модель. Повтор сообщения и команды доставки не создают новый аналитический запрос. Доступ проверяется перед отправкой и выдачей. Ключи маркетплейсов и DeepSeek не передаются программному исполнителю.

Файловая изоляция и ограничение ресурсов необходимы: входной файл доступен только для чтения, рабочая папка ограничена tmpfs, внешняя сеть выделенного UID закрыта. Нативная проверка подтвердила невозможность записи во вход, отсутствие каталога реальных ключей и ограниченность рабочего диска. После завершения/отмены файлы удаляются; аварийные неактивные папки проверяет отдельный таймер. Это защита сервера, а не лимит числа платных вызовов пользователя.

Ошибки API в шаблонном пути проверены целиком: полученные 400/422/обычный 403 доходят до итоговой модели как ошибка; 429 повторяется до передачи итоговых данных. Отказ не подменяется нулём. Распознавание требования Premium опирается на ответ Ozon, а не на догадку по каталогу; соответствующие проверки входят в полную регрессию.

Для полной квитанции DeepSeek подсчёт корректен: берётся последняя `message_delta.usage`; вход равен cache miss + cache hit, выход не складывается с reasoning повторно. Это соответствует [официальной документации DeepSeek](https://api-docs.deepseek.com/guides/anthropic_api/). Неполная квитанция обозначается неизвестной, а не бесплатной.

## Приоритетные замечания

### R1 — P1: один длинный расчёт блокирует обработку остальных запросов

**Доказательство кодом:** `runtime.py:96–117` запускает один рабочий поток. `model_answer.py:121–122` синхронно вызывает `model_program.run`. Внутренний цикл `model_program.py:43–62` держит этот поток до окончания всей сессии, включая ожидание 429/503. Дополнительно исполнитель сериализован глобальным lock и одним портом.

**Последствие:** новые вопросы принимаются, но их этапы выбора/API не выполняются, пока долгий программный вопрос не завершится. Справедливая очередь действует между шагами; здесь один шаг стал всей многоходовой сессией. Heartbeat продлевает аренду, но не доказывает, что расчёт продвигается.

**Исправление:** программную сессию обслуживать отдельно от диспетчера обычной очереди. Сохранить один идентификатор задания и единый учёт; занятость тяжёлого исполнителя не должна блокировать лёгкие задания. Не запускать неограниченное количество процессов. Не добавлять произвольный лимит токенов как замену правильному планированию.

### R2 — P1: повтор отправляется после отключения исполнителя

**Воспроизведено:** подставной брокер передал `call` и закрыл Unix-соединение. Первый вызов получил отсрочку; после её окончания `model_program.run` выполнил второй вызов и только затем обнаружил, что ответ некому передавать. Проверка — `dead_peer_retry`.

**Причина:** цикл ожидания проверяет только строку задания и аренду. Состояние соединения с исполнителем перед новым `_call` не проверяется. Heartbeat тоже следит за базой, а не за жизнью брокера.

**Исправление:** потеря канала/завершение исполнителя должны отменять ожидающие отправки. Перед повтором нужны действующая сессия исполнителя и актуальное право задания. Уже отправленный запрос учитывать как отправленный; не обещать отмену расходов, уже возникших у провайдера.

### R3 — P1: результат уничтожается до подтверждённого сохранения

**Доказательство кодом:** `program_broker.py:103–110` читает ответ, удаляет рабочую папку, затем отправляет `complete`. Ядро сохраняет ответ позднее, в `model_answer.py:117–122`. Подтверждения записи от ядра нет.

**Последствие:** при аварии между этими действиями оплаченный результат теряется. `resume_safe=False` правильно предотвращает слепой платный перезапуск, но восстановить готовый ответ уже неоткуда. Это окно отказа установлено анализом последовательности; производственный процесс для его имитации не убивался.

**Исправление:** короткое долговечное хранение завершённого результата под идентификатором задания, затем запись в существующую очередь и подтверждение. Очищать результат после подтверждения; данные для вычисления можно удалить раньше. Повтор передачи готового результата должен быть идемпотентным и не обращаться к модели.

### R4 — P1: граница исполнителя разрешает незаявленные возможности провайдера

**Воспроизведено на подставном HTTP:** `model_program_wire.py:8–15` проверяет верхние поля, модель и streaming, но не разрешённый набор инструментов. Запрос с `tools=[{type: web_search_20250305, ...}]` дошёл до границы отправки. Подставная квитанция с `server_tool_use` была принята, а счётчики серверного инструмента отброшены. Проверка — `provider_tool`.

Штатный запуск сейчас предлагает локальный расчёт; реального веб-поиска этой системой в ревью не выполнялось. Воспроизведена недостаточная проверка границы, не факт эксплуатации или утечки. У программы доступен локальный транспортный токен в её папке, поэтому закрытие внешней сети само по себе эту границу не заменяет. Официальный API поддерживает [серверные инструменты и отдельные счётчики их использования](https://api-docs.deepseek.com/guides/anthropic_api/).

**Исправление:** фиксировать доступные операции по профилю исполнителя и проверять их на стороне ядра. Для задачи расчёта документа не разрешать незаявленные серверные поиск/загрузку. Это проверка полномочий инструмента, не классификация бизнес-показателей и не шаблон речевого ответа. Если дополнительные услуги когда-либо включатся намеренно, учитывать их отдельно от токенов.

### R5 — P2: обработчик сетевого исключения сам вызывает исключение

**Воспроизведено:** `model_program_wire.py:20` присваивает имя `http` объекту Request, а строка 31 использует `http.client.HTTPException`. При таймауте получается `AttributeError: 'Request' object has no attribute 'client'`. Внешний Worker превращает его в `UNEXPECTED_TRANSPORT_OUTCOME`; основная служба не падает, но причина сбоя теряется.

**Исправление:** переименовать локальную переменную. Добавить проверки точного кода и сохранённой квитанции для DNS/TLS/timeout/reset. Старый smoke-тест unknown принимал любой итоговый CallError, поэтому этот дефект проходил незамеченным.

### R6 — P2: потоковый ответ буферизуется целиком; при таймауте теряется полученный usage

**Воспроизведено:** локальный HTTP-сервер отправил полностью сформированную квитанцию `message_delta.usage`, затем оставил соединение открытым. Общий транспорт завершился по сроку ожидания без передачи накопленных байтов парсеру. Квитанция потеряна. Проверка `receipt_then_timeout` одновременно обнаружила R5.

В производстве действует общий срок **90 секунд на весь HTTP-обмен**. Наличие поступающих токенов его не продлевает. Настройка Harness `streamIdleTimeoutMs=180000` не исправляет это: Harness получает уже собранный ответ. `request_timeout_seconds=600` в установленном Python SDK также не является ограничителем всей сессии: после принятия запроса используется ожидание уведомлений. Это подтверждено установленным `api.py:188–196` и [документацией SDK](https://github.com/deepseek-ai/deepseek-harness/blob/master/python/sdk/README.md).

**Исправление:** отдельное чтение SSE с сохранением валидной квитанции по мере поступления. Различать отсутствие соединения, отсутствие прогресса и длительную успешную генерацию. При неполном ответе не выдавать его как полный и не перезапускать неизвестно оплаченный вызов вслепую. Не считать недополученную квитанцию нулевой стоимостью.

## Несогласованности в подсказках, ограничениях и расходах

**R7 — P2: `purpose` всё ещё передаётся итоговой модели.** В `template_runtime.py:209–214` вместе с `notes` прикладывается `purpose`. Сквозной пример `B08.finance_accrued` это подтвердил. Требуемое разделение нарушено: `purpose` нужно оставить выбору, `notes` — озвучиванию. Комментарии базовых зависимостей составного шаблона при этом правильно не наследуются.

**R8 — P2: расчётные инструкции не выделены и не доведены до итоговой модели.** В шаблонах формул есть `calculation_contract`, но в итоговый контекст из шаблона попадают только id/version/purpose/notes. В `drr_ordered` и `finance_storage_logistics_share` notes содержат общий текст о том, что формула не задаёт речевой ответ, а не сам порядок расчёта. Сервер уже знает выражение, но итоговая модель по этому пути снова получает исходные API-данные. Имеет смысл передавать проверенную формулу/инструкцию отдельным контекстом расчёта выбранного шаблона, сохранив `purpose` и `notes` раздельными. Новые финансовые правила в обработчик добавлять не нужно.

**R9 — P2: старый предел вывода на выборе шаблона остался.** `template_protocol.py:60` явно отправляет `max_tokens=6000`. При `finish_reason=length` текущий путь заканчивает запрос с `TEMPLATE_EXECUTION_FAILED` после единственного вызова выбора; это воспроизведено. В программном ответе подстановка max_tokens удалена, однако утверждение «во всей системе нет такого ограничения» было бы неверным. Нужно отдельно устранить этот оставшийся предел и определить восстановление незавершённого выбора без повторения API-запросов. Это не повод менять шаблоны.

**R10 — наблюдаемость экономики неполна.** Сам подсчёт токенов для полной квитанции верен. Однако основной административный путь вызывает `model_usage.summary()` без тарифов; групповые стоимости остаются `not_quoted`/null. Есть функция расчёта с явно переданными ставками, а стоимость в прежних приёмочных отчётах считалась отдельно. Для эксплуатации нужен автоматический итог на запрос: маршрут, время ожидания/расчёта, все отправки, полнота квитанций, датированные тариф и курс, известная стоимость и признак неполноты. Хранить эти компактные числа в существующем семидневном журнале; отдельный журнал полных документов не нужен.

## Что лишнее и что не стоит добавлять

1. **Упаковка данных на программном пути сейчас делается впустую.** `model_answer.step` сначала строит упакованное сообщение, затем `model_program.run` отбрасывает последнее сообщение и передаёт исходный документ. Пороги одинаковые — 10000 символов: новый короткий запрос не упаковывается, новый длинный расчёт не получает упакованный текст. Это лишние обходы и копии в памяти, без экономии токенов на этой ветке. Выбирать маршрут до построения сообщения; старую упаковку оставить только там, где она действительно используется, и для восстановления закреплённых старых заданий.
2. **85 systemd drop-in файлов для ядра — эксплуатационный долг.** Итоговый выбранный release сейчас правильный, но порядок многочисленных старых переопределений затрудняет следующую установку и откат. Свести рабочее описание службы к одному управляемому указателю версии, после отдельной сверки действующих прав и ограничений. Сам исполнитель и фиксированная версия SDK должны быть частью проверяемого комплекта поставки.
3. Не нужны ещё одна модель-проверяющий на каждый запрос, повтор ради прогрева кэша, жёсткие словари допустимых финансовых ответов или автоматический дорогой переход к чтению всего документа при любом отказе исполнителя.
4. Порог 10000 символов — установленное простое правило из ограниченной серии опытов. Он не доказывает экономию для любого вида документа. Не нужно повторять всё исследование сейчас; достаточно собирать реальную стоимость по маршрутам в штатной серии.

## Граница гарантии правильности чисел

Выполненная программа может завершиться успешно и всё равно неверно выбрать строки, перепутать дату события, повторно посчитать страницу или молча пропустить значения. Проверка «процесс завершился и есть текст» этого не обнаруживает. Предыдущие опыты с пропущенными строками нельзя объявить универсально закрытыми новой изоляцией. В этом ревью новая математическая ошибка на платной модели не воспроизводилась.

Практичная защита — ясные инструкции выбранного шаблона и контрольные сквозные примеры при его приёмке: непустой результат, подтверждённый ноль, отсутствующее поле, отрицательные суммы/возвраты, страницы и составные периоды. Правильность сверять с независимым результатом в тестах. Для самой модели передавать требование не скрывать пропуски/ошибки преобразования и использовать все нужные строки. Это подсказки для расчёта и проверка качества шаблона, а не новый серверный парсер пользовательского вопроса.
