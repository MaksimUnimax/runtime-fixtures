# ADR-002: сохраняемое уточнение запроса, инцидент 03.11.2026

Статус: диагноз подтверждён чтением действующих исходников; ниже план исправления, не утверждение о готовом развёртывании.

Владелец показал последовательность: «дай продажи ща вчеар» → уточнение смысла продаж → «заказанные» → ошибочное PERIOD_REQUIRED. Последний Request имеет ту же session_id и следующий message_id. Токен, raw Request и пользовательские ID не копировать в Git или тесты.

## Причина

Действует runtime build6 и web r3. Engine.submit вызывает parse ДО enqueue. METRIC_AMBIGUOUS вызывает Rejected; safe_submit преобразует это исключение в текст, не сохраняя исходный вопрос или слоты. Следующее «заказанные» попадает в parse как новый вопрос без периода. Кроме того, Unix IPC передаёт только tenant/command/request_id/body_hash, а conversation ID и номер сообщения до исполнителя не доходят. Web session_state содержит лишь counter. Кэш READY здесь не участвует. Предыдущее исправление источника финансовых данных не завершило сценарий уточнения.

## Решение

Серверное состояние незавершённого диалога в SQLite отдельно от кэша отчётов. Ключ tenant + HMAC идентификатора сессии навыка; номер сообщения проверяет порядок. Web после OAuth передаёт эти два поля по прежнему локальному сокету; ключи и access_token не передаются. Старые вызовы IPC без полей сохраняют прежний stateless-контракт и не получают чужой «последний вопрос».

Хранить исходную/нормализованную фразу, дату её приёма, разрешённую область, недостающий слот и срок действия. «Заказанные» заполняет только недостающий смысл в исходной фразе; период/площадки/фильтры остаются. Относительная дата закреплена по дню первоначального запроса, а не дню последующего ответа. Нераспознанную дату уточнять, а не молча выбирать. Для точной опечатки «ща вчеар» допускается узкая явно отображаемая нормализация в «за вчера»; SKU, бренды и числа не исправляются автоматически.

Переходы: вопрос → ожидание смысла → при необходимости ожидание периода → одна постановка задания. Отмена снимает именно pending-уточнение. Новый полный вопрос заменяет старое уточнение. Повтор сообщения не создаёт новое задание и не восстанавливает старый pending поверх нового. Права и состав магазинов повторно проверять. Истёкший, чужой или другой session context не использовать.

Запись квитанции сообщения, изменение pending и постановка задания должны быть в одной транзакции; после рестарта процесс восстанавливает состояние из SQLite. До разрешения всех условий ноль LLM/marketplace-вызовов.

## Приёмка

Полная цепочка из сообщения владельца, обычный вариант без опечатки, месяц вместо вчера, явная площадка/фильтр, два последовательных уточнения, новый вопрос, отмена, рестарт, истечение, смена суток, повтор/изменённый повтор/задержавшийся пакет, два пользователя/две сессии, отзыв доступа. Отдельно проверить настоящий webhook с временной OAuth-БД/синтетическими токенами и локальным gateway, затем разрешённое новое read-only задание на живом исполнителе. Не использовать присланный владельцем access_token.

Первичный составной вызов статуса RDC отклонён до исполнения общим сообщением безопасности; конкретный триггер не раскрыт. Проверены аргументы, отдельный штатный systemctl show выполнен. Дальнейшие действия — по TOOL_FAILURE_RUNBOOK.md.

Контракт Яндекса сверён: https://yandex.ru/dev/dialogs/alice/doc/ru/request (session_id, возрастающий message_id), https://yandex.ru/dev/dialogs/alice/doc/ru/session-persistence . Серверное хранение не требует помещать частные финансовые данные в session_state.
