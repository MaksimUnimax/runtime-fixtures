03.11.2026. Отдельный голосовой сервис Alisa. Перед разработкой опубликован ADR_002_DURABLE_CLARIFICATION.md, commit 847d2b14e88dc48b5e82d797140cbac35cda2822. ## Подтверждённый пользовательский дефект

«дай продажи ща вчеар» → сервис уточняет смысл продаж → «заказанные» → «Для сравнения укажите два периода; для обычного отчета — один».

Это не промах финансового кэша. В действовавшем build6 Engine.submit вызывал parse до enqueue. METRIC_AMBIGUOUS выбрасывался как Rejected, safe_submit только возвращал текст. Исходный вопрос/период/магазины и ожидание ответа НЕ сохранялись. Следующее слово разбиралось как новый самостоятельный запрос. Дополнительно web→Unix IPC передавал только tenant, command, request_id, body_hash: session ID и номер сообщения до исполнителя не доходили. session_state.counter считал реплики, но не хранил смысл вопроса.

Предыдущий sales-basis fix остановил подмену заказов финансовыми данными, но не довёл собственный уточняющий сценарий до работающего диалога. Это дефект реализации, не требование к владельцу повторять полный запрос после каждого уточнения.

## Реализовано

Добавлен dialogue.py и две таблицы в существующей SQLite: dialogue_context / dialogue_receipts. Pending-уточнение отделено от финансовых jobs/cache. Ключ — tenant + HMAC(skill_id|session_id); message_id задаёт порядок доставки. Web после неизменённой OAuth-проверки передаёт эти поля локальному gateway; provider credentials/access token не передаются.

Сохраняются исходная и рабочая фразы, дата первого вопроса, выбранный смысл, незаполненный слот, снимок доступной области и версия компилятора. «Заказанные» дополняет исходную фразу, не является новым вопросом без даты. Период, площадки, группировка и поддержанные фильтры сохраняются. При переходе суток вчера определяется по дате первого вопроса. Если даты действительно не было, второе уточнение спрашивает только дату, сохраняя выбранные показатели.

Точная пара опечаток «ща вчеар»/«за вчеар» нормализуется в «за вчера» вне кавычек; уточнение явно показывает полученную дату. Это не произвольная автокоррекция SKU, брендов или чисел. С неизвестным периодом не подставляется случайная дата.

Сохранение квитанции, изменение pending и enqueue выполняются в одной SQLite-транзакции. Дубликат сообщения не отменяет новое уточнение и не ставит второй job. Изменённый replay/запоздалое сообщение не применяются. Состояние переживает рестарт; права, состав магазинов и версия проверяются при продолжении. Сессии и пользователи не делят pending. TTL ожидания 900 секунд; квитанции доставки сохраняются 24 часа; устаревшие состояния очищаются.

Помощь/диагностика сохраняют pending. Отмена отменяет незавершённое уточнение, не другой уже существующий отчёт. Новый полный вопрос заменяет старое уточнение. «Результат» во время незавершённого уточнения не подсовывает прежний финансовый отчёт. Статический IPC без conversation_id/message_id остаётся совместимым, но не получает неявную память всего аккаунта.

## Реальная новая двухрепликовая проверка после установки

Через действующий gateway под штатным UID web-процесса, в отдельной диагностической беседе:

1. «дай продажи ща вчеар» → «Период 2026-11-02 сохранён. Что считать продажами: заказанные товары и их сумму или выкупы? Можно ответить одним словом: „заказанные“».
2. «заказанные» → NEW / QUEUED, без PERIOD_REQUIRED.
3. Worker → READY / complete. План: ordered_revenue + ordered_units, Ozon и WB, 2026-11-02…2026-11-02. Сохранено происхождение: исходный вопрос, ответ, нормализация и восстановленная фраза.
4. Ledger: ozon_orders HTTP 200 / 4833 мс; wb_orders HTTP 200 / 394 мс; DeepSeek не вызывался.
5. «Результат» → обе площадки, правильный период, заказанные товары, text==tts. Повтор того же result идентичен. Поздний replay «заказанные» возвращает квитанцию того же job, не новый расчёт. Итоговое число provider-вызовов этого job осталось **2**.
