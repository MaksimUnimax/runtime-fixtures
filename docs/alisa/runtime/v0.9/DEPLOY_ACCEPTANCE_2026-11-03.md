## Как реализовано требование «сначала база, потом шаблоны»

P1 и P2 используют один типизированный компилятор. P1 — необязательный ускоритель понимания из JSON-словаря. P2 возвращает вложенные выражения над известными показателями, не только список metrics. Неизвестной комбинации не нужен отдельный речевой шаблон или if-сценарий.

Слои: registry.json — прежние источники/показатели; expression_catalog.json — формулы и ссылки на другие формулы; speech_catalog.json — синонимы и наборы; query_program.py — проверка языка, раскрытие зависимостей, общий DAG и вычисление; program_providers.py — группировка источников и выдача. Прежняя durable очередь, ограниченный HTTP-worker, credentials, права, отмена, lease, P0 replay и UNKNOWN сохраняются.

Сохранены 42 прежних семантических показателя; шесть прежних вычисляемых формул перенесены в каталог, добавлены две демонстрационные вложенные формулы. Итого каталог содержит 8 формул и 44 группы речевых показателей — это не 44 новых API. Новая формула и синоним добавляются только JSON-правкой: отдельный тест в чистой копии меняет каталоги, запускает новый процесс и подтверждает одинаковые SHA256 всех Python-файлов до/после.

Язык `alice-scalar-dag/v1`: add, subtract, divide, percent, relative_change, per_day, minimum, maximum. Вложенность, ссылки, общие подвыражения, два сервером разрешённых периода. Типы/валюты/временные основания/область и известное пересечение расходов проверяются до HTTP. Нулевой знаменатель — неопределённость, а не ноль. Исходные суммы магазинов агрегируются до отношения, не усредняются проценты.

## Реальный вопрос без шаблона

«Какой процент финансовых продаж составили хранение, логистика и эквайринг за октябрь 2026 на Озоне?»

P2, без специальной записи для этой фразы или формулы на три затраты. Модель собрала:

`percent(add(finance_acquiring_cost, finance_logistics_cost, finance_storage_cost), finance_sales)`

Четыре атомарных поля, шесть уникальных узлов, один выход. Реальная проверка в заключительной линии 0.9: DeepSeek HTTP 200 / 1203 мс; Ozon finance HTTP 200 / 124 мс; READY/complete. Четыре поля получены одним запросом целого месяца, не четырьмя и не 31 дневным. Независимый прямой Decimal-расчёт по полученным полям совпал с вычислителем DAG.

После последней правки точной дедупликации повтор всей той же свободной фразы новым сообщением дал READY/HIT того же задания: новых jobs, LLM и marketplace-вызовов нет. Ledger исходного задания по-прежнему содержит только два обращения. Повтор `результат` с тем же message ID идентичен, text==tts, ответ 577 символов. `план запроса` показывает percent(add(...),finance_sales), 6 узлов, а не просто перечень метрик. Финансовые значения и клиентские идентификаторы здесь не публикуются.

## Найденные ошибки и исправления, не скрытые за PASS

1. Слишком длинная подпись вложенного выражения: ограничена только подпись, полное дерево и расчёт сохранены.
2. Первый live-тест сравнения: HTTP 200 модели, но LLM_CLARIFY. Найдено удаление существенного слова «сравни» при передаче очищенного остатка. Теперь P2 получает полную проверенную фразу плюс разрешённые сервером параметры. Конкретный внутренний мотив ответа модели неизвестен. После исправления тот же вопрос выполнен; предыдущий неуспех остаётся неуспехом.
3. Модель может вернуть только root разности. Renderer теперь добавляет оба операнда сравнения из того же графа, без дополнительного HTTP.
4. Язык, формат ответа и source registry закрепляются до P2. Несовместимая смена версии ожидающего задания отклоняется до модели вместо молчаливой переинтерпретации.
5. Первоначальный повтор готовой свободной фразы создал лишний LLM-разбор и ALIASED, без повторного финансового API. Repository исправлен: точное unresolved-сопоставление может переиспользовать уже скомпилированный READY при тех же параметрах/правах/TTL. После исправления реальный повтор дал HIT без модели/API. Это не семантический поиск похожих вопросов.

## Незакрытые границы

Это расширяемое ядро скалярных расчётов, не произвольный табличный JOIN/TOP SKU, оконные ряды, причинность или прибыль без себестоимости. Даты, магазины и фильтры должны поддерживаться серверным нормализатором; неподдержанный слот уточняется/отклоняется. Новый API/поле/гранулярность требует адаптера и квалификации. Новый оператор требует версии языка и тестов. Любую новую русскую фразу модель не обязана понимать безошибочно; такие две успешные live-проверки не являются универсальной оценкой точности.

Выпуск каталогов: правка → typed validation → independent examples/regressions → разрешённый canary → отдельный release/readback. Автоматическое редактирование production моделью не вводится.

Начальная составная диагностика RDC отклонена до исполнения общим сообщением безопасности; конкретный триггер не предоставлен. Проверенный узкий штатный вызов состояния прошёл. Далее запись/тесты/установка проходили штатно; маскировка и обход защиты не применялись. Правило: TOOL_FAILURE_RUNBOOK.md.
