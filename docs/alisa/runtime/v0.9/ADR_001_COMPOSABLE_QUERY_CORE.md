# ADR-001: универсальное ядро составных запросов — проект 0.9

03.11.2026. Статус: решение для реализации по прямому поручению владельца; этот документ сам по себе не означает внедрение или PASS. Исходный HEAD alisa: de6c0cbcf165a5e1b4a2fabb5f62239ec7d9b5d2. База — работающий runtime 0.8; OAuth, transport credentials, exact-only policy и независимый контур Alisa сохраняются.

## Задача и обнаруженный разрыв

Владелец требует сначала базу для вопросов вне речевых шаблонов, затем пожизненно изменяемую библиотеку. Запрос должен распознаваться целиком, составляться из нескольких совместимых источников/вычислений, а не запускать поисковую цепочку LLM по API. REPORT_v0.1.0 уже описывает семантический компилятор и DAG. Документ ARCHITECTURE 0.8 прямо ограничивает P2 выбором metrics; PHRASES/BUNDLES и несколько формул связаны с кодом. Поэтому добавление очередных KPI не устраняет архитектурный разрыв.

## Решение

Один проверяемый язык выражений для P1 и P2. P1 — оптимизация понимания, а не единственный способ исполнить вопрос. P2 возвращает дерево разрешённых операций над зарегистрированными показателями. Оба маршрута передают результат одному компилятору. Модель не получает credentials/tenant, не задаёт URL, SQL/Python, произвольную арифметику исполнения или финансовые значения. JSON проверяется по точному составу ключей, типам, размерам, полноте и всем ограничениям области.

Слои:
1. Источники и атомарные показатели — прежний квалифицированный registry и адаптеры.
2. Язык операций — типизированные арифметические выражения, проценты, разности, относительное изменение, расчёт на календарный день. Никакого eval.
3. Каталог составных формул — декларативные вложенные выражения, ссылки на другие формулы, версии и контроль циклов.
4. Каталог речевых синонимов/наборов — данные, а не HTTP и не реализация расчёта.
5. Компилятор — раскрытие формул, проверка размерностей/временной семантики/площадок/фильтров/валют, DAG с общими подвыражениями, список необходимых базовых данных и минимальные совместимые задачи API.
6. Исполнение — существующая durable очередь, ограниченный worker, проверка полноты/прав, Decimal, exact-ready-result и text/tts.

## Важные границы универсальности

Универсальность означает любые композиции внутри явно поддержанного языка и реальных возможностей источников, а не выполнение любого русского пожелания. Новая формула на имеющихся примитивах и новый речевой синоним должны добавляться JSON-правкой без изменения компилятора. Новый API-контракт/гранулярность требуют адаптера и квалификации; их нельзя придумать моделью. Row-level JOIN, произвольные SKU TOP/окна времени и причинные объяснения нельзя объявлять реализованными, если адаптер выдаёт только скалярные итоги.

Первая интеграция использует существующие проверяемые области: выбранные магазины, один период и при необходимости второй сравниваемый период, существующие фильтры WB, текущий снимок отдельно от потоковых показателей. Отдельные расширения типов/операторов добавляются версионно; неподдержанный оператор отклоняется до HTTP. Ограничения размера/глубины графа защищают от бесконечной рекурсии, не являются искусственным ограничением числа магазинов.

## Контракт составления

Пример без специального шаблона: процент от отношения суммы расходов на хранение и логистику к продажам финансового отчёта. Граф = percent(add(storage,logistics),finance_sales). Ещё один запрос может использовать этот узел в разности или сравнении периодов. Общие storage/logistics/sales не запрашиваются повторно для каждого выхода. Стандартный ДРР — та же конструкция percent(ad_spend,ordered_revenue), а не отдельная ветка исполнения.

Проценты магазинов не усредняются; исходные суммы агрегируются до формулы. Разные валюты, неподдержанные фильтры, несопоставимые временные основания и известное двойное включение расходов отклоняются. Неизвестный/пустой ответ не равен нулю. Нулевой знаменатель возвращает неопределённость, распространяемую на зависимые узлы.

## Версионирование и кэш

Скомпилированный план хранит развёрнутый граф, определения и хеши каталога/языка/источников. Повтор исполняет сохранённый граф, а не заново интерпретирует имя изменившегося шаблона. Изменение доступа/источника блокирует старую выдачу. Изменение формулы меняет каноническое задание. Exact-only сохраняется: никакого overlap, извлечения части старого результата или склейки недель. Общие подвыражения переиспользуются только внутри одного нового задания.

Каталоги изменяются через редактирование → валидацию зависимостей/типов/примеров → offline/regression → ограниченную live-проверку → отдельный release с rollback. Непроверенный каталог не активируется. Автоматическое редактирование production моделью не вводится.

## Обязательная приёмка

A. Запрос вне речевых шаблонов → P2 AST → тот же компилятор → полный результат.
B. Новая вложенная формула добавляется только в каталог, без изменения engine/compiler.
C. ДРР + его числитель/знаменатель и несколько формул не дублируют совместимые API-выборки.
D. Отрицательные сценарии: цикл, неизвестный metric/operator, лишний JSON-ключ, несовместимые единицы/валюты/периоды, фильтр только на одной стороне отношения, нулевой знаменатель, неполные страницы.
E. Exact-cache, UNKNOWN, отмена, отзыв доступа, replay, перезапуск и старые 0.8 сценарии не деградируют.
F. Смена каталога не переинтерпретирует уже поставленный план; новый и старый смысл не получают один ключ.
G. До включения — сравнение хешей активной базы и отсутствие чужой незавершённой работы. После — readback build, одно новое read-only задание, ledger и чтение результата. Успех localhost не называется пользовательской проверкой в консоли.

## Сверенные внешние принципы (не новые зависимости проекта)

CEL разделяет parse/check/evaluate и типизирует выражения относительно объявленного окружения: https://cel.dev/overview/cel-overview . Apache Calcite разделяет логические операции, адаптеры источников и оптимизацию: https://calcite.apache.org/docs/ . Эти принципы подтверждают выбранное разделение; Java/CEL/Calcite не добавляются как тяжёлые runtime-зависимости.

DeepSeek JSON mode требует собственного контроля пустого/обрезанного ответа и не гарантирует нужную бизнес-семантику: https://api-docs.deepseek.com/guides/json_mode/ . Контракт модели проверяется кодом; сетевой UNKNOWN не повторяется автоматически.
