## Подтверждённая причина накопления

В build7 pending имел expires_at, но чистился только на новой реплике и по updated, а не абсолютному сроку. Законченные задания и финансовые payload, control_inbox/inbox/calls не имели полного цикла удаления. Истечение срока чтения не равно удалению данных. Очистка не работала, пока пользователь не возвращался.

Оставлена SQLite, не добавлен Redis. При измеренном объёме порядка сотен килобайт отдельный сервер кэша не нужен для выполнения этой задачи. Использован общий паттерн TTL + активное истечение + ограниченное окно идемпотентности; конкретные сроки — наша явная продуктовая политика, не гарантия сторонней библиотеки.

Короткие транзакции: до 200 строк на таблицу за проход, до 10 проходов/около 2 секунд на запуск. При перегрузке/долгом reader физическая очистка может отставать; проверка срока при чтении действует сразу. Нельзя обещать физическое удаление строго на 900-й секунде при любой нагрузке.

Порог приёма новых данных: 64 МиБ занятых страниц, 10000 jobs, 100000 квитанций на таблицу, 5000 на аккаунт. Это не абсолютный лимит всей файловой системы: принятые задачи, индексы/WAL/backup потребляют место отдельно. При пороге новые запросы отклоняются без стирания действующего уточнения. Число UNKNOWN также ограничено; дальнейшее разрешение таких случаев — отдельная административная операция.

## Физическое освобождение места

Однократно при остановленном только market-worker выполнена миграция в auto_vacuum=INCREMENTAL и VACUUM; перед ней приватная согласованная SQLite backup. Дальше — secure_delete, пакетные DELETE/UPDATE, checkpoint и incremental_vacuum(128), без полного VACUUM на каждой реплике. После incremental_vacuum выполняется ещё один checkpoint: тест обнаружил, что иначе уменьшение page_count могло оставаться только в WAL.

WAL/SHM не удалялись вручную; занятые читатели не завершаются принудительно. Не заявляется криптографическое стирание SSD, внешних снапшотов или уже скачанных копий.

## «Всё что выкупили вчера»: что исправлено, что нет

Корень второй ошибки: в buyout_axis принимались только буквальные «по дате выкупа/события», естественная фраза начинала новый вопрос и теряла pending. Теперь выражение фактического выкупа продолжает исходный запрос, сохраняет дату и не предлагает вместо него когорту заказов.

После установки через штатный gateway в отдельной диагностической беседе:
`Дай продажи за вчера` → `выкупы` → `Все что выкупили вчера блядь!!!`.

Ответ подтвердил **фактические выкупы за 2026-11-02 независимо от даты заказа**, сообщил, что соответствующий источник не подключён, и не вызвал ни финансовый, ни когортный API. Следующая отмена очистила pending, не другой отчёт. Исходные credentials/пользовательские access_token из чата не использовались для имитации сессии.

**Сам источник фактических выкупов по дате события этим изменением НЕ реализован.** Это по-прежнему недостающая функция, а не неясная речь владельца. Не называть распознавание оси выполненным отчётом и не выдавать заказанную сумму/финансовые начисления вместо выкупов. IoT-автоозвучка также не менялась.

## Два реальных сбоя установки и устранение

1. Первый rollout получил **216/GROUP**: в unit ошибочно задана несуществующая группа alice-market. Реальная primary group пользователя alice-market — alice-lab. Группа теперь разрешается по pwd/grp, без создания лишних аккаунтов.
2. Второй — logrotate **Operation not permitted**, смена euid 0→999. Ротация перенесена в службу владельца логов alice-lab с собственным state-файлом и без su. Права не расширялись. Root-служба занимается только разрешёнными приватными backup/probe-файлами.

Обе неуспешные установки вернули прежний код build7; устаревшая backup БД не накатывалась поверх нового очищенного состояния. После проверки фактического состояния выполнен контролируемый повтор. Третья установка успешна 14:45:39 UTC. Это ошибки конфигурации Linux, не отказы API и не систем безопасности инструмента.
