# RCA-001 — почему реализация отклонилась от матрицы и как это предотвращается

04.11.2026. Прямое поручение владельца: вместе с исправлением записать причину ошибки, работать по документации и не отступать от неё. Документ опубликован до корректирующей реализации. Канонический контракт: ADR_005_MATRIX_ONLY_EXTENSION_CONTRACT.md; исходная цель — REPORT_v0.1.0.md и ADR_001_COMPOSABLE_QUERY_CORE.md. Активный build8 не меняется ради обхода проверки.

## Подтверждённое нарушение

Кандидат events-rows 0.10 добавлял ветки по именам источников в table_analytics.py и http_transport.py. Матрица содержала URL и квоты, но не полный контракт запроса, нормализации и полноты ответа. В результате новый совместимый источник требовал править Python. Это противоречит требованию владельца. Общая алгебра filter/group/rank не устраняет этот дефект.

## Причина — конкретные решения при разработке

Я, исполнитель, начал закрывать отдельные пользовательские сценарии (WB события, Ozon товарные строки, рейтинги) до завершения общего механизма чтения источников. Вместо переноса контракта в данные добавлял специальные if-ветки. Затем трактовал успешные функциональные проверки как достаточную готовность, хотя они доказывали результат конкретных сценариев, а не требуемый способ расширения. Это моя ошибка реализации и контроля, не вина пользователя, API, токенов или инструмента.

Документация существовала, но не была обязательным исполняемым критерием выпуска. Не хватало проверки «добавить ранее неизвестный совместимый источник, не меняя ни одного Python-файла». ADR_004 описал новый слой, но не обеспечил выполнение прежнего инварианта. Количество зелёных тестов подменило проверку архитектурного требования. Предыдущий отказ установочного инструмента препятствовал публикации, но НЕ объясняет, почему исходный код был спроектирован неправильно.

## Что меняется в процессе

Каждый последующий шаг содержит: ID требования → изменение в матрице или общий примитив → конкретный тест → полученное доказательство. Требования не переопределяются ради существующего кода. Для нового вида протокола/операции сначала дополняется ADR и тесты; для известного вида запрещено добавлять ветку по имени площадки/эндпоинта. Нельзя переименовать специальный обработчик в «универсальный» или хранить исполняемый Python/SQL в JSON.

Один реестр задач — этот документ плюс ADR-005; итоговая приёмка указывает отдельные статусы: спроектировано, код написан, offline проверено, записанные реальные ответы проверены, новый live-canary, включено в навык, проверено из Яндекс Диалогов. Ни один уровень не следует автоматически из предыдущего.

## Обязательные gates

| ID | Требование | Доказательство |
|---|---|---|
| M01 | Общий движок request/JSON binding/page/decode не содержит provider/operation literals | Автоматический source audit + отрицательный тест намеренно внедрённой ветки |
| M02 | Четыре имеющихся табличных источника описываются данными | Независимые fixtures и differential сопоставление со старым кандидатом |
| M03 | Два НОВЫХ совместимых источника добавляются только JSON | До/после SHA256 всех Python неизменны; новые request/response/pagination/aggregation проходят |
| M04 | Новая формула и речевой шаблон не меняют Python | Каталог-only тест в новом процессе, прежний DAG и voice result |
| M05 | Ошибочная схема не превращается в частичный отчёт | Missing field, duplicate ID, cursor stall, currency/date/unit/total checks, zero/null/returns |
| M06 | Безопасность не спрятана в декларации | Нет eval/import/callback/file/network в выражениях; только заранее реализованные операции; URL фиксирован и квалифицирован, секреты только в auth boundary |
| M07 | Стабильное поведение существующей системы | Не ослаблять 681 проверки; при изменении внутреннего контракта документировать адаптацию, сохранять смысл assertions |

| M09 | Установка отдельно от реализации | Только после M01–M08 и fresh live qualification; никакого обхода отказов или правки активного релиза на месте |

## Очерёдность исправления

1. Инвентаризировать специальные ветки, зафиксировать исходный архив и хеши. Сохранить действующий build8 и незавершённый кандидат.
2. Написать ограниченный data-only язык binding/validation/pagination и его спецификацию. Он работает с нормализованными полями и операторами, а не именами конкретных методов.
3. Перенести четыре табличных источника в JSON, подключить тот же generic interpreter к существующей очереди и транспорту; убрать четыре ветки декодера и request builder.
4. Выполнить matrix-only extension gates и весь прежний набор. Проверить реальные сохранённые ответы без повторного HTTP. Новый canary выполнять только с актуальным допуском и ledger.
5. Зафиксировать оставшиеся старые адаптеры и ограничения ЧЕСТНО: миграция четырёх методов не означает автоматической миграции всего старого скалярного каталога или всех будущих протоколов.
6. Опубликовать исходники и доказательства; переключать навык только после действительной приёмки и безопасной доступности операции.
