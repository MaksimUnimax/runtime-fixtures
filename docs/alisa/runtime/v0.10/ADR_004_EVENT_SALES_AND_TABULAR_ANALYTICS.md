## Критерий правильного результата

Результат по дате заказа, финансовой проводки и фактической продажи — разные показатели. Не объявлять статус delivered или is_marketplace_buyout покупательским выкупом. У WB исходные продажи/возвраты предварительные; деньги могут дозаполняться. У Ozon месячный/дневной отчёт реализации имеет собственные сроки публикации/подписку. Если конкретному кабинету недоступен нужный источник, показывать точную границу, не молча брать другой.

Первоисточники:

Текст query параметра date противоречиво называет дату заказа; до допуска сверить спецификацию поля response и фактическую выборку. RU-портал отдаёт 498 в web; это ошибка документационного чтения, не токена магазина.
- https://dev.ozon.ru/community/1344-Metod-dlia-poluchenie-otcheta-o-realizatsii-za-den/ — официальный модератор: /v1/finance/realization/by-day, отмены/невыкупы исключены, последние 32 дня, подписка Premium Plus. Требуется реальная проверка доступности.
- https://dev.ozon.ru/community/1809-API-metod-dlia-fakticheskikh-vykupov/ — модератор рекомендует месячные realization/posting; это не доказательство наличия оперативного вчера и не абсолютное доказательство невозможности дневного источника.

Новые методы сначала проходят отдельную read-only qualification: валидный запрос, HTTP, схема, даты, полнота, единицы/цена/валюта, лимиты. Сырые ответы только в закрытой серверной области с существующим TTL, не Git/чат. Ключи не меняются, не печатаются. UNKNOWN не повторяется автоматически. Нельзя помечать всякий 200 как полную приёмку.

## Расширение общей основы

Добавить типизированную табличную обработку рядом со скалярным DAG: источник -> полный набор нормализованных строк -> поддержанный фильтр -> группировка по товару/дню -> точные суммы -> сортировка/Top -> сравнение. Примитивы source и aggregation отделены от речевых синонимов; не писать отдельный независимый API-скрипт для каждой фразы. Пагинация полная до ranking; топ первой страницы не является топом кабинета. Ozon day/sku измерения проверяются независимо, не выводятся из месячного скалярного ответа. Для WB используется поддержанный источник с полной выборкой.

План фиксирует источник, временную ось, метрики, измерения, фильтры, порядок/rank и версии. Никакого произвольного SQL/Python/eval. Сопоставление идентификаторов товаров между площадками не выдумывается. Раздельные списки Ozon/WB по namespaces; общий money итог только при совместимых определениях и валюте. Произвольный JOIN между разными источниками без ключей не объявляется завершённым.

Очередь, права, exact-only, TTL, активная очистка, защита дублей и отмен сохраняются. Расширение не должно откатить диалоговый контекст или потребовать хранить всю историю. Новые наборы данных ограничиваются по строкам/байтам; превышение не становится частичным READY.

## Проверки перед переключением

1. Все прежние 607 тестов без удаления смысловых assertions.
2. Отрицательные кейсы новых схем/дубликатов/временных осей/цен/нулей/пагинации/фильтров/лимитов.
3. Независимые суммы и top/series по одним полученным строкам; межисточниковую сверку не называть сверкой с личным кабинетом.
4. Сценарии естественного языка/уточнения/кэша/повторов через вход навыка, затем разрешённые live-API. Свободный вопрос не должен молча терять фильтр.
5. Отдельный релиз, хеши действующей базы, lock, backup, отсутствие активных jobs, единичное переключение, health и readback. Не менять чужие изменения ветки alisa.
