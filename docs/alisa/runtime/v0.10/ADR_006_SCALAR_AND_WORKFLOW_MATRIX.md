# ADR-006 — перенос скалярных источников и многошаговых операций в матрицу

04.11.2026 UTC. Основание: ADR-005, RCA-001 и MATRIX_BINDINGS_SPEC.md. Поручение владельца — продолжать без возврата к отдельным обработчикам. Статус документа: план до реализации, не PASS. Начальная сверка: HEAD alisa 44a5b3d686882aa48fbe2ebb34efe1a37fa2702a; Alisa 04:58:22 UTC исполняет build8. Неактивный matrix-refactor-r2 совпал по хешам с приложенным архивом 840a902296f2a08e02a23df73eb1ad22084265080dad037a83a8383abc1c1d38. Baseline 717/717 заново пройден до правок. Другие ветки/сервисы и параллельные ценовые исследования не затрагиваются.

## Разрыв, который закрывает этот этап

Четыре табличных контракта уже декларативны. Однако providers.py/finance_stock.py содержат старые скалярные request/response ветки, HTTPTransport отдельно знает рекламный token endpoint и стадии складского отчёта, registry.py запрещает новые metric IDs закрытым Python-набором. Эти остатки нельзя объявлять выполнением требования «меняется только матрица».

## Решение

Расширить тот же конечный язык безопасных bindings общими операциями над вложенными JSON-коллекциями и точными числами. Валидация всех ветвей до исполнения, ограничения глубины/числа элементов/объёма. Никаких eval, Python, SQL, сетевого доступа или имён функций-импортов в каталогах. Идентификаторы Ozon/WB и названия их полей находятся в JSON, не в общем ядре.

1. Запросы и декодирование. Оставить общий SourceMatrix; добавить описываемые схемой нормализованные скалярные наборы, редукцию полей и курсор с объявленным общим количеством. Все значения/даты/валюты/полнота должны повторять квалифицированные старые определения. Не менять смысл ради удобства общей схемы.
2. Планирование. Связь площадка + семейство + метрики → рецепт, совместные периоды одного ответа, максимальный интервал, поля/агрегации задаются каталогом. Новая совместимая метрика с source binding не требует нового Python whitelist.
3. Асинхронный отчёт. Общий конечный автомат: начальная стадия → запрос → проверка и захват минимальных полей → переход/ограниченный polling → итоговый декодер. Имена стадий, условия готовности/отказа, task ID и URL-параметры задаются матрицей. В persisted progress только проверенный task ID/счётчик/нормализованные данные; ключей и произвольных URL там нет. Число обращений и время ожидания ограничены; UNKNOWN не повторяется.
4. Краткоживущая внешняя авторизация. Общая transport dependency по auth profile: токен получается отдельным учитываемым в ledger запросом, валидируется и хранится только в ограниченной памяти transport, раздельно по магазину/версии доступа. Секреты не попадают в Request.body, SQLite, LLM или отчёты. Заголовок/секретное тело допускаются только внутри закрытой credential boundary и только для квалифицированного фиксированного HTTPS.
5. Закрытый реестр превращается в проверяемую схему данных. Проверяются ID/ссылки/циклы/единицы/платформы/совместимые scopes/диапазоны и live qualification; список конкретных metric IDs не зашивается в Python. «Можно загрузить запись» не равно «можно отправить реальный запрос»: допуск остаётся отдельным.

## Совместимость

Сохранить существующие Request/result структуры, очередь, TTL, защита повторов, отмена, UNKNOWN, скалярный DAG и речевой вывод. Прежние экспортируемые функции декодеров допустимы только как тонкий compatibility facade общего механизма, без собственной схемы и без участия в расширении; новые источники не добавляют новые фасады. Прежние 717 проверок не ослаблять. При доказанной необходимости изменить внутренний формат progress документировать изменение, сохранять негативный смысл теста.

Новая версия языка/каталога входит в план и qualification. Принятые ранее планы не переинтерпретируются без контроля версии. Исходный build8 не меняется в процессе разработки.

## Проверяемые gates этого этапа

| ID | Требование | Доказательство |
|---|---|---|
| S01 | Все девять старых семейств строят/декодируют запрос через матрицу | прежние fixtures + differential values/ошибки и schema audit |
| S02 | Создание/опрос/получение отчёта — общий workflow | restart, ограничение polling, неверный task ID, отмена, UNKNOWN, отсутствие повторного create |
| S03 | Рекламная авторизация — общее ephemeral dependency | отдельный ledger-вызов, TTL/изоляция store/revision, отсутствие секрета в persisted state |
| S04 | Новый скалярный metric и новый совместимый источник добавляются только JSON | новый процесс, неизменные SHA256 всех Python, очередь/transport fixtures/полный результат |
| S05 | Новый многошаговый отчёт добавляется только JSON | другой URL/поле task ID/статусы, неизменный Python, целый путь до READY |
| S06 | Старые 717 тестов сохранены | полный baseline + новые тесты, исключены TCP/DNS |
| S07 | Источники проверены на прежних реальных ответах | отдельная квитанция, не называется новым HTTP или сверкой с кабинетом |
| S08 | Актуальные runtime hashes/конфигурация/активация разделены | staging отдельно, безопасный readback, свежая live-квалификация только при допуске |

Тесты добавляются в код, но сам тестовый новый источник/метрика/формула меняет только JSON в чистой копии продукта. Сравниваются именно runtime Python-файлы, а не только один выбранный модуль. Synthetic URL не объявляется реальным сервисом.

## Очерёдность

Сначала контракт/общие примитивы, затем перенос определений в JSON, затем совместимые фасады/transport, далее независимые числовые ожидания и matrix-only acceptance. После положительных offline результатов — отдельная серверная staged-копия и проверка на доступных разрешённых записанных ответах. Истёкшие пробы не обещать восстановить; новые обращения только по разрешённому ledger пути. Установка не выполняется путём обхода прежнего отказа или изменения защиты.

## Что не скрывается этим этапом

Свободный табличный AST/P2, все будущие протоколы, фактический Ozon event source, IoT-автоозвучка, кабинетная сверка и коммерческая нагрузочная приёмка — отдельные требования. Если закрыта только часть S01–S08, итог прямо перечисляет её; количество тестов не заменяет архитектурную приёмку. Интеграция в расширение Octoport по этому поручению не производится.
