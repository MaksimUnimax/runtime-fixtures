# Исправление архитектуры: «код один раз, матрица меняется всегда»

Дата: 04.11.2026. Статус: архитектурное корректирующее решение; **не означает, что refactor/деплой уже выполнен**. Относится к проекту «Октопорт маркет», ветке `alisa`. Активная версия 0.9 build8; кандидат 0.10 лежит отдельно.

## Обязательное требование владельца

**Один стабильный универсальный исполнитель заранее реализует поддерживаемые классы операций.** Добавление очередного голосового шаблона, KPI, источника того же класса, формулы или нового разреза, который выражается уже предусмотренными примитивами, должно требовать **изменения и квалификации матрицы, а не правки Python**. Эта цель задана в `docs/alisa/command-planner/REPORT_v0.1.0.md` и `runtime/v0.9/ADR_001_COMPOSABLE_QUERY_CORE.md`.

«Все запросы» означает все комбинации выразимых операций и квалифицированных источников: не произвольный HTTP, незнакомые протоколы и отсутствующие поля. При появлении **принципиально нового типа** ответа/авторизации/оператора требуется единоразово расширить универсальный механизм, затем снова работать через матрицу. Не писать отдельный обработчик на каждую голосовую фразу, KPI или эндпоинт.

## Что сейчас не соответствует требованию

Кандидат `/opt/alice-market/releases/20261104-v010-events-rows-r1` использует `table_catalog.json` с URL и квотами, **но** в `table_analytics.py` содержит специальные ветки `ozon_table_orders`, `wb_table_orders`, `wb_table_history`, `wb_event_sales`: построение request, разбор конкретных форм ответа и cursor/offset. Дополнительно в `http_transport.py` появляются provider-specific branches. Модуль `table_analytics.py` уже содержит часть действительно общей алгебры (filter/group/top/series), но новый совместимый источник по такой схеме может потребовать новой Python-ветки. Это **архитектурный долг и отступление** от задачи владельца, не «готовая универсальная матрица». Не маскировать 681 offline PASS под выполнение данного критерия. Рабочий build8 не заменён, candidate0.10 ещё не активирован.

## Исправленная целевая схема

1. **Словарь смысла**: semantic metric + единица измерения, granularity, date-axis (order/event/accrual/snapshot), currency, допустимость фильтров, формулы зависимостей и синонимы. P1 и P2 выдают одну проверяемую IR, без URL/ключей или исполняемого кода от LLM.
2. **Матрица источников (data-only)**: provider, разрешённый id/method/path, auth profile lookup (без ключей), date/selector binding, request body/query template **из ограниченных переменных**, тип ответа, JSON paths/колонки, нормализованные поля, schema guards, null/sign policies, пагинация/полнота, тарифные/квотные условия, profile qualification, допустимые grain/dimensions. Сами API-ключи только в защищённом хранилище.
3. **Универсальные заранее написанные операции**: `fetch` (GET/POST), `offset_page`, `cursor_page`, `single_page`, `decode_json_rows`, `validate_types`, `filter`, `group_by`, `sum`, `count`, `rank_top`, `time_series`, `compare`, `join_qualified`, `decimal_arithmetic`, `voice_projection`; исполнение по типизированному плану, а не `if endpoint == ...`. Обработка нескольких магазинов и страниц: полнота до выдачи READY.
4. **Компилятор**: определяет, можно ли выполнить нужный вопрос с выбранными активными квалифицированными рецептами; строит DAG, объединяет общие физические вызовы, гарантирует даты/права/валюту/периоды/исключения. Не выкидывает неопознанный фильтр и не заменяет события заказами.
5. **Единый рантайм**: очередь/leases/UNKNOWN/replay/exact-only cache, пользовательская сессия с TTL, отдельный фон/отложенная выдача, контроль доступа, предохранители по лимитам, размеру и расходам; без новых модулей под каждый показатель.
6. **Версионность матрицы**: новые рецепты и формулы публикуются отдельно после schema tests, offline fixtures, реального read-only canary и сравнения хешей. Уже запущенное задание закрепляет версию определений. Непроверенные API остаются недоступными.

### Пример: WB «всё что выкупили вчера»

В семантическом слое `actual_sale(event_date)` отдельно от `order_date` и `finance_accrual_date`. В source binding заявлены `GET /api/v1/supplier/sales`, метод пагинации по квалифицированному `lastChangeDate`, поля `date,nmId,saleID,priceWithDisc`, проверка S/R, валюты и пустой цены, отдельные знаки возвратов. Никакой новой ветки `if wb_event_sales` в компиляторе/декодере. Это допустимо **только если** общий engine уже реализует cursor и безопасную проверку условных полей.

### Пример: Ozon top товаров

В метрике `ordered_units/ordered_revenue` и source binding: POST analytics, dimension `sku`, offset-page и документированное покрытие. Разбор JSON paths и типы описываются матрицей. Общий оператор `group_by(sku) → sort(revenue DESC) → top(5)` работает для Ozon или WB только при совместимом нормализованном контракте, без отдельной функции `ozon_top5`.

### Составные запросы

ДРР `percent(sum(ad_spend),sum(ordered_revenue))`; дневная динамика `group_by(local_day)→sum(ordered_revenue)`; самые доходные товары `group_by(product_id)→sum(ordered_revenue)→rank`; доля рекламных расходов по товару — только при квалифицированном соединении источников на ключах магазина/товара/периода. Если ключей или временной семантики нет, fail-closed. Одна готовая формула может ссылаться на другую.

## Условия приёмки refactor

- **Критический тест «только матрица»**: два новых совместимых источника и как минимум два шаблона/формулы/разреза добавляются только изменением JSON-каталогов. Контрольные SHA256 Python-модулей компилятора, транспортного слоя, валидатора, декодера и исполнителя **одинаковы до/после**; сквозные fixture/IPC тесты и ограниченные live-запросы проходят.
- Успех на Ozon/WB: event sales vs orders vs finance date разделены; WB возвраты отдельно, нулевая/отсутствующая цена не подменяется; Ozon Premium Plus остаётся платным ограничением.
- Никакого `eval`, исполняемых выражений матрицы, динамических URL от модели, скрытых HTTP и запросов без квалификации. Whitelist endpoints, фиксация версии, квоты, cancellation/UNKNOWN/exact-ready.
- Каждая операция матрицы имеет тест примера, отрицательный ответ/неполную страницу и исходную API-квалификацию; добавить один рецепт без изменения движка.
- Последний 607/607 baseline и дополнительные 681/681 regression не ослабляются; новые тесты именно на «изменена матрица без изменения кода».
- Новый релиз — только после отдельной проверки staging/locks/чужой работы, с rollback, active build/health/ledger и проверкой в настоящей консоли. **Не переключать build8 и не объявлять v0.10 готовым до этой приёмки.**

## План исправления

1. Зафиксировать build8 как действующий, 0.10 как candidate с его lock. Не трогать работу параллельного исполнителя.
2. Извлечь имеющуюся общую row algebra из `table_analytics.py`, затем **заменить endpoint-specific декодеры на универсальный интерпретатор** declarative bindings, paginate, normalize.
3. Перенести четыре существующих row API на один общий protocol/JSON-row DSL. Удалить provider-specific branching из `engine.py` и `http_transport.py` для новых рецептов того же класса.
4. Усложнять новые каталоги, а не код: прогнать 681 тест и matrix-only addition cases, декодеры на записанных ответах, затем реальные авторизованные canary.
5. Только после выполнения требований переключить working release и документировать результат. Параллельные изменения Git ветки не затирать.

**Итог:** это исправление архитектуры, а не выпущенный код. Текущий кандидат 0.10 не проходит главный архитектурный критерий «источник этого класса добавляется только матрицей», даже если его функциональные тесты зелёные.
