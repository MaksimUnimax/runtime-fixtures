## Где ломался пользовательский путь

| Ограничение частоты источника | 429 без Retry-After тормозил только одно задание, остальные продолжали обращаться к тому же источнику. | Пауза относится к общему источнику. Retry-After соблюдается, при его отсутствии пауза увеличивается. Искусственного числа попыток нет. |

| Повтор вопроса | Новый вопрос мог снова присоединиться к уже FAILED заданию. | Новый вопрос получает новую попытку. Повтор идентичного request_id сохраняет прежнюю квитанцию. |

| Передача на колонку | Техническая команда доставки при отказе IPC могла стать новым аналитическим вопросом. | Она распознаётся до обращения к модели; допустимые IPC-повторы не создают новый расчёт. |
| Смена вопроса | Поздние служебные сообщения старого вопроса могли заменить новый. | Связь вопроса, задания и подтверждения сохраняется; устаревшее подтверждение не подменяет новый вопрос. |

## Как добавляются новые шаблоны

Сетевое восстановление находится в общем обработчике, а не в отдельных шаблонах. Шаблон описывает источники, параметры, преобразования и вычисления. Запрос без шаблона выбирает доступные методы из каталога и использует тот же транспорт, журнал запросов и очередь.

Совместимые шаблоны добавляются данными матрицы. Новый протокол или ранее неизвестный формат внешнего сервиса может потребовать общего адаптера. Это не означает, что для каждого нового шаблона нужно писать отдельную обработку 429 или таймаутов.

## Установка и сохранение состояния

Установка сверяла активную базу и неизменённые файлы, сохраняла частную резервную копию, проверяла отсутствие выполняющихся заданий и действующих связей со старой версией каталога. Готовые планы и сроки хранения не переписывались. Менялись только код runtime и его pin каталога. Первый запуск установки выявил ошибку её защитного сравнения: в команду systemd включались изменяемые время запуска и PID. Код/конфигурация ещё не были заменены, службы восстановлены автоматически. Сравнение исправлено на путь и аргументы; повторная установка успешна.

При неудачном запуске предусмотрен возврат кода и конфигурации без восстановления всей базы поверх новых пользовательских действий.

## Что проверить владельцу

1. Открыть [подключённую колонку](https://alisa.octoport.ru/app/station/): подключение должно сохраниться. Повторная QR-привязка не требуется.
2. Открыть [настройки озвучивания](https://alisa-admin.octoport.ru/admin/station/): проверить включённую автовыдачу, нужный интервал и текст ожидания.
3. В уже используемом навыке сказать: **«Обнови сводка заказов за вчера на Озоне»**. Дождаться полного ответа.
4. Сказать: **«Обнови в каких акциях участвуют мои товары на Озоне»**. Проверить, что после ожидания произносится ответ, а одна фраза ожидания не крутится бесконечно.
5. Эти длинные ответы в текущей версии разделены на части: после первой сказать **«дальше»**. Переход ко второй части проверен через установленный сервер; автоматическое произнесение всех частей подряд здесь не реализовывалось.
6. Аналогично: **«Обнови какие акции доступны сейчас на Вайлдберриз»**.
7. Во время ожидания нового вопроса задать другой. Проверить, что старый ответ не заменяет ответ на новый вопрос.

HTTP-приём запуска Яндексом не доказывает слышимый звук. Физическое произнесение на колонке в этой серверной проверке не подтверждено.

## Границы и следующий шаг

Повтор после потерянного ответа на запуск аналитического отчёта может повторно создать отчёт у провайдера. Бизнес-данные магазина не изменяются; ровно один внешний запуск в такой ситуации не обещается.

Следующий шаг исполнителя — сверить фактический прогон на колонке с журналами по времени вопроса: приём вопроса, данные маркетплейса, готовый ответ, запуск навыка и обратный вызов. До этого серверные проверки не выдаются за подтверждение физической озвучки.
