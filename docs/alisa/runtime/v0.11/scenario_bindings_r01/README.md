## Реализованная цепочка

1. Защищённый source producer передаёт bounded нормализованную исходную когорту и расходные наблюдения на точный магазин/валюту/период. Требуются полный охват и trusted authorization, не JSON-флаг пользователя.
2. OwnerInputs разрешает действующую себестоимость конкретного товара на квалифицированный basis_day. Изменения дат остаются отдельными значениями; quantity физической единицы не переименовывается в исходный ordered denominator.
3. JSON-сценарии выбирают исходное количество либо количество после исключений. Исключённые единицы не создают выручку или COGS; текущая unit cost сохраняется отдельно. Реальные прочие расходы автоматически не обнуляются.
4. Existing ReportContracts проверяет обязательные расходы/контроли, currency/axis/period/expiry/zero/expense-keys. Control суммы не добавляются как затраты. Пропуск рекламы блокирует пригодный двухсценарный результат.
5. Existing matrix arithmetic формирует total, на физическую единицу сценария, на исходно заказанную единицу и процент той же сценарной цены продавца. Нулевые знаменатели дают null и явный флаг, не0.

`prepare` закрепляет hashes owner/source snapshots, context, всех каталогов и четырёх исполняемых модулей. `execute` повторно проверяет права и immutable pin. `check_pin(action='read')` проверяет актуальные права/сроки без пересчёта формул/HTTP. За сохранность результата и выдачу после read-check отвечает будущий adapter к существующему Repository; один result hash не подтверждает, что пользовательский JSON действительно рассчитан.

## Пропуски и происхождение

VALUE/EXCLUDED_BY_OWNER/NOT_PROVIDED/неприменимое нулевое количество различаются. Если cost известна лишь для части строк, известная часть сохраняется отдельно, а неполная общая COGS не выдаётся за полную и целиком исключается из основного subtotal с omission. Основной результат подписан как остаток после перечисленных затрат; net_profit=null. Renderer не имеет права скрывать exclusions.

Exact-period налог/собственные расходы не распределяются с месяца на день автоматически. Текущее распределение рекламы/хранения допускается только явно для всей исходной когорты магазина за тот же период и с её exact hash. Это не точная атрибуция к одному заказу и не повод перенести весь расход магазина на выборочный SKU.

ACTUAL_MATCHED, API_TARIFF_ESTIMATE, OFFICIAL_TARIFF_ESTIMATE и ACTUAL_PERIOD_ALLOCATION сохраняются отдельно. Одна компонентная строка не должна маскировать смесь actual/estimate: producer обеспечивает однородную basis либо объявляются раздельные компоненты в JSON. Отрицательная фактическая корректировка допускается по политике; отрицательный тариф отвергается.
