# R8 — сохранённые коэффициенты в составном задании

14 ноября 2026. **ISOLATED_COMPOUND_SAVED_PARAMETER_FLOW_TESTED_NOT_DEPLOYED.**

## Результат этого этапа

Механизм R7 подключён к настоящему исполнителю шаблонов и существующим Query/RuntimePort/private-authority RPC. В отдельном кандидате одно составное задание читает сохранённые коэффициенты, при отсутствии заполняет только нужные через зарегистрированные producer-шаблоны, получает данные отчётного периода и формирует ответ. Второй очереди, сервиса или независимого сборщика нет.

Первый квалифицированный составной сценарий — **`economics.delivery_projection.v1`**: количество заказанных товаров, оценка потерь и оценка прямой+последней доставки. Это специально ограниченная часть экономики, **не полная прибыль, не фактические выкупы и не вся юнит-экономика**.

Формулы описаны в `parameter_report_catalog.json`:

- ожидаемое оставшееся количество = заказано × (1 − сохранённая доля потерь);
- ожидаемые потери = заказано × доля потерь;
- оценочная прямая+последняя доставка = заказано × сохранённая средняя объединённая доставка.

Доставку коэффициентом потерь не уменьшаем, последнюю доставку второй раз не прибавляем. Числа магазина в код не зашиты. Себестоимость, налоги, реклама, комиссия, эквайринг и прочие удержания пока не включены в этот ограниченный шаблон и не заменяются нулями.

## Исполнение в одном задании

При заполненных значениях запросы годового источника не выполняются; ноль — полноценное число. Запрашивается только зарегистрированный источник заказов нужного отчётного периода. При отсутствии одного коэффициента собирается только он; при отсутствии двух выполняются оба производителя в том же Query/job. После их готовности продолжается исходный отчёт. Проверен сценарий: один selector и один итоговый ответ без дополнительных модельных вызовов на каждую зависимость/страницу. Это наблюдение синтетического теста, не измеренная стоимость живого запроса.

Дневной период не наследуется коэффициентом: запрошенный год/явный диапазон хранится отдельно. Исходная московская дата планирования закреплена в Query; восстановление или переход через полночь не сдвигает уже принятый период. Поддержано переиспользование коэффициента, ранее рассчитанного за полгода, без возвращения к году.

Для начального заполнения разрешён только `fill_missing`, не произвольная замена. Если владелец вручную заполнил значение во время сбора, расчёт не затирает его, а отчёт читает новое текущее число. Подтверждённые source-данные текущего отчёта сохраняются в текущем job, поэтому пересчёт итоговой формулы не вызывает повторный запрос заказов.

## Авторизация и ограничения

Новый путь по умолчанию выключен. В изолированной платформе `OWNER_PARAMETER_COMPOUNDS_ENABLED`, в native — точный кодовый PIN. Обычный запрос WEB фиксирует прежнюю проверенную WebSession и вопрос; наличие одного поля от модели не даёт права записи. Приватный RPC проверяет Query, владельца, entitlement, магазин/привязку, активность сессии, зарегистрированный профиль и точное первоначальное намерение. Чужая переменная, изменённый период, произвольная формула или несуществующий профиль не принимаются.

Те же проверки повторяются перед обращением к источнику, записью, итоговым ответом и вызовами программного исполнителя. Отмена или выход после уже начатого связывания запрещают дальнейшие источники/запись. Голосовой bearer reports:read не повышался до записи; R8 пока относится к WEB-заданию.

Идентификаторы магазина в платформе и ядре сопоставляются через действующие права, а не по одному имени. Новых ключей, OAuth scopes, grants, ролей, таблиц или миграций не создано. Private RPC использует уже имеющуюся службу и подписанные ответы.

## Перезапуск и отсутствие истории

Если потерян ответ после commit коэффициента, повторяется тот же идемпотентный commit, а не годовая сборка. В continuation и в отметках завершения остаются только ссылка, область, период новой зависимости, хеш и техническая ревизия; числа и прежние паспорта коэффициентов туда не добавляются.

Для финального ответа коэффициенты и их текущие даты читаются в память. После модельного ответа проверяются те же ревизии: при изменении устаревший текст не публикуется, новый ответ пересчитывается по уже полученным данным. Числовые результаты не складываются в структурированную историю переменных. Готовый текст отчёта остаётся по обычной политике пользовательских результатов, а не служит восстановлением старого коэффициента.

## Программное исполнение модели

Проверен реальный клиент программного режима через отдельный Unix-сокет тестового исполнителя. Recovery сохраняет идентификатор исходного запуска и его первоначальные ревизии коэффициентов. Полученный позже старый результат нельзя объявить рассчитанным по новым данным.

Если ревизии изменились, сначала завершается восстановление/отбрасывание прежнего результата, затем начинается новая генерация ответа в том же отчётном job с отдельным revision-bound ID исполнителя. Заказные данные не запрашиваются повторно. Без R8 optional generation отсутствует и прежние идентификаторы программного режима не изменяются. Отдельный тест отозвал сессию перед программной командой: следующий модельный вызов не отправился.

## Что нашла регрессия

Первый вариант R8 ожидал объект в data итогового результата, тогда как старые отчёты иногда возвращают список. Это вызвало новые WORKER_INTERNAL_UNKNOWN. Обработчик исправлен: неприменимые списки/None проходят прежним путём, добавлены отдельные проверки.

На окончательной версии сравнительный native-прогон: **91 проверка, 81 PASS, 10 прежних отказов**. Те же 10 тестов с теми же идентификаторами отдельно упали на нетронутой закреплённой R5-базе. Новых отказов относительно этой базы нет, но **общий прогон не объявляется полностью зелёным**. В основном эти старые сценарии обращаются к прежнему универсальному пути; причина/актуальность каждого требует отдельного разбора. Универсальный fallback ради их прохождения не включался. Список сохранён в TEST_RECEIPT.json.

## Код и воспроизведение

Новые модули платформы: parameter_report_catalog.json, parameter_report_contract.py, parameter_report_rpc.py. Точечные изменения — default-off настройка, metadata original-principal в существующем queries.submit, dispatch новых report_* методов внутри прежнего parameter_collection RPC.

Native overlay: parameter_report_runtime.py и prepare_candidate.py. До применения сверяются все BASELINE.json hashes. В каталоге кандидата89шаблонов, прежние88определений независимо проверены по BASELINE_TEMPLATE_HASHES.json. Изменённые native/support файлы перечислены в CANDIDATE_HASHES.json. Патч предназначен только для отдельной копии; текущий сервер перед будущим выпуском надо заново сверить, а не копировать поверх параллельных исправлений.

Независимое review и полный GitHub CI: **NOT_RUN**. Это отдельный draft-кандидат, не разрешение на установку. Никакого live-флага не включено; тестер продолжает установленную R5/R6-версию без этой новой89-й карточки.

## Остаток и следующий шаг

Полная прибыль требует отдельного квалифицированного состава входов: себестоимость/налоги/собственные расходы и реальные реклама, комиссии, эквайринг, прочие удержания — с согласованными периодами и формулами. Их нельзя дописать по догадке или принять отсутствующее за0. Голос, SKU-доставка по детализации и live-доказательство короткой истории также остаются открытыми.

**Следующий шаг:** независимое ревью этого точного пути авторизации/fill_missing/recovery, затем подключение остальных финансовых составляющих к полной формуле составной экономики на базе исходных отчётов. До окончания браузерной приёмки второго агента новую ветку не развёртывать.
