# Коэффициенты R5: запуск из ЛК через существующую очередь и права владельца

14 ноября 2026. **LK_COLLECTION_ADMISSION_AND_SAVE_VERIFIED_NOT_DEPLOYED.**

Завершён изолированный этап, который оставался открытым в R4: запуск расчёта из формы ЛК связан с существующими Query, RuntimePort, Worker и настоящей платформенной проверкой владельца. Код не установлен в рабочий сервис. Голос и составная юнит-экономика ещё не подключены.

## Как работает запуск

Пользователь выбирает параметр, магазин/товар, период и режим: «Рассчитать и заменить» либо «Рассчитать без сохранения». Период по умолчанию — год, его можно поменять до отправки. Нажатие кнопки является явным намерением; дополнительное повторное подтверждение не требуется.

Платформа проверяет текущую WebSession, OWNER_CLIENT, магазин, подтверждение SKU и ожидаемую ревизию. Точное намерение сохраняется в continuation существующего Query: параметр, область, период, режим, исходная ревизия и привязка к сессии. В нём нет коэффициента, его прежнего числа, сырой выгрузки или session token. Новая таблица очереди и отдельная служба не создаются.

Через существующий приватный RuntimePort вызывается `parameter_submit`. Это отдельная зарегистрированная операция приёма, а не обход авторизации или произвольный вызов API. Ядро запрашивает подтверждение сохранённого Query через существующий подписанный private-authority RPC. Платформа возвращает ровно один зарегистрированный шаблон и подписанную привязку к этому намерению.

Форма уже определила шаблон и параметры, поэтому модель не выбирает их повторно. Используется прежний компилятор, Worker, ledger, транспорт и повторы. В проверенном простом сценарии selector-вызовов0, итоговый model_answer1. Это не измерение живой стоимости и не обещание одного вызова для всех вопросов.

## Реальные права вместо тестового разрешения

R4 проверял запись через тестовый AdmittedWebIntent. В R5 этот обход для сквозных LK-тестов не используется. Проверены настоящий SessionPrincipal, RuntimeAuthority, текущий доступ/entitlement, действующая Seller-credential, store mapping, execution ticket, UID Unix-peer и подпись private RPC. Синтетические только аккаунт, служебные записи credentials и ответы источников/модели.

При записи заново проверяются первоначальный владелец, его текущая сессия, доступ, магазин, исходное намерение, период и ожидаемая ревизия. Runtime подписывает не новое право, а подтверждённый результат уже принятого действия. Модель и браузер не передают actor_id, SQL, свободное число calculated-result или произвольный template/API URL.

Новые OAuth scope, аккаунты и привязки не создавались. Нынешний `reports:read` колонки не стал правом записи. Этот этап реализует только LK/WebSession-путь.

## Сохранение и восстановление

После проверки источников и формулы обновляется одна текущая запись owner_data. Расчёт без сохранения эту запись не меняет. Ручная правка во время сбора остаётся действующей: поздний результат не перезаписывает её, а интерфейс сообщает о конфликте.

Потеря ответа о приёме не создаёт второй Query/job. Проверка читает прежний исход; явное восстановление использует тот же номер и первоначальный период, не новые значения формы. В localStorage находятся только ID/область/срок команды, без чисел и токенов.

Если ответ о commit потерян после записи PostgreSQL, существующий Worker откладывает ту же задачу и повторяет только идемпотентный commit, а не сбор. Completion hash и техническая квитанция не содержат прежнее число. Проверены одна запись и одна ревизия после такого сбоя.

Короткий not_after ограничивает ПРИЁМ новой команды; после медленной проверки готовности он проверяется повторно. Он не становится длительностью самого сбора: уже принятое задание живёт по существующим правилам Query и текущим проверкам прав. Не подтверждённая и истёкшая команда не удерживает форму навечно: после проверки серверного времени можно явно начать новый расчёт.

Отмена до commit отзывает намерение записи. Начатый HTTP-запрос может завершиться, но записать коэффициент уже нельзя. Поэтому ответ отдельно различает отзыв записи и подтверждение остановки runtime. Отмена после commit не откатывает число и явно сообщает, что оно уже сохранено.

## Только актуальное число в форме

Чтение коэффициента или его даты не запускает сбор. Ручная замена очищает прежнее расчётное основание. При новом запуске и ручной правке форма убирает старый текст расчёта. Если старый завершённый Query проверен после последующего изменения, сервис отдаёт нынешнее число с superseded, а старый ответ не выдаётся за актуальный.

Даты остаются раздельными: calculated_at — последний успешный расчёт; collected_at — получение самих исходных данных; updated_at — запись/ручное изменение; actual_period — статистический период. Возраст и явный ноль не запускают обновление. История коэффициентов не создаётся.

Сквозные проверки включают logout, отзыв entitlement/Seller, повтор ID, изменённый период под прежним ID, потерю приёма/commit-ответа, отмену до/после записи, ручную гонку и запрет подмены обычного submit явно разрешённой collection-командой. Readiness не создаёт job и не требует Performance для коэффициента потерь.

Новые серверные тесты блокируют внешние socket/DNS-вызовы; реальны только приватные Unix RPC и одноразовая PostgreSQL16.15. В браузере использованы настоящий BFF и текущий модуль авторизации, не заглушка права «разрешить всё». Начальные непрошедшие прогоны сохранены отдельно: исправлены тестовая разница часов, общий тестовый DB lifecycle и выбор последнего задания при одинаковом времени. Эти ошибки не скрыты под PASS. Два legacy-теста требовали корректного пути к Node на build-host; валидатор и ожидаемое поведение не ослаблялись.

Сохранённые исторические коэффициенты R3 не выдаются за свежий сбор. Вызовов живых Ozon/WB, платных моделей и физической колонки здесь0. Полная регрессия всего проекта и независимое ревью R5 не выполнены.

## Компоненты

- owner_data/parameter_collection.py: приём/статус/восстановление/отмена и строго связанный private commit.
- существующие queries/service.py, RuntimeClient и authority_rpc: добавочный путь без новой очереди.
- parameter_collection_runtime.py + точечный native patch: допуск, закрепление намерения, чистая direct-selection и идемпотентная передача результата.
- существующая форма /app/parameters и BFF: запуск, просмотр, статус, восстановление и отмена.

Режим сбора закрыт `ALISA_OWNER_PARAMETER_COLLECTION_ENABLED=0` по умолчанию. Для включения нужны прежние параметры/Query/authority и совместимый runtime PIN. Флаг не создаёт права голоса. Новых R5-миграций нет; общая установка всё равно должна учитывать миграцию CurrentParameter из R1.

Native R5 применяется ПОСЛЕ квалифицированного R4-addon в отдельной копии. Сборщик проверяет все исходные SHA до первой записи и не работает с /opt. Установщика production в этом пакете нет. Основной агент и его worktree не менялись.

## Следующий шаг и оставшееся

Далее — связать голосовые команды чтения числа/даты, ручной установки и пересчёта с тем же owner-data и проверяемым намерением, не повышая автоматически reports:read. Затем подключить saved-value/первичное заполнение/независимый период к составной юнит-экономике.

Также остаются подтверждение доступной короткой истории в живом источниковом пути, детальная доставка по SKU при наличии доказуемого распределения, совместная установка и приёмка на реальных запросах/колонке. Ручные SKU-исключения и коэффициент потерь SKU уже проверены ранее; общую доставку не выдаём за индивидуальную.

Рабочие БД, службы, аккаунты, OAuth, привязки и тестовая нумерация другого агента не изменены. От владельца на этом этапе новых ключей или действий не требуется.
