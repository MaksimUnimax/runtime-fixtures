# R11 — идентичность начислений, квитанции Worker и правильный запуск CI

15 ноября 2026. **SOURCE_OBSERVATIONS_AND_LEDGER_TESTED_NOT_FULL_ECONOMICS.** Код в отдельной ветке и draft PR430. Установленный сервис, пользовательские параметры, доступ, браузер и работа второго агента не менялись. Новых запросов Ozon/WB или модели рабочего сервиса нет.

## 1. Что удалось подтвердить на настоящем источнике

Вместо агрегата `/v1/finance/accrual/postings`, где нет устойчивого ID отдельного начисления, проверен уже зарегистрированный READ `/v1/finance/accrual/by-day`. В сохранённых ответах действительно есть **accrual_id**. Его нельзя заменять сочетанием суммы и даты: разные начисления могут иметь одинаковые деньги.

На сервере Alisa выполнен ТОЧНЫЙ новый pure-normalizer с проверкой SHA-256, без загрузки рабочего Django/config и без сетевых соединений. Использованы сохранённые ответы 13–14ноября, а не новый API-запрос:29записей,29ID,51выделенный компонент,0дублей,обе страницы terminal. Исходные ID/строки не покидали сервер, исходные файлы проверены хешами и не менялись. Свидетельство — [SAVED_SOURCE_REPLAY.json](SAVED_SOURCE_REPLAY.json).

Идентификатор компонента строится из фактического accrual_id и однозначного смыслового места: вид вложенного поля, SKU и тип услуги. Сумма, дата и индекс массива не становятся идентификатором. Повтор того же ID с тем же содержимым не удваивается; изменившееся содержимое с тем же ID требует явного разрешения версии, а не молчаливого latest-wins. Два неразличимых элемента внутри родителя отклоняются.

## 2. Важная оставшаяся граница

**Полученный идентификатор не доказывает, исходный это дебет или корректировка/возврат.** В проверенных родительских полях нет подтверждённой связи original/parent/nature. Знак суммы, financial date, delivery status и совпадение цены не объявляются таким доказательством.

Поэтому модуль сохраняет `origin=UNCLASSIFIED`, `original_economics_ready=false`, а `qualified_original_fees()` возвращает `ECONOMICS_ORIGINAL_EVENT_RELATION_UNPROVEN`. Это справедливо и при полном наборе страниц. Пустой день не означает, что по заказу никогда не появится более позднее начисление.

Этот отказ предотвращает повторную коррекцию уже нетто-комиссии коэффициентом потерь. Он **не означает**, что полноценную экономику нельзя реализовать или у Ozon нигде нет нужных сведений: следующий участок — квалифицировать подходящую реализацию/позаказный отчёт или другое подтверждённое соответствие первичных и корректирующих событий. Нельзя объявлять всю текущую работу готовой юнит-экономикой.

## 3. Новый источник через прежний исполнитель

`economics_accruals.py` — чистое приведение и проверка источника. `accrual_source_runtime.py` — лист сбора для уже существующего родительского задания. Один шаг делает один registered READ через прежний `Worker._call`, транспорт, лимиты источника, Retry-After и журнал вызовов. Нового HTTP-клиента, сервиса или очереди нет.

Проверяются даты и непрерывная цепочка cursor, наличие всех дней, терминальная страница, принадлежность магазину, версия кода и текущие права. Повтор курсора, пропущенная дата, пустая промежуточная страница, повтор receipt-ID и незавершённое продолжение не становятся успешной полнотой.

Квитанция связывается с событием RECEIVED/HTTP200 того же job, источником, параметрами, хешем ответа и временем. Состояние до завершения зашифровано AES-GCM с привязкой к job/tenant/fragment/version. Исходные идентификаторы заменены scoped HMAC. После успешного завершения родительский API использует прежнюю очистку progress.

Проверки гонки отзыва прав, повторного Worker, повреждения cipher, подмены ledger и429 используют настоящий код Worker/SQLite. Ответы API синтетические. **Родитель здесь — явный тестовый драйвер источника, не уже подключённый пользовательский compile полной экономики.** Подключения нового пользовательского шаблона не сделано; заявка не может сама выдать себе разрешение записи.

## 4. Что было неправильно в CI и как исправлено

Общий foundation runner рекурсивно импортировал специализированные Django-наборы без их настроек/приложений/БД. Вместо skip или отключения проверок сделано разделение:

- foundation выполняет все корневые тесты;
- известные специальные модули точно назначены base/collection/compound/ledger и выполняются отдельным GitHub job на одноразовой PostgreSQL с Unix-сокетом и network=none;
- неизвестный модуль или каталог тестов, в том числе без __init__.py, вызывает отказ; вложенные имена не схлопываются;
- симлинки в тестовом дереве явно запрещены, а не позволяют скрыть новые тесты;
- каталог вопросов остаётся на прежнем отдельном CI-шаге;26старых owner-catalog проверок включены в ledger-набор;
- исторический `runtime_client/test_job_client.py` явно относится к закреплённому старому RT-JOB-R01.1 окружению и не засчитан как новый PASS. Он и прежде не выполнялся обычным recursive foundation без отдельного источника. Полная историческая регрессия не объявляется закрытой.

Для GitHub добавлен source-only архив точного входа R4→R5→R8. Сборщик сначала проверяет SHA архива, весь состав, каждый файл и прежние baseline pins. В архиве нет рабочего config, ключей, пользовательской БД, зависимостей или шрифтов. Его прежний parent manifest имел один известный overlay каталога; actual каталог совпадает с независимо закреплённым R4 baseline, это явно записано в outermanifest. Архив не считается пакетом установки.

Убрана зависимость тестовых request-builder от серверного пути Node: берётся ALISA_TEST_NODE/PATH, а схемы запросов не подменяются. Пустой или пропущенный набор не получает PASS.

## 5. Найденная гонка проверки версии

На правильном foundation-окружении воспроизведён ранее существовавший тестовый отказ `runtime_versions_sync`: изменение source_commit внутри manifest той же длины могло иметь те же stat-метки. Проверка только inode/size/time пропускала смену содержимого.

В отдельной ветке snapshots теперь включают SHA содержимого manifest и каждого проверяемого файла; перед публикацией выполняется повторный secure-read. Добавлен тест, принудительно сохраняющий прежние metadata при новых bytes. Он отказывает `SOURCE_CHANGED`, не перезаписывая закреплённые версии. **Живой установленный helper не менялся.**

## 8. Следующий шаг

Проверить уже зарегистрированные месячный отчёт реализации и позаказный отчёт на подтверждённые исходные суммы/корректировки и товарные связи. Сопоставить их с наблюдениями accrual_id, не объединять события по одной сумме. После доказательства семантики — соединить источник с R10 и полным составным Query/Worker/ответом в изолированном прогоне. Отдельно дождаться и разобрать CI точного финального SHA до слияния; во время браузерной приёмки второго агента ничего не устанавливать.
