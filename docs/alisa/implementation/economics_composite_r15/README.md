# R15 — полный прогноз экономики заказов Ozon

15 ноября 2026. Зарегистрированный шаблон: `economics.unit_forecast.v1`.

## Объём изменения

Полный шаблон соединяет исходные заказы, наблюдаемые начисления OTHER, текущие тарифы, расходы хранения и рекламы, закрытые документы реализации и текущие данные владельца. Он исполняется в существующих Query, RuntimePort, private authority RPC, Worker и журнале `calls`. Отдельного исполнителя, очереди, HTTP-клиента или общего обходного маршрута нет.

Это прогноз выбранной когорты исходных физических заказов. Наблюдаемый финансовый снимок и текущий тариф не означают окончательные исторические расходы или фактическую чистую прибыль. Новый путь по умолчанию выключен. Тестовая fixture и source review сами по себе не являются установленной приёмкой.

## Финансовые правила

Основание — согласованные правила `MaksimUnimax/blood_sand`, ветка «статистика», revision r16, commit `f66b1475e4babd7184698168049a672f8682afd8`. Формулы остаются декларативными в `economics_cohort_catalog.json`.

| Группа | Основание и применение потерь |
|---|---|
| Комиссия | Полностью сопоставленный исходный SALE standard_fee из согласованной пары документов, включая ноль; иначе явно обозначенная оценка по текущему тарифу. Исходная комиссия уменьшается на потери один раз; RETURN не вычитается из SALE перед применением коэффициента. |
| Эквайринг | Рублёвый тариф на исходную единицу, без коэффициента потерь. |
| Прямая и последняя доставка | Сохранённая объединённая средняя доставка × исходное количество. Компоненты повторно не прибавляются. |
| Обратная доставка | Исходное количество × тариф возврата × потери; в сценарии без потерь — ноль. |
| Обработка | Для FBO — ноль; для FBS — исходное количество × (минимальный + максимальный тариф) / 2, без коэффициента потерь. |
| Хранение | Подтверждённая согласованная статья за весь выбранный период. |
| Реклама | Полный выбранный период, все кампании зарегистрированного источника. |
| OTHER | Расход O = −Σ начислений согласованного type 93, сопоставленных с исходными отправлениями и реальными accrual IDs, без коэффициента потерь. Например, положительное начисление 20 ₽ даёт расход −20 ₽. |
| Себестоимость | Текущие одобренные данные владельца по SKU и дню заказа, с коэффициентом потерь. |

Два сценария используют одинаковое исходное физическое количество N. Все денежные величины «на единицу» делятся на N, а ожидаемое оставшееся количество Q выводится отдельно. Пустая когорта подтверждается полными FBO/FBS цепочками; периодные расходы сохраняются, деление на ноль даёт неизвестное значение.

Налоги и собственные расходы разрешаются только для точного периода. Неизвестное значение и явное исключение владельцем не превращаются в ноль. Итог после этих статей формируется только при наличии обеих числовых сумм. Явно неизвестная себестоимость SKU не наследует общее значение.

Конечные десятичные сложение, вычитание, умножение и отношения вычисляются точно с точностью, выведенной из операндов. Периодические отношения сохраняют 60 значащих цифр. Внешний NUMBER и сохраняемые производные входы строк сохраняют прежнюю границу в 60 цифр; переполнение этой границы даёт типизированный отказ. Малый знаковый остаток после взаимного погашения крупных начислений не теряется.

### Контрольный синтетический пример

Worker fixture задаёт две исходные единицы FBO по 1 000 ₽ и одну FBS по 2 000 ₽; потери FBO 10%, FBS 0%. Это вымышленные входы, не финансовые данные владельца. FBS processing min/max равны 0 и 5 ₽, поэтому обработка составляет 2,50 ₽. При хранении 120 ₽, рекламе 300 ₽ и положительном OTHER начислении 20 ₽ ожидаются следующие результаты:

| Показатель | С потерями | Без потерь |
|---|---:|---:|
| Исходное количество N | 3 | 3 |
| Ожидаемое количество Q | 2,8 | 3 |
| Выручка, ₽ | 3 800 | 4 000 |
| Все девять выбранных расходов, ₽ | 2 445,50 | 2 517,50 |
| Остаток до налогов и собственных расходов, ₽ | 1 354,50 | 1 482,50 |
| Остаток на исходную единицу, ₽ | 451,50 | 494,166… |

Налоги и собственные расходы в этом примере неизвестны, поэтому итог после них отсутствует. Отдельный вариант с полностью сопоставленной исходной нулевой комиссией FBO должен заменить ненулевую тарифную оценку: общая комиссия с потерями 600 ₽, остаток 1 714,50 ₽. Эти числа — независимый численный oracle; сам факт появления READY не заменяет его проверки.

## Полнота и происхождение источников

- Заказы проходят все последовательные окна и страницы обеих схем. Окно 31 день — существующая граница зарегистрированного запроса, а не объявленный максимум API или всей длины отчёта. Цена берётся из строки товара, FBO использует `created_at`, FBS — `in_process_at`, даты переводятся в Москву.
- Тарифы проходят полный price cursor и отдельное точное сопоставление product ID → SKU. Тарифная оценка не выдаётся за исторический факт.
- OTHER сначала получает точный набор отправлений из проверенных заказов, затем полные финансовые дни до даты наблюдения. Снимки согласуются по posting, дате, типу, SKU, количеству, валюте и знаковой сумме. Повторный accrual ID удаляется только при неизменном содержимом; одинаковые суммы разных IDs сохраняются.
- OTHER имеет отдельную процессную печать и основание `OBSERVED_SIGNED_POSTING_ACCRUAL_SNAPSHOT`. Для него не создаётся фиктивный пустой блок ORIGINAL fees. Несопоставленные расходы магазина не распределяются на выбранные заказы. Неутверждённый тип выбранной когорты блокирует расчёт.
- После завершения финансового сбора `captured_as_of` фиксируется. Изменение коэффициента через сутки не расширяет финансовое окно и не запускает скрытое обновление.
- Документы реализации выбираются по закрытым месяцам реально найденных заказов. Каждая POSTING/MONTHLY пара согласуется отдельно. Суммарное SALE quantity не может превышать исходное количество даже при частичном покрытии в другом месяце. Частичные документы не склеиваются в выдуманную подтверждённую исходную комиссию.

Пакеты источников защищены AEAD в progress того же job. Возобновление проверяет фактические квитанции именно этого job. Перед HTTP, после ответа и до выдачи квалифицированных данных заново проверяются текущие права. Внутренние проверяющие функции отдельных квитанций не запускают рекурсивное восстановление всей когорты: полный синхронный проход окружён свежими проверками прав.

## Текущие коэффициенты и владелец

Private RPC полного шаблона принимает только заранее определённые поля владельца и ограниченный пакет уникальных пар SKU/день. Один пакет содержит не более 64 пар; число пакетов и общая длина отчёта этим не ограничиваются. Все пакеты связаны с тем же Query/job и точным source attestation. Идентификаторы пакетов образуются сервером и не пересекаются с идентификаторами выбора модели.

Сохранённый ноль является полноценным коэффициентом. Возраст значения не вызывает пересчёт. При отсутствии используется существующий producer с `fill_missing`; ручное значение, появившееся во время сбора, имеет приоритет. Период сбора коэффициента отделён от периода отчёта. Произвольные поля и числа в `parameter_periods` не принимаются.

Перед финальной арифметикой источники восстанавливаются из защищённых пакетов, затем читаются текущие owner inputs. Финальные fences включают все owner batches и текущие revisions. Устаревший ответ модели отбрасывается; новая generation использует те же исходные пакеты. Уже допущенный активный producer возобновляется до поиска новой недостающей зависимости, поэтому изменение первого пакета не подменяет reference выполняющегося второго.

Переход к финальному ответу атомарно переносит зашифрованный source cache рядом с PENDING, отдельно от model API data. Marker не содержит финансовых пакетов или старых owner values. После завершения progress очищается штатным `complete_answer`.

## Включение и установленная приёмка

Native требует точные PIN существующих parameter sources/compounds и нового `economics_composites`. Platform/authority требуют `ALISA_OWNER_PARAMETER_COMPOUNDS_ENABLED=1` и `ALISA_OWNER_ECONOMICS_COMPOSITES_ENABLED=1`; новый флаг по умолчанию выключен. Проверка доступности всех обязательных источников и producers выполняется до начала сбора.

Изменение не добавляет миграцию, публичный endpoint, право владельца или историческое хранилище коэффициентов. Строгая существующая политика owner source не ослаблена. Совместимость реально установленных `CONNECTED_NATIVE_OWNER` credentials с требованием owner source `CONNECTED`, одобрение owner dataset и окно параллельной приёмки должны быть подтверждены отдельно перед живым сценарием.

`build_native_fixture.py` воспроизводит только изолированную source fixture. R15 `prepare_candidate.py` не является production-установщиком и запрещает изменение `/opt/`. Подготовка выпуска должна сохранить актуальные базы web/platform/authority/native и принятый publisher fix; исходный R14 worktree и чужая browser-сессия не изменяются.

Точные результаты общих удалённых прогонов и CI записываются после их завершения. Промежуточный PASS источника или готовый синтетический job не заменяет численную проверку полного ответа и установленную приёмку.
