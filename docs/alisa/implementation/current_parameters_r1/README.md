# Current-only saved parameters — backend candidate

14 ноября 2026. **IMPLEMENTED + ISOLATED_POSTGRES_TESTED; NOT_DEPLOYED.**

Прямое требование владельца: хранить один текущий коэффициент на магазин/параметр/область, дату его последней успешной сборки; прежние значения и сборки не хранить. Канонический контракт: `docs/alisa/architecture/CURRENT_PARAMETERS_CONTRACT_20261114.md` в основной ветке alisa, с приоритетом над старым предложением ParameterVersion/history.

## Что сделано

Расширен существующий owner_data, без отдельного сервиса/очереди:

- CurrentParameter и expand-only миграция0002: unique current key, scalar value/passport; tenant/store compositeFK, происхождение/пустота контролируются БД. Исторической таблицы нет.
- Ревизия текущего слота — только CAS. SKU-состояние INHERIT хранит техническуюревизию без числа/старого паспорта, чтобы поздняя команда не восстановила удалённое исключение.
- Чтение current/effective, ручная установка, возврат кобщему и внутреннее сохранение проверенного calculated-результата. Один текущий row обновляется целиком; oldvalue/evidence не добавляются в OwnerCommand.
- После успешной замены receipt храниттолько метаданные эффекта; replay выдаёт именно нынешнее значение. Послеистечения admission deadline удаление старой metadatareceipt не разрешает поздний replay.
- Время успешного расчёта коэффициента calculated_at, время получения исходных данных collected_at, время записи updated_at. На вопрос «когда собирали/пересчитывали коэффициент» используется calculated_at; свежесть исходных данных сообщается отдельно. При reuse ранее собранных данных collected_at не подменяется сегодняшним временем.
- Ручное значение имеет origin=manual, updated_at и пустые collected_at/calculated_at/period/evidence. Прежнее вычисленноеоснованиек нему не приклеивается.
- Ноль заполнен, устаревшее по возрасту число продолжает использоваться. Никаких таймеров/TTL-refresh и дополнительных LLM-вызовов.
- Общий планировщик зависимости: use/status/preview/recalculate; только missing или explicitrecalculate требуютproducer. Отчёт по одному SKU не сужает область отсутствующего ОБЩЕГО параметра.
- JSON-каталог определений двух первых параметров содержит формулы и необходимые источники. Значения993/7761и101.61не зашиты в код и не импортированы в рабочиймагазин.
- Период: календарный год поумолчанию, явные полгода/диапазон; подтверждённая короткая история допустима только без скрытого сокращения явной команды.
- Общая Decimal-арифметика, проверкаединиц/диапазона/знаменателя/целочисленныхфизическихединиц. Внутренний verifier обязан подтвердить реальные источники и полноту, не одно поле complete=true.

## Авторизация и API

`api/v1/account/parameters` использует прежнюю account/service boundary и WebSession. Внешние действия только read/set_manual/use_general; client action replace_calculated отвергается. ДляSKU нужен подписанный reference, выданный платформой по реально прочитанной карточке выбранного магазина. Он связан с tenant/store/sku/store_revision/security_revision. Транспорт маркетплейса и ключи не меняются.

Код закрыт `OWNER_PARAMETERS_ENABLED`; дефолт false. Existing_OWNER_DATA_ENABLED также требуется. Новых ключей/логинов/перепривязок нет. config/urls и settings получили только добавочные строки; при слиянии сохранить параллельные изменения AL-S11.

`commit_calculated` — внутренний Python seam для существующего job/authority адаптера, не endpoint, которому можно прислать выдуманное число. Он принимает результат квалифицированногоproducer и callback проверки источников. Нельзя подставить production-реализацию `lambda:True`: такая функция есть только в синтетическихтестах.

Долгая годоваясборка должна закреплять намерение в существующемjob, а перед commit получать свежую авторизацию существующимспособом. Этотмодуль не продлевает180секунднуюкомандумоделью и не вводит ограничение длительности годовогорасчёта.

## Что НЕ готово / не заявляется установленным

1. Подключение квалифицированных исторических producers к действующему template-runtime и source receipt verifier.
2. Передача актуальной voice-authority в команду записи после долгого job.
3. Форма в ЛК (ручнойввод/расчёт,годпоумолчанию) и голосовой выбор соответствующихшаблонов.
4. Интеграция очистки временного job-payload и проверкаcurrentrevision до публикации отчёта; никаких постоянных старых parameter snapshots.
5. Производственная миграция/включение/сквозная браузерная и голосовая приёмка.

Это обязательные следующиеинтеграции, не повод объявить незавершённыйпуть рабочим. Активноеядроосновногоагента и живыеданные не менялись.
