# Сохраняемые коэффициенты: только актуальное значение и дата сбора

Прямое уточнение владельца от 14.11.2026. Этот контракт заменяет рекомендации независимых анализов о хранении истории значений коэффициентов. Статус: серверный current-only блок реализован в изолированной ветке и проверен 77 тестами на одноразовой PostgreSQL; ещё 18 прежних тестов каталога прошли. В production не установлен; подключение производителей к ядру, ЛК и голосу — следующий этап.

## Обязательные правила

1. Для каждого tenant/магазина/площадки/параметра и области (все товары либо конкретный SKU) хранится **одно актуальное значение**. После успешной замены прежнее число и прежний паспорт сборки удаляются из оперативного хранилища; таблицы исторических значений, historical API и механизм отката к старому коэффициенту не создаются.
2. Сохраняются дата и время успешного получения исходных данных (`collected_at`), момент вычисления (`calculated_at`) и момент записи (`updated_at`). Это не границы статистического периода. Пользователь может спросить, когда собирали данные для текущего коэффициента, и самостоятельно решить, нужен ли пересчёт. Обычное чтение/отчёт эти даты не меняет.
3. Для ручного числа `origin=manual`, дата ручного изменения ставится сервером. Нельзя придумывать дату сбора: `collected_at` и `calculated_at` отсутствуют, статистический период не требуется. Ответ: «Задано вручную …; сбор для этого значения не выполнялся». При замене рассчитанного числа ручным прежние дата/основание сборки не присваиваются новому числу.
4. Возраст значения не означает пустоту. Нет TTL, расписания, автоматического обновления по новому дню/отчёту/изменению шаблона. Получение запускается только при отсутствии действующего значения или по прямой команде пользователя. Явный ноль является значением.
5. При новом расчёте по умолчанию год; если истории меньше — подтверждённый доступный интервал. ЛК открывает форму с годом по умолчанию и возможностью изменить период ДО запуска. Явные даты не сокращаются скрытно. Ошибка API/пропуск страниц не равны короткой истории.
6. В ЛК два действия: ввести число без сбора либо собрать шаблоном. Голос использует ту же серверную механику. Preview/разовое допущение не меняют сохранённое значение. Обычный запрос информации о дате не запускает сбор.
7. Индивидуальный SKU имеет приоритет; иначе применяется общее значение магазина без копирования числа в каждый SKU. Изменение общего значения сохраняет исключения. Удаление исключения означает наследование, не ноль.
8. Сохранение атомарное: сначала полностью получить и проверить новое значение, затем заменить текущее. Не очищать старое перед сетевым сбором. При ошибке, отмене, недостаточной полноте или конфликте записи старое число/даты остаются без изменений. Это не хранение истории, а сохранение единственного рабочего значения до успешной замены.
9. Ревизия текущей записи — техническая защита от гонки ЛК/голоса, а не архив значений. Старое значение не сохраняется в квитанциях повторов, журнале before/after, task-results, файлах кандидатов или отдельной резервной таблице. Идемпотентная квитанция содержит только идентификатор операции, исход и техническую ревизию; повтор не воскрешает прежнее число.
10. Значения и дата сбора выдаются только владельцу соответствующего магазина; SKU подтверждается его каталогом. Авторизация повторяется перед записью. Модель/программа не пишут в БД напрямую.

## Определения и исполнение

Определения параметров и формулы остаются версионированным кодом/каталогом. Запрет истории относится к пользовательским значениям и сборкам коэффициентов, не к Git-истории программы или к исходной независимой статистике магазина. Не удалять чужие отчёты/данные и не чистить глобальные резервные копии в рамках этой задачи.

Потребитель объявляет необходимые переменные, производитель — источники, независимый период/область и проверяемую формулу. Общий исполнитель читает сохранённое либо вызывает производителя при разрешённом намерении. Отчёт за день не подменяет годовой период коэффициента; фильтр SKU отчёта не сужает область общего коэффициента.

Не создавать постоянные структурированные снимки старых коэффициентов для воспроизведения прошлых расчётов. Уже сформированный пользовательский отчёт остаётся текстом/документом своего времени с обычной политикой хранения; это не источник переменных, и автоматически восстанавливать из него старое число запрещено. Если отчёт ещё рассчитывается при замене параметра, необходимо обнаружить смену технической ревизии до публикации и продолжить по актуальному согласованному набору, не выдавая смесь значений. Не перезапрашивать marketplace-данные лишь из-за изменения коэффициента.

Технический staging текущего незавершённого расчёта не должен превращаться в архив прошлых сборок: после фиксации/отмены промежуточные результаты и ссылки очищаются штатным механизмом. Не обещать физическое мгновенное стирание из PostgreSQL WAL/инфраструктурных backups; новая функция не создаёт из них пользовательскую историю. Удаление общих backups не входит в допуск.

## Какая дата отвечает на вопрос пользователя

«Когда последний раз собирали/пересчитывали коэффициент?» — дата завершения его последнего успешного расчёта `calculated_at`. «Насколько свежие исходные данные?» — `collected_at` и даты компонентов текущего основания. Для разных источников collected_at консервативно показывает самую раннюю дату наблюдения; более свежие компоненты не скрывают старые. В ЛК обе даты подписаны раздельно. `updated_at` не подменяет ни одну из них. Ручное значение показывает дату ручного изменения, без выдуманного сбора.

## Минимальная структура текущей записи

Ключ: product/tenant/store/parameter/scope/SKU. Текущие поля: типизированное значение, единица/валюта, origin, collected_at, calculated_at, updated_at, запрошенный/фактический период для рассчитанного числа, компактное основание последнего расчёта, definition/template version, техническая revision. Прошлого payload нет. Для состояния «использовать общее» допустима запись без числа и без старого паспорта — лишь текущее состояние/ревизия.

Для расчёта по уже собранным данным `collected_at` берётся из доказанного паспорта источников, а не из времени открытия формы. Если источники наблюдались в разное время, их timestamps отражаются в текущем основании; повторный расчёт из тех же данных не создаёт ложную свежую дату сбора. Ручной импорт даты без доказательства не становится подтверждённым свежим сбором.

## Приёмка

- Повторное чтение текущего значения, его даты и новый отчёт не обращаются к API/модели-производителю и не меняют updated_at/collected_at.
- Успешный пересчёт заменяет ровно одну запись; старое значение/период/дата недоступны ни через read, ни через историю/receipt.
- Ошибка пересчёта и конкурентная ручная правка не теряются.
- Ручной ноль сохраняется; ручная замена очищает старый паспорт сбора.
- Общий параметр и SKU-исключение изолированы; чужой tenant/SKU запрещён.
- Сбор за полгода становится текущим до следующей прямой команды, не возвращается к году.
- Дата сбора и статистический период показаны раздельно в ЛК и голосовом ответе.
- Никаких новых usage-квот, автономных таймеров или программных веток по имени коэффициента.

## Контрольная точка R4

Штатный Worker прошёл изолированный сбор и передачу проверенного числа в существующую текущую запись; перезапуск после commit не дублирует сбор/запись. Это не production-интеграция голосовой записи или кнопки ЛК. Неявное наследование периода отчёта в producer блокируется до отдельной схемы зависимостей. Даты и current-only retention выше остаются обязательными. Доказательства: `docs/alisa/runtime/v0.11/current_parameters_r4/README.md`.

## Контрольная точка R5

В отдельной сборке реализован запуск из ЛК через действующего владельца и существующий Query/Worker; он больше не использует тестовый AdmittedWebIntent. Нажатие явно задаёт период/область/режим, приватная запись перепроверяет их и актуальные права. Старые числа не хранятся и не возвращаются через старый ответ как текущие. Голосовая авторизация и production-включение не объявляются готовыми. Подробности — `docs/alisa/runtime/v0.11/current_parameters_r5/README.md`.
