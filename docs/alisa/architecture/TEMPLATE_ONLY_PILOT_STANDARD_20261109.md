# Стандарт шаблонов и временный режим их обкатки

Основание: прямое распоряжение владельца 9 ноября 2026. Базовая реализация стандарта установлена в `alisa-template-only-r2-20261109`; последующее уточнение владельца требует два модельных вызова вместо трёх — выбор шаблонов и финальный ответ; отдельный template_verify удаляется; отдельная итоговая приёмка и контрольные суммы публикуются в `docs/alisa/quality/TEMPLATE_ONLY_PILOT_ACCEPTANCE_2026-11-09.md`.

## 1. Режим работы

**TEMPORARY_TEMPLATE_ONLY_PILOT — временный режим обработки и обкатки шаблонов.** Основной вопрос исполняется только после выбора зарегистрированного шаблона или полного сочетания шаблонов. Свободный поиск read-методов моделью, универсальный fallback и прямой пользовательский read_method отключены. Наличие метода в каталоге API не разрешает обойти отсутствие шаблона.

Низкоуровневые API-контракты, проверенные источники и обработчики остаются частью ядра. Это не удаление API-возможностей, а запрет самостоятельного универсального выбора операций в активном пользовательском пути. Старые обработчики и речевые ускорители могут оставаться для совместимости и регрессии; production-вход не использует их для обхода template-only режима.

Если хотя бы одна часть составного вопроса не покрыта, не выполняется даже его поддержанная часть. Обходной маршрут не включается автоматически. Изменение режима после обкатки — отдельное решение владельца.

## 2. Единый каталог

`template_catalog.json`, корневая схема `alisa-template-catalog/v1`: версия каталога, явная политика временного режима и словарь templates.

Каждая запись содержит:

| Поле | Назначение |
|---|---|
| id, version | Устойчивый идентификатор и версия |
| purpose | Назначение данных, не пользовательская реплика |
| platforms | Допустимые площадки |
| kind | scalar, compound, formula, dataset, event или information |
| input_policy | Ось времени, snapshot/period, поддержка условий |
| steps | Зарегистрированные источники/операции либо ссылки на другие шаблоны |
| qualification | Ссылка на существующие требования квалификации источников |
| metrics, notes | Бизнес-смысл данных и существующие ограничения |

В записи запрещены голосовой вопрос, phrase/phrases, utterance, речевые regex, готовый текст/TTS, системный/финальный промпт, credentials и произвольный URL. Исходный вопрос, магазины, права и общие настройки модели находятся в задании/ядре, а не размножаются по шаблонам.

### Простой источник

Шаг содержит `id`, `platform`, `operation`, `source_registry`, `params`, привязки `bind` и при необходимости ссылку на зарегистрированный source workflow. Для scalar-рецепта сохраняется имя проверенного рецепта. `params` — точное зарегистрированное выражение запроса источника; оно не является свободным HTTP-кодом модели.

В текущей миграции используется адаптер существующих проверенных source handlers. Публикация каталога проверяет совпадение operation/params/field bindings/workflow с исходным реестром. Нельзя изменить только декоративное имя операции, продолжив исполнять другую. Новый источник сначала регистрируется и проверяется общим механизмом, затем используется шаблоном.

### Составной шаблон

```json
{
  "id": "SUMMARY.43",
  "version": 1,
  "purpose": "Сводка заказанных товаров",
  "platforms": ["ozon", "wb"],
  "kind": "compound",
  "steps": [
    {"id": "part_0", "template": "B01.ordered_units"},
    {"id": "part_1", "template": "B01.ordered_revenue"}
  ]
}
```

Выше показаны основные поля, не полная запись. Входной магазин/период наследуются из конкретного вызова. Зависимости проверяются на циклы и отсутствующие ссылки. Повторные исходные чтения объединяются: количество и сумма заказов одного магазина/периода не требуют двух одинаковых HTTP-запросов.

Формулы сохраняют существующий `calculation_contract` и именованные зависимости; таблицы — исходные flow/relations/columns/group_by/aggregates/output_stage. Эти поля описывают данные и проверенные преобразования, не формат обычного конечного ответа модели. Справка — локальный информационный шаблон, не выдуманный API-вызов.

## 3. Мигрированные определения

Всего85:42показателя,15сводок,2событийных отчёта,9формул,16табличных наборов,1справка. Идентификаторы и проверенная бизнес-семантика сохранены. Четыре WB-таблицы без подтверждённой полноты источника не включены автоматически.

Речевые фразы удалены из базовых и табличных определений. Старые фразы табличного парсера вынесены в отдельный compatibility speech-layer для проверки старых исходных обработчиков; в новом активном режиме они не выбирают шаблон.

При изменении hash табличного каталога из-за удаления phrases обновлены только10уже существовавших квалификационных ссылок. Равенство всех остальных полей и источников проверено; новые допуски магазинам не добавлялись.

## 4. Контракт выбора моделью

Модель получает исходный вопрос, уточнения, серверную дату/часовой пояс, разрешённые магазины, каталог назначений/ограничений и настоящий `input_contract`. Она не получает права задавать свободные operation или URL.

Поддержанный выбор:

```json
{
  "action": "plan",
  "complete": true,
  "missing": [],
  "requirements": [
    {"id": "r1", "description": "Запрошенная часть вопроса", "invocations": ["a"]}
  ],
  "invocations": [
    {
      "id": "a",
      "template_id": "SUMMARY.43",
      "store_id": "<разрешённый магазин>",
      "input": {
        "period": {"from": "2026-11-08", "to": "2026-11-08"},
        "comparison": null,
        "filters": {},
        "group_by": "marketplace"
      }
    }
  ]
}
```

`group_by` — строка marketplace или total, не null. Для текущего снимка period=null; для временного интервала — from/to. Это внутренний контракт выбора, не новая догаданная схема API. Сервер не преобразует неправильное значение из сообщения об ошибке.

Модель перечисляет все части исходного вопроса и выбирает полный набор шаблонов одним вызовом. Затем сервер проверяет ID, входные условия, площадку, источник, квалификацию и полную связанность объявленных требований с вызовами. По прямому уточнению владельца отдельный модельный контроль template_verify удалён: после успешной локальной компиляции сервер выполняет выбранные шаблоны. Сопоставление естественного вопроса с каталогом выполняет первый модельный вызов.

Только после успешного полного preflight начинается HTTP. Композиция выполняется существующими scalar/dataset/table обработчиками в одном root job, с общими правами, ledger, retry и source semantics. Это не отдельная очередь. Локальная компиляция проверяет допустимость и связанность выбранного состава, но не является отдельным смысловым разбором естественного вопроса. Реальные отклонения сохраняются для обкатки.

## 5. Отсутствие шаблона

Основной код: **TEMPLATE_NOT_FOUND**. Отдельная диагностическая причина различает отсутствие подходящего определения, неизвестныйID, неподдержанные условия, недоступное определение, неразобранный выбор или неполную композицию.

Точная строка пользователю и на колонку:

**Извините, данный запрос не поддерживается**

Без добавления диагностических деталей, перечня шаблонов, предложения покупки или другого текста. Выборщик инструктируется возвращать эту строку. Для надёжной точности сервер доставляет проверенную постоянную строку, а не делает дополнительный свободный модельный вызов для её перефразирования. Это явно предписанное владельцем временное исключение из обычного свободного финального ответа.

Результат содержит ok=false,status=TEMPLATE_NOT_FOUND,data=null,retryable=false,temporary_mode=true и case_id. READY здесь означает готовность сообщения отказа, а не аналитических данных. Ноль marketplace-вызовов для не принятого полностью состава.

Фактический403из-за подписки, отозванные права владельца,401,429и5xx не подменяются отсутствием шаблона. После принятого плана продолжают действовать общие обработчики API-ошибок и восстановления.

## 6. Защищённая очередь доработки

До завершения отказа сохраняется один idempotent case на tenant/job:

- полный исходный вопрос и уточнения;
- точный payload каждого фактического вызова выбора, включая общие инструкции и каталог-контекст;
- полные полученные ответы выбора, в том числе некорректныйJSON;
- выбранные определения, все условия и непокрытые части;
- версии каталога/кода, снимок определения шаблонов, модельные квитанции, время и контекст задания;
- диагностическая причина и связь с запросом/заданием.

Хранилище отдельно от короткоживущих отчётов: `template-gaps.sqlite3`, ключ `template-gaps.key`, права0600, AES-GCM с аутентифицированной привязкой к tenant/job/версии/hash. Чужойtenant и повреждённыйciphertext отвергаются. Авторизационные заголовки, API-ключи и execution_ticket туда не добавляются.

**OPEN-кейсы сохраняются до явного разбора/закрытия.** Обычная15-минутная очистка отчётов и недельная метрикаLLM не удаляют эту очередь. Это не разрешение бессрочно хранить все успешные запросы или весь модельный трафик. При сбое сохранения система не сообщает, что случай сохранён, и не выдаёт ложный успешный terminal result.

Внутренний read-only CLI `template_gap_admin.py` запускается с правами runtime-service/оператора. Список показывает метаданные; точное содержимое читается по tenant+case_id. Публичный клиентский endpoint/экран просмотра не добавлен. В GitHub и общих логах — безопасные квитанции и тестовые сценарии, не архивы произвольных реальных вопросов.

## 7. Совместимость и критерии приёмки

Сохраняются RuntimePort/current-authority, один job/reader-scope, автоматическая Station, пользовательские настройки ответа, учёт каждого реального LLM-вызова, временные повторы и отсутствие usage-квот. НативныйRuntimePort не включается самовольно, если до установки он был выключен.

Требуются проверки всех85компиляций без речевого выбора;комбинацииодного/разныхисточников;дни/пагинация;полнотаусловийдоHTTP;недоступные4WB;запретuniversal/read_methodобхода;точныйtext/tts;перезапуск/идемпотентность;сохранностьполногоmodelpayloadпослеобычнойочистки;шифрование/изоляция;отзывправдоотправки;реальныеподдержанный/неподдержанный/частичныйсоставнойсценарии.

Следующие шаблоны добавляются только в этот каталог с проверенными источниками и зависимостями. Ошибка_TEMPLATE_NOT_FOUND — вход для доработки каталога, не повод включить скрытый универсальный поиск.

## 8. Уточнение владельца: два обращения к модели

Штатный поддержанный запрос: один template_select → локальная компиляция/проверка доступа → API всех выбранных шаблонов → один model_answer. Простой и составной запрос используют один и тот же порядок; число API-страниц и фрагментов не добавляет модельных стадий. Старый сохранённый state=verify повторно компилируется локально и продолжается без template_verify. Перезапуск не повторяет успешный выбор или уже полученные API-данные.

Все фактические попытки сохраняются в недельном счётчике. Сетевые повторы могут дать больше двух попыток; отсутствие шаблона по прежнему завершается одним вызовом выбора и точным отказом. Исторические прогоны с тремя обращениями не пересчитываются задним числом.
