# Решение владельца: только точное совпадение запроса — v0.2

Дата: 2026-11-03. **OWNER DECISION**: отказаться от поиска по истории и сборки результата из ранее сохранённых периодов/показателей. Кэш — это только *готовая полная выдача того же канонического задания*. Это решение заменяет более широкую идею перекрывающихся периодов в предыдущих предложениях.

## Как должен работать путь

1. Яндекс прислал фразу. Система устанавливает учётную запись, права и формирует **полный канонический план** (набор магазинов, показатель, включительный интервал дат, группировка, фильтры, определения метрик, версия матрицы и версия методики расчёта). Если параметр не определён — уточнение, а не частичный кэш-хит.
2. По полученному плану вычисляется один ключ. Поиск кэша — **один точный SELECT по (tenant_id, plan_key)**. Нет SQL по пересечению дат, поиску подмножеств магазинов, склейки результатов по дням и чтения чужих cached reports.
3. Только **READY + complete + nonexpired + authorized** может возвращаться пользователю. Устаревший или неполный ответ не используется.
4. При miss один идентичный запрос создаёт только одно исполняемое задание. Параллельный дубль ожидает его результат. Другой интервал, иной набор магазинов или иная группировка — новое задание.
5. При явном «обнови» bypass кэша для данного задания. Если маркетплейс/LLM ответил с неизвестным исходом, статус **UNKNOWN** и никаких слепых перезапусков.
6. При изменении источника/схемы/доступа корректные механизмы инвалидируют затронутые готовые записи; не выдают сохранённые цифры уже отключённому аккаунту.

## Примеры

| 1-й запрос | 2-й запрос | Решение |
|---|---|---|
| продажи за 1–7 октября | продажи за 1–31 октября | **MISS**: новый месячный запрос, без чтения недельного кэша |
| продажи за 1–31 октября | продажи за 1–7 октября | **MISS**, даже если месяц включает эту неделю |
| «за октябрь» | «с 1 по 31 октября», тот же показатель/магазины/группировка | **HIT**, если совпал канонический план и TTL |
| продажи октября все магазины | продажи октября только Ozon | **MISS** |
| продажи октября итого | продажи октября по каждому SKU | **MISS** |
| количество заказов октября | сумма заказов октября | **MISS** |
| продажи октября | «обнови продажи октября» | **REFRESH** |

**Не путать кэш с обычным запросом к маркетплейсу:** внутри *одного нового* задания скрипт может объединять два совместимых показателя в один HTTP-запрос к Ozon. Это оптимизация состава одного запроса, а не построение ответа из старых кэш-записей. Когда API поддерживает полный октябрь, делаем один запрос на этот период, а не 31 ежедневный; при пагинации, лимитах кампаний или разных рекламном/продажном API количество реальных вызовов может быть больше одного.

## Проверенный прототип

Новая часть `exact_cache.py` в прототипе — только SQLite, без сетевого доступа. Точный уникальный ключ `(tenant, plan_key)`. Состояния `RUNNING`, `READY`, `UNKNOWN`. Проверка владельца claim и запрет выдачи неполного результата. **Нет** функций просмотра истории/overlap/period join; явный `invalidate`.

Вместе с существующими тестами матрицы: **50/50 PASS** (`test_results_v02.txt`): 32 старых теста (планировщик и пример Ozon) + 18 тестов точного кэша. Это локальная проверка *образца*, не опубликованная функциональность на сервере Alisa и не реальная проверка marketplace API.

## Условия перед production

- Нынешний `UserPlan` поддерживает только intent, период, магазины, group и default metric variant. **Любые будущие произвольные фильтры, валюта, часовой пояс, определения метрики и источник версии должны включаться в канонический ключ либо приводить к отказу**, а не молча опускаться. Базовая версия каталога уже включена; токены, пароли и сами ключи маркетплейсов в кэш не кладём.
- При наличии нескольких серверов заменить учебный однофайловый SQLite на транзакционное хранилище, обеспечить атомарные claim/complete и владение заданием; резервные копии, TTL и retention — отдельные политики.
- Для популярных исторических отчётов возможен больший TTL, но не вечный: изменения данных и отзыв прав должны корректно инвалидировать готовый результат. Сохранённый отчёт может быть неизменяемым снимком с явным временем обновления, однако **не должен** выдаваться как актуальный без отметки снимка.
- Метрики ratios (например, ДРР) считаются по сумме исходных числителя и знаменателя **в рамках нового полного задания**; не усреднять проценты по сохранённым отчётам.

**Итого:** кэш может только *переиспользовать идентичный завершённый отчёт*; никакого дополнительного поиска по историческим отчётам или их склейки. Подтверждение реальных Ozon/WB рецептов и интеграция с вебхуком — отдельные невыполненные задачи.
