# Алиса + DeepSeek: архитектура матрицы команд и минимального API-плана

**Версия:** `0.1.0-prototype`, 03.11.2026. **Статус:** исследование + работающий локальный прототип маршрутизатора, **не установленный production-сервис**. Реальная модель Flash испытана на сервере Alisa отдельно; реальные вызовы Ozon/WB в этом проходе не производились.

## 0. Основное решение

Вместо «LLM пробует разные инструменты до получения ответа» строится **семантический компилятор запроса**:

`фраза → анализатор смысла → нормализованный план (IR) → проверка прав и определений метрик → выбор источников из версионированной матрицы → оптимизация плана (кэш, совместимые метрики, пакеты) → ограниченный исполнитель HTTP → проверка полноты → вычисление кодом → речевой ответ`.

Модель **не имеет прямого доступа к HTTP, SQL, ключам, библиотекам произвольного кода, тратам и выбору аккаунта**. Выход DeepSeek — строго структурированный *запрос к семантическим возможностям* (`intent`, `metrics`, `period`, `store_selector`, `group_by`, `filters`, `comparison`, `freshness`); наш компилятор авторизует, проверяет совместимость и только после этого создаёт конкретные HTTP-инструкции. Для стандартных команд модель не нужна. Для новых словесных формулировок используется один вызов `deepseek-flash` (non-thinking) в режиме ограниченного JSON; он не может создавать новые реальные API endpoints.

**«Один вопрос → один HTTP-запрос» не является принципом:** один период за месяц можно передать одним интервалом, **но** разные источники рекламы и заказов, несколько продавцов, лимит страниц и кампаний, разные определения показателя могут объективно требовать больше одного запроса. Целевой критерий — **минимальный корректный физический план при гарантированной полноте**, а не «любой ценой ровно один запрос».

## 1. Словарь и сущности

| Уровень | Назначение | Пример |
|---|---|---|
| `utterance` | Исходная речь как текст от Диалогов, включая контекст | «Дай ДРР за октябрь по всем» |
| `semantic_operation` | Нормальное бизнес-значение, независимое от площадки | `drr_ordered` |
| `semantic metric` | Определение единиц, момента признания, дроби | `ad_spend / ordered_revenue` |
| `store selector` | Текущий аккаунт и список доступных кабинетов | `ALL_AUTHORIZED`, не строка `Север` без разрешения |
| `calendar period` | Однозначные даты с часовым поясом | 01.10–31.10.2026 (локальные дни) |
| `capability` | Требуемые права доступа | seller_analytics, ads_read |
| `recipe` | Подтверждённая реализация получения метрики у площадки | `ozon.orders_analytics` |
| `provider request` | Метод, URL, тело, лимит, пачка, курсор | POST `/v1/analytics/data` |
| `dataset` | Сохранённый снимок данных с полнотой и свежестью | все страницы получены, updated_at |
| `derived result` | Вычисление обычным кодом по совместимым источникам | ДРР, разница, % изменения |
| `voice projection` | Короткая русская фраза с TTS-форматированием | «ДРР… процентов, обновлено…» |

**Четыре разные «матрицы», а не огромная таблица из десятков тысяч фраз:**
1. Матрица **показателей** — семантика и формулы.
2. Матрица **источников** — какие методы Ozon/WB дают какие поля и при каких правах.
3. Матрица **операций** — допустимые фильтры, группировки, календарь и сравнения.
4. Матрица **действий** — цена и оптимизация API-вызовов, кэш и поведение при неполноте.

Это позволяет внести один новый метод WB в матрицу источников, не переписывая все фразы/интенты, которые используют его показатели.

## 2. Пошаговый основной тракт

### 2.1 Приём речи и контекста

Ввод из Яндекс Диалогов — нормализованный текст `request.command` вместе с исходной фразой, метаданными, идентификатором текущей сессии и OAuth-доступом. Перед планированием: проверить токен; связать его с **нашим** tenant; получить актуальные магазины этого tenant; выполнить разрешение на чтение. Нет токена → запускаем account linking; нет активных магазинов → инструкция по добавлению на сайте; не поддерживается нужная поверхность → текстовое объяснение. Сырой звук колонка нашему серверу не передаёт.

### 2.2 Выделение типа операции

**P0**: команды самой беседы — «повтори», «стоп», «результат», «дальше», «помощь», «поменяй магазин»; никакой DeepSeek.

**P1**: надёжно разобранные шаблоны/интенты — количество заказов, сумма заказов, расходы на рекламу, ДРР, остатки, сравнение. Использовать список поддерживаемых слотов и синонимов, контекст периода и магазина. Но не «отрезать» остаток фразы: `кроме`, `без`, `отдельно`, `не`, `по каждому`, `заказано/выкуплено` меняют смысл. Если не распознаны все существенные ограничения, переключиться на P2.

**P2**: свободная фраза → **один** ограниченный вызов DeepSeek Flash без thinking. Показать модели **только** допустимые семантические операции и слоты (без реальных токенов, без SQL, без списка внутренней инфраструктуры). Ответ JSON проверяет сервер: whitelist intent, поля, даты, уровень свежести, ограниченный размер, отсутствие неизвестных ключей; иначе уточнение/ошибка. Пустой JSON, обрыв, слишком долгий ответ → честное уточнение или фоновая обработка, не угадывать поля.

**P3**: просьба вне модели — редактирование цены/кампании, чистая прибыль без затрат, выгрузка персональных данных, непроверенный KPI → `NOT_SUPPORTED`, `MISSING_DATA` или конкретное уточнение; не искать случайные методы.

### 2.3 Понимание календаря

- «вчера» → вчера по согласованному часовому поясу продавца; не по UTC сервера.
- «октябрь» 03.11.2026 → 01–31.10.2026; если сейчас более ранний месяц, прошлый октябрь. Для неоднозначной истории уточнить год.
- «за прошлую неделю» → полные календарные 7 суток (нужно зафиксировать начало недели — для RU понедельник).
- «за последние 30 дней» → скользящий интервал, отличен от календарного месяца.
- «за месяц» → уточнить: текущий, предыдущий или последние 30 дней; не подставлять октябрь без оснований.
- `date_to` может быть включительной датой, часовая зона/время события в каждом API разные; адаптер должен перевести к документированному контракту и не терять часть суток.
- Финансовые документы/реализация, дата заказа, дата выкупа, дата возврата имеют разные временные оси. Не смешивать в расчёте.

### 2.4 Выбор магазинов

Решение владельца — **не ограничивать число магазинов**. Один пользователь может иметь N Ozon, M WB, несколько юрлиц. В запросе допускаются `ALL_AUTHORIZED`, одна площадка, идентификатор/голосовой псевдоним одного магазина, подмножество, «сравни» и «по каждому». Названия могут повторяться: при коллизии уточнение, не выбор первого. Физический `store_id` фиксируется, смена ключа и имени историю не меняет. Состав «все» снимком фиксируется в момент постановки отчёта. Чужие ID, возвращённые моделью, отвергаются сервером.

### 2.5 Проверка бизнес-смысла

Определить точную операцию, например:

- `ordered_revenue`: **заказано на сумму**; не равно выкупам, выплате или прибыли;
- `ordered_units`: число заказанных товаров;
- `returned_units`: факт возврата по принятому определению даты;
- `ad_spend`: расход на платное продвижение, с проверкой включения НДС/скидок и типов кампаний;
- `drr_ordered`: `100 * SUM(ad_spend) / SUM(ordered_revenue)`. При нуле знаменателя → «не определяется», а не 0%;
- `drr_attributed`: отдельный KPI с рекламно-атрибутированной базой, не переименовывать как общий ДРР;
- `profit_net`: не рассчитывается только из двух публичных метрик: обязательны себестоимость, комиссии, логистика, возвраты, хранение, реклама и налоги, критерии признания;
- `stock_units`: текущий **снимок**, не допустимо использовать месячный интервал аналогично продажам.

Не складывать проценты ДРР разных магазинов простым средним. Суммировать числители и знаменатели и считать общий процент заново **только при сопоставимых валютах и базах**.

### 2.6 Планирование источников

Для каждой пары `(store, required_metric)` сервер ищет в матрице источников методы с подходящими: версией, правами, схемой, оплаченной подпиской, покрытием дат, группировкой, фильтрацией и актуальностью.

Составляем **DAG / дерево зависимостей показателя**. Например `drr_ordered` → `ad_spend` + `ordered_revenue`; «сравни периоды» → два среза `ordered_revenue`; «топ SKU» → тот же набор данных с группировкой `sku` и полной пагинацией. Все зависимые данные должны быть готовы до речи.

**Найденные конкретные API-кандидаты:**

| Источник | Метод | За месяц целиком? | Важные ограничения | Статус допуска |
|---|---|---|---|---|
| Ozon сумма/кол-во заказанного | `POST /v1/analytics/data` | Период `date_from`/`date_to`; можно указать **две метрики в одном запросе**; 61 минутный лимит | без Premium-режима не все метрики и история; новые лимиты 50 вызовов/сутки без подписки, не чаще 1/мин; возможна пагинация | **Документирован**, live schema/данные нужного кабинета не проверены |
| Ozon расходы рекламы | Рекламный API / отдельный источник | Пока **не доказано** | доступ и атрибуция могут быть отдельными от Seller API | **не утверждать метод** |
| WB продажи за период | `POST /api/analytics/v3/sales-funnel/products` (кандидат) | По интервалу, не 1 день × 30 | тип токена, тарифы, пагинация, временная семантика, точные поля | кандидат по документации WB; ещё не принят live |
| WB реклама за период | `GET /adv/v3/fullstats` | до **31 дня** одним календарным интервалом | до **50 campaign IDs** за вызов; список ID нужен отдельно, статусы кампаний; базовые токены имеют иные лимиты | метод документирован, реальный набор кампаний ещё не проверен |
| WB финансовые продажи и комиссии | `GET /api/v5/supplier/reportDetailByPeriod` | поддерживает период | курсор `rrdid`, страницы/отчётные периоды, финансовые документы | отдельно квалифицировать |

**Важно:** документация Wildberries по региональному зеркалу и сторонним клиентам полезна для подготовки, но не заменяет проверку текущей RU-спецификации и авторизованного вызова. Некоторые первичные страницы `dev.wildberries.ru` возвращали HTTP 498. Без подтверждения контрактов новый рецепт **не попадает в production allowlist**.

### 2.7 Оптимизация API-плана

Сначала `0 вызовов`: ищем полностью пригодный кэш, включая нужный период, магазин, метрику, группировку, свежесть, версию определения.

Потом группируем по `(store, provider, endpoint, range, grouping, compatible filters)` и объединяем массив совместимых `metrics`: например Ozon `ordered_units` + `revenue` за весь октябрь одной заявкой. Близкий `ordered_units` и `ordered_revenue` не требуют двух HTTP-вызовов.

Если API поддерживает целый месяц, не дробим на дни. Если API ограничивает 31 день, квартал делим **только по максимально разрешённым интервалам**, а не автоматически по дням. Если реклама WB имеет 80 кампаний и предел 50, нужно минимум две группы кампаний **плюс при необходимости один отдельный вызов списка ID**. Если ответ сам требует `offset`-страницы — до конца пройти пагинацию; один стартовый HTTP != полная выгрузка.

Пакеты не объединять через разные токены/кабинеты, если API не допускает общий доступ: 100 магазинов требуют учёта их прав и независимых квот. Порядок выгрузок можно параллелить **по независимым профилям** только в пределах их лимитов и фактической производительности сервера.

Ставим *предохранители*: максимальная оценка вызовов, размер ответа, стоимость, лимит минут и суток, справедливая очередь по магазинам, приоритет уже готовых ответов, предел параллелизма. Слишком дорогой или невозможный запрос → отказ/ETA, без слепых повторов и перерасхода.

### 2.8 Отправка и нормализация

Интеграционные адаптеры исполняют только **проверенные** записи реестра. API-ключ извлекается по внутреннему `store_id` из защищённого хранилища на сервере; DeepSeek его никогда не видит. Запрос содержит только whitelisted параметры и no-write метод; raw URL от модели не допускается. Результат сохраняется с `source_endpoint`, `request_parameters_hash`, временем, версией контракта, идентификатором страницы/курсорной позиции, точным количеством строк и `completeness`.

Сбой 401/403 → нет доступа, не ноль заказов. 429 → учесть указанную паузу, не одновременно повторять всем клиентам. 5xx → ограниченный backoff с jitter только если исход определён; UNKNOWN может означать выполненную платную операцию, не дублировать автоматически. Полнота по страницам/документам — обязательна до ответа «итого».

### 2.9 Кэш и обновление

Разделить четыре слоя:

1. **Сырые подтверждённые страницы и документы** — надёжное хранилище фактов на ограниченный срок, без паролей.
2. **Нормализованные таблицы** — заявки/заказы/финансы/расходы/остатки со своей временной семантикой и источником.
3. **Материализованные агрегаты** — итоги по дню/неделе/месяцу, по магазину, по SKU.
4. **Кэш готового отчёта** — готовый ответ пользователя с фиксированным составом магазинов и версией.

Ключ: `tenant + store_ids + metric_definition_version + period + grouping + filters + currency + provider_contract_version + source_watermark`. Не складывать данные разных клиентов, даже если магазины названы одинаково. **TTL не фиксированный для всех метрик**: октябрьский закрытый период обычно меняется реже сегодняшнего, но поздние корректировки возвратов/начислений могут изменить историю; нужен периодический reconciliation. Текущие остатки — отдельная быстрая политика свежести, без подмены факта текущего состояния вчерашним кэшем. Точно повторенный запрос использует ранее загруженный срез и не оплачивает API/LLM снова.

### 2.10 Расчёт и валидация результата

Код считает деньги с Decimal или целочисленными копейками; суммы разных валют без конверсии не складываются. Нулевая база — неопределённый процент. Неполная сумма по 3 из 4 магазинов не выдаётся как общая, при допустимости отдельно озвучивается «частично: три из четырёх». Все сравнения учитывают неполный сегодня vs полный вчера, сопоставимые дни недели, и часовой пояс.

Для ДРР октябрь: за месяц нужен агрегат `ad_spend = S`, `ordered_revenue = R`, итог `S / R * 100`. Модель не вычисляет процент. Для рекламы не подменять фактические расходы бюджетом кампании; не путать рекламные продажи с суммой всех заказов.

### 2.11 Озвучка и отложенная работа

Если есть валидный агрегат — короткий шаблон TTS без DeepSeek. Если нужна интерпретация — DeepSeek возвращает только план, а не финансовую цифру; при нетипичном объяснении возможен отдельный LLM, но **не по умолчанию**.

Webhook обязан полностью ответить Яндексу в 4,5 секунды; наш внутренний допустимый бюджет короче и калибруется по реальным перцентилям. Сложный/дорогой запрос фиксируется **до** ответа и обрабатывается отдельным worker. ETA рассчитывается по реальным лимитам и очереди, а не по длине вопроса. В новую беседу передаются только ID сохранённого задания, а не вся таблица. При следующем вопросе в нашем навыке можно напомнить о готовом отчёте, при выдаче прекратить напоминания. Автоматическая повторная озвучка через сценарий умного дома — отдельная пока не проверенная функция и не причина блокировать планировщик.

## 3. Матрица пользовательских операций

В будущем не писать отдельную ручку на каждый пример. **Операции — независимые параметры**:

| Нормализованная операция | Период/показатели | Выход / подводный камень |
|---|---|---|
| Число заказанных единиц | yesterday, week, month; ordered_units | одна дата или полный диапазон |
| Сумма заказов | revenue, period, store set | это НЕ чистая прибыль |
| Сводка заказов | ordered_units + ordered_revenue | метрики Ozon объединяются в один payload |
| Заказы по каждому кабинету | same, group by store | N кабинетов, без отдельной повторной LLM |
| Заказы по каждому товару | group SKU | страницы/limit, не гарантировать один API |
| Топ товаров по обороту | revenue by SKU, top K | вычислить после полной выборки |
| Динамика по неделям/месяцам | revenue group week/month | один диапазон с соответствующей группировкой, если поддержано |
| Сравнение 2 периодов | 2 compatible slices | по возможности один интервал с детализацией; иначе минимальные 2 запроса |
| Возвраты за период | returned_units / finance returns | нельзя просто `orders - returns` назвать выкупами |
| Расходы на рекламу | ad_spend | отдельное рекламное API / возможны пакеты кампаний |
| ДРР на заказанную сумму | ad_spend / ordered_revenue | минимум 2 независимых источника при отсутствии кэша |
| ДРР по рекламной атрибуции | ad_spend / attributed_revenue | отдельный KPI и источники |
| Расходы по кампаниям | ad_spend group campaign | ID, статусы, limit 50 на WB |
| Сколько оплачено/начислено | marketplace payout/realization | отдельная финансовая ось и отчёты |
| Комиссии и логистика | commission, logistics | финансовые отчёты, часто разная задержка |
| Себестоимость и валовая прибыль | cost table + revenue | только при наличии себестоимости магазина |
| Чистая прибыль | revenue minus all cost components | нельзя обещать без налогов, себестоимости, возвратов и полного набора затрат |
| Текущий остаток | snapshot at T | отдельный endpoint и freshness |
| На сколько дней хватит остатков | stock / velocity | нужно определить скорость продаж и сезонность |
| Какие товары упали | compare SKU periods | нужны сопоставимые срезы и полное покрытие |
| Почему снизились продажи | correlations / hypotheses | нельзя заявлять причинность по 2 показателям |
| Нет ли ошибок подключения | auth status, data freshness | не LLM, служебный путь |
| Где готовый отчёт | job state | не инициировать повторный платный запрос |
| «Скажи одним предложением» | projection only | берём сохранённый итог, новый API не нужен |
| «Кроме товара X» | filter by stable SKU, not guessed name | проверка неоднозначного товара |

Для каждой операции со временем появятся тестовые срезы: одинаковая фраза, другие магазины и периоды, неверные права, неготовность, пустой ответ, ошибки, актуальность и денежные границы.

## 4. Примеры физических планов

**«Сколько товаров заказали в октябре на Ozon?»** Если в аккаунте ровно один Ozon, права подтверждены, кэша нет и выборка помещается: один 68 `POST /v1/analytics/data` с `date_from=2026-10-01`, `date_to=2026-10-31`, `metrics=[ordered_units]`. Не 31 HTTP-запрос.

**«Сколько заказали товаров и на какую сумму за октябрь на одном Ozon?»** Одна совместимая заявка с `metrics=[ordered_units,revenue]`, `dimension=[month]`. Без доступа к Premium ограничение истории и лимиты могут остановить запрос. Пагинация для SKU и других размерностей требует завершить все страницы.

**«ДРР за октябрь в одном Ozon»** 0 запросов при полностью валидном кэше; иначе минимум один источник заказанной суммы и отдельно фактические расходы на рекламу, метод которого пока не утверждён. Производственный результат сейчас `INCOMPLETE_COVERAGE` и **не отправляется** ни в один API. Реклама/продажи не смешиваются только для красивой цифры «один HTTP».

**«ДРР за октябрь на WB с 80 рекламными кампаниями»** Нужно определить ID кампаний и требуемые статусы; `/adv/v3/fullstats` имеет предел 31 день и 50 ID, значит не меньше двух партий расходов (плюс возможно получение ID) и источник суммы заказов/выкупов. Вопрос пользователя при этом **один**, семантический план **один**. Нельзя говорить «нужно 31 дневной вызов».

**«Общая сумма заказов 60 магазинов»** одна модельная интерпретация/правила, 60 *обособленных по правам* источников при отсутствии кэша (могут быть независимые HTTP). Агрегируем одним ответом после проверки покрытия. Отказ от искусственного лимита магазинов не означает исчезновение лимитов каждой площадки.

**«Прибыль за месяц»** без себестоимости и финансовой методики → 68 `MISSING_COST_DATA`. Отчёт за готовый Ozon месяц не может ответить на этот KPI даже при миллиардном бюджете модели.

## 5. Управление изменениями API

Нужен **единый версионируемый реестр** в GitHub, без отдельного демона или системы управления «как Octoport»:

- Описание каждого источника: 68 API hostname/path/method, schema hash, версия и точная ссылка на документацию; тип токена, доступность по тарифу/региону, покрытие дат, max interval/IDs/page, лимиты по профилю, ретрай, status 68 `DISCOVERED` → `DOC_CHECKED` → `CANARY_PASS` → `PRODUCTION_VERIFIED` → `DEPRECATED` → `DISABLED`.
- Смены документации и release notes: ежедневная/еженедельная выборка (без автоматической замены production), сравнение контрактов и отрицательных изменений. Например, Ozon удалял рекламные метрики из `/v1/analytics/data`, а WB менял поля статистики — старый рецепт нельзя бездумно вызывать годами.
- Правки матрицы через PR с 68 source citation → fixture diff → contract test → малый разрешённый live canary на одном тестовом кабинете → фиксация SHA → развёртывание. Если документация недоступна или API отказал — 68 UNKNOWN/QUARANTINE и сохранение последнего валидного среза с пометкой свежести.
- Рецепт и пользовательский KPI версионируются **независимо**: если меняются методы WB, меняем адаптер и contract tests, а не все голосовые фразы.
- При несовместимом обновлении фиксировать какие сохранённые срезы допустимо использовать на новой версии, иначе инвалидировать кэш.
- Наблюдаем: долю вопросов без LLM, долю правильного разбора, среднее/P95 времени, requests/semantic query по провайдеру, cache hit, cache stale, error 401/429/5xx, API expenditure, ratio of unknown and partial results, data reconciliation with Seller cabinets, growth of memory/disk.

## 6. Реальные результаты испытаний 03.11.2026

**Контекст сервера Alisa** (read-only до испытаний): 1 vCPU, ~1 ГБ RAM; службы `alice-lab-web`, `alice-lab-worker`, `alice-lab-llm` активны, DeepSeek Flash live без thinking. На старте было 4 записи запросов за день, посчитанный сервисом расход ~0,000261 USD. В production-сервисе новой матрицы пока нет.

**Локальный planner prototype, без внешних сетевых запросов:** 6832/32 тестов PASS. В частности:

- октябрь формируется одним интервалом, а не 31 отдельным днём;
- `orders + revenue` одного Ozon = **одна** предложенная заявка;
- `drr` одного Ozon = **две** семантические ветви (ads + orders), не одна, причём неподтверждённый источник рекламы **не допускается к production исполнению**;
- трем магазинам по одному утверждённому recipe = три независимых запроса, хотя речь пользователя одна;
- 115 магазинов не вызывают придуманного лимита;
- `profit` без необходимых данных → отказ с причиной;
- чужой store ID не попадает в запрос;
- cache hit → ноль API;
- mismatch tenant/period → разные кэш-ключи;
- Ozon preview payload за октябрь 68 `date_from/date_to/metrics/dimension/limit/offset`, а ключи магазинов не входят в preview;
- попытка выполнить неизвестный endpoint отклоняется.

**Настоящий DeepSeek Flash на сервере Alisa:** четыре новых тестовых фразы, все 4 семантических намерения/периода распознаны верно в ограниченном JSON, без thinking, время отдельных ответов **834, 1034, 1136, 685 мс**, примерно **$0,000083–0,000086 за вызов** (оценка по токенам). Тесты: «Дай ДРР за октябрь», «За прошлый месяц заказано товаров на Озоне», «Сравни продажи вчера Ozon/WB», «Чистая прибыль с закупочной ценой». **Это 4 примера, не 100% гарантия точности для всех формулировок**. Тест записывал ограниченный расход в существующий дневной ledger. Никакие реальные ключи Ozon/WB не использовались.

### Что НЕ проверено

1. Полные, актуальные тела ответов каждого Ozon/WB метода и доступность конкретных метрик при разных тарифах/токенах.
2. Источник ad_spend Ozon и валидный рекламный KPI; не выдуман.
3. Достоверность WB orders/revenue и корректность календаря на реальных данных.
4. Полнота отчётов при пагинации и 80/100+ кампаниях на реальном профиле.
5. Независимая проверка всех русских формулировок и защитная матрица из сотен adversarial-кейсов.
6. Производительность 3 000 клиентов на VM 1 vCPU/1 ГБ RAM и реальный расход при множестве магазинов.
7. Сквозная выдача этих метрик на физической Станции — не требуется для разработки planner, но нужна перед релизом.

## 7. Следующая последовательность без потери времени

1. Принять определение и название главных KPI: заказы, выкупы, факт расходов, ДРР на полную заказанную сумму или иную базу. Без этого API-интеграция будет давать «правильные» числа с неверным смыслом.
2. Подтвердить необходимые Ozon Seller API методы на одном разрешённом тестовом кабинете: один месяц, две метрики, группировки, limit/offset, тариф, ответ 200, сверка с кабинетом.
3. Подтвердить WB sales funnel и статистику рекламы на тестовом кабинете с несколькими кампаниями; убедиться в limit 50 IDs и полном расходе.
4. Проставить лишь проверенным рецептам статус `PRODUCTION_VERIFIED`; активировать их исполнение и кэш. Остальные не делать рабочими через догадки.
5. Расширить корпус фраз **не меньше чем 100–200**: разные месяцы, фильтры, отрицания, необычные сравнения, неоднозначные магазины, составные показатели; для каждой — ожидаемый IR и физический план/отказ.
6. Замерить P50/P95 всех стадий и расход; от этого задать лимиты быстрого ответа и ETA фоновой очереди. Зафиксировать source SHA/registry version и результаты.
7. Подключить первую защищённую реальную метрику к опубликованному приватному навыку Алисы без публикации доступа к чужим данным.

**Вывод:** в одном запросе модели получаем **целиком готовый смысловой план**; в одной компиляции получаем **минимальный физический план**, где необходимы 0/1/N API-вызовов. Не путать N, обусловленное реальным контрактом маркетплейса, с искусственным N из неудобной архитектуры.
