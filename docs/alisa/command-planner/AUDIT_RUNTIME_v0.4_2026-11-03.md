## Проверенные исходные дефекты и ограничения

В неизмененном v0.2 воспроизведены: допуск будущих дат; выбор дешевого непроверенного рецепта перед проверенным с последующим отказом вместо корректного выбора; возможность завершить просроченный claim, если до этого не выполнялся lookup. Отдельно подтвержден незакрытый контракт canonical identity: отсутствие полноценной валюты, timezone и source/access revisions. Последнее — ограничение исходного UserPlan, а не доказанная межвалютная утечка.

В v0.4 даты проверяются кодом; первый выпуск использует фиксированные допущенные рецепты вместо незаконченного универсального оптимизатора; commit проверяет владельца, состояние и срок; нормализованный план содержит валюту, timezone, ревизии источников и версии определения. Неизвестная валюта не подменяется RUB. Исправлены также SQLite resource leaks, отмена через alias-job и возможность занизить минимальный provider interval конфигурацией.

## Архитектура кандидата

Проверенный аккаунт → P0/P1/P2/P3 → полный смысловой план → snapshot разрешенных магазинов → exact-key → постоянная очередь → ограниченный HTTP worker → проверка схемы/периода/страниц/валюты → Decimal → сохраненный полный результат → text/tts.

Webhook не выполняет долгий marketplace HTTP. P1 разбирает только полностью учтенную фразу. P2 — один ограниченный JSON-разбор: модель выбирает разрешенные показатели, но не tenant, магазин чужого аккаунта, даты, endpoint, SQL, секреты или арифметику. Календарь и явно названные площадки задаются сервером. В новом адаптере thinking явно disabled; это свойство написанного кандидата, не новый live-замер модели.

Первый исполняемый контракт ограничен `ordered_units` и `ordered_revenue`, целым периодом, одной/обеими площадками, раздельными либо совместимыми общими итогами. Неоднозначные «продажи»/«количество заказов» требуют уточнения. ДРР, реклама, выкупы, прибыль, остатки, фильтры SKU/бренд/склад, исключения и сравнения пока не включены и не подменяются другим ответом.

Ozon-кандидат: один POST `/v1/analytics/data` с совместимыми revenue/ordered_units за весь период. WB-кандидат: POST `/api/analytics/v3/sales-funnel/products` с полным периодом и limit/offset до конца. Не дробить месяц на дни; дополнительные HTTP допустимы только по требованиям источников, кабинетов и страниц. Точный формат Ozon month dimensions, WB currency/selected.period, тип токена и кабинетная сверка нового декодера остаются gate перед live.

Кэш строго по OWNER DECISION EXACT_CACHE_POLICY_v0.2: полный READY идентичного задания, TTL и повторная авторизация; RUNNING присоединяет дубль; UNKNOWN не повторяется вслепую; refresh не перезапускает активный/неизвестный job. Неделя/месяц, разные метрики, магазины, валюты и ревизии — разные задания. Промежуточные страницы хранятся только в текущем job, без исторической склейки.

Состояния кандидата: QUEUED/RUNNING/READY/FAILED/UNKNOWN/CANCELLED/PREVIEW/ALIASED. Резерв обращения записывается до отправки. 401/403 блокируют выдачу кэша ревизии; 429 фиксирует Retry-After без автоматического повтора; timeout/неизвестный исход — UNKNOWN; неполные данные не становятся нулем или общим итогом.

Локальный rate gate Alisa не учитывает обращения того же кабинета из Octoport или других клиентов. Нужен общий бюджет/координация перед постоянной нагрузкой. Тестовый календарь фиксирован в Europe/Moscow; фактические даты озвучиваются.

- `диагностика аналитики` — версия preview и явное отсутствие внешних вызовов.
