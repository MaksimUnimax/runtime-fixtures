# Отложенный roadmap объединения · v0.5

**Не входит в текущую очередь запуска Алисы.** Начинать только после готовности Octoport и отдельного решения владельца. Все этапы DEFERRED, проверки NOT_RUN. Сохранена последовательность отдельно от AL-S01–24.

## AL-M01. Новый вход открывает существующий аккаунт Октопорта на стенде

Уже есть: AL-S24 не является единственным условием: требуется реально готовый Octoport candidate, отдельное решение владельца и совместимый identity v0.5.

Создаём: Добавить OIDC consumer adapter текущего Octoport, не менять local account/device IDs. Сохранить старый вход для контролируемой миграции, отобразить external identity на существующего пользователя.

Проверка: Войти новым identity в старый тестовый account; проверить ту же установку расширения. → При отказе adapter старый разрешённый путь доступен.

Готово: Ни один существующий аккаунт/устройство/доступ не пересоздан.

## AL-M02. Пользователь подтверждённо связывает два своих аккаунта

Уже есть: Принят AL-M01, есть разные/одинаковые email и несколько организаций в fixtures.

Создаём: Доказательство контроля обоих аккаунтов, step-up, одноразовое подтверждение exact IDs, audit. Запрет автоматического merge по email; конфликт цели/replay исключён.

Проверка: Связать разные email при контроле обоих аккаунтов. → Совпавший email без доказательства не даёт связи; параллельные подтверждения идемпотентны.

Готово: Одна подтверждённая связь личности, организации/магазины не смешаны.

## AL-M03. Один ЛК показывает два продукта с сохранёнными данными и оплатой

Уже есть: Приняты AL-M01–02, security review общего origin выполнен.

Создаём: Общая оболочка на существующем app.octoport.ru, профиль/выбор продукта/аккаунта. Раздельные product APIs и владельцы journals; UI library pinned и own deploy.

Проверка: 40 дней Алисы и неоплаченный Octoport сохраняются. → Отключить один backend: второй доступен, недоступный не показывает нули.

Готово: Общий действующий ЛК, не две ссылки и не миграция всех БД.

## AL-M04. Одна админка управляет продуктами только в своих scope

Уже есть: Принят общий ЛК, готовы продуктовые staff API и MFA.

Создаём: Общая admin-shell на существующем app.octoport.ru/admin либо отдельно утверждённом admin origin. Поиск person со связанными accounts; все команды routed владельцу ledger; новые права назначаются явно.

Проверка: Админ Алисы видит свою область и не выполняет команду Octoport. → Возврат/подарок одного продукта не меняет другой.

Готово: Единый рабочий UI без расширения полномочий и дублей денег.

## AL-M05. Поэтапное объединение выпускается без поломки Станции и старой воронки

Уже есть: Приняты AL-M01–04 и merge tests, есть rollback и согласие владельца на изменение публичных маршрутов.

Создаём: Canary → выбранные клиенты → расширение; сохранить issuer и legacy token contracts. Отдельно принять общую главную/продуктовую страницу Алисы, точные SEO redirects, старые campaign paths и атрибуцию. Не удалять свою главную только из-за общего входа; до этой приёмки она работает. Не объединять физически БД без отдельной необходимости.

Проверка: Старая Станция обновляет токен и отвечает; старое расширение сохраняет device/account. → Переход по прежней рекламе приводит к правильной Алисе. Откат UI не теряет новые платежи/удаления.

Готово: Доказанное постепенное объединение с сохранёнными клиентами, деньгами и публичными входами.
