# Алиса и Октопорт: самостоятельный запуск с последующим единым входом, ЛК и админкой

**Дата исследования:** 4 ноября 2026 года.  
**Статус:** архитектурная рекомендация по новому поручению владельца; не реализовано, не развёрнуто, не заменяет автоматически весь комплект v0.3.  
**Область:** сайт, идентичность, кабинеты, администрирование, доступ и безопасное последующее объединение двух продуктов. Аналитическая матрица не изменяется.  
**Главное требование:** Алиса может выйти в production раньше расширения; её работа не зависит от готовности, БД или релизов действующего Октопорта.

## 1. Рекомендуемое решение

Не создавать два несвязанных продукта с последующим массовым слиянием БД. И не подключать Алису сейчас к недописанному backend Октопорта.

Сделать два независимо развёртываемых продуктовых модуля с заранее совместимыми интерфейсами. Новый вход Алисы сразу оформляется как небольшой самостоятельный центр идентификации на стабильном адресе, способный позднее обслуживать оба продукта по OpenID Connect. Сначала к нему подключается только Алиса. Существующий вход, пользователи и доступ Октопорта остаются нетронутыми.

Позже Октопорт подключается к этому центру через адаптер, а общий кабинет и общая админка обращаются к обоим продуктовым API. Рабочие продуктовые базы, платёжные журналы и секреты при этом физически объединять не требуется.

**Это одна учётная запись человека и единые интерфейсы в целевом состоянии, но не одна бесконтрольно общая таблица прав, ключей и оплат.**

Невозможно честно обещать объединение без каких-либо работ: понадобятся адаптер авторизации Октопорта, подтверждённое связывание существующих пользователей, общие интерфейсы и миграционные испытания. Можно заранее избежать наиболее опасной части — переноса всех рабочих данных Алисы в новую схему и пересоздания клиентских подписок.

## 3. Почему выбрана именно эта схема

| Вариант | Последствия | Решение |
|---|---|---|
| Сейчас общий backend/БД действующего Октопорта | Алиса зависит от его допуска беты, схемы подписки, миграций и выпуска | Не рекомендован |
| Две полностью несвязанные копии с обещанием «потом сольём» | Возникнут дубли пользователей, несовместимые роли, платежи и интерфейсы | Не рекомендован |
| Независимые продукты, новый переносимый вход и явные связи идентичностей | Алиса запускается первой, позже добавляется второй потребитель входа и общий интерфейс | Рекомендован |

Способ постепенного переключения интерфейсов и сохранения старых компонентов соответствует идее поэтапной миграции через фасад, описанной Microsoft. Здесь предлагается использовать этот принцип для объединения, а не обещать обязательную замену всей старой системы. [W1]

Поддомен вашего домена — `alisa.octoport.ru`, а не `octoport.alisa`. Один корневой домен не требует одного сервера. Новый хост Алисы не следует проксировать через незавершённый backend Октопорта. У DNS/TLS и инфраструктуры всё равно есть собственные общие риски; независимость продуктов не означает независимость от владельца домена.

На текущей главной сайта слово «Алиса» уже относится к поддержке веб-чата расширением. В навигации необходимо явно различить «Расширение для ИИ-чатов» и «Голосовой аналитик для Яндекс Станции», чтобы не продавать разные продукты под одной неясной кнопкой.

## 5. Вход: самостоятельный сейчас, общий позже

### Сейчас

Новый identity-компонент отвечает за человека: неизменяемый идентификатор, подтверждённый контакт, вход, сессии, MFA и глобальные защитные действия. Он не управляет формулами, аналитикой, тарифами или ключами магазинов.

Кабинет и админка Алисы — отдельные клиенты этого входа. Нынешний Октопорт продолжает использовать собственную авторизацию. Нет синхронизации пользователей с БД Октопорта, доступа к ней или зависимости от его beta admission.

Нейтральное имя `id.octoport.ru` — подготовка к будущему, а не фактическое объединение нынешних продуктов. Внешне вход может быть оформлен как «Вход в Алису».

### Позже

Октопорт получает OIDC-адаптер. Проверенный внешний субъект отображается на существующий локальный user UUID. Старый accountId и device/auth/bootstrap-контракты расширения сохраняются, если их изменение отдельно не спроектировано и не принято. Не нужно менять первичные ключи пользователей во всех таблицах ради единого входа.

Новый вход пользователя впервые в другой продукт не должен автоматически включать коммерческую подписку, создавать магазин или расширять staff-права.

### Протокол

OpenID Connect для браузерного входа; Authorization Code с PKCE и проверкой state/nonce, issuer, audience, подписи и срока. Точные redirect URI, разные client IDs для кабинета и staff. Access token не заменяется ID token в API. Токены не публикуются в URL и не передаются в JavaScript ради произвольного cross-domain доступа. Точные параметры закрепляются контрактом и проверками выбранной библиотеки. [W2, W3]

Сессии продуктов — собственные host-only cookies. Не ставить общую cookie `Domain=.octoport.ru`, не делить session secret между приложениями, не разрешать `*.octoport.ru` без разбора через CORS. SSO обеспечивается проверенным переходом через центр входа, а не общедоступной cookie. [W4]

Отдельно определить «выйти из этого приложения» и «выйти везде». Изменение ролей и блокировка проверяются продуктовым сервером, а не только в старом ID token. Межсервисный отзыв имеет измеряемую задержку; при невозможности подтвердить актуальные критические полномочия запрещаются опасные действия, а не разрешается бесконечный старый доступ.

## 6. Данные: подготовить связи, не сливать строки

Предлагаемые логические сущности (это не готовая DDL-миграция):

| Сущность | Ответственность |
|---|---|
| `person_id` | Стабильный человек в новом центре входа, не email |
| `external_identity(issuer, subject)` | Уникальная проверенная внешняя идентичность и связь с человеком |
| `product_user_link(product_id, local_user_id, person_id)` | Связывание человека с локальным пользователем продукта |
| `product_account_link(product_id, local_account_id, workspace_id)` | Необязательное подтверждённое объединённое представление клиентских аккаунтов |
| `product_membership` | Продуктовые права человека в конкретном аккаунте |
| `product_entitlement` | Доступ именно к продукту по оплате, подарку и ограничениям |
| `staff_assignment(product_id, permission, scope)` | Административные полномочия в установленной области |

На старте нужны person, локальный аккаунт Алисы и стабильная связь между ними. Не надо заранее строить сложные организации/командные продажи; структура не должна запрещать их позже.

В стандартном OIDC стабильная идентичность — пара issuer + sub, а не email. Pairwise sub может отличаться для разных клиентов; нельзя самостоятельно считать sub одинаковым между клиентами. Центр входа/подтверждённая таблица связей разрешает соответствие. [W2]

### Правила связывания старого Октопорта

1. Совпадение email — кандидат на связь, а не разрешение объединить данные.
2. Пользователь подтверждает новый вход и контроль конкретного старого аккаунта, включая требуемую для него MFA.
3. Одноразовое подтверждение связывается с обоими точными ID, инициатором, браузерной сессией и сроком; replay и подмена цели отвергаются.
4. Записывается уникальная, журналируемая связь. Повтор не создаёт новую и не меняет оплаченные периоды.
5. Связывание личности не сливает организации/магазины. Несколько рабочих аккаунтов могут остаться отдельными с выбором в кабинете.
6. Спорные связи идут в отдельный процесс восстановления. Staff-права не объединяются по email.

Опасность автоматического связывания по совпавшим данным отдельно описана в документации Keycloak; это основание для требования подтверждения, а не рекомендация обязательно ставить Keycloak. [W5]

## 7. Платежи, доступ и статистика

С первого дня аналитика, grants, платежи, уведомления и audit несут контекст продукта. Предлагаемые стабильные product IDs: `alisa_market` и `octoport_extension`.

У каждого платёжного потока свой источник истины. Общий кабинет позднее показывает обе подписки и историю, обращаясь к продуктовым API. Он не записывает второй финансовый журнал с новыми ID и не делает повторную выдачу доступа при связывании.

Пример: у пользователя осталось 40 дней Алисы, а доступ к расширению отсутствует. После объединения остаются ровно 40 дней Алисы и отсутствие доступа к расширению. Бесплатные дни Алисы не становятся оплатой другого продукта.

Статистика общей админки — сводное представление с явно обозначенными источником и временем данных. Недоступный модуль отображается как недоступный, не как нулевая выручка. Команды возврата и выдачи дней выполняет владелец соответствующего журнала с product-scoped полномочиями и идемпотентностью.

Перенос merchant/кассы/продавца не следует из единого бренда. Старые оплаты и чеки остаются в исходном контексте. Единая покупка двух продуктов, общий тариф и единый платёжный backend — возможный отдельный этап, не условие объединения входа и ЛК.

## 8. Магазины, ключи и приватность

Возможен будущий общий экран магазинов: имя, площадка, продукт, доступность и ограничения. Но нельзя автоматически выгружать ключи расширения на сервер Алисы.

Для расширения бизнес-запросы и секреты остаются в предусмотренной им модели; для голосового продукта секреты доступны разрешённому серверному transport. Подключение одного реального кабинета во втором продукте требует отдельного подтверждения и своих прав. По совпадению названия магазина идентичность не выводится. [P6]

Данные спроса на шаблоны принадлежат Алисе. Общая админка позднее может показывать их через очищенный API. Не переносить финансовые ответы, сырые реплики или API-ключи в общую базу пользователей.

## 9. ЛК и админка: реальное объединение, а не две ссылки

Целевой ЛК содержит единый профиль, переключение продуктов/аккаунтов, обзор подписок и общую навигацию. Продуктовые разделы сохраняют собственные API, данные и цикл выпуска.

Целевая админка содержит единый вход, поиск пользователей, карточку человека со связанными аккаунтами и вкладки продуктов. Видимость и команды определяются product-scoped правами. Админ Алисы не получает автоматически управление расширением; общий суперадминистратор назначается отдельным защищённым действием.

Рекомендация для новых долгоживущих экранов — React/Next.js, поскольку эта семья уже используется в портале и админке Октопорта. Общие компоненты оформления и навигации можно выделять в версионированные пакеты. Изменение такого пакета не должно самопроизвольно менять обе установленные системы: фиксировать версии и обновлять отдельно.

Это уточняет прежнее предложение Django Admin: он может остаться внутренним техническим интерфейсом Алисы, но не должен быть единственным рабочим UI, который потом придётся целиком переписывать для общего кабинета. Django как backend не мешает объединению по API; Python-матрицу переписывать на TypeScript не требуется.

Для постепенного объединения страниц подходят маршрутизация nginx и схема Next.js Multi-Zones. Она поддерживает независимые приложения под общим адресом. Нужны уникальные маршруты/префиксы ресурсов; переход между зонами может перезагружать страницу. Сама маршрутизация не создаёт SSO и не объединяет права — это отдельные контракты. [W6]

Включать два приложения под один origin допустимо только после выравнивания их доверия и security-проверок: path не является полноценной границей безопасности. До этого сохранять разные origins. [W4]

## 10. Инструменты и пределы выбора

| Часть | Рекомендация |
|---|---|
| Существующий публичный сайт | Сохранить текущий nginx/static выпуск; изменение навигации отдельной поставкой |
| Новый кабинет/админка Алисы | React/Next.js, отдельные сборки и контракты; не копия backend Октопорта |
| Новый платформенный backend Алисы | Можно сохранить ранее предложенный Python/Django и PostgreSQL; продуктовые модули отдельно от identity |
| Новый вход | OIDC-совместимый компонент со стабильным issuer; библиотечная реализация, не собственная криптография |
| Первый кандидат для identity | Django + django-allauth: документация подтверждает email-code login и собственный OIDC provider |
| Альтернативный OIDC-компонент | Django OAuth Toolkit; выбрать один OIDC authority, не включать параллельно две реализации одних endpoints |
| Действующее ядро Алисы | Существующий Python-runtime через версионированный адаптер |
| Внешний фасад будущего общего кабинета | Ограниченные server-side API маршруты, отдельно к Алисе и расширению |

Поддержка email-code login и OIDC в allauth подтверждена документацией, не нашим стендовым испытанием. Перед фиксацией реализации проверяются совместимые версии, UUID subject, PKCE, scopes/audience, logout, refresh, staff MFA, ротация ключей и лимиты; выбирается один провайдер. Результат этой проверки — часть готового входа, а не новая платформа ради платформы. [W7, W8]

Не требуется сейчас вводить Kubernetes, Kafka, универсальную шину, единый commerce-service или полноценный dynamic microfrontend framework. Не нужно устанавливать большой IAM-стек поверх текущей Alisa без ресурсной проверки.

## 11. Связка с Яндексом — отдельный контракт

Браузерный общий вход и разрешение навыку обращаться от имени пользователя — разные вещи. Яндекс Диалоги используют authorization code, access token и refresh token по зарегистрированным адресам. [W9]

Существующие endpoints, token store и отображение токена на tenant сохраняются до проверенного перехода. Новый браузерный вход не должен автоматически инвалидировать связь Станции. Смена issuer, ключей или реализаций старого токена не выполняется как побочный эффект переноса сайта.

Гарантию «никому не придётся перепривязывать» заранее дать нельзя. Обязательная цель миграционного теста — сохранить текущие связи. Для действительно несовместимого остатка необходим явный ограниченный сценарий повторной привязки без потери аккаунта, магазинов, оплаты и подарков. Яндекс отдельно описывает повторные запросы обновления токена и прекращение авторизации при неуспехе; endpoint нельзя заменить обычным HTML-redirect. [W10]

## 12. Практическая последовательность сейчас

Эта последовательность дополняет начало функционального roadmap, а не запускает разработку текущим исследованием.

| Шаг | Готовый проверяемый результат |
|---|---|
| N01. Отдельный сайт Алисы | На тестовом origin открываются страница продукта, справка и вход; приложения Октопорта не затронуты |
| N02. Вход и настоящий первый ЛК | Регистрация по коду → собственный пустой кабинет → выход → повторный вход в тот же аккаунт; identity и продуктовый account различаются |
| N02-совместимость | Второй синтетический OIDC-клиент проверяет будущую совместимость без доступа к данным Алисы. Это доказательство протокола, не готовности Октопорта |
| N03. Отдельная рабочая админка | Защищённый staff-вход, список реальных тестовых клиентов, подаренный доступ и аудит в области alisa_market |
| N04. Полный самостоятельный продукт | Магазины, связка Яндекса, матрица, отчёты, gaps, поддержка, платежи и эксплуатация — по функциональным шагам v0.3 с новыми границами идентичности |
| N05. Независимый production Алисы | В изолированном испытании все Octoport backend-зависимости отключены, а новый пользователь Алисы может войти, подключиться и получить услугу |

Настройка identity не сдаётся вместо кабинета. В N02 обязательны и экран, и сохранённый аккаунт, и вся наблюдаемая цепочка входа. Изолированная проверка будущего SSO не требует незавершённого продукта Октопорт.

## 13. Последовательность будущего объединения

| Шаг | Проверяемый результат и сохранение старого пути |
|---|---|
| M01. Адаптер identity Октопорта в staging | Новый OIDC-вход отображается на существующий local user/account; старые device IDs и bootstrap accountId не меняются |
| M02. Подтверждённое связывание | Пользователь контролирует оба аккаунта, связь создаётся один раз; одно совпадение email ничего не объединяет |
| M03. Общий ЛК | Один вход, общий профиль и два продуктовых раздела; исторические оплаты/подарки отображаются без повторного предоставления |
| M04. Общая админка | Единая карточка и действия по продуктам; staff Алисы не управляет расширением без отдельного права |
| M05. Поэтапный выпуск | Тестовые аккаунты → ограниченная группа → расширение охвата; прежние адреса доступны на переходе, маршрутизация откатывается отдельно |
| M06. Необязательная дальнейшая консолидация | Только после стабильной работы оценить единые магазины/биллинг/организации; физическое слияние БД не обязательно |

У каждой записи один владелец. Не вводить бессрочную двустороннюю синхронизацию user/payment-таблиц и не писать одну оплату в два журнала. Связи и административные действия идемпотентны; сервисные события используют устойчивый журнал доставки. Откат интерфейса не восстанавливает старую финансовую БД поверх новых платежей.

Пока Октопорт не готов, этапы M01–M06 не являются зависимостями production Алисы. Общий центр входа после подключения обоих станет общей зависимостью для новых входов: его эксплуатацию и резервирование надо принять отдельно. Независимость бизнес-модулей не превращает SSO в систему без общей точки ответственности.

## 14. Критерии доказанного объединения

Все проверки ниже — будущие, NOT_RUN.

| ID | Проверка | Обязательный итог |
|---|---|---|
| MERGE-01 | API/БД старого Октопорта недоступны в стенде | Алиса работает по своим разрешённым сценариям; нет скрытого обращения к старому auth |
| MERGE-02 | Один человек, одинаковые email в двух продуктах | До подтверждения связи аккаунты не смешиваются |
| MERGE-03 | Разные email, доказанный контроль обоих аккаунтов | Связь возможна без изменения исходных account IDs |
| MERGE-04 | Два браузера повторяют подтверждение связи | Одна корректная связь, конфликт цели отклонён, audit сохранён |
| MERGE-05 | Разные организации одного человека | Единый вход не объединяет их данные или владение |
| MERGE-06 | У Алисы 40 дней доступа, у расширения нет | После объединения состояния неизменны |
| MERGE-07 | У двух продуктов оплаты, подарки и возвраты | Нет дублей и потери сроков, суммы сводки подтверждены первичными журналами |
| MERGE-08 | Вход общим staff с правами только Алисы | Операции управления расширением запрещены самим API |
| MERGE-09 | Локальная блокировка клиента в Алисе | Не блокирует иной продукт без отдельного глобального решения |
| MERGE-10 | Глобальный защитный отзыв | Соблюдена заданная и измеренная политика сессий обоих продуктов, нет бессрочного stale access |
| MERGE-11 | Ранее привязанная Станция после SSO-выпуска | Тот же tenant, корректные refresh и получение результата; несовместимость не скрыта |
| MERGE-12 | Старая поддержанная версия расширения | Сохранены account/device/bootstrap и принятые границы автономности |
| MERGE-13 | Общая карточка магазина | Никакой передачи ключа расширения на Alisa без отдельного подтверждения |
| MERGE-14 | Отказ одного backend за общим кабинетом | Другой раздел доступен, недоступный не отображается как пустой или нулевой |
| MERGE-15 | Откат общей оболочки после новых оплат | Платежи, grants, связки и отзывы не теряются и не повторяются |
| MERGE-16 | Куки соседнего поддомена и поддельный callback | Не дают чужой сессии; issuer/audience/state/nonce/PKCE проверены |
| MERGE-17 | Обновление общей UI-библиотеки | Вторая установленная система не обновляется без собственного выпуска |
| MERGE-18 | Удаление продукта и глобальной личности | Области удаления различены, нет случайного стирания оплаченного другого продукта |

## 15. Изменения к прежней документации

Требование самостоятельности сохраняется. Уточняется его смысл: независимый продукт сейчас, но не несовместимый с будущей общей идентичностью.

Потребуют согласованной новой редакции: SPEC (границы независимости и продуктовые права), ARCHITECTURE/ADR (identity и композиция интерфейсов), DATA_MODEL (постоянные ID и связи), API (отдельные audiences и продуктовый контекст), UX (общий будущий профиль и роли), SECURITY (host-only cookies и связывание), BILLING (продуктовый журнал), MIGRATION/ACCEPTANCE (MERGE-01–18), первые шаги ROADMAP.

Не отменяются: один тариф Алисы с разными сроками, бесплатные периоды, неограниченное тарифом число магазинов, обязательный сбор неподдержанных вопросов, каталог и квалификация матрицы, изоляция данных и независимость от B22 браузерного расширения.

Сейчас **не** выполнены правка всех файлов v0.3, публикация в GitHub, создание DNS, установка новой авторизации, перенос БД или тесты совместимости. Документ фиксирует основанную на обследовании рекомендацию для следующей редакции.
