# Домены и готовое окружение для исполнителя · v0.5

**Историческая проверка: 04.11.2026, 08:10–08:13 UTC. В v0.5 заново не повторялась. Инструкция, не отчёт о внесённых изменениях.** Ни DNS, ни сертификаты, ни настройки nginx этим документом не созданы. Передача готовых адресов состоит из двух действий: владелец добавляет записи, инфраструктурный исполнитель настраивает на сервере новые hosts и HTTPS. Только потом прикладной исполнитель принимает ENV-00 и начинает AL-S00.

## 1. Что проверено, а что предложено

Через подключённое устройство **Alisa** в 08:10 UTC прочитан внешний IPv4 интерфейса `185.244.51.141`; `alice-lab.octoport.ru` разрешается в тот же адрес. `octoport.ru` разрешается в `78.17.68.165` (существующий Easyscript). DNS-зона обслуживается `ns1.adminvps.ru`, `ns2.adminvps.net`, `ns3.adminvps.ru`, `ns4.adminvps.net`. В 08:13:37 UTC прямой запрос к `ns1.adminvps.ru` вернул авторитетный **NXDOMAIN для всех шести новых имён**.

Это подтверждает место редактирования DNS и свободные на момент проверки имена, но не владение учётной записью панели или готовность мощности сервера. Перед записью сверить назначенный IP в панели VPS. Если уже выбран другой хост — заменить value у шести строк и в паспорте, а не направлять часть одного окружения на случайные адреса.

**Базовый вариант подготовки сейчас:** шесть имён направить на текущий ingress Alisa `185.244.51.141`, не через Easyscript. Здесь подготовить только отдельные virtual hosts/HTTPS. Перед запуском приложения увеличить ресурсы Alisa с сохранением IP либо развернуть отдельный согласованный хост и сменить эти шесть A-записей. Прежний alice-lab не переносить попутно. Смена IP не требует смены доменных имён/issuer.

Наблюдаемые ресурсы Alisa: 1 CPU; MemTotal 984740 kB (~962 MiB); MemAvailable 386576 kB на момент измерения. **ENV-00 не получает INFRA_READY по одному DNS на такой машине.** Начальный ориентир оценки нового стека — от 2 vCPU/4 GiB, с отдельной сборкой; это не гарантия достаточности, нужны замеры и лимиты, резерв для действующей матрицы. Ресайз/новый сервер и возможная перезагрузка — отдельное разрешённое инфраструктурное действие.

**Не менять и не удалять:** `@/octoport.ru`, `www`, `app`, `api`, `mail`, `alice-lab`, существующие MX/SPF/DKIM/DMARC/CAA/NS/SOA и сертификаты. Не переопределять весь домен на IP Алисы. Не создавать отдельную DNS-зону `alisa.octoport.ru` с новой делегацией: достаточно шести записей в существующей зоне.

## 3. Действия владельца в панели DNS

1. Войти в аккаунт, управляющий **зоной DNS на AdminVPS**. Это может быть DNSmanager/панель услуги, а не страница регистрации домена. Факт NS указывает провайдера DNS; точный вид закрытой панели в этом исследовании не просматривался. Если в личном кабинете нет редактирования ресурсных записей — использовать готовое поручение поддержке ниже, не менять NS.
2. Открыть существующую зону **octoport.ru** и список ресурсных записей. Экспортировать/сохранить снимок текущей зоны до правок.
3. По очереди добавить шесть A-записей по таблице. В поле «Имя/Host» обычно вводится короткое имя `alisa`. Если интерфейс требует FQDN — `alisa.octoport.ru.`. Не получить `alisa.octoport.ru.octoport.ru`: проверить итоговую строку.
4. Значение — только IPv4 `185.244.51.141`, без `https://`, пути и порта. TTL = 300, если панель позволяет; иначе её допустимое стандартное значение. TTL — время кэширования, а не обещание мгновенного появления.
5. Не добавлять AAAA, пока IPv6 не назначен и не проверен для nginx/ACME. Не добавлять CNAME поверх A и не включать произвольный proxy/CDN ради этой настройки.
6. Сохранить каждую запись. Проверить новые строки и неизменность старых. Зафиксировать время/снимок без паролей и API-токенов.
7. Выполнить DNS-проверки раздела 6. До корректного ответа authoritative DNS не повторять выпуск сертификатов многократно.

**Текст для поддержки/администратора DNS:**

> В существующей зоне octoport.ru добавьте только шесть A-записей: alisa, alisa-admin, id, alisa-stage, alisa-admin-stage, id-stage. Значение каждой 185.244.51.141, TTL 300 (либо минимальный поддерживаемый). Не меняйте @, www, app, api, mail, alice-lab, NS и почтовые записи. Wildcard/AAAA/CNAME не создавать. Перед изменением проверьте отсутствие конфликта; после пришлите таблицу добавленных имён, время и ответы authoritative DNS. Это только DNS-поручение, не перенос существующих сайтов.

Текущий IP проверен 04.11.2026; при смене hosting target до исполнения замените значение во всём поручении. Файлы `infra/dns-records.csv` и `.zone.example` содержат тот же набор. Это **фрагмент добавления**, не файл для перезаписи всей зоны.

## 4. Что делает инфраструктурный исполнитель на сервере

### 4.1 Безопасная подготовка

Через штатный список устройств выбрать текущую Alisa, сверить hostname/IP, nginx и занимаемые порты. Сохранить адресную копию изменяемых файлов; не снимать locks матрицы, не трогать её службы/БД. Создать отдельные config files и webroot только новой платформы. Не использовать app/api конфиги Easyscript.

В `infra/nginx/01-http.conf.example` дан образец шести **точных server_name** на 80 с отдельным ACME webroot `/var/www/alisa-platform-acme`. На прочие маршруты временно 503, не прокси в alice-lab. Подготовить эти vhosts до публикации новых DNS, чтобы новые имена не показывали чужой default site. Добавить только в принятый include-каталог nginx; не перезаписывать весь `/etc/nginx`.

Перед каждым применением: `sudo nginx -t`. Только при успехе — `sudo systemctl reload nginx`. Не делать restart, не останавливать nginx для standalone ACME, не удалять старые сертификаты. Если тест/reload неуспешен — восстановить только собственный изменённый файл и повторить проверку; не откатывать чужие параллельные правки.

### 4.2 DNS → сертификаты

Внешние TCP 80/443 должны доходить до ingress. HTTP-01 использует **порт 80** и `/.well-known/acme-challenge/`; этот путь не закрывается CAPTCHA, Basic Auth, VPN-only или редиректом на логин. Для закрытого ingress нужен отдельно спроектированный автоматизированный DNS-01, а не ручной бессрочный сертификат.

Использовать уже поддерживаемый на сервере ACME-клиент. Не устанавливать вторую конкурирующую систему сертификатов без ревью. Для Certbot вариант без автоматической перезаписи nginx:

```bash
# Только после разрешённой подготовки 80/vhosts, webroot и DNS.
# ADMIN_EMAIL — ваш служебный контакт, передаётся приватно, не пароль.
: "${ADMIN_EMAIL:?set service contact email}"
for h in alisa.octoport.ru alisa-admin.octoport.ru id.octoport.ru \
         alisa-stage.octoport.ru alisa-admin-stage.octoport.ru id-stage.octoport.ru; do
  sudo certbot certonly --webroot -w /var/www/alisa-platform-acme \
    --cert-name "$h" -d "$h" --email "$ADMIN_EMAIL" --agree-tos
  # При ошибке остановиться и выяснить причину; не повторять бесконечно.
  test "$?" -eq 0 || break
done
```

Перед этим проверить CAA и наличие действующего ACME клиента. Существующие root CAA при проверке не найдены; это не разрешение менять их без причины. При новой CAA-политике не ослаблять ограничения молча. Секрет DNS API не требуется для HTTP-01 и не передаётся разработчику приложения.

### 4.3 HTTPS без ещё не написанного приложения

После появления файлов сертификатов добавить **отдельный TLS vhost для каждого имени** из `infra/nginx/02-https.conf.example`. HTTP перенаправляет на HTTPS, но ACME остаётся доступен. На `/__setup/ready` — 200 с точным host/environment и меткой `ALISA_PLATFORM_PREFLIGHT_V04`. Остальные маршруты временно 503 (stage root может 403 по политике). `Cache-Control: no-store`, `X-Robots-Tag: noindex`. Никаких клиентских данных и выдачи рабочей готовности приложения.

В nginx настроить журнал без raw query string, cookie и Authorization. Корневой HSTS `includeSubDomains/preload` не менять. Не ставить `Domain=.octoport.ru`. При развёртывании приложений каждый новый host получает свой upstream; отдельный API-host не нужен. Маркер остаётся только как проверка маршрутизации, не health продукта.

Проверить автоматическое renewal, ограниченно по каждому **новому** cert-name: `sudo certbot renew --cert-name <новое-имя> --dry-run`. Не запускать экспериментальную массовую правку всех старых сертификатов. Проверить deploy hook: после успешного обновления сертификата nginx выполняет безопасный reload. Сохранить расписание/контроль истечения; выпуск не считается готовым без renewal.

### 4.4 Изоляция stage

Stage имеет отдельные процессы/DB roles/БД/ключи/OIDC clients/payment sandbox и почтовую тестовую аудиторию. Не копировать production данные ради проверки. Пользовательские stage страницы закрыть разрешённой командой по VPN/IP/именному доступу. `noindex` не заменяет авторизацию.

Не вешать общую Basic Auth на все будущие протокольные URLs: это сломает OAuth/Яндекс/payment webhooks. Точные внешние callbacks/webhooks открываются только вместе с реализацией соответствующего шага, на них остаётся собственная протокольная аутентификация/лимиты. Initial `/__setup/ready` и ACME могут быть публичны: в них нет данных. Проверки с телефона/OAuth входят в отдельную разрешённую stage-политику.

## 6. Как проверить готовность

**На Windows (PowerShell):**

```powershell
$hosts = 'alisa','alisa-admin','id','alisa-stage','alisa-admin-stage','id-stage'
foreach ($h in $hosts) {
  Resolve-DnsName "$h.octoport.ru" -Type A -Server ns1.adminvps.ru
}
curl.exe --fail --show-error https://alisa.octoport.ru/__setup/ready
```

**На Linux:**

```bash
for h in alisa alisa-admin id alisa-stage alisa-admin-stage id-stage; do
  dig @ns1.adminvps.ru +short "$h.octoport.ru" A
  dig @1.1.1.1 +short "$h.octoport.ru" A
  dig @8.8.8.8 +short "$h.octoport.ru" A
  curl --fail --show-error --max-time 10 "https://$h.octoport.ru/__setup/ready"
done
```

DNS ожидается согласованный `185.244.51.141` либо явно утверждённый новый IP. TLS должен проходить обычную проверку имени/цепочки **без `-k`**. Ответ каждого host обязан называть именно его, а не чужой site/lab. Проверить также HTTP→HTTPS, отсутствие неожиданных AAAA/CNAME, сертификаты SAN/expiry, изоляцию stage и неизменность старых сайтов.

`python tools/check_domains.py --expected-ip 185.244.51.141 --output domains-check.json` автоматизирует только read-only DNS/HTTPS/marker/redirect проверку. Он не создаёт записи/сертификаты, не проверяет ресурсы и не объявляет всё INFRA_READY. Его локальная DNS-проверка не заменяет authoritative + независимые resolvers выше.

## 7. Когда передавать roadmap разработчику

**DNS_READY:** все шесть имён возвращают согласованный IP, существующие записи не повреждены.
**HTTPS_READY:** корректный сертификат/автопродление и правильный host marker для каждого имени, нет чужого default vhost.
**INFRA_READY:** подтверждены пригодные ресурсы, доступ, build-host, разрешённые корни и возможность создать отдельные DB/роли. Приложения, CI, миграции и воспроизводимый выпуск создаёт AL-S00; почта нужна до первого использования на AL-S01.

Ни один из этих статусов не означает готовую регистрацию, admin или оплату. Они позволяют разработчику сразу начать AL-S00 на подготовленных адресах. Ссылка на существующий публичный сайт Октопорта вместо этих проверок не принимается.

Чек-лист/поручение в [HANDOFF_ENVIRONMENT.md](HANDOFF_ENVIRONMENT.md). Статус этого пакета: **NOT_READY / NOT_RECHECKED.** NXDOMAIN относится к чтению 04.11.2026 08:13 UTC; актуальное состояние DNS/TLS проверяет инфраструктурный исполнитель.
