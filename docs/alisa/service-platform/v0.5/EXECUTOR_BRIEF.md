# Поручение исполнителю · v0.5

Работай над самостоятельной платформой «Октопорт Маркет — Алиса» в существующем репозитории MaksimUnimax/runtime-fixtures. Исходная документальная ветка alisa; перед стартом перечитай её фактический HEAD. Платформа не является расширением Octoport и не должна менять его 33 блока.

Прими полный комплект v0.5, проверь manifest и документационный валидатор. Исходный пакет 0.4 больше не является очередью. Назначь автора и независимого проверяющего, зафиксируй base SHA и ветку реализации. Не выдавай исторические тесты матрицы за новую приёмку платформы.

Сначала проверь ENV-00: домены/TLS, разрешённый stage, мощности, build-host и доступы. Затем строго **AL-S00 → AL-S01 → … → AL-S24**. Нулевой шаг — отдельный runnable technical skeleton по FOUNDATION_00 и SOURCE_LAYOUT: из чистой копии собираются/ставятся процессы и отдельные БД, реальная инженерная проба проходит UI/API/DB/worker, переживает повтор/restart/rollback. Одни директории, диаграммы, README и статический health не сдавать.

После принятия 00 создай собственную главную Алисы и рабочую подтверждённую заявку; после 01 — email/OIDC вход вместе с настоящим защищённым ЛК; затем отдельную admin. Каждая предметная поставка включает UI, backend, persistence, права, интеграцию, ошибки и доказательства. В ранних тестах не вызывать ещё не созданные публикации, платежи и задания.

Код платформы размещай в products/alisa, независимый workspace/locks/release. UI Next.js, platform Python/Django, отдельный library identity, PostgreSQL — по принятому направлению и квалифицированным версиям. Не копируй чужие конфиги/секреты и не делай неявных импортов из старого backend.

Нынешние сайты/app/api/admin Octoport на Easyscript, Business Bridge, текущие alice-lab OAuth/credentials и рабочую матрицу не изменяй попутно. С ядром работай через закреплённую версию RuntimePort и одного согласованного владельца adapter. Не строй вторую матрицу для удобства кабинета.

Identity готовь для будущего второго продукта, но сейчас без его подключения. Product IDs, локальные аккаунты, grants, платежи и staff права изолированы. Совпадение email не объединяет аккаунты. Ключи расширения не переносятся в Алису. Будущую AL-M очередь не запускай до отдельного допуска.

На каждом шаге передавай commit/artifact hash, адрес и версию, инструкции, конкретные входные данные, действия/ожидания, реальные эффекты и safe evidence. Авторский тест не называй независимым. При блокировке укажи точный недостающий вход, действия по устранению и доступную независимую работу; не подменяй её PASS. Публичные клиенты/рассылки/production/payments требуют относящегося разрешения, а не наличия документа.

Публикация документации в alisa выполняется отдельно инструментом tools/publish_docs.py либо разрешённым GitHub write. После неё сохранить commit и проверенный URL. Ни локальный ZIP, ни начатая передача не означают сохранения в GitHub.
