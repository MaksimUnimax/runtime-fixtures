# AL-S00 · работающий архитектурный фундамент

**Статус: NOT_STARTED. Приёмка: NOT_RUN.** Это конечная инженерная поставка перед сайтом. Она следует за инфраструктурным ENV-00, а не заменяет его.

## 1. Результат и границы

Другой исполнитель из чистой копии commit собирает артефакт, устанавливает его на stage, выполняет технический путь **браузер → BFF → platform API → PostgreSQL → platform worker → результат**, перезапускает компоненты и возвращает прежний совместимый выпуск без потери записи.

На основе этой системы дальше создаются главная, ЛК и админка. Набор папок, красивая диаграмма, статический `/health` или README с ещё не существующими командами **не закрывают AL-S00**. Вместе с тем не нужно заранее реализовывать все бизнес-модули — это увеличило бы первый блок без проверяемой необходимости.

План минимального исполняемого каркаса использует подход walking skeleton; организация архитектурного описания — arc42/C4. Это инженерные основания, а не внешнее доказательство готовности нашей реализации. См. METHOD_AND_SOURCES.

## 2. Реальные входы

ENV-00 предоставляет согласованные мощности и доступ, три stage-host с TLS, build-host/runner, право создать platform/identity БД и отдельные сервисные роли. DNS всех шести имён и production setup-страницы готовятся отдельно. Нет требования заранее иметь приложение, его миграции или новый CI — это выход AL-S00.

SMTP нужен для первой воронки AL-S01, но не для technical probe. Рабочий marketplace-ключ, платёжный договор, завершённая матрица, готовый Октопорт или перенос Яндекс OAuth для этого шага не нужны.

## 4. Инженерный сценарий

Только stage, за отдельным инженерным допуском через защищённый ingress. `FOUNDATION_PROBE_ENABLED` явно включает тест. В production маршрут всегда отсутствует. Payload ограничен `probe_id` UUID и фиксированным `kind=foundation-v1`; произвольные строки, URL, SQL, пути и команды не принимаются.

1. Страница `/__engineering` отправляет UUID через собственный BFF. Это помеченная техническая диагностика, не макет ЛК.
2. BFF проверяет маршрут и передаёт собственную service identity. Пользовательский заголовок не становится доверенным. Прямой upstream обход запрещён.
3. API атомарно записывает `foundation_probe` и задачу. Уникальный ключ защищает от дублей. Ответ `ACCEPTED` отдаётся только после commit.
4. Worker сохраняет `PROCESSED` для того же ID. Никаких бизнес-вызовов и обращения к матрице. Это техническая платформенная очередь, не второй executor маркетплейсов.
5. UI читает ID/состояние/среду/версию. После остановки и перезапуска тот же результат доступен. Технический payload имеет короткий TTL; секрета в нём нет.
6. Отключение stage БД даёт readiness 503; liveness проверяет процесс, а не всю систему. Функция не сообщает ложный успех.

Инженерный допуск — не продуктовый ADMIN и не обход будущего login. Например, допускается отдельный Basic поверх TLS с дополнительным IP/VPN ограничением. Механизм фиксируется ENV-00. После приёмки write-проба выключается; в CI запускается в временной среде.

## 5. Identity и DB foundation

Identity получает отдельные процесс/DB/секреты и стабильную UUID-модель человека. В Django `AUTH_USER_MODEL` выбирается до первых auth migrations, не после появления клиентов. Это техническая подготовка модели, не реализованная регистрация. Email-code/MFA/OIDC endpoints не имитируются: полный вход проверяется в AL-S02.

Platform DB не читает identity DB. Cross-DB FK и общий superuser запрещены. Локальные tenant/membership и подтверждённая связь `(issuer, sub)` появляются на 02. Миграции будущих billing/catalog/stores не требуется создавать на 00.

Runtime adapter имеет версионированный контракт и честный `RUNTIME_NOT_CONNECTED` до интеграции. Тестовый adapter строго помечен synthetic. Ни один не объявляется настоящим отчётом. SQLite матрицы и текущие marketplace credentials не переносятся.

## 6. Что передать на тестирование

Точный commit, safe diff защищённых путей, toolchain/locks, artifact SHA256, manifest, DB migration heads, перечень процессов и адреса, пошаговые команды, фактические probe/correlation IDs, результаты 18 сценариев и r1→r2→r1, доказательство default deny/DB isolation и неизменности текущих служб.

Проверяющий не ищет потерянный конфиг и не пишет deployment script. Квитанция FOUNDATION_READY относится только к этой сборке и среде. Авторский локальный прогон не переименовывается в независимую приёмку.

## 7. Не входит и не блокирует

Нет продуктовых экранов, оплаты, новой матрицы, общего CRM, Kubernetes/Kafka, своей криптографии, массового переноса людей и public production. Сайт — 01; полный login+ЛК — 02; staff — 03; магазины — 05; отчёт — 07; деньги — 20. Существующий Octoport и Business Bridge остаются нетронутыми.

При отсутствии stage допускается подготовка кода и локальных доказательств, но AL-S00 не получает окончательный PASS. Нехватка ресурсов или разрешения записывается конкретным blocker, а не маскируется зелёными документальными проверками.
