## AL-S00. Работающий архитектурный каркас и воспроизводимый выпуск

**Предыдущий:** ENV-00. **Статус:** NOT_STARTED. Автор/проверяющий назначаются перед стартом.

**Уже есть:** ENV-00 принят как инфраструктура: разрешённые stage-адреса/TLS, ресурсы, build-host, доступ и возможность создать отдельные БД. Готовые приложения, CI и миграции на входе не требуются — их создаёт этот шаг.

**Создаём:**
1. Создать отдельный workspace products/alisa с приложениями web/admin, сервисами platform/identity, contracts, tests и infra по SOURCE_LAYOUT.md. Зафиксировать зависимости, владельцев, правила импортов и места хранения данных.
2. Поднять настоящие web/admin/platform/identity и platform worker на изолированном stage. Создать отдельные platform/identity БД, runtime/migration роли и начальные миграции; UUID-модель identity выбрать до первой auth-миграции.
3. Реализовать закрытую инженерную пробу: браузер → BFF → platform API → запись UUID в PostgreSQL → worker → результат. Не использовать матрицу и внешние бизнес-API; не подменять этот путь статическим health.
4. Реализовать сборку из чистого checkout по lockfiles, CI-проверки, артефакт с manifest, установку, readback версии и откат совместимого кода. Не собирать тяжёлый стек рядом с рабочей матрицей.
5. Проверить повтор запроса, restart, отказ БД, межбазовую изоляцию, отсутствие секретов и закрытость будущих личных маршрутов. Production не принимает инженерную пробу.
6. Передать проверяющему commit, artifact hash, команды, stage URL, migration heads и безопасные доказательства всех 18 сценариев. Получить FOUNDATION_READY до шага 01.

**Проверяем:**
1. Из чистого checkout собрать и установить точный артефакт на изолированный stage.
2. Открыть инженерную страницу через HTTPS, создать UUID-пробу и показать одинаковый ID в UI/API/БД/worker.
3. Остановить worker после принятия, запустить снова и получить один результат; повтор запроса не создаёт второй эффект.
4. Установить совместимый r2 и вернуть r1: версия подтверждена, проба сохранена.
5. Без допуска проба запрещена; в production отсутствует; при недоступной БД readiness = 503.

**Готово:** Другой исполнитель по runbook воспроизводит сборку, установку, настоящий технический путь, restart и rollback без доработки исходников. Папки, схема, HTML-макет и один зелёный /health не закрывают шаг.

**Не входит:** Не реализуются публичный сайт/воронка, регистрация, ЛК, бизнес-аналитика, деньги, OIDC вход или общая система обоих продуктов. Старые серверы и исходники не меняются.

**Внешние входы:** Только инфраструктура ENV-00. Финальная матрица, merchant, SMTP и новый OAuth навыка не нужны для технической пробы.

**Пути:** `products/alisa/`, `.github/workflows/alisa-platform-ci.yml`.
**Производит:** source_layout, technical_stage, platform_db_foundation, identity_shell, runtime_adapter_boundary, technical_probe, build_release_pipeline, foundation_default_deny, foundation_receipt, release_identity, safe_runtime_logs.
**Потребляет:** инфраструктуру ENV-00.

**Сценарии:** AL-T00-01, AL-T00-02, AL-T00-03, AL-T00-04, AL-T00-05, AL-T00-06, AL-T00-07, AL-T00-08, AL-T00-09, AL-T00-10, AL-T00-11, AL-T00-12, AL-T00-13, AL-T00-14, AL-T00-15, AL-T00-16, AL-T00-17, AL-T00-18. Подробности: [TEST_PLAN.md](TEST_PLAN.md).

**Регрессия:** Чистая сборка, stage технический E2E, отрицательные границы и точный readback. Минимальная техническая регрессия при каждом выпуске; доменное восстановление на 17, финансовое на 23.

## AL-S02. Регистрация через будущий общий вход и первый настоящий ЛК Алисы

**Предыдущий:** AL-S01. **Статус:** NOT_STARTED. Автор/проверяющий назначаются перед стартом.

**Уже есть:** Шаг 01 принят. Готовы отдельные HTTPS origins сайта и identity из ENV-00, безопасная доставка email и отдельные test credentials. OIDC-реализация фиксируется совместимой версией в рамках шага, не отдельным абстрактным результатом.

**Создаём:**
1. Создать защищённый /app: свой профиль, пустое состояние, статус доступа, выход. Регистрация обязательно заканчивается здесь; отдельный auth API без кабинета не закрывает шаг.
2. Ввести самостоятельный identity authority на id-stage (позже id.octoport.ru), product_id=alisa_market, постоянный person_id и локальные user_id/tenant_id. Подтверждённый email — контакт, не первичный ключ. Старые users/account Октопорта не читаются и не меняются.
3. Реализовать путь /auth/start → библиотечный OIDC Authorization Code + PKCE → /auth/callback → host-only session → /app. Проверять issuer/audience/signature/state/nonce/expiry; токены хранит BFF, не localStorage. Адрес issuer фиксируется; не менять его при будущем объединении.
4. Первый кандидат authority — django-allauth OIDC; подтвердить email-code, MFA, subject, logout и rotation. При несовместимости выбрать один альтернативный зрелый OIDC provider отдельным ADR, не писать свой криптопротокол и не держать два issuer одной среды.
5. Проверить второй синтетический OIDC-клиент без данных и прав Алисы. Пара (issuer,sub) уникальна для клиента; совпадение email/разных pairwise sub не является автоматическим merge. Это тест протокола, не подключение недописанного Октопорта.
6. Заменить информационный маршрут входа на работающий. Перенести безопасную атрибуцию воронки по короткому непрозрачному flow ID в серверном состоянии; не передавать контакты/UTM/ключи через OAuth URL. Привязать свою заявку только после проверки контакта.

**Проверяем:**
1. С главной Алисы открыть вход, получить код на identity origin и попасть в собственный /app.
2. Выйти и войти снова: тот же person и тот же tenant; второй клиент не видит данные первого.
3. Повторить callback, подменить state/issuer/audience, попробовать чужой return_to: безопасный отказ.
4. Войти во второй тестовый OIDC-клиент: идентификация работает, доступ к данным/деньгам Алисы не появился.
5. В стенде запретить исходящие обращения к API/БД/auth нынешнего Октопорта; регистрация и вход Алисы продолжают работать.

**Готово:** Работает единый наблюдаемый путь от собственной главной через независимый identity до реального ЛК. Identity подготовлен для второго приложения, но Октопорт ещё не подключён.

**Не входит:** Нет автоматического объединения с Октопортом и нет регистрации клиента в его beta admission.

**Внешние входы:** Приёмник тестовой почты — локальная проверка. Отдельно проверить доставку кода на контролируемую настоящую почту до реальных клиентов.

**Пути:** `products/alisa/apps/web/`, `products/alisa/services/identity/`, `products/alisa/services/platform/src/alisa_platform/accounts/`.
**Производит:** customer_identity, customer_session, private_home, email_outbox, consent_records, oidc_authority, product_identity_links, oidc_client_compatibility, funnel_identity_handoff.
**Потребляет:** web_origin, guest_entry, identity_shell, runtime_adapter_boundary.

**Сценарии:** AL-T01-01, AL-T01-02, AL-T01-03, AL-T01-04, AL-T01-05, AL-N02-01, AL-V04-05, AL-V04-06, AL-V04-07, AL-V04-08, AL-V04-09. Подробности: [TEST_PLAN.md](TEST_PLAN.md).

**Регрессия:** Повторить путь от главной через кабинет до последней уже поставленной функции; на новой сборке проверить затронутые прежние сценарии.

## AL-S04. Бесплатный период: админ выдаёт, клиент видит доступ

**Предыдущий:** AL-S03. **Статус:** NOT_STARTED. Автор/проверяющий назначаются перед стартом.

**Уже есть:** Есть пользовательский кабинет и карточка клиента в админке: шаги 02–03.

**Создаём:**
1. Добавить журнал предоставлений GIFT/COMPENSATION, расчёт границ и страницу «Доступ» в кабинете.
2. Сделать выдачу, предварительный просмотр, ограничение staff, отзыв допустимого остатка, массовую выдачу и безопасные повторы.
3. Отобразить основание, дату окончания, историю и уведомление. Истечение меняет видимый статус; не создавать фиктивный платёж.
4. Каждый grant и его дедупликация имеют product_id=alisa_market. Поле paid на общей личности запрещено. В карточке клиента видно, что подарок относится только к Алисе.

**Проверяем:**
1. Администратор выдаёт семь дней конкретному клиенту.
2. Клиент обновляет кабинет и видит дату и основание GIFT.
3. Повтор того же действия не меняет срок второй раз.
4. Проверить истечение, отзыв подарка и частично выполненную массовую выдачу.
