# Архитектура платформы Алисы · v0.5

Этот документ заменяет выбор UI и локальной идентичности прежнего v0.3. Остальные подтверждённые требования матрицы/денег/TTL сохраняются. Ничего не развёрнуто этим документом.

## ADR-PL01. Независимый продукт, переносимая идентичность

Новый identity authority отдельный от нынешнего backend Октопорта. Сначала только Алиса. Затем к нему добавляется Octoport через adapter; данные не сливаются по email. Источник деталей — [IDENTITY_AND_UNIFICATION.md](IDENTITY_AND_UNIFICATION.md).

## ADR-PL02. UI совместим с будущим объединением

Next.js/React для сайта, ЛК и рабочей админки Алисы, отдельные сборки. API/backend Алисы — Django/PostgreSQL, если окончательный ADR зависимостей не выберет совместимый вариант. Django Admin допустим для внутренних технических справочников, но не как единственная будущая рабочая админка. Дизайн-пакет версионируется; автоматического одновременного deploy обоих продуктов нет.

Identity: первый кандидат django-allauth OIDC с библиотечным email-code/MFA. Фиксируем поддержанные версии и проверяем flows в шаге 02. Запрещены две конкурирующие identity authorities одной среды и собственная криптография. Старый OAuth навыка остаётся за совместимым фасадом.

## ADR-PL03. Владельцы данных

```text
alisa(.stage) / Next.js: главная + ЛК ── OIDC ── id(.stage)
             │ product BFF / host-only session
             ▼
Платформа Алисы / PostgreSQL
 stores · grants · payments · leads · funnel · gaps · catalog · support
             │ versioned runtime_adapter / проверенный local tenant
             ▼
Существующее Python-ядро → матрица → очередь → transport → Ozon/WB
             │ очищенные события / результат с TTL
             └──────────────────→ платформа

alisa-admin(.stage) / Next.js → отдельный OIDC client + MFA
                            → staff API с alisa_market scope
Нынешний Octoport: другие сессии / API / БД / выпуск, не в этом пути
```

Схема имён в рисунке сокращённая; точные FQDN в DOMAIN_SETUP.md. Identity владеет person/контактами/факторами, продукт — local user/tenant/roles/доступом, runtime — временными job/результатами/фактом HTTP. Платёжные facts не дублируются в identity.

## ADR-PL04. Право доступа и runtime

Источник доступа — product-scoped grant ledger и security revisions. При submit создаётся ограниченный ticket (предлагаемо до 30 минут, окончательно по квалификации): local tenant, stores/credential versions, runtime/catalog versions и срок. Естественное истечение подписки отличается от security revoke. Перед следующей внешней операцией и выдачей результата проверяется текущая локальная security epoch; при недоступной authority опасное действие запрещено. Уже отправленный HTTP не объявляется отменённым задним числом.

Не переписываем runtime/SQLite ради новых кабинетов. `RuntimePort`: capabilities, submit, status, cancel, read_result, revoke_scope, current_versions. На одном host — Unix socket/peer credentials, между hosts — mTLS/эквивалентная проверенная service identity. Без trust binding поле tenant_id не даёт доступа. Истёкший результат не пересчитывается при чтении.

## ADR-PL05. Домены и среды

Шесть новых имён: prod site/admin/id и stage site/admin/id. DNS и TLS подготавливаются до прикладного AL-S01, но наличие сертификата не равно работающему кабинету. Внешний API отдельным поддоменом не нужен: browser→свой BFF, upstream приватен. Поддомены не требуют размещения на Easyscript. Текущий Alisa ingress может принять только новую маршрутизацию после согласования; ресурсная готовность измеряется отдельно.

## ADR-PL06. События, собственная воронка и матрица

Lead/funnel/gap имеют отдельные цели и хранилища. Неподдержанная реплика очищается в runtime до outbox; без безопасной очистки только metadata. At-least-once доставка + idempotent effect; episode revision защищает от переупорядочивания. Никаких raw запросов/денег в маркетинговых labels.

Каталог: draft → проверка → approval exact hash → immutable package → runtime assignment/readback → наблюдение. Admin не редактирует рабочие JSON непосредственно. Совместимые источники добавляются матрицей; новый класс требует общего примитива. Неподходящий вопрос не публикует новый шаблон автоматически.

## ADR-PL07. Платежи и ключи при объединении

Product ID обязателен в grants/orders/permissions/audit. Общая личность не даёт общий paid_until. Ключи расширения не уходят на сервер Алисы автоматически. При будущем общем UI backend остаётся владельцем каждого платежа/секрета; физическое объединение БД не обязательно.

## ADR-PL08. Простое развёртывание и рост

Платформенный API, bounded worker, отдельный быстрый голосовой пул, identity и Next.js процессы изолируются ресурсами. Постоянные данные — PostgreSQL, очередь матрицы остаётся её собственной. Никаких Kafka/Kubernetes/универсальных брокеров без измеренной потребности. Внешний HTTP вне DB-транзакций, durable jobs с fencing/идемпотентностью.

При наблюдавшихся 1 CPU/~1 GiB на Alisa весь стек не считается размещаемым без расширения/отдельного хоста. Стартовый ориентир для оценки платформы — 2 vCPU/4 GiB, не гарантия production-мощности. Build выполнять отдельно, лимиты и достаточность подтверждать замерами. Stage/production могут временно иметь общий ingress, но отдельные процессы, роли, БД и ключи; публичный нагрузочный stage не должен исчерпывать prod.

## ADR-PL09. Будущее объединение отдельно

[MERGE_ROADMAP.md](MERGE_ROADMAP.md): OIDC adapter → подтверждённая связь → общий ЛК → общий admin → поэтапный выпуск и решение о главной. AL-S01–24 не зависят от этих шагов или B22 расширения. Перед общим origin нужен security review: path не изолирует приложения.
