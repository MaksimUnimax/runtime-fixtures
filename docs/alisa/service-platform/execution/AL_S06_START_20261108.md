## Найденная действующая часть

Read-only проверка сервера: `alice-lab-web.service` активен из `/opt/alisa-station/releases/station-auto-r1`; `alice-market.service` активен из `/opt/alice-market/releases/alisa-runtime-429-wait-r1-20261108`. В поставке Station уже находятся `alice_lab.py`, `alice_bridge.py`, `station_client.py` и шлюз. В `alice_lab.py` есть `/oauth/authorize`, `/oauth/token`, `/oauth/refresh` и поддержка настроек `ALICE_SKILL_ID`, `LAB_OAUTH_CLIENT_ID`, `LAB_OAUTH_CLIENT_SECRET`. Их значения не читались и не переносились; наличие этих имён в исходнике не выдаётся за самостоятельную OAuth-приёмку.

В проверенной платформенной ветке пока нет `services/platform/src/alisa_platform/alice_link/`. Новый пользовательский путь нужно связать с существующим customer/tenant и текущим доступом. Действующая Station/native-часть принадлежит параллельной работе; её файлы, callbacks, grants и tenant mappings этой поставкой не менялись.

## Ближайшая реализация и проверка

Сначала изучить контракт уже работающего native OAuth и его реально загруженную настройку, затем определить минимальный мост между подтверждённым клиентским кабинетом и отдельным skill grant. Не просить новое приложение или новый клиент, не проверив существующий. Одинаковая почта, подпись магазина или совпавшее имя не являются разрешением на автоматическое объединение аккаунтов.

Кабинет должен показывать статус подключения Алисы, голосовую приватность, отзыв и повторную привязку. Авторизацию навыка и браузерный OIDC нельзя смешивать: token/refresh должны отдавать протокольный JSON, а действующие grants лабораторного навыка сохраняться. Приёмка включает настоящую консоль Диалогов, возврат в тот же аккаунт, refresh, unlink/relink, сохранение срока доступа и изоляцию чужого tenant. Поддельный клиент и mocked API не заменяют этот результат.

**Действия владельца:** сейчас не требуются. Ближайший шаг исполнителя — проверить существующий native OAuth-контракт и конфигурацию перед изменениями платформы.
