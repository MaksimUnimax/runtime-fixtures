# AL-S02 · самостоятельный вход и кабинет

Состояние: SOURCE_IMPLEMENTED_QUALIFICATION_IN_PROGRESS. Это дополнение исполнения; замороженный комплект v0.5 не меняется. Единственный автор исходников — существующий исполнитель платформы. Матрица и обработчик исключены.

## Границы данных

Identity использует только свою БД: UUID Person, подтверждённый контакт, согласия, библиотечные OIDC/MFA, пару Person/client → постоянный pairwise subject, сессии и почтовый outbox. MFA adapter шифрует TOTP/recovery secret стандартным Fernet; исходный no-op hook библиотеки не используется для секретов. Issuer среды фиксирован. Перед библиотечной проверкой Basic credentials выполняется однократное стандартное form-decoding компонентов по [RFC 6749 §2.3.1](https://datatracker.ietf.org/doc/html/rfc6749#section-2.3.1): закреплённый openid-client экранирует даже `_`/`-`, а parser allauth их не декодирует. Проверка хеша секрета, grant и PKCE остаётся библиотечной; допускаются только заранее созданные ASCII IDs и случайные URL-safe secrets. Неверный секрет по-прежнему получает 401.

Django-allauth 65.21.1 закреплён вместе с Django 5.2.19; динамическая регистрация клиентов/CIMD выключены. Только заранее созданные confidential clients с client_secret_basic и обязательным S256.

Session token создаётся случайно до начала входа и хранится в зашифрованном flow. После успешного OIDC проверенный payload создания сессии повторяется максимум один раз при неопределённом ответе API, без изменения hash/blob. Повтор callback уже потреблённого flow получает безопасную квитанцию и новый вход, без восстановления потерянной cookie.

BFF использует openid-client 6.8.9 с включённой проверкой подписи ID token, проверяет issuer/audience/state/nonce/expiry и одноразово забирает flow из своего platform API до обмена кода. Токены и проверочные значения шифруются стандартной jose 6.2.15 (JWE dir/A256GCM); platform видит непрозрачные blobs. В браузере только случайный host-only HttpOnly Secure SameSite=Lax cookie; bearer-токенов в localStorage нет. Web не подключается к БД.

Platform владеет локальными Customer/Tenant/Membership и привязкой (issuer, client_id, subject). Email не ключ и не основание объединять людей. Повторный вход сериализуется по verified subject и сохраняет tenant. Роль OWNER_CLIENT ещё не предоставляет магазин, пробный период или платный доступ. Профиль выводится по серверной сессии; передаваемые tenant/user IDs отвергаются.

Согласия хранятся в identity и platform. S01 Submission UUID передаётся отдельным HttpOnly cookie, затем хранится только в серверном flow. Привязка заявки возможна после подтверждённого совпавшего контакта, подтверждённой неистёкшей заявки и свежего Submission; она переносит только допустимую атрибуцию и не создаёт права. OAuth URL не получает UTM/контакт/ключи.

## Время, одноразовость и выход

Код identity живёт 600 секунд, максимум пять неверных попыток. Общие DB cache и PostgreSQL advisory locks защищают обмен authorization code и изменение identity session несколькими процессами. Транзакция закрывается до любого SMTP/HTTP обращения. Identity session/cache/mail шифруются Fernet с возможностью ротации ключей; JWT подписывается отдельным RSA-ключом.

Собственный account-cleanup выполняет максимум 1000 строк каждого вида, стирает payload истёкших/отозванных сессий и flow, удаляет строки старше суток; активные записи сохраняются. Timer работает раз в 60 секунд. Lookup отклоняет истёкшую сессию; немедленное стирание при lookup не заявляется.

Identity mail batch конечный, использует свою lease и не отправляет ничего кроме example.invalid в приватный loopback SMTP. После подтверждения SMTP payload удаляется. При ошибке SMTP остаётся зашифрованная очередь. Внешняя SMTP доставка имеет семантику at-least-once со стабильным Message-ID; атомарное exactly-once между БД и SMTP не заявляется.

Выход из кабинета отзывает серверную продуктовую сессию. Это не глобальный выход из identity/будущих приложений. Следующий продуктовый вход запрашивает prompt=login и новый код; отдельный identity logout остаётся библиотечным. Другой синтетический RP получает свой audience/pairwise subject и не получает доступ к platform API.

## Проверка и установка

CI не имеет stage credentials. Сначала проверяет регрессию S00/S01 на своей пустой PostgreSQL 16.15, удаляет свои БД/роли, затем устанавливает пакет offline в новую одноразовую среду и проходит настоящий HTTPS/Chromium/identity/BFF/API/PG. Собственный временный CA доверяется Python/Node/изолированному браузеру явно; проверка сертификата не отключается. Отрицательные проверки не заменяются анализом конфигурации.

Пакет ещё не считается принятым до фактического результата и независимого вердикта для точной версии. Живой S01 остаётся прежним. Новый live S02 требует конкретного допуска на пакет, собственные platform/identity миграции, clients/keys/env, собственный identity mail timer и ограниченные собственные nginx изменения. Admin, lab, старый OAuth, матрица и обработчик в установку не входят. Возврат — прежний совместимый код/приватная конфигурация с сохранением добавочных таблиц и данных, без обратных миграций/восстановления старой БД поверх новых записей.

Следующий шаг: получить сквозную квалификацию, закрыть независимые находки, закрепить точный пакет и предъявить узкий план установленной проверки.
