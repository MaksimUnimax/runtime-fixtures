# Canonical admin and identity cutover · 2026-11-05

Owner explicitly requested the admin link and immediate relocation from test domains. Scope: existing deployment only; public admin https://alisa-admin.octoport.ru, authority https://id.octoport.ru, website https://alisa.octoport.ru. Existing internal stage namespace is retained. This is not a new production DB or production runtime admission.

One explicit ALISA_CANONICAL_AUTH_ENABLED=1 flag pins both new auth origins. It is strict0/1 and stage-only; unflagged stage, loopback dev and closed prod retain their boundaries. No dual-issuer acceptance, wildcard callback, Host-derived issuer or automatic account merging.

Before cutover verify TLS/DNS, exact reviewed package hashes/locks/migrations and current releases. Preserve existing Client IDs/secrets, signing/data keys, all Person/Subject and factors. Record private identity/account/staff fingerprints (never user factor data) and exact authority counts/composition. The owner must remain the same known verified person and pairwise admin subject.

Hold existing rollout locks. Install immutable package without activating. Put all three public entry points into maintenance before changing authority or bindings; stop only own web/admin/platform/identity and relevant own mail/cleanup workers/timers. No new issuer may admit requests before platform rebind. Back up exact private configs and origin files under root-only rollback directory, without exporting secrets.

Set all consumers to the new issuer and canonical auth flag. Set admin origin and exact registered admin callback to the new domain, identity allowed hosts/CSRF to new host. Preserve web/probe callbacks on alisa.octoport.ru and all client IDs/secrets. Run closed canonicalize_staff_callback --apply from exact package: it changes only the existing confidential admin callback, invalidates native tokens (including opaque access/refresh), codes/cache, Django sessions and pending mail payloads. It does not inspect or alter factors. Then run closed canonicalize_identity_issuer --apply with expected links/staff counts, owner ID/revision and SHA256 of the exact old binding snapshot. It atomically renames only the existing web/product staff issuer, advances staff revisions, revokes sessions/clears flow payloads, and appends safe audit events. Identical retries are no-ops; partial/different state refuses. No new account or staff session is created.

Switch all four existing service pointers and restart all consumers to clear cached discovery. Check readiness before opening ingress. Install canonical-auth.conf.example with existing local engineering ACL values preserved. Old admin GETs lead to fresh canonical login without query; old callback code/state are dropped. Old identity account GETs lead to fresh canonical login; old protocol/token/discovery fail410, old account POSTs409. Safe logs contain method/path/status only. Never replay a POST or carry old OAuth parameters into the new authority.

After cutover verify canonical discovery/issuer/endpoints, actual admin authorization redirect uses new identity and callback, wrong Host/Origin rejection, former codes/tokens denied, preserved Person/Subject/customer/tenant/role/permission fingerprints, one real OWNER, unchanged factor counts, and no operator-issued real owner session. Synthetic actual email/OIDC round trip must return to the same synthetic customer/tenant; never enroll/operate the real owner's factor. User then starts at the canonical admin login and completes native email/MFA manually.

Rollback before reopening may guardedly restore only the exact renamed issuer/client fields after verifying the saved state and invalidate sessions again; it must never restore an entire identity DB or recreate factor/session payloads. After reopening, new registrations/factors must be preserved; rollback requires a fresh guarded reverse migration, never replaying a DB snapshot. On unknown outcome inspect saved receipts/actual mappings before retrying. No changes to marketplace runtime, lab, old Octoport or Business Bridge.
