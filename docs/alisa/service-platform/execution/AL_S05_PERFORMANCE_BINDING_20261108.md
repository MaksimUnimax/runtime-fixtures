# AL-S05: подтверждение связи рекламы Ozon с магазином

## Что сделано

Пакет исправлений входа **AL-S02** установлен и проверен: [результат](AUTH_NAVIGATION_20261108.md). Это не закрывает весь AL-S05.

По **AL-S05** Seller и Performance сохраняются отдельно в одной карточке. Настоящая пара Performance успешно получает токен, но не возвращает доказательства общего кабинета с сохранённым Seller-доступом. Предыдущий минимальный живой probe и границы вывода сохранены в [исследовании](AL_S05_OZON_IDENTITY_RESEARCH_20261106.json) и [безопасном receipt](s05-real-keys-20261108/performance-identity-probe.json).

Дополнительно проверен конкретный предполагаемый способ сопоставления: числовой префикс существующего Performance Client ID **не совпадает** с Seller Client-Id владельца. В отчёт записаны только булевы значения, без самих идентификаторов или секретов. Значит, разбор префикса не решает этот реальный случай. Новых запросов к API с ключами и изменений файлов credentials не было.

В официальном [анонсе Ozon от 6 апреля 2026](https://dev.ozon.ru/news/691-Performance-API-Optimizatsiia-kontrolia-dostupov-cherez-OAuth/) описан общий OAuth-доступ к двум API с выбранными разрешениями, включая роль для чтения. Это кандидат для полноценного подключения, а не доказательство принадлежности уже сохранённой старой пары ключей. В [официальном описании OAuth](https://dev.ozon.ru/start/450-Protsess-OAuth-avtorizatsii-dlia-dostupa-k-Ozon-Seller-API/) `sub` имеет разный смысл для `authorization_code` и `client_credentials`; подменять один другим нельзя.

Историческая проверка до получения документа: полный точный контракт Performance на тот момент не был получен. Публичная страница не даёт читаемого описания в поисковом fetch. Прямая ограниченная загрузка официального Swagger с разрешённого сервера возвращает HTTP 307 и `text/html` вместо JSON; результат сохранён в followup исследования. URL подтверждён существующим registry API Watch. Обход challenge, смена идентичности браузера или перебор адресов не выполнялись.

Работающая версия сайта, ключи, Seller-подключение, статусы карточки и конфигурация не менялись. Реклама не объявляется подключённой по одному факту получения токена. Новая регистрация приложения Ozon пока не запрашивается: сначала нужен точный поддерживаемый контракт.

## Актуализация 08.11.2026: документ получен

Владелец уже приложил описание Performance. Нормализованный JSON проверен: OpenAPI 3.0.0, 47 путей, 48 операций, SHA256 `c15c0e295a1feefca05a2f3db6c12c11a58bd128206f4e430ab3eea120e60c87`. Документ принят с происхождением `OWNER_SUPPLIED_REVIEWED`; это не успешная автоматическая загрузка. Метод `/api/client/organisation/vendor_tag` сам по себе не предоставляет доказательства общего Seller-кабинета. Формального crosswalk и полного OAuth-контракта для этой связи в приложенной схеме не найдено.

Отдельная ранняя часть **AL-S16** установлена из `7cbe3059a83677aeb42a086898a48067918f16a2`: Swagger Watch без мониторинга ИИ, клиентской БД и ключей маркетплейсов. [Статус документов](https://alisa.octoport.ru/health/swagger), [ход установки и проверки](swagger-watch-20261108/PROGRESS.md). Полное подтверждение рекламной связи этим не добавлено.

## Действия владельца

Не требуются. Прежняя просьба самостоятельно скачать Swagger выполнена приложенным документом; повторно файл или ключи не нужны.

## Следующий шаг

**AL-S05:** проверить полученный официальный OpenAPI на метод, который подтверждает кабинет, либо на точный поддерживаемый OAuth-контракт. Затем внести конкретное исправление и проверить чужой кабинет/ключ, замену и отзыв, сохранность действующего Seller, tenant isolation и отсутствие секретов в ответах/логах. Неподтверждённую связь не превращать в CONNECTED; имеющаяся схема не доказывает принадлежность Seller-кабинету.
