# Алиса: форма MFA и доступ настоящего владельца · 5 ноября 2026

**Установлено: понятная форма и роль OWNER для подтверждённой учётки владельца. Личный вход владельца с MFA ещё не завершён: WAITING_FOR_USER_FACTOR_SETUP.**

Исправлены две отдельные причины проблемы. Нативный перевод называл и длинный ключ подключения, и проверочный код одинаково; пользователь вставлял ключ в поле кода. Кроме того, единственный OWNER был связан с синтетической тестовой учёткой, а у подтверждённого настоящего владельца не было staff-привязки. Исправление только текста не открыло бы ему админку.

## Установленное поведение

Верхнее поле — «Ключ подключения приложения», только для добавления записи в приложение. Нижнее — «Проверочный код из приложения — 6 цифр», с цифровой клавиатурой, ограничением длины6 и без повторного отображения неверно вставленного ключа. QR, CSRF, нативные ошибки, endpoint и проверка allauth сохранены. На промежуточной странице объяснены настройка приложения и продолжение входа.

Закрытая однократная процедура проверила ровно одного первоначального OWNER, bootstrap audit, старую синтетическую identity, активную настоящую identity с подтверждённой совпадающей основной почтой и отдельный confidential admin client. Подготовлен admin-client subject этой же личности; существующая роль OWNER передана ему с ревизией1→2. Старые staff-сессии отозваны, их payload очищен; append-only audit содержит fingerprints. Обычный customer, tenant, membership и product identity links сохранены.

Публичного способа назначить OWNER не добавлено. Повторный обычный bootstrap по-прежнему закрыт. Команды требуют --apply, точную область, ожидаемые прежние subject/revision и допустимое первоначальное состояние; последующая смена владельца через них запрещена. Личный фактор, QR/секрет владельца и staff-сессия оператором не читались и не создавались.
