# Ручной вход владельца: понятная MFA и первая передача тестового OWNER

Показанная владельцем форма называла длинный ключ и шестизначный проверочный код почти одинаково. Это исправляется собственным шаблоном поверх нативного allauth, без изменения проверки MFA. Установленный код требует код приложения для admin client по AL-S03; ключ с QR не является этим кодом. Ключ и реальные факторы владельца не читаются и не генерируются оператором.

Дополнительно read-only проверка установила: у подтверждённой реальной учётки владельца ещё нет admin subject/StaffMember, единственный активный OWNER относится к синтетической identity example.invalid, revision1, с исходным closed bootstrap audit. Поэтому нужна первая закрытая передача владельцу, а не повтор bootstrap и не выдача роли через обычную регистрацию.

Операторская процедура:
1. Под блокировкой изменения проверить точную принятую сборку, одного активного OWNER, его id/subject/revision и closed bootstrap audit. В identity независимо подтвердить, что текущая привязка — синтетическая; целевой person активен, его основной контакт совпадает с уже подтверждённым контактом владельца из этого рабочего потока.
2. prepare_verified_staff_subject --apply --person-id UUID возвращает стабильный subject только для закреплённого confidential admin client. При неподтверждённом или неактивном person — отказ. Команда не создаёт фактор, токен, сессию или роль.
3. handover_initial_staff_owner --apply с точными owner-id, expected-subject, expected-revision, new-subject и именем переносит ту же единственную OWNER-запись. Проверяются product/issuer/client, исходный bootstrap и отсутствие прежней передачи. Счётчик ревизии увеличивается, старые staff sessions отзываются и очищаются, аудит содержит только fingerprints субъектов.
4. Совпадающий повтор безопасен; иной запоздалый запрос или повторная смена владельца закрыты. У операции нет публичного API. Обычный bootstrap по-прежнему не заменяет существующего владельца. Клиенты, организации, настройки и MFA человека не меняются.
5. После передачи прочитать привязку к целевому person и права OWNER, отсутствие активных старых staff sessions и единственный аудит передачи. Настоящий вход остаётся за пользователем: приложение на его устройстве, его QR и шестизначный код. Без нативной MFA админ-сессия не выдаётся.

Новая процедура проверяется на disposable PostgreSQL: проверенный/непроверенный person, идемпотентность subject, отсутствие созданного фактора, точная ревизия, конфликт привязки, отсутствие публичного маршрута, сохранение одного владельца, отзыв сессий, отсутствие выдачи новой сессии, повтор/устаревший запрос и запрет второй передачи. Реальная операция разрешена только после независимого review точной сборки и этих проверок. Этот документ не утверждает, что она уже выполнена.
