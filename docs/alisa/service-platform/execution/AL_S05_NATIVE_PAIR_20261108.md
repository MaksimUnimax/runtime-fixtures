# AL-S05: существующие ключи Ozon без нового приложения

## Исправленная причина

Просьба искать или создавать приложение Ozon была ошибочной и отменена. В действующей серверной настройке уже находятся Seller и Performance одной native-привязки, ранее прошедшей read-only квалификацию. Read-only сверка подтвердила точное совпадение обеих пар с сохранённой карточкой сайта. Секреты, MAC, их отпечатки и идентификаторы клиента в отчёт не включены.

Старая проверка сайта после принятого Ozon рекламного токена всегда возвращала `AUTHENTICATED_UNLINKED`. Исправление использует уже существующую доверенную связь с явным происхождением `NATIVE_OWNER_CONFIGURED_PAIR`. Оно не выдаёт owner-настройку за предоставленный Ozon crosswalk и не подтверждает произвольные новые пары.

## Исходник и проверка

Точный продуктовый источник — `8e1a695d71f1004b03564570b880a915efdb539e`, дерево `5ed062fb9fc74e9a2c8689e1234f748ff0c2951e`, [PR 402](https://github.com/MaksimUnimax/runtime-fixtures/pull/402). [Platform CI 42461710315](https://github.com/MaksimUnimax/runtime-fixtures/actions/runs/42461710315) и [Documentation CI 42461710338](https://github.com/MaksimUnimax/runtime-fixtures/actions/runs/42461710338) — SUCCESS. В CI: runtime 1 091, RT-CHECK 26, S05 PostgreSQL/Unix 50; native identity 246 и registration 157 сохраняют собственные scoped статусы и не являются owner-приёмкой. [Связь с артефактами](s05-native-pair-20261108/ci-artifact-binding.json).

API установлен небольшим overlay поверх фактически работающей версии `917600ca66cd6afaaf906ec468078cbd6eaba083`: изменены сервис магазинов, узкая проверка поля provenance в текущем адаптере и скопирован launch. Остальные исходники и зависимости ссылаются на прежний неизменяемый выпуск. Доработки каталога другого автора сохранены. Worker/IPC/catalog/shared HTTP проверяющей службы сохранены побайтно; заменён только checker и добавлен resolver.

## Установленные проверки и восстановление

Подготовка прошла. Первая активация остановилась из-за ошибочного имени системной группы; собственный drop-in удалён, прежний checker восстановлен, API не переключался. R4 остановился до изменений из-за сброса systemd runtime metadata после `daemon-reload`. R5 сравнивает точную команду и отдельные PID/Invocation/права, сохраняя эти ограничения, и успешно установлен.

После R5 реальный Performance через штатный socket от фактического UID API вернул `CONNECTED`, совпадение Seller identity и native provenance. Реальный Seller также вернул `CONNECTED`. Под UID и в mount namespace работающего checker проверены положительная связь и отказы при неверном секрете, другом tenant/store и Seller kind. Отчёты площадки не запускались, клиентская БД не изменялась.

При последующей сверке обнаружен новый запуск native core другим исполнителем после успешной активации. Checker уже связан с core через `BindsTo`/`PartOf`; ключи и полный квалифицированный источник остались прежними, но generation в projection устарел. Подготовлен конечный root oneshot в `ExecStartPre` checker: он проверяет прежний HMAC полного источника и обновляет только generation и производный MAC. Изменение ключей, scope, разрешений или квалификации не принимается автоматически. Постоянного runner, таймера или мониторинга ИИ нет. Native core/API/web/identity/admin этим hook не перезапускаются. Локальные fixture-проверки: шесть новых и пятнадцать прежних — 21 PASS.

**Установлено и сверено:** [R5 activation](s05-native-pair-20261108/activate-r5.json), [проверка Seller и границ resolver](s05-native-pair-20261108/installed-verification.json), [restart hook](s05-native-pair-20261108/refresh-install-r2.json), [readback](s05-native-pair-20261108/readback.json). Первый hook откатился: отдельный systemd unit не видел credentials другого unit. Диагностика воспроизвела FileNotFound, после точного read-only bind только существующего файла Ozon повторная проверка всех восьми границ прошла. Установка R2 обновила stale generation и снова получила настоящий Performance CONNECTED через UID API. Все четыре службы сайта готовы; native core и checker активны; ранее неактивный alice-lab-worker остался неактивным. На итоговой сверке свободно 3 223 064 576 байт, 482 295 inode; минимум 3 GiB/200 000 сохранён. Новый принудительный перезапуск native core ради теста не выполнялся. Секреты не копировались в новую credential store, БД или отчёт.

## Граница результата

Это исправление setup-check существующей квалифицированной пары, а не подтверждение рекламных отчётов, финансовых данных, голосового сценария или всей AL-S05. `LIVE_OWNER` переход карточки в браузере не выполнен; сохранённый `PENDING` не переводился в ACTIVE прямой записью БД. Native core generation/source drift остаётся fail-closed; автоматическая requalification допускает только неизменённый уже квалифицированный источник.

## Действия владельца

Новые ключи, приложение Ozon, регистрация или повторный ввод реквизитов не нужны. Для обновления прежнего сохранённого результата после установки:

1. Открыть [Мои магазины](https://alisa.octoport.ru/app/stores) в своём кабинете.
2. Нажать «Обновить список».
3. В карточке магазина, в разделе «Реклама Ozon», нажать «Проверить новый ключ»; если ключ уже текущий — «Проверить текущий ключ».
4. Ожидаемый результат после ответа: «Текущий ключ, версия 1: Подключение подтверждено». Seller остаётся подключённым. Фактическая owner-проверка этого перехода пока не заявлена.
