# AL-S05: рекламный доступ Ozon — причина блокировки и следующий вход

Статус: **LEGACY_BINDING_BLOCKED; OAUTH_PROTOCOL_PREPARED_ONLY**. Это исследование установленного кода и решение о следующем пути, а не реализованный OAuth, новый CONNECTED или приёмка рекламы.

## Подтверждённая причина

Установленная служба `alisa-store-check.service` использует `/opt/alice-market/checker-releases/owner-catalog-853e2b2f85759c42/store_checker.py`, SHA256 `ce6973646121160fb6f3a428d4577c119037ef650ca618805eb44f74772cc5d1`. Read-only AST-проверка нашла один явный возврат AUTHENTICATED_UNLINKED: после успешной выдачи Performance token код не имеет ветки подтверждения того же Seller-кабинета. Это незавершённый путь реализации, а не установленная ошибка ввода владельцем. Повторная проверка правильной пары не завершит привязку.

Действующий [RT-CHECK контракт](../../../../products/alisa/contracts/runtime/store-check-v1.md) требует для Performance доказанную ту же canonical Seller identity; `stores/service.py` сравнивает результат с `Store.verified_identity`. Нельзя просто выдать отдельный рекламный Client ID за Seller identity. Префикс Client ID, название, ИНН, хеш секрета и декодированный непроверенный JWT не заменяют доказательство. Сохранённые реальные проверки уже показывали token200, неверный secret401 и oauth/me404 с legacy Performance bearer; новых provider calls сейчас не было.

Приложенный владельцем Performance OpenAPI проверен: 47 путей,48 операций, SHA256 `c15c0e295a1feefca05a2f3db6c12c11a58bd128206f4e430ab3eea120e60c87`. `GET /api/client/organisation/vendor_tag` принимает обязательный caller-supplied `orgId` и возвращает `tag`. Схема не даёт crosswalk с Seller Client-Id и не доказывает принадлежность ключа этому кабинету.

## Официально поддержанный кандидат

[Ozon описывает единый OAuth-доступ к Seller и Performance](https://dev.ozon.ru/news/691-Performance-API-Optimizatsiia-kontrolia-dostupov-cherez-OAuth/) с выбранными разрешениями и ролью для чтения. [Authorization-code flow](https://dev.ozon.ru/start/450-Protsess-OAuth-avtorizatsii-dlia-dostupa-k-Ozon-Seller-API/) требует приложение, зарегистрированный callback и разрешение продавца. В нём `sub` обозначает Seller ID; в client_credentials `sub` обозначает ID приложения. Эти namespaces нельзя отождествлять.

Это новый согласованный OAuth-доступ, а не автоматическое доказательство принадлежности уже сохранённой legacy-пары. [FAQ Ozon](https://dev.ozon.ru/start/442-FAQ-Magazin-prilozhenii-i-Lichnyi-kabinet-razrabotchika/) отдельно предупреждает: некоторые Seller методы могут ещё требовать API-key. Поэтому единый токен нельзя без проверки подставить во всю существующую матрицу.

## Конкретная граница реализации

| Часть | Требование до включения |
| --- | --- |
| Приложение | Реальные Client ID, серверный Secret, точные согласованные read-only scopes; значения не передавать в чат/отчёт |
| Авторизация | Зафиксированные authorize/token URL, registered redirect URI, `prompt=select_company`, одноразовый случайный state, TTL не более5мин, привязка tenant/customer/session/store/security revisions |
| PKCE | Сначала проверить поддержку S256 у Ozon; в прочитанных публичных инструкциях она не определена, не выдавать её за готовый контракт |
| Callback | Нет готового endpoint и callback URL для регистрации. До реализации нужны duplicate/state/replay/CSRF проверки; code и query не должны попасть в access logs, referrer или API-ответ |
| Identity proof | Квалифицировать provider-attested Seller identity и её namespace; не переносить legacy identity в OAuth без доказанной связи или явного отдельного режима подключения |
| Хранение | Отдельный OAuth grant в vault; токены/refresh не в браузер; ревизии и запрет позднего ответа после отзыва, удаления, выхода и замены |
| Продвижение | Существующий Seller/Performance остаётся действующим до успешного нового проверенного перехода; принятие токена не включает объединённые отчёты |
| Матрица/transport | Чужие активные файлы не меняются. Поддержку OAuth конкретных операций согласовать отдельно до отчётов |

Будущий переход: start сессии → одноразовый state → разрешение продавца у Ozon → проверенный callback → bounded server-side exchange → квалифицированная Seller identity и scopes → revision-safe commit. Ошибка или неизвестная identity завершает только pending попытку и сохраняет прежний доступ.

Нужны негативные сценарии: другой tenant/store/session/state, повтор callback/code, истёкший state, отказ продавца, неожиданный issuer/redirect, недостающий scope, другой Seller, поздний ответ после отзыва/замены, потеря ответа при exchange и refresh rotation, отсутствие секретов в логах/браузере. Они ещё не запускались: реализации OAuth пока нет.

## Что проверено без владельца

В Alisa stage env не обнаружено setting names для Ozon OAuth/refresh/app. Ограниченный read-only поиск в конфигурационных корнях Easyscript также не нашёл соответствующих имен; это не доказывает отсутствия приложения в личном кабинете Ozon. Поиск значений секретов и новый вход в Ozon не выполнялись.

Browser connector вернул: `Browser access requires the originating browser context`. Поэтому список частных приложений владельца не просмотрен. Другой браузер или чужая сессия для обхода этого ограничения не использовались.

Службы, конфигурация, ключи и клиентская БД не менялись. [Swagger Watch установлен ранее](AL_S16_SWAGGER_WATCH_20261108.md). Само исследование не закрывает AL-S05.

## Действия владельца

Нужен один факт о существующем приложении, без ключей и секретов:

1. Открыть [частные приложения Ozon](https://dev.ozon.ru/apps/private/) под своим Ozon ID. Ожидается список приложений, к которым есть доступ.
2. Если приложение для Алисы/Октопорта уже есть, сообщить его название и доступно ли редактирование системных настроек. Client Secret, токены и авторизационные ссылки с code/state не присылать.
3. Если список пуст или приложения нет, сообщить «приложения нет». Это конкретный недостающий вход; пока не предлагается регистрировать несуществующий callback или изменять разрешения.

[Официальная инструкция создания частного приложения](https://dev.ozon.ru/start/447-Zavedenie-chastnogo-prilozheniia-v-Seller-API/) размещает его в Seller → Настройки → Управление частными приложениями. Создать его может управляющий/администратор; для настройки есть переход в кабинет разработчика. На этом шаге создание не требуется: сначала устанавливаем наличие и текущий scope, чтобы сохранить существующую настройку.

## Следующий шаг исполнителя

Получить доступный контракт конкретного приложения и точные scopes, подготовить callback/token/identity adapter в отдельной ветке, пройти независимую проверку и квалификацию без чужой матрицы. Только затем дать владельцу готовый callback и полноценные шаги выдачи разрешения. До этого сохраняется честный AUTHENTICATED_UNLINKED.
