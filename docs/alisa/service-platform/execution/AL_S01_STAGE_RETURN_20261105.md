## Порядок возврата в согласованных границах

1. Проверить текущие manifest, фактические процессы и свободную `/run/lock/alisa-s01-rollout.lock`. Если исход другой операции неизвестен, сначала прочитать её результат. Не запускать повторно `apply_s01_stage.py`: он закрывается при наличии activation checkpoint.
2. Под конечной блокировкой остановить и выключить только `alisa-lead-mail@stage.timer`, затем дождаться завершения/остановить собственный `alisa-lead-mail@stage.service`. Не удалять outbox и письма. Сохранить приватные текущие web/platform конфиги для последующего возврата вперёд, без вывода значений.
3. Восстановить только `/etc/alisa-platform/stage/web.env` и `platform.env` из root-private резервной копии `/var/lib/alisa-platform/stage/rollout-backups/s01-8d680f775c8ccdf2/0-web.env` и `1-platform.env`. Сохранить root:root и режим 0600. Это выключает новый intake. Приватный SMTP может быть остановлен отдельно; его inbox 0700 и файлы 0600 сохраняются.
4. Проверить неизменяемый manifest принятого S00 и атомарно заменить только `site-current` на сохранённую сборку S00. Instance drop-ins web/API продолжают использовать этот указатель; общий `current` не менять. Перезапустить только `alisa-platform@stage.service` и `alisa-web@stage.service`.
5. Проверить их `/health/ready` на 18102/18100: READY и `alisa-77d0f8ee2643ef65`. Проверить закрытость S01 intake, выключенные инженерную пробу/worker, активный `alisa-probe-cleanup@stage.timer`, неизменность PID/config исключённых служб. Собственный path-only nginx журнал можно сохранить: он совместим с S00 и не раскрывает параметры.
6. Проверить сохранность тех же синтетических записей в собственной platform БД и записать фактический результат возврата. При частичном восстановлении указать конкретный незавершённый пункт; не объявлять COMPLETE по одному успешному рестарту.

Обе аддитивные миграции `funnel.0001_initial` и `leads.0001_initial`, пять таблиц, индексы и новые записи остаются. Не делать migrate назад, DROP, восстановление старой БД поверх новых данных или удаление выпусков. S00 не использует эти новые таблицы. При последующем возврате вперёд использовать тот же квалифицированный пакет и сохранённые собственные конфиги; уже применённые миграции не повторять.
