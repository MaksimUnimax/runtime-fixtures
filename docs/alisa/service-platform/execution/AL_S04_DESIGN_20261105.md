## Результат и пути

Администратор выбирает клиента/фиксированный список, источник GIFT или COMPENSATION, дни, причину и уведомление. Сервер выдаёт preview с абсолютными UTC границами и revision каждого tenant ledger. Подтверждение предоставляет период один раз. Клиент на основном сайте видит то же основание, дату, историю, текущий статус и уведомление. Новых платёжных/paid/person полей нет.

Единственный автор новых `platform/entitlements/`, access BFF/UI клиента и админки, S04 tests/migration. Общие изменения ограничены settings/urls, вычислением profile.access_status, существующими permission/reason/audit allowlists, BFF maps и включением квалификации в существующий Alisa CI. Не редактируются identity/почтовые/доменные пути. SOURCE review precedes installed changes. Новая additive migration сохраняется при возврате кода; старые grants не удаляются.

## Данные и операции

- Ledger — `(product_id,tenant_id)` + revision. Grant/adjustment — append-only original intervals, source, actor, reason, source request identity. Только alisa_market участвует в этом API; другой product не наследует доступ. Customer/Person/Identity не создаются и не перепривязываются.
- DAYS = N×86400 seconds, [start,end). Явная preview policy AFTER_LAST_SCHEDULED добавляет после последнего ещё не закончившегося периода, сохраняя все разрывы и абсолютные интервалы. UI прямо показывает эту политику и даты. Preview истекает через5мин; его absolute start/end фиксированы. Любое изменение ledger revision до применения даёт конфликт вместо скрытого пересчёта.
- Только действующая staff session, свежая native MFA и оба права `access.grant`/`users.read` допускают каждую preview/выдачу/продолжение/отзыв. Изменение роли/отзыв немедленно проверяются заново. Обязательные reason codes и ограниченный comment не попадают в аудит/логи как свободный текст.
- Тестовые конфигурируемые технические границы, не коммерческая оферта: обычный ADMIN≤30days,≤10recipients,≤300tenant-days; OWNER≤365days,≤50recipients,≤5000tenant-days. Невалидные/bool/float/duplicate recipients отвергаются. Лимит и snapshot сохраняются; динамические фильтры не выполняются при продолжении.
- Bulk — durable batch + fixed rows, unique batch/tenant grant, отдельная транзакция каждого элемента, до5элементов на HTTP. Стабильный batch UUID отделён от command UUID каждого HTTP шага. Durable command receipt привязан к actor/action/batch/preview/limit и фиксированным reserved item IDs; тот же UUID возвращает тот же результат, другой payload даёт409. Потерянный ответ повторяет только тот же шаг, явное продолжение использует новый command UUID. Preview потребляется только одним batch. Частичный результат читается и продолжается тем же batch; новый session без прав не может продолжить. Preview/batch привязаны к staff revision: отзыв и последующее назначение не оживляют старую команду. Batch явно показывает BLOCKED; OWNER может выбрать только не-APPLIED строки для отдельного нового preview, сохраняя прежний результат. Это продуктовая bulk операция, не управляющий runner/очередь разработки.
- Сначала существующий staff owner lock → principal → ledger. Такой порядок сериализует отзыв/роль и выдачу, не допускает stale authority. Успешный grant + ledger revision + безопасный audit + notification/outbox создаются атомарно. Сбой не оставляет grant без результата.
- Отзыв: отдельный preview, выбранный GIFT/COMPENSATION, preview показывает нижнюю границу cutoff=max(preview_time,start); при подтверждении cutoff=max(commit_time,preview_cutoff,start), чтобы не отозвать уже использованное за время ожидания. Только остаток выбранного grant; PAYMENT не допускается. Ledger revision проверяется, история и все другие интервалы сохраняются. Не перепаковывать будущие grants и не заполнять разрывы.
- Notification атомарно доступна внутри кабинета при notify=true. Durable email outbox допускает только отдельную явную синтетическую доставку в уже имеющийся приватный SMTP sink; реальные письма и новая массовая почтовая задача не запускаются этим потоком. UI предлагает уведомление в кабинете, не обещает письмо.
- `ALISA_ENTITLEMENTS_ENABLED` default0 закрывает новую capability до миграции/квалификации. Отключение staff не уничтожает ранее выданный клиентский доступ. Customer read использует только собственную BFF session; tenant/customer/product поля из браузера не принимаются. Статусы вычисляются по текущим UTC часам без обязательного expiry worker.

## Проверка и установка

Source pure calendar/limits; isolated PostgreSQL: upgrade/rollback-compatible schema, concurrent same/different UUIDs, immutable original records/DB runtime ACL, actor revoke/role change, tenant/product isolation, current/future/expired/revoked/gaps, exact time boundaries, partial bulk resume и fixed recipients, no fake payment, atomic notification/outbox. Browser: staff preview/confirm7days → клиентский кабинет с тем же сроком, повтор, отзыв, восстановление bulk после прерывания, no-right deny; прежний registration/TOTP/profile flow не регрессирует. Обновления доков проходят существующий docs-check.

На сервере только проверенный immutable package, свежие topology/config/manifest/resource readback и существующие native rollout locks. Сохранять≥3072MiB disk,200000inode,1024MiB available RAM сверх caps; никаких удалений архивов/чужих paths. Запуски конечными OS units, original failed receipts сохраняются. Согласованное применение additive S04 schema и capability следует исходному поручению реализовать на сервере; фактическая проверка затрагивает только собственных synthetic customers.
