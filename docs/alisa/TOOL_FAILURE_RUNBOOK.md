# Отказы инструментов: обязательный порядок диагностики и восстановления

Дата: 2026-11-03 UTC. Область: отдельный проект «Алиса + DeepSeek + Ozon/WB», ветка `alisa`. Прямое поручение владельца: при каждом отказе выяснять сообщённую причину, проверять контекст и данные вызова, применять уже подтверждённый корректный штатный способ и продолжать доступную работу. Не ограничиваться фразой «инструмент заблокировал» и не просить повторно уже данное разрешение.

## 1. Сначала установить, что именно произошло

Сохранить имя инструмента, выбранное устройство, UTC, безопасное описание действия и точный текст ошибки. Не записывать значения ключей, cookies, access/refresh tokens, Authorization, OAuth state/code или полные клиентские ответы.

Различать:
- Ошибка схемы вызова: неверное поле, тип, путь или неподдерживаемая форма URL. Исправить по актуальной схеме инструмента.
- Устройство offline / transport timeout: проверить `list_devices`; использовать фактически возвращённый deviceId. Таймаут не доказывает, что действие не выполнилось.
- Pending/executing с call_id или PID: получить состояние того же вызова; не запускать побочный эффект второй раз.
- Ошибка процесса на сервере: анализировать exit code и безопасный stderr, исправлять конкретный дефект.
- HTTP 401/403/429/5xx провайдера: это уже ответ площадки; обрабатывать согласно её контракту и состоянию задания. Не путать с отказом инструмента до исполнения.
- Отказ защитного слоя до исполнения: приводить сообщение дословно; не приписывать его маркетплейсу, невалидному токену, отсутствию разрешения владельца или конкретному правилу, которого инструмент не сообщил.

Известное сообщение: «Этот вызов инструмента был заблокирован системами безопасности OpenAI. Внимательно проверьте отправляемые данные.» Оно не раскрывает конкретный триггер. Формулировка диагноза: «Вызов отклонён защитным слоем; конкретная причина не предоставлена». Не выдумывать объяснение.

## 2. Проверить контекст до следующего действия

Прочитать последние подтверждённые действия в текущем диалоге, актуальный отчёт в `docs/alisa`, текущую схему инструмента и при необходимости доступную историю вызовов. Старую инструкцию об остановке или ошибке не считать текущей после более позднего подтверждённого исправления. Не переносить сюда ограничения и задачи других веток Octoport.

Проверить: правильный сервер Alisa, абсолютный путь, существование нужного релиза, правильную функцию и её параметры, кавычки/синтаксис, отсутствие случайно вставленного текста страницы/токена, актуальное разрешение владельца, допустимость операции и возможные побочные эффекты. Полный stdout с секретами не использовать как диагностику.

## 3. Восстановление штатного вызова

Если сообщение просит проверить данные и обнаружена исправимая ошибка аргументов либо разрешённый, проверенный вызов не исполнился: исправить данные и отправить контролируемую повторную попытку через штатный инструмент. Перед повтором записи/запуска проверить, не выполнено ли действие уже. Предпочтителен один ясно ограниченный шаг с читаемыми аргументами, а не смешение поиска, изменения конфигурации, получения секретов, сетевых запросов и деплоя.

Никакого универсального «снятия фильтра» или гарантии успеха нет. Нельзя маскировать действие кодировками/обфускацией, менять транспорт или исполнителя специально для обхода отказа, отключать защитные настройки, выдавать неизвестный исход за неисполнение либо заставлять тест проходить без проверки. Если повтор не помог, не устраивать бесконечные одинаковые вызовы: зафиксировать ограничение и продолжить независимую разрешённую часть (аудит исходников, локальные тесты, документация).

Смена имени файла/разбиение кода не являются способом обойти отказ. Обычная модульная разработка и проверка отдельных разрешённых операций допустимы только по их собственному назначению, не как маскировка запрещённого действия.

## 4. Подтверждённый случай из этого проекта

2026-11-03 около 07:27:44–07:27:45 UTC после проверки устройства и аргументов штатный `Remote Desktop Commander.start_process` выполнил существующий read-only скрипт:

`python3 -B /opt/alice-lab/marketplace_readonly_probe_20261103.py`

Результат: процесс завершился exit code 0; Ozon analytics, WB seller-info и WB funnel вернули HTTP 200. Затем сохранённая квитанция была прочитана отдельно:
`/var/lib/alice-lab/probe-reports/oct2026_probe_20261103T072745Z.json`.

Ранее запуск этого скрипта отклонялся до исполнения. Этот факт доказывает успешность поздней штатной попытки, но НЕ устанавливает неизвестную причину прежней блокировки и НЕ означает, что повтор всегда разрешён или всегда поможет. Не повторять платные/сетевые пробы только для восстановления контекста, если уже есть достаточное доказательство.

## 5. После любого восстановления — readback

Проверить фактический результат, а не только отсутствие ошибки инструмента: для файла — наличие, состав и контрольная сумма; для процесса — exit code и итог; для API — статус, схему и полноту; для деплоя — активный build и адресный пользовательский сценарий. Pending не называть PASS. Новый успешный вызов не переписывает историю предыдущего UNKNOWN. Не считать повтор того же теста новым независимым тестом.

## 6. Формат сообщения владельцу

«Отклонено [действие]. Инструмент сообщил [точный текст или код]; [что известно / что неизвестно]. Проверены [конкретные аргументы и контекст]. Исправлено [что именно, если исправлено]. Повтор [выполнен / не выполнен по причине]; фактический результат [доказательство]. Далее выполнена [независимая часть]».

Не обещать работу в фоне без реально созданного механизма. Не выдавать отказ инструмента за отсутствие разрешения владельца, если разрешение уже дано. Не просить присылать ключи заново. Публиковать в Git только обезличенные доказательства; финансовые отчёты и токены оставлять в закрытом контуре.
