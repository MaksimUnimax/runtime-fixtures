# Ozon: дневная цена покупателя и количество за октябрь 2026

Статус: **полный месячный отчёт получен и проверен вне навыка**. Источник и составная операция квалифицированы на живых входах. **В работающую Алису новый источник и речевая команда не установлены**. Прежний LLM_CLARIFY не объявляется успешным отчётом.

## Что выполнено

По поручению владельца получены все 31 даты 01–31.10.2026 через POST /v1/finance/accrual/by-day. Один логический отчёт потребовал 31 физический HTTP: все 200, все курсоры исчерпаны, повторов и сетевых ошибок не было. В этой итерации новых сообщений в консоль Алисы, вызовов DeepSeek и WB не выполнялось: текущая неподдержка голосового сценария уже воспроизведена в предыдущем журнале.

Всего проверены 2 154 исходные записи, в том числе 774 начисления по отправлениям и 575 положительных товарных строк реализации. Для каждой строки проверены денежные компоненты и для каждого из 774 отправлений итог с доставкой и комиссией. Расхождений нет. Денежные значения и товарные строки находятся в приватном отчёте владельца, не в публичном Git.

[Дневной журнал ошибок](OZON_CUSTOMER_PRICES_BUG_LOG_2026-11-04.md) дополнен предотвращённой ошибкой OZCP-005. [Дневной кандидат](../runtime/v0.10/candidates/OZON_CUSTOMER_PRICES_CASE.json) обновлён до ревизии 2.

## Как вычислено

1. Для каждой запрошенной даты получены все страницы одного и того же источника начислений.
2. Отобраны строки posting.products с блоком commission. Остальные ITEM/NON_ITEM и чисто логистические строки не считаются продажами.
3. Количество = SUM(quantity).
4. Сумма реализации для покупателя = SUM(commission.sale_price.amount). Поле sale_price уже является **суммой строки**, включая её quantity.
5. Средняя цена дня = сумма реализации / количество. Средняя месяца = сумма реализаций за месяц / количество за месяц. Простое среднее дневных средних не используется.
6. Те же строки дополнительно сгруппированы по SKU и дню. Дни без реализации имеют неизвестную цену продажи, а не искусственную нулевую цену.
7. Коэффициенты связи вычислены кодом: по 31 дню, после исключения линейного временного тренда и по центрированным наблюдениям внутри одинакового SKU. Это описательная статистика, не доказательство ценовой эластичности.

Для двух строк с quantity=2 отдельно подтверждены равенства seller_price × quantity = sale_amount и sale_price + bonus + coinvestment = sale_amount. Для единичной средней используется sale_price / quantity. Отдельные чековые цены каждой единицы внутри многотоварной строки не наблюдаются.

Расчёт денежных сумм выполнен Decimal из строк источника. DeepSeek не получал финансовую выборку и не выполнял арифметику. В Excel вычисления сохранены формулами и независимо сверены с Decimal-результатом.

## Нужен ли отдельный шаблон

**Для каждого месяца или сочетания «цена + количество» отдельный жёсткий шаблон не нужен.** Один источник одновременно даёт количество и сумму покупателя. Период и группировка day/SKU должны быть параметрами одного общего плана; средняя — составное выражение деления двух аддитивных показателей.

При этом существующая установленная матрица ещё не содержит этого источника и определений. Нельзя исправить отсутствие источника только новым синонимом в speech_catalog.json. Для патча нужно один раз встроить адаптер начислений, его определения и проекцию в общую очередь/transport allowlist/квоты/exact cache, затем зарегистрировать речевые варианты. После этого день, месяц по дням и SKU используют общую реализацию.

DeepSeek может преобразовать свободный вопрос в проверяемый план. Данные, денежные вычисления, полнота и корреляции остаются в коде. Для точной канонической фразы model call не нужен, если её разбирает детерминированный маршрут.

## Ограничение для анализа спроса

Источник использует **дату начисления**, не подтверждённую дату заказа или выдачи покупателю. Поэтому новый результат нельзя склеивать со старым числом заказанных товаров за октябрь и нельзя называть готовым исследованием реакции спроса на цену.

Средняя цена агрегата также меняется из-за состава проданных товаров. В этой выборке общая связь заметно ослабевает при сравнении одинаковых SKU. Остаются неконтролируемыми дата, реклама, наличие, позиции в поиске, регион покупателя и задержки начислений. Цена в дни без продажи не наблюдается.

Следующий шаг именно для зависимости спроса: отдельная согласованная выборка по SKU и **дате заказа**, с исторической ценой предложения и количеством, включая нулевые дни; по возможности — реклама, остатки и день недели. Текущий отчёт полезен как первичная наблюдаемая связь, но не даёт доказанного процента изменения спроса при смене цены.

- 14/14 новых регрессий PASS: многотоварная сумма строки, повторный SKU, дубли начисления, неверная дата, валюта, разница компонентов, цена продавца за единицу, неизвестные возвраты, итог отправления с несколькими товарами, явный ноль, пустой день, непрозрачная ставка, нечисловая сумма и контрольный коэффициент корреляции. Полный прежний suite 607 в этой итерации не перезапускался, runtime не изменялся.
- Все 31 дневные суммы/количества/средние и итоговые коэффициенты в Excel сверены с независимым вычислением. Изменение входа обновило среднюю и корреляцию; изменение восстановлено.
- Проверены все четыре листа, отсутствие ошибок формул и сохранённый редактируемый scatter chart с привязками к дневной цене и количеству.
- INFRA-002: первый вариант полной SKU-календарной сетки был тяжёлым при создании файла. Для пользовательского товарного листа оставлены 377 наблюдений SKU-день с реализациями; все 31 календарные даты основного отчёта сохранены.
