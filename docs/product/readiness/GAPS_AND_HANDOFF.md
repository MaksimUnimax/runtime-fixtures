# Недоработки и передача в A/B/C

Актуальное уточнение: [ответы и решения владельца 2026-09-23](OWNER_DECISIONS_2026-09-23.md). При расхождении прежних вопросов/планов с этой записью применяется запись владельца.

Это ограниченное дополнение принятой программы, подготовленное по прямому запросу владельца. Не менять текущие задачи A/B и не запускать параллельную реализацию общих файлов. C принимает документационный кандидат обычным последовательным путём. До этого он не объявляется присутствующим в main.

## Что меняется в понимании задачи

Документация не отсутствует, но распределена между SPEC/UX, историческими Stream-1/2 receipts, Q1 и бизнес-эталоном в другом репозитории. Старые слова PASS/READY и старые курсоры несовместимы с автоматическим объявлением нынешней RC готовой. Этот комплект связывает функцию, входные данные и доказательство без переписывания старой истории.

## Встраивание без нового набора промптов

- C добавляет ссылку на этот README в общий индекс документации/план после проверки кандидата. Текущие PROMPT_A/B/C остаются целыми и не требуют замены.
- В A04/A06 добавляется traceability по 45 бизнес-строкам и новым точным доказательствам; это детализация текущего расширения, не новая перепись runtime. Общие механики должны оставаться одними для двух площадок.
- В B04/B06 используются O01/O02 и существующий Q1/auth contract. B05/C05 отдельно фиксируют восстановление приложения и внешнюю копию.
- В C04 конкретно используются O03–O05/O17–O18/O23; новые секреты только в защищённом окружении, не в state JSON или PR.
- В C06 проверяются публикационные, смысловые и browser gates. C07 остаётся отдельным разрешением выпуска, этот документ его не выдаёт.
- Каждый запрос владельцу ссылается на Oxx + scenario/gate, указывает готовность и длительность. Несколько запросов собираются в одно окно; не гонять пользователя между потоками.

## Что не нужно делать сейчас

Не собирать все личные пароли/сессии «на будущее»; не покупать автоматически Premium/Apple/cloud Mac/новый SMTP; не начинать коммерцию; не переписывать принятые contracts; не закрывать owner_requests самим потоком только потому, что есть шаблон файла; не ставить всей разработке STOP из-за Safari/почты/модерации, когда остаётся независимая работа.

Серверный intake подготовлен только для Telegram. Токен и identity bindings теперь предоставлены; актуальный статус указан в записи решений владельца. Работающие сервисы, БД, учётки, токены и A/B/C worktrees в этой задаче не изменялись. Защищённый каталог — изоляция файлов от случайного коммита, а не новая граница безопасности от root/RDC администратора.

## Решения, которые действительно остаются владельцу

1. Доступные реальные магазины/почты/сессии/устройства и разрешённые данные.
2. Safari уже отложен владельцем: бета без Safari, работа вероятно после релиза. Повторное решение о переносе, Mac и Apple Developer сейчас не требуются; отдельный будущий старт не назначен.
3. CAP24: полный учёт прибыли с предоставленной себестоимостью/внешними затратами либо честно ограниченный вклад после расходов площадки. Минимум не должен обещать неизвестные расходы.
4. Издатель/контакты/география, число мест бесплатной беты, окно публикации и необходимые оплачиваемые ресурсы.
5. Режим ручной смысловой приёмки: полный просмотр либо описанное в TEST_PLAN риск-ориентированное покрытие при сохранении всех автоматизированных запусков.

Выбор библиотек, схемы БД, реализация шифрования/очередей, endpoint mappings и исправление дефектов не перекладываются на владельца.
