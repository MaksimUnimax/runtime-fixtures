### Почему нельзя загрузить существующий developer ZIP

Его прежняя точная инвентаризация: Manifest V3; \`action.default_popup=popup.html\`; service worker \`service_worker_entry.js\`; пять API permissions — \`storage\`, \`alarms\`, \`tabs\`, \`unlimitedStorage\`, \`scripting\`; 27 \`host_permissions\`, включая \`http://127.0.0.1:43100/*\` и \`http://127.0.0.1:43101/*\`. \`content_scripts.matches\` содержит ChatGPT (2 шаблона), Алису (1), Qwen (1), но **не** доказывает установленную поддержку всех режимов этих ИИ. Разрешения и назначение каждого домена нужно повторно оценивать на **новом точном Opera candidate**, а не переписывать содержимое проверенного developer ZIP.

В этом developer ZIP исторически не было PNG-иконок и значений \`manifest.icons\`/ \`action.default_icon\`. Это **не означает**, что текущий store-mode builder не умеет вставлять иконки: \`composition.json\` содержит три исходные статические PNG (\`16/48/128\`), и store-only builder обрабатывает их отдельно. Но фактического Opera release ZIP, его ZIP CRC, non-interlaced PNG, хеша и publisher review пока **нет**.

Принятый B1 Chrome-only режим имеет \`releaseScope: CHROME_ONLY\` и уже проверялся на запрет применения как доказательства Opera transition. Не считать Chrome-only manifest автоматическим Opera publisher package. Для Opera нужен конкретный утверждённый канал, точный конечный ZIP и доказанная совместимость, а не переименование Chromium/Chrome архива.

## 3. Минимальная цепочка для настоящего Opera STORE-1 → STORE-2

1. **Выбрать и заморозить реальный checkout и release identity.** \`main db531\` — лишь проверенный SOURCE-срез документа. Для фактического пакета B/Ops и владелец устанавливают подлинную уже одобренную \`octoport_release_authority_v1\`, привязанную к **фактическим** \`HEAD/tree\`, \`0.2.37\`, \`control_plane_v2\`, migration \`61\`, \`PREPRODUCTION\`, двум разным каноническим HTTPS origins и настоящему принятому публичному Ed25519 trust bundle. **UNKNOWN** не заменять тестовым signer, фальшивым каталогом или ключом из локального I1.
2. **C проверяет точный Opera-target package.** Отдельная конечная identity/версия, реальный package SHA256 и архивные байты, manifest, icons, permissions, runtime/config/trust, B1-подтверждение в применимом режиме, независимый reviewer и все обязательные CI точного исходника. Наличие только Chrome/Firefox B1 source modes **не** подтверждает Opera package flow; если маршрута нет, это отдельный подтверждаемый технический блок, а не повод применять Chrome-only approval.
3. **B/Ops подтверждает совместимость целевого сервера.** На точном пакете нужны \`release/catalog/profile\`, нормальные \`authenticated=true\`, \`workAllowed=true\` и безопасное восстановление лишь для реально затронутого среза. Live/DB не менять без отдельного полномочия.
4. **A и назначенный Тестер подтверждают настоящий Opera runtime.** Браузер, ОС, carrier ID, exact ZIP hash; исходный toolbar popup (не sidebar, новая вкладка или отдельное окно), нормальный device flow, магазин, Start, один явный read-only результат Ozon/WB в том же ИИ, Finish; отрицательные/UNKNOWN не повторяются скрыто. R53 worker identity P2 и прежние platform refusals не обходить. Отдельно проверить перенос ключей внутри *того же popup*, если заявлен для этой версии. Для согласованного исходного сценария отдельно сохранить безопасное доказательство: конкретная подтверждённая учётная запись/магазин, разрешённая операция чтения Ozon/WB, объём переданного **пользователем** результата выбранному ИИ, доставка ровно один раз и отсутствие передачи ключей/скрытого external-store export; никаких сырых данных или пользовательских токенов в evidence. Это функциональное свидетельство **не** является проверкой разрешённости внешней передачи по политике Opera: при неопределённости или применимости её запрета STORE-1 остаётся закрытым для подачи, даже когда кнопки и auth работают.
5. **Проверяемый путь ревьюера.** Только действительный ограниченный тестовый аккаунт/синтетический магазин и штатный OTP/device flow с реальной разрешённой выдачей. Никаких секретов владельца, универсального OTP, отключения подписи, reviewer-only обхода, других профилей или фиктивного PASS.
6. **Издатель выбирает фактические поля и подаёт только готовый пакет.** Проверить category/license/description/screenshots/support/disclosures, upload hash, item ID, видимость, фактический статус и timestamp через настоящий Opera dashboard. Подготовленный текст, GitHub CI, upload, submission, approval и publication — **разные** события. Владелец уже дал **общее условное** разрешение на раннюю публикацию по [STORE_POLICY](../../development/coordination/STORE_POLICY.md) и [PUBLICATION](PUBLICATION.md). Но его применимость к **конкретному Opera item, конечному SHA пакета и режиму распространения** необходимо подтвердить перед действием, вместе с фактическим доступом издателя и достигнутым безопасным минимумом. Пока точная область полномочия/доступ неизвестны, статус **AUTHORITY_UNKNOWN**, Submit не выполняется; регистрация издателя и этот документ сами по себе не являются полномочием подачи. При реально отсутствующем разрешении требуется только минимальное адресное действие владельца, а не повторный абстрактный запрос на весь ранний Store. Независимо от этого разрешения **дополнительно обязателен** отдельный `PRIVACY_POLICY_FIT=PASS` для точного потока Ozon/WB → выбранный ИИ по правилам Opera; пока допустимость передачи частных данных не доказана, Store Submit запрещён.
7. **STORE-3 после принятой установки.** Переход \`N → N+1\` для того же Opera item/extension identity с сохранением account/store/keys, штатным обновлением и без replay после UNKNOWN. Яндекс Браузер, даже через каталог Opera, получает **отдельную** установленную проверку, не Opera PASS по умолчанию.
