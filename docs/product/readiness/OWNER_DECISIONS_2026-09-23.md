## Найденные правила AI-авторизации

Основания: docs/integrations/ai/README.md; docs/operations/MONITORING.md; docs/development/stream2/S2_L5B_AUTH_SESSION_AUTHORITY_AND_DEEP_PROBE_FOUNDATION_R1_2026-09-18.md; docs/development/stream2/S2_L8_WHOLE_LLM_HEALTH_FINAL_ACCEPTANCE_2026-09-19.md.

1. Сначала NO-SESSION проверки всех восьми провайдеров: ChatGPT, Alice, DeepSeek, Grok, Claude, Gemini, Qwen, Kimi.
2. Глубокие проверки используют девять идентичностей поверхностей: у ChatGPT отдельно Standard и Work. Work не определяется одним URL: требуется положительная идентичность нужной поверхности/контекста по принятому контракту.
3. Только отдельная техническая сессия и фиксированный разрешённый Health-диалог. Личная история, чужие профили и произвольные диалоги не используются как fallback.
4. Runtime получает opaque handle сессии; содержимое cookies/storageState/паролей/OTP не переносится в Git/evidence. Низкоуровневые session loaders работают только в закрытой runtime-области.
5. Exactly-one-send; после неопределённого исхода Send не повторять автоматически. Login expired, verification/CAPTCHA, blocked account и network uncertainty отличаются от продуктового BROKEN.
6. Отсутствующая техническая сессия не останавливает все публичные проверки и разработку. Владелец нужен для конкретного входа/2FA; он не должен вручную выполнять каждый периодический Health.
7. Первоначальные адаптеры расширения ChatGPT/Alice и мониторинг восьми провайдеров — разные матрицы. Ответ «все из ТЗ» сохраняет обе матрицы; он не является новым требованием немедленно поддержать все восемь в расширении.
8. Регистрация внешнего аккаунта выполняется только в фактически нужном сервисе через его официальный flow, с фиксацией подтверждённой identity. «В базе один зарегистрирован» не позволяет выдумать, что это Chrome publisher или аккаунт любого ИИ.

## CAP-24 и объём первой беты

Обязательным остаётся корректный расчёт по данным площадки: продажи, комиссии, логистика, хранение/placement, возвраты, реклама; пропуски и распределяемые общие суммы видны. Ошибка XLSX/пропущенное хранение не оправдываются отсутствием себестоимости.

Результат называется вкладом после учтённых расходов площадки. Полная прибыль с себестоимостью/внешними расходами/налогами отложена по решению владельца. Полный CAP24 расширяется позже; перенос 45 сценариев и проверки их безопасных границ не отменяются.

## Набор 100 → 200 → 300

Считается общий лимит принятых регистраций по существующей BETA_ADMISSION policy, а не дополнительные 100+200+300 новых мест. Место не возвращается автоматически при удалении аккаунта. Увеличение лимита делается штатным админ-действием с revision/requestId/audit после проверки стабильности предыдущей волны; не по таймеру и не прямой правкой таблицы.

До C06/C07 остаётся закрытый owner-test режим. Отдельная регистрация второго тестового email требует штатного согласованного пути, не скрытого bypass. Адрес уже дан: повторно просить его у владельца нельзя.

## Приём JSON

Владелец не умеет пользоваться SFTP и выбрал последовательный ввод в своей консоли. Подготовлена одна команда: python3 /root/octoport-owner-intake/fill_marketplace_json.py. Порядок в [OWNER_SETUP.md](OWNER_SETUP.md). Закрытый каталог /root/octoport-owner-intake/marketplace-json принимает ozon.json и wb.json; имена, JSON-валидация и права назначаются скриптом. Не присылать секреты сообщением, не коммитить файл и не выводить содержимое в инструменты.

После загрузки A/контроллер проверяет формат локально с выводом только версии/типа формата/числа записей/результата проверки. Права файлов 0600, каталога 0700. Импорт — штатным UI/поддерживаемым importer в изолированном разрешённом тестовом профиле. Не расшифровывать экспорт путём ослабления пароля/валидации; пароль защищённого файла предоставляется отдельным приватным вводом только при фактической необходимости.

Server staging разрешён этим поручением для переноса тестовых данных владельца; это не облачное хранение ключей продукта. После успешного подтверждённого импорта staging очищается, либо фиксируется конкретный незакрытый импорт и срок повторной проверки. Единственным обычным местом хранения остаётся локальное хранилище расширения в разрешённом профиле.

## Публикация этих уточнений контроллером

Владелец прямо указал, что контроллер может сам менять сервер и GitHub, и оспорил обязательное ожидание C для документации. В этом поручении контроллер самостоятельно доводит документационные уточнения до main через отдельную чистую ветку и обычное GitHub-слияние с проверками и свежей базой. C получает уведомление о точном результате, а не задание заново внести эти правки.

Это ограниченный документационный scope: не разрешение переписывать незакоммиченный C04, менять DB/migrations, публиковать production или отключать hooks/CI. Повседневная интеграция исполняемого продукта A/B остаётся у C. Постоянные промпты не меняются; актуальное прямое поручение владельца имеет приоритет в этой конкретной операции.

## Дополнение 2026-09-24: owner gates для первого store-кандидата

- Действий владельца **сейчас нет**. Прежний немедленный запрос обычного OTP/login был преждевременным: A/C сначала подготавливают точный пакет, installed acceptance и конкретную проверку. Только если эта подготовленная проверка реально требует owner OTP/2FA, запрашивается одно ограниченное окно входа; коды, cookies, токены и содержимое почты в чат/логи не передаются.
- Любая минималистичная иконка с осьминогом заранее одобрена владельцем для расширения и первой магазинной подачи. A создаёт и использует такую иконку без нового согласования; позже её можно заменить обычным обновлением.
- Публичный адрес поддержки подготовлен командой как `support@octoport.ru`; личный адрес владельца не публикуется. На сервере проверены Exim routing и SMTP RCPT acceptance без тестовой доставки владельцу; фактический внешний delivery receipt остаётся отдельным уровнем доказательства, если понадобится перед Submit.
- Ранняя подача разрешена по мере готовности каждого канала; не ждать C06, всех браузеров или Safari. Перед фактическим Submit всё равно сверяются текущие требования конкретного магазина и сохраняется реальный submission/moderation receipt.
