## 2. Что автоматизируют A/B/C, а что проверяет человек

| Слой | Исполнитель | Что доказывает |
|---|---|---|
| Контракт/fixtures | A/B/C | Парсинг, подписи, auth, разрешённые операции, ошибки, лимиты, вычисления, отсутствие утечки |
| Исходник и извлечённый пакет | A/C | Что в ZIP действительно попал проверенный runtime; воспроизводимость/хеши |
| Установленный браузер с synthetic data | A | DOM/composer/кнопки/MV3/restart/files/isolation на реальной поверхности браузера |
| Live provider + разрешённая сессия ИИ | A с подготовленными владельцем входами | Что данные реально получаются и доходят в нужный диалог/файл |
| Независимая численная сверка | A + контрольные итоги владельца | Суммы, периоды, знаки, join, дубли, отсутствующие строки |
| Смысловая оценка | Владелец; контроллер готовит разбор | Правильность бизнес-вывода, полезность, применимость рекомендации, опасные необоснованные выводы |
| Production/mail/TG/store | B/C + точечное участие владельца | Доставка до его ящика/Telegram, реальный publisher/account/device и опубликованный пакет |

ИИ может проверить арифметику и предварительно оценить ответ другой модели. Это полезный фильтр, но не независимое окончательное доказательство смысловой правильности. Проверка «кнопка нажалась» также не означает, что ИИ прочитал attachment и понял таблицу.

## 3. Перенос Ozon → общий runtime → WB

1. Зафиксировать эталонные IDs и исходные критерии; не переносить приватные числовые результаты в общий репозиторий.
2. Выделить общие механики: parsing/HELP, dependency closure, read-effect, cardinality, quota, recovery, delivery, durability, privacy. Они получают одинаковые проверки с двумя адаптерами.
3. Для Ozon сверить новый runtime с эталоном поведенческим тестом. Старый файл рядом с новым кодом — не доказательство переноса.
4. Для каждой WB-строки заполнить карту операции по официальной схеме/registry и текущим правам, включая семантику метрик. В таблице пока стоят честные `API_MAPPING_REQUIRED`; это техническая очередь A/C.
5. Создать WB fixtures с собственными IDs, схемами складов/заказов/статусов, nullable и периодами. Не переименовывать Ozon JSON в WB.
6. Пройти deterministic/source/package/installed. Затем запускать реальные вопросы с разрешёнными кабинетами и контрольными периодами.
7. Закрывать отдельно функциональную полноту, безопасность отказа, качество ответа и удобство. Provider outage/нет прав/нет данных не превращаются в дефект кода, но и не дают полноценный feature PASS.

## 5. Данные для воспроизводимого бизнес-прогона

Выбираем один закрытый календарный месяц с продажами/возвратами/рекламой и дополнительный короткий период 7–14 дней. Даты, часовой пояс, валюта, модель поставок и время формирования отчёта фиксируются. «Вчера» сохраняется как конкретная дата каждого run, а не плавает между сравниваемыми ответами.

Набор должен включать обычный товар, возврат/отмену, расход рекламы, остаток и пропущенную/ограниченную строку. Каталог/SKU/кампании получают разработчики через продукт; владелец не составляет вручную весь ассортимент. Если в кабинете нет реального случая приёмки/возврата/аварии, используется отдельный synthetic/replay тест с точной маркировкой, а live-критерий остаётся непроверенным.

Для финансов выбираем независимый официальный итог. Допуск округления определяется документированными единицами/округлением источника, а не произвольными 1–5%, скрывающими ошибку. Для закрытого периода учитываются возможные поздние корректировки; для текущего — задержка источника.

Приватный gold set остаётся на разрешённом устройстве/в защищённой тестовой области с заранее определённым сроком. В Git — синтетические fixtures и безопасные evidence IDs. Если диагностика конкретного дефекта требует исходного файла, доступ/срок/удаление согласуются именно для этого файла; базовое правило не расширяется на постоянный сбор отчётов.

## 6. Карточка каждого run

Обязательные поля: scenario ID; marketplace; browser/OS/version; AI surface и видимая модель/режим; extension version/package SHA/source SHA; auth/profile/contract revision без секретов; период и dataset ID; ожидаемые показатели; действия/число бизнес-запросов; результат доставки; численная сверка; предварительная смысловая оценка; решение владельца; дефект/ограничение; следующий проверяемый шаг.

Статусы не сводить в одно слово PASS:

- `NOT_RUN`, `BLOCKED_OWNER`, `BLOCKED_ENVIRONMENT`, `BLOCKED_PROVIDER`, `BLOCKED_ENTITLEMENT` — непроверенное/заблокированное.
- `FAIL_PRODUCT`, `FAIL_MODEL_REASONING`, `FAIL_DATA_INTERPRETATION`, `FAIL_DELIVERY` — конкретная неудача.
- `PASS_BOUNDARY` — правильно объяснено ограничение, но полноценная возможность не доказана.
- `PASS_FEATURE` — функция доказана на указанном наборе и окружении.
- `HUMAN_REVIEW_PENDING`, `HUMAN_ACCEPTED`, `HUMAN_REJECTED` — отдельное состояние оценки владельца.

Оценка ответа: (1) факты и арифметика; (2) полнота/ограничения; (3) правильность причинных выводов; (4) пригодность действия; (5) самостоятельный выбор данных/восстановления. Каждый пункт 0/1/2, сумма /10. Любая утечка, смешение магазинов, выдуманная финансовая цифра или скрытый опасный повтор — критический FAIL независимо от среднего балла. Порог ≥8/10 без критических ошибок — предлагаемый критерий смысловой приёмки, который владелец может ужесточить; не утверждение, что текущие ответы его достигли.

## 7. Очерёдность и время владельца — Alice-first

Сначала полный технический Alice-scope B22; ранний STD-01 до него не принят. Затем восемь контрольных задач B23: STD-01, STD-08, STD-16, STD-20, CAP-01, CAP-12, CAP-19, CAP-24. Это начало всей смысловой проверки, не замена остальных вопросов.

До первого production проходят все 45 основных и 8 резервных вопросов на Алисе, Ozon и WB по фактической применимости. Недоступная метрика требует доказанного ограничения; PASS_BOUNDARY не закрывает обещанную функцию. 53 вопроса × 2 площадки = 106 планируемых пар до уточнения индивидуальной применимости, не утверждение о 106 одинаковых live-запусках. Резервные STD-21…28 имеют свои lineage/gold; восемь контрольных B23 — повторные ранние проверки основных вопросов, не резервные.

Четыре браузера (Chrome, Opera, Yandex, Firefox) проходят полную техническую матрицу и согласованные смысловые controls по применимости. Не умножать вслепую 106 на четыре и не пропускать специфическую доставку/authority каждого браузера. При каждом из семи патчей повторяется весь применимый смысловой scope нового ИИ и затронутая регрессия активных; ChatGPT Work отдельно. Прежние формулы 270 запусков для трёх поверхностей и 138 ручных просмотров не являются текущим планом; сохранены в Git-истории до решения 02.11.

Владелец получает готовые пакеты по 5–8 результатов с независимыми контрольными цифрами и расхождениями. Предварительная H-оценка 10–20 минут на пару даёт около 18–35 часов подробного просмотра 106 пар, без ожиданий и сложных повторов; это не замер и не обязательная нагрузка. После первых десяти пригодных результатов оценка пересчитывается по факту, повторные/неприменимые пары учитываются отдельно. Автоматическая сверка не объявляется HUMAN_ACCEPTED. Время семи последующих патчей оценивается отдельно по реальному остаточному ручному scope, без старых 24–54 часов как готовой общей суммы.

## 8. Правило вызова владельца

Не звать владельца на неготовую установку или зависший тест. Перед окном разработчик проверяет: exact RC доступна, среда/сессия готовы, нужные API-права известны, synthetic gates пройдены, действия безопасны и укладываются в заявленное время, есть карточка ожидаемого результата. После воспроизводимого технического дефекта окно прекращается для этого кейса; владелец не ждёт дебаг. Поток исправляет дефект и возвращается с конкретным повторным контролем.

При провале не вычёркивать сценарий ради движения по таблице: сохраняются причина, ответственный, условие возврата и незакрытый gate. Независимые задачи можно продолжать; старая команда эталона NO_SKIP не означает остановку всей нынешней параллельной разработки.
