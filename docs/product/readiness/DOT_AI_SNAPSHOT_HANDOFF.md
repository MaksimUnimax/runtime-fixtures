## 2. Порядок и распределение работы — решение владельца

1. Владелец сообщил, что авторизовал ChatGPT и Алису в сохранённом серверном Chromium. Это USER_REPORTED, не новый самостоятельно проверенный LIVE PASS. **ChatGPT и Алису доту не снимать, не запрашивать их авторизацию и не собирать их данные.** Их проверяет Тестер самостоятельно. ChatGPT Work пока исключён.
2. Для остальных ИИ владелец при необходимости сам авторизует браузер дота штатным способом. Дот собирает данные в своём доступном браузере и передаёт их сюда. Перенос профиля, cookies или сеансов на Easyscript не требуется.
3. Тестер читает полученные материалы, уточняет только реально недостающие состояния, пишет код в разрешённом scope и проверяет адаптер. Дот — сборщик UI-данных и, по следующему точному запросу, исполнитель проверки конкретного кандидата; это не передача ему исходников, роли Тестера или чужого WIP.
4. Дот не управляет сохранённым Chromium Тестера, его драйвером, QA_COMMAND, профилем и установленным расширением. A/B/C и Контроллер не затрагиваются.
5. Сначала группа A, затем B и C. Если один сайт блокирован, сохранить точное препятствие и собирать следующий доступный. Сайт, модель внутри агрегатора и режим одного сайта — разные понятия: одинаковая модель в Poe и на сайте производителя не доказывает одинаковый DOM/адаптер.
6. Нужны все доступные поверхности из списка. Недоступность части не обнуляет полученный пакет. Дополнительный официальный обычный текстовый AI-чат можно добавить отдельной строкой после проверки его назначения; не уходить в каталоги клонов, API-only консоли или несвязанные приложения.
7. Утверждение «остальные не работают из-за Chromium» пока **гипотеза владельца**, причина UNKNOWN. Не объявлять несовместимость браузера без точного наблюдения. Записывать фактический браузер/версию/ОС и сообщение сайта.
8. Этот порядок действует для дальнейших обменов: запрос Тестера → вход владельца при необходимости → данные дота → код Тестера → точечная установленная проверка нужного кандидата. Не повторять уже полученные неизменные снимки без конкретной причины.

## 4. Что нужно для написания адаптера

Нужны **PNG + доступное дерево интерфейса + очищенный DOM релевантных узлов + последовательность действий и фактические результаты**. Внешний вид помогает понять интерфейс; технические данные нужны для выбора элементов и проверки их принадлежности диалогу.

Для каждого состояния записать UTC, site_id, фактический origin, путь тестового чата, состояние входа, видимый режим/модель, язык интерфейса, браузер/версию/ОС, viewport, масштаб, наличие расширения и его точную версию/SHA (если оно установлено). Нет установленного Октопорта — прямо указать.

Для DOM/дерева нужны только следующие участки:
- корень текущего диалога, контейнер сообщений, отдельное сообщение пользователя и ассистента;
- основной composer, ближайший form/container, textbox/contenteditable/textarea, реальные атрибуты role, aria-label, data-testid, type, disabled, aria-disabled, aria-busy, placeholder, contenteditable, readonly;
- Send, Stop, Retry/Regenerate, Attach и Copy: видимые подписи, связь с composer/сообщением, состояние доступности;
- кодовый блок, его язык, текстовый контейнер, кнопка Copy, Expand/Collapse и виртуализированный редактор, если присутствует;
- штатная область прикрепления файла, связанный input[type=file] после открытия обычного меню, accept/multiple, карточка вложения, progress/error/ready, Remove;
- выбранная строка истории только тестового диалога и наблюдаемый источник conversation/message identity.

Передать очищенный outerHTML выбранного узла и 1–3 уровней его ближайших контейнеров либо эквивалентное дерево; не полный HTML страницы. Убрать script/style, обработчики, токены, email/телефон/аватар/имя аккаунта, чужие диалоги и приватные URL-параметры. Применять постоянные замены вроде CHAT_A / MSG_A1, сохраняя одинаковость ID между снимками, тип и структуру. Не удалять полезные структурные имена атрибутов.

Если штатные возможности инструмента позволяют, записать для каждого предлагаемого селектора число совпадений и число видимых совпадений в данном состоянии, связанный контейнер и исключённые ложные цели. Не выдумывать селекторы по картинке; кандидат по одному снимку помечать UNVERIFIED. Проверку чтением DOM выполнять только доступным разрешённым инструментом, без инъекции скрытых API, смены окружения или обхода запрета инструмента.

Если DOM недоступен, передать PNG + accessibility snapshot + точные наблюдения и поставить DOM_UNAVAILABLE/PARTIAL. Не выдумывать отсутствующие данные. Тестер сформирует конкретный оставшийся запрос.

## 6. Готовые безопасные тексты и файлы

### Основной промпт для одного ответа

Отправить в обычный тестовый чат один раз, подставив site_id и UTC:

> Это проверка отображения интерфейса, а не просьба выполнить код или внешние действия. Не используй инструменты, поиск и внешние сервисы. Выведи строку OCTOPORT_UI_BEGIN_<site_id>_<UTC>, затем два отдельных блока кода. Первый — text с одной строкой: OCTOPORT_UI_PROBE_V1 {"case":"single","value":17}. Второй — json с переносами строк: {"case":"multi","label":"Тест ё 😀","values":[1,2,3],"literal":"<tag> & quote"}. После блоков напиши OCTOPORT_UI_END_<site_id>_<UTC>. Ничего не запускай.

Сохранить фактически полученный ответ; если модель изменила текст, отметить это отдельно от работы UI. Это не обучение поведения ИИ и не тест качества ответов. Команды маркетплейсов и реальные ключи в этот запрос не входят.

При необходимости S06 — один дополнительный запрос: вывести один блок text из 120 пронумерованных коротких строк, с уникальными BEGIN/LAST-маркерами, без выполнения. Не повторять массово ради достижения скрытого лимита; если виртуализация не проявилась — так и записать.

### Файлы

Создать один общий комплект обычных синтетических файлов доступными средствами и переиспользовать на сайтах:
- `octoport-ui-small.txt`: UTF-8, несколько строк с BEGIN/MIDDLE/END, русским текстом и emoji;
- `octoport-ui-large.txt`: UTF-8, 1 048 576 байт (если существующее средство позволяет получить точный размер; иначе указать фактический), нумерованные нейтральные строки и три непредсказуемых контрольных маркера в начале, середине и конце;
- `octoport-ui-small.csv` и `octoport-ui-small.json`: по несколько синтетических строк для наблюдения type acceptance; `small.pdf` только если уже доступно штатное средство создания.

Хешировать локальные исходные байты. Контрольные значения большого файла не писать в сопровождающем промпте. Промпт к вложению: «Прочитай приложенный файл; выпиши значения маркеров BEGIN, MIDDLE и END и последнюю строку. Не используй внешние инструменты». Ответ модели подтверждает доступ к указанным фрагментам, но сам по себе **не доказывает побайтовую полноту** или SHA256 полученного ею файла. Если доступно обычное скачивание отправленного вложения — можно сравнить его bytes/SHA256 с исходником; иначе FILE_BYTE_IDENTITY_NOT_PROVEN.

Для базового пакета достаточно фактической отправки TXT. CSV/JSON/PDF сначала фиксировать по видимому accept и штатному preview; «расширение перечислено в accept» не означает доказанную успешную доставку. Непроверенные XLSX/DOCX/ZIP и максимальные размеры/число файлов не объявлять поддержанными. Искать предельный размер загрузками большого объёма не требуется.

## 7. Дополнительные наблюдения для сложных UI

- **Composer:** тип редактора, обычная вставка/многострочность, что включает Send; основной ввод отдельно от поиска истории, командного поиска, редактора кода, modal input.
- **Send/Stop:** точные независимые признаки enabled, disabled, generating, upload busy, неизвестного состояния. Видимый Stop не должен быть принят за Send. Уточнить, может ли Enter отправлять при наличии файла; наблюдение не требует второй отправки.
- **Ответ и команды:** завершённый assistant turn, границы вложенных цитат, code fence, inline code, таблиц; Copy whole answer отдельно от Copy code. Прокрутка и виртуализация не должны подменять полный текст видимым фрагментом.
- **Идентичность:** URL до/после первой отправки, стабильный token чата, принадлежность message ID, выбранный чат в истории, SPA-переход, reload. ID аккаунта/модели/проекта не считать ID чата.
- **Файл:** visible attach → input/drop surface → upload progress → ready → sent attachment → ответ. Имя файла само по себе не доказывает окончание загрузки. Не обращаться к скрытому input в обход закрытого гостевого/платного пути.
