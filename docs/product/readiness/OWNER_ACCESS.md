# Постоянный администратор проекта

Актуальное поручение владельца 2026-09-23: новый предоставленный им email становится постоянной учётной записью владельца проекта, минимум на всю бету. Адреса и идентификаторы хранятся только в /root/octoport-owner-intake/owner-inputs.json и закрытой записи owner-access.json. Это назначение роли, а не жёстко зашитый в исходники email.

## Проверенные факты и незавершённая операция

Read-only проверка работающей owner-test БД: один подтверждённый EMAIL-пользователь, ACTIVE admin principal и активная роль ADMIN_OWNER у прежнего адреса. Нового пользователя нет. Набор CLOSED, capacity=1, admitted=1, revision=3. Проверка исходников main 1bb60d3 и работающего API d31a59a подтверждает passwordless OTP и штатные административные routes.

Смена пока не выполнена: нужны подтверждения почты, регистрация нового пользователя и безопасное окно допуска. Предыдущий владелец остаётся действующим до проверки нового. Этот документ фиксирует решение и порядок, не заявляет LIVE acceptance.

## Порядок переноса

1. Получить свежий обычный OTP-вход прежнего администратора и отдельную admin session. Не извлекать чужие cookies, не подписывать себе сессию и не подменять actor ID.
2. Подтвердить новую почту штатным OTP. Текущий CLOSED/1 изолирует регистрацию: предварительно подготовить ограниченное окно только для этой операции без публичного открытия набора. Изменение квоты только штатным авторизованным beta API с revision/requestId/audit; при отсутствии безопасной изоляции сначала запрос B на адресный admission path, а не SQL-вставка пользователя. Не отключать OTP/auth проверки. Код сам по себе ещё не означает принятую регистрацию.
3. Через admin API создать principal для нового подтверждённого user ID и выдать ADMIN_OWNER. Затем в отдельной сессии новой учётной записи проверить /v1/admin/me и фактическую доступность управления.
4. Только после этого снять ADMIN_OWNER с прежнего principal. Других админ-ролей без конкретной обязанности не выдавать: выбран обычный пользователь беты. Его собственный account membership не удалять и не переносить магазины/данные между аккаунтами.
5. Проверить, что новый ADMIN_OWNER активен, старый не имеет административных полномочий даже с прежней сессией, последний владелец защищён от удаления, набор снова CLOSED. Сохранить безопасную квитанцию с состояниями до/после и audit IDs, без OTP/cookies.
6. Последующие назначения/снятия владельцев разрешены нормальным управлением ролями; постоянный email не означает неизменяемые полномочия.

Первичный admin:bootstrap-owner не подходит для этой смены: он работает только при отсутствии активных admin grants и только с уже подтверждённым пользователем. Повторный bootstrap не обходится изменением таблиц. Пароль для Octoport не генерируется, потому что такого способа входа нет. Пароль от почтового ящика не нужен.

Почтовые коды вводятся владельцем в штатный вход либо используются контроллером только для явно порученной конкретной операции подтверждения. Не сохранять их в скриптах, Git, отчётах или постоянных файлах. Запросить коды непосредственно перед выполнением, а не перед длинным CI.

## Граница готовности

Перенос роли не закрывает B06 и production security review. До публичной беты остаются усиленная авторизация администраторов, проверка reauthentication/session revocation, безопасного аудита и негативных сценариев. Проверка админки не равна приёмке marketplace/AI функций.

Владелец не программист: контроллер готовит операции и даёт только необходимые действия с почтой/интерфейсом. B/C продолжают независимую работу; общий набор 100/200/300 этим поручением не запускается.
