# Octoport: минимальный продукт и подготовка владельца

Актуальное уточнение: [ответы и решения владельца 2026-09-23](OWNER_DECISIONS_2026-09-23.md). При расхождении прежних вопросов/планов с этой записью применяется запись владельца.

Дата проверки: 23 сентября 2026. Это результат проверки документации, исходников и состояния сервера, а не приёмка готового продукта.

## Вывод

Основное ТЗ существует: 26 требований SA-*, описание UX и матрица приёмки. Не хватало связанного плана «конечная функция → данные → тест → участие владельца → выпуск». Этот комплект добавляет такую детализацию, сохраняет существующие решения и выделяет действительно неизвестное.

Заранее можно снять большую часть ожиданий ключей, аккаунтов и исходных данных. Полностью исключить владельца нельзя: остаются подтверждение личности/2FA, доступ к своим кабинетам, оценка бизнес-выводов, отдельные проверки на его устройствах и разрешение выпуска. Эти действия не должны превращаться в ожидание всего A/B/C.

## Что выяснено фактически

- Канонический remote main при исследовании: `de45ce6c6b9dc99c79c4140e28043e17f10fdda5`. Рабочие A/B/C продолжают меняться; это снимок, не заявление об их текущем HEAD.
- Почта владельца предоставлена. Реальная OTP-проверка ещё не принята; текущая регистрация CLOSED и 1/1 мест занято. Адрес хранится вне Git.
- SMTP работающего owner-test API уже указывает на локальный почтовый транспорт. Покупать новый SMTP или передавать пароль от личной почты сейчас не требуется. Ранее выполненные DNS/PTR-настройки не объявляются заново незакрытыми.
- Telegram secret/bindings теперь подготовлены вне Git; getMe/getChat и одна API-отправка прошли. Человеческое получение подтверждено владельцем; полный monitoring runtime ещё не принят.
- В Telegram нужны **числовой user ID администратора** и **chat ID адресата**, а не IP. Токен не отправляется в чат с ИИ.
- Эталон содержит **44 основных сценария + CAP-25 = 45**, а не «45 закрытых тестов». CAP-24 переоткрыт из-за хранения/placement; CAP-22 частичный; CAP-25 незавершён. У других строк тоже сохранены entitlement/provider/guidance ограничения.
- WB нельзя принять простой заменой Ozon на WB в вопросах: отличаются модели заказов, статусы, склады, идентификаторы, расходы, рекламная атрибуция и доступные метрики.
- Сайт/SEO остаётся отдельной работой, но рабочие страницы входа, установки, поддержки и privacy нужны перед распространением. Отсутствие SEO не причина откладывать эти страницы.
- [Safari исключён владельцем из беты](SAFARI_AFTER_RELEASE_2026-09-23.md), вероятная работа после релиза без обещанной даты. Бету не блокирует; сейчас Mac/Apple Developer не запрашивать. Для будущего выпуска нужен реальный Safari/macOS для приёмки. На текущей официальной странице Apple есть web packager через App Store Connect без локального Mac/Xcode: старое утверждение «Mac обязателен именно для упаковки» больше нельзя использовать без проверки выбранного маршрута.

## Когда резервировать время

Планировать лучше окна по готовности результата, а не ежедневное присутствие. Оценки ниже — активное время владельца, без ожидания проверки издателя, ответов API и исправления дефектов.

| Окно | Ориентир | Условие вызова |
|---|---:|---|
| Подготовить почты, Telegram, перечень кабинетов/устройств и разрешённые данные | 60–120 минут | Можно начать сейчас; если аккаунты уже есть, быстрее |
| Publisher accounts | Регистрация выполнена по подтверждению владельца | Доступ/недостающие поля проверяются при конкретной подаче; Apple отложен. Не отправлять владельца регистрироваться повторно |
| Один контрольный набор бизнес-данных | 45–120 минут | Автоматически собраны данные; владелец уточняет только учёт и контекст |
| Почта + Telegram | 25–45 минут | C/B прислали готовую карточку точной сборки и прошли технический preflight |
| Установка, два браузера беты, перенос, UX; Safari отложен | 45–90 минут | A проверил пакет и автоматизируемые сценарии |
| Бизнес-приёмка | Отдельный существенный блок | См. расчёт в TEST_PLAN; нельзя честно обещать «все сценарии за час» |
| Выпуск | 20–40 минут на канал | Готовы RC, описание, доступ ревьюера, backup и план возврата |

Не складывать механически все 38 строк реестра: многие выполняются за один вход в кабинет, часть возникает только при смене ключа/тарифа/издателя.

## Организация запросов владельцу

Поток заводит запрос по конкретному ID Oxx: что нужно, готовность технической части, время, критерий успеха, срок и что он продолжает. Контроллер объединяет готовые запросы в одно окно. Владелец не переносит API-команды, JSON, логи и отчёты между чатами.

Заблокирован только зависимый live/release шаг. Остальные разрешённые задачи продолжаются по текущему PROTOCOL. Пропущенная ручная проверка остаётся `BLOCKED_OWNER`, а не исчезает из отчёта. Новые временные инструкции не требуют замены трёх постоянных промптов: после принятия C этот комплект читается через общий индекс документации.
