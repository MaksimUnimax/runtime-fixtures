# Магазины расширений и участие владельца

Актуальное уточнение: [ответы и решения владельца 2026-09-23](OWNER_DECISIONS_2026-09-23.md). При расхождении прежних вопросов/планов с этой записью применяется запись владельца.

Проверено по официальным страницам 2026-09-23. Условия аккаунта, доступность оплаты/регистрации по региону и требования dashboard уточняются в настоящем аккаунте владельца. Не обещать фиксированный срок модерации.

## Объём беты и отложенный Safari

[Решение владельца 2026-09-23](SAFARI_AFTER_RELEASE_2026-09-23.md): бета без Safari. Safari / App Store — DEFERRED_POST_RELEASE_BY_OWNER, вероятная работа после релиза без обещанной даты; не блокирует STORE-1…STORE-4/C06/C07 беты. Сейчас Apple Developer, оплату membership и Mac/Safari у владельца не запрашивать. Будущая Safari-публикация потребует собственной приёмки; поддержку в карточке беты не заявлять.

## Постоянный приоритет

По [новому решению владельца](EARLY_STORE_PUBLICATION_2026-09-23.md) ранняя публикация оценивается при каждом контроле и выполняется сразу по минимуму отдельного канала. Аккаунты зарегистрированы; разрешение на ранний Submit/Publish уже дано. [STORE_POLICY](../../development/coordination/STORE_POLICY.md) определяет минимум и обязательную строку отчёта. Регистрация, draft, signing, review и publication — разные подтверждаемые статусы.

## Когда начинаем

Магазинная установка и обновление — часть подготовки беты. Прежний порядок «первый Submit только после C06» заменён следующими gates. C06 использует уже полученные результаты магазинной установки/обновления; нельзя создавать круговую зависимость.

| Gate | Когда / кто | Результат и участие владельца |
|---|---|---|
| STORE-0 | Сейчас, параллельно A/B/C | Регистрация выбранных publisher accounts подтверждена владельцем, кроме Safari; не запрашивать её повторно. C проверяет конкретные поля/доступ при подаче, готовит карточку, privacy/support/install страницы и reviewer flow. SEO не блокирует эти минимальные страницы |
| STORE-1 | Минимальный рабочий срез одного канала по [STORE_POLICY](../../development/coordination/STORE_POLICY.md); не ждать полного закрытия A03/A04/B02/B04/B05/C05 | Точный пакет, обычная установка и заявленный сценарий, безопасность/данные, нужный backend/trust, privacy/карточка и выполнимая инструкция ревьюера. Recovery нужен для реально затронутой среды/изменения, не для независимых будущих работ |
| STORE-2 | Немедленно после STORE-1 любого канала, до C06; разрешение владельца уже получено | Подать раннюю рабочую версию на реальную модерацию/публикацию выбранного канала; зафиксировать item/version/hash/видимость и результат. Не ждать других браузеров. Владелец нужен только для фактически требующегося доступа/подтверждения; текущие лимиты набора сохраняются |
| STORE-3 | После первой магазинной установки; до расширения аудитории | A+C выпускают следующую тестовую версию с большим номером и проверяют реальное обновление N→N+1 того же package ID. Владелец подтверждает Windows install/update и понятность интерфейса |
| STORE-4 | C06 и затем разрешённый C07 | Открытая бета: общий лимит аккаунтов 100→200→300 по результатам наблюдения. Исправления проходят тот же канал и проверку совместимости |

STORE-0 начинается сразу. STORE-1 не ждёт завершения независимых улучшений/всех последующих функций, но требует отсутствия блокирующих дефектов безопасности и данных в выпускаемом объёме. Неподтверждённые функции/браузеры явно исключаются из карточки этой волны; это не отменяет полный product scope. Владелец уже разрешил раннюю подачу/публикацию при выполнении минимума; контроллер фиксирует конкретный ограниченный кандидат и доказательства без повторного абстрактного запроса разрешения. Подано/опубликовано отмечается только после фактического подтверждения магазина.

Для Chrome предпочтителен один постоянный item: Private / trusted testers для первых проверок, затем Public либо Unlisted по решению о распространении. Private тоже проходит модерацию. Unlisted доступен любому, кто знает ссылку, поэтому не заменяет ограничение доступа. При переходе на публичный канал сохраняется item; отдельный тестовый item при необходимости имеет другую идентичность и не доказывает перенос пользовательских данных между ID.

Для раннего присутствия Firefox в каталоге рассмотреть listed AMO с отметкой experimental и честными ограничениями. Подписанный self-distributed XPI остаётся вариантом ограниченного теста, но не считается публикацией в каталоге или завершённой ручной модерацией. Обычного AMO prerelease-channel нет. Для self-distribution C отвечает за HTTPS/update manifest и реальное обновление; смена канала требует проверки маршрута.

### Что проверять в STORE-3

- Установка подписанного/выданного пакета обычным способом; прежний unpacked build удалён из тестового профиля либо строго отделён.
- Обновление существующей установки без удаления расширения: сохранены локальные ключи и магазины, настройки, активация и правильная account identity. Содержимое секретов не попадает в evidence.
- Перезапуск браузера/MV3 worker; корректное завершение либо явное безопасное прерывание незавершённого действия, без повторной отправки при UNKNOWN.
- Совместимость нового backend со старой и новой версиями: распространение обновления не мгновенно. Поведение неподдерживаемой версии и смены разрешений понятно пользователю.
- Чистая установка N+1 и обновление N→N+1 — отдельные результаты. При новых permissions проверяется запрос пользователя.
- Неисправная версия: остановка дальнейшего распространения, доступный магазину rollback/исправляющий пакет и сохранность локальной схемы. Откат backend не возвращает автоматически клиентскую БД и версию на каждом устройстве.
- Evidence: store item/channel, source SHA, package hash, versions N/N+1, браузер/ОС, время наблюдения, результат каждого шага. Публичное расширение аудитории запрещено при потере ключей, account leakage, неверной подписи или повторной отправке.

Chrome требует новую версию ZIP и review для изменения кода. Процентный rollout в dashboard доступен только при более чем 10 000 активных пользователей за семь дней; наша бета 100/200/300 управляется серверной квотой и доступом тестеров, а не выдуманной доступностью этого механизма.

## Различия каналов

| Канал | Владелец | Разработчики | Граница |
|---|---|---|---|
| Chrome Web Store | Собственный Google publisher account, подтверждения/2FA, разовый registration fee по dashboard | ZIP, разрешения/приватность, описание/изображения, тестовая инструкция и доступ | При Submit for Review выбрать нужный режим. Документация допускает отложить публикацию после approval; есть 30-дневное окно, после него draft |
| Mozilla AMO / Firefox | Mozilla account с подтверждённой почтой | Пакет, необходимые исходники/инструкция сборки для reviewer, signing, listed/unlisted route | Подпись нужна для обычного Firefox release/beta, включая самостоятельную unlisted-раздачу; developer temporary install не заменяет её |
| Opera Add-ons | Opera publisher account, принятие условий | Upload, категория/лицензия/описание/иконки/screenshots/support page, совместимость | Проверить текущий процесс фактического выпуска после принятия; не обещать тот же defer-switch, что в Chrome |
| Yandex Browser | Отдельного выдуманного Yandex publisher account не требуется | Проверить конкретный пакет и маршрут установки | Официально используются совместимые расширения из Chrome/Opera каталогов; Yandex runtime всё равно имеет отдельный тест |
| Safari / App Store — после релиза, вне беты | Только при отдельном будущем старте: Apple Account/2FA, enrollment, membership, App Store Connect | Safari-пакет, разрешения, карточка, тестовый путь/TestFlight, реальные runtime proofs | У Apple есть web packager без локального Mac/Xcode; его ограничения проверяются на нашем ZIP. Реальный Safari/macOS тест остаётся обязательным |

Apple указывает 99 USD за год Developer Program с региональными различиями; фактическая сумма/доступность в аккаунте владельца может отличаться. Для организации нужны соответствующие юридические данные/полномочия и, где применимо, D-U-N-S. Не просить владельца присылать документы личности в этот чат: они подаются самому Apple/магазину.

### Если Chrome Web Store недоступен

Путь Opera Add-ons → Яндекс Браузер не требует публикации в Chrome: Яндекс официально устанавливает совместимые расширения из каталога Opera. После approval Opera пользователь открывает карточку в Яндекс Браузере и устанавливает оттуда; отдельного publisher account Яндекса для этого пути нет. A/C проверяют обычную установку и N→N+1 именно из Opera в Yandex, работу продукта и фактическую package identity/trust/origins. Проход Opera не равен Yandex PASS. Причина отказа Chrome, связанная с безопасностью/данными, требует исправления независимо от выбранного магазина. Путь включён в уже разрешённую раннюю публикацию при выполнении минимума конкретного канала.

## Что нужно от владельца до review

Текущий owner gate на 2026-09-24: **действий владельца сейчас нет**. Публичный support contact подготовлен как `support@octoport.ru`; личный адрес владельца не публикуется. Минималистичная иконка с осьминогом заранее одобрена владельцем и создаётся A без повторного согласования. Обычный OTP/login не запрашивается до готового exact installed acceptance; если конкретная подготовленная проверка потребует OTP/2FA, владелец выполняет только этот штатный вход без передачи кода/сессии в чат.

1. При фактической подаче конкретного канала сверяются только реально требуемые dashboard поля: публичное имя/тип издателя, страны распространения и доступ к подтверждениям/оплате. Регистрацию publisher accounts повторно не запрашивать.
2. Контакт поддержки и privacy/deletion запросов для первого store-кандидата — `support@octoport.ru`; техническое описание обработки составляют разработчики по реальному коду.
3. Решение первой волны принято: подтверждённые каналы подаются по мере минимальной готовности с открытыми ограничениями; не ждать остальных браузеров. Это не полная приёмка всего browser scope.
4. Разрешение раннего Submit/Publish уже дано владельцем. Подготовить конкретный пакет/карточку и сохранить receipt; обращаться только за реально недостающим доступом/фактом. Действия с production и расширение набора имеют отдельный exact-artifact план.

## Что готовит C без участия владельца в программировании

- Один проверенный artifact на канал: version, package hash, source SHA, contract/migration/profile compatibility, production endpoints и доверенные ключи из авторитетного input.
- Стабильная идентичность расширения/пакета и допустимые origins/device activation для магазинной сборки; developer ID не должен случайно остаться единственным разрешённым.
- Обоснование каждого permission/host permission и минимальный набор. Удалённый config не подменяет запрещённый remotely hosted executable code в Manifest V3.
- Честная privacy policy: локальные ключи; transient encrypted transfer; отправка выбранных отчётов стороннему ИИ по действию пользователя; account/device metadata; diagnostics; сроки; удаление/контакты. «Мы вообще ничего не передаём» неверно.
- Минимальные HTTPS страницы установки/поддержки/privacy и работающий portal login. Полный маркетинговый сайт/SEO не нужен для их подготовки.
- Безопасный reviewer путь. Если требуется вход, один демонстрационный аккаунт и синтетические данные через нормальный auth flow; никаких ключей владельца, доступа к его почте, постоянного универсального OTP или отключения авторизации ради review. C/B должны доказать, что ревьюер сможет сам завершить предоставленную инструкцию.
- Инструкция воспроизводимой сборки/исходники для магазина, когда требуются; clean install/update и минимальный smoke именно подписанного/выданного пакета.
- Подготовленный ответ модерации с фактами и проверками, без автоматической отправки от имени владельца без разрешения.

## Эксплуатация после публикации

Модерация может попросить уточнение или отклонить пакет; аккаунт может потребовать повторную проверку, membership — продление. UI ИИ и API меняются; понадобятся новые подписанные версии и иногда новые runtime/смысловые проверки. Ротация marketplace token или вход в AI-профиль остаются действиями владельца. Эти зависимости стоят в реестре, а не исчезают после первой подготовки.

Публикация в store и deployment backend — разные операции. При сбое необходимо понимать, можно ли отозвать/приостановить распространение, отключить несовместимую возможность существующей policy и восстановить backend. Нельзя обещать мгновенно откатить уже установленное у всех пользователей расширение.
