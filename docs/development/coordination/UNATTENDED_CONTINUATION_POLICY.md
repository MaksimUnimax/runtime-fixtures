# Самостоятельная работа A/B/C без присутствия владельца и контроллера
Основание: прямое указание владельца 2026-09-28, 17:23 +05. Это уточнение действующего PLAN, а не новый проект.
Правила действуют через свежие controller-notices сразу; код управляющей команды вводится обычной интеграцией C.
Более поздний прямой STOP сохраняет приоритет. Этот документ сам по себе не возобновляет остановленные диалоги.

## Правило выбора работы
Каждый поток сам выполняет разработку, проверку и обычные технические решения в своей области PLAN/SPEC и принятой архитектуры.
Заблокированное действие и весь поток — разные вещи. Недоступность владельца, контроллера, входа, OTP, магазина, Codex или чужого кандидата блокирует только зависимое действие.
На каждой безопасной границе: сохранить результат -> проверить новые адресные входящие -> взять первую действительно готовую задачу. Текущую задачу и две следующие хранить в состоянии, когда они существуют.
Если человеческое действие нужно сейчас, сохранить один точный запрос и подготовленное состояние; сразу продолжить независимую работу. Не ждать ответа в финале сообщения при наличии следующей работы.
После двух обоснованных неудачных гипотез или трёх попыток с теми же входными данными: сохранить воспроизводитель, владельца и условие возврата; взять другую задачу. Новый автопромпт не обнуляет счётчик попыток.
Не повторять тяжёлые тесты/опросы неизменившегося кандидата ради занятости. Новая работа должна закрывать доказанный пробел требования, реализации или уровня проверки.
Отсутствие SOURCE-дефекта не означает, что вся очередь исчерпана: отдельно рассмотреть ещё не проверенные PACKAGE/INSTALLED_SYNTHETIC границы, отказы, обновление, отзыв, перезапуск и совместимость в разрешённой тестовой среде.
Такую проверку нельзя выдавать за LIVE_OWNER, обычный вход, магазинную установку или ручное одобрение оператора. Не внедрять тестовые ключи/обходы в STORE или живой backend.
Если конкретное требование уже полностью доказано на неизменившихся входах, переиспользовать evidence и идти дальше. Не выдумывать новую функциональность.

## Прямое взаимодействие
A/B передают готовые exact SHA C через существующий control.py submit. C сам читает, проверяет, принимает или возвращает точное замечание; отсутствие контроллера не запрещает штатную техническую приёмку.
Пока готовый кандидат ожидает C, автор продолжает свою независимую очередь. C не откладывает все поступления из-за отсутствия владельца для другого сценария.
Адресный вопрос/предложение: /root/octoport-control/peer-handoffs/<TO>/<ID>.request.json. Обязательные поля: id, from, to, created_at, task, plan, base_sha, paths, requested_result, acceptance, evidence, blocked_action.
Автор создаёт запрос один раз атомарно; для нового смысла/входных данных создаёт новый ID. Нельзя перезаписывать чужой запрос.
Получатель пишет свой <ID>.response.json с from, to, state ACKNOWLEDGED|IN_PROGRESS|DONE|BLOCKED, exact_sha/evidence при результате и конкретным next. Ответ может обновлять только получатель.
Проверять входящие в начале цикла и между задачами; ориентир не реже30мин активной работы, без прерывания атомарной операции и без фонового пустого опроса.
C вправе назначить один конкретный общий файл одному автору, определить совместимый интерфейс и тесты потребителей внутри принятой архитектуры. Записать пути/базу/владельца до изменения.
A/B не захватывают чужую область при молчании C. Нужный контракт или назначение фиксируется как зависимость, после чего выбирается доступная собственная работа.
Большие архитектурные/продуктовые решения, отмена инвариантов и расширение полномочий не делегируются этим правилом. Для них сохранить запрос владельцу/контроллеру и двигаться по независимой очереди.

## Исполняемая защита waiting/resume
После интеграции этого кандидата control.py ROLE waiting требует --receipt <queue-scan.json>.
Формат: version1, role, head точного текущего Git, checked_at с timezone; entries покрывают каждый PLAN ID роли.
Каждая entry: id, plan, state, outcome; state = READY|IN_PROGRESS|BLOCKED|DONE|DEFERRED_BY_OWNER.
Для DONE/BLOCKED/DEFERRED_BY_OWNER обязателен непустой evidence[] с проверяемыми ссылками; для BLOCKED также blocked_action, owner, unblock_when и independent_work_complete=true.
READY/IN_PROGRESS, неполный PLAN, старый head или скан старше30мин запрещают команду waiting. Ошибка не меняет прежнее состояние и не стирает запросы.
Это проверка наличия корректно оформленного обоснования, а не автоматическое доказательство истинности произвольного отчёта. Родитель отвечает за полноту и реальные evidence.
При resume конкретный receipt становится одноразовым. Его повтор не может отменить более поздний STOP; для нового прямого разрешения нужен новый receipt. pause сохраняет stopped_at/stop_reason.
До интеграции новых команд потоки соблюдают тот же порядок через документы/state; не редактируют чужой control.py и не обходят STOP ради внедрения.

## Передача новых диалогов
Полный PROMPT_<ROLE>.md для переноса содержит одноразовое разрешение владельца на первый запуск и постоянные правила. После первой записи токена повтор этого текста — обычный governor, а не новое resume.
Прогресс/кандидаты/незакоммиченное/вопросы сохраняются. Исторический старт A01/B01/C01 удалён из постоянных промптов как причина ошибочного перезапуска.
Действующий автопромпт и доступ к инструментам должны оставаться доступны; эти файлы сами по себе не запускают чат и не создают нового фонового управляющего сервиса.
STOP распространяется на дочерние задания роли; сохранить рабочую точку и штатно закончить собственные тестовые группы. Не останавливать продукт/мониторинг только ради остановки разработки.
