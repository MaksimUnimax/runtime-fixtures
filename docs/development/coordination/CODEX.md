# Серверный Codex в каждом потоке

Профили уже существуют и авторизованы через ChatGPT, не через API key. Проверено 2026-09-23 через login status. Не менять их авторизацию, не копировать auth.json и не выводить credentials.
Назначение новых дочерних заданий:

| Поток | Launcher | Модель в новом exec | Lock |
|---|---|---|---|
| A | codex | gpt-6-luna | /root/octoport-control/codex-A.lock |
| B | codex2 | gpt-6-luna | /root/octoport-control/codex-B.lock |
| C | codex3 | gpt-6-luna | /root/octoport-control/codex-C.lock |

У codex3 в старом config указана другая модель, поэтому модель нового задания задаётся явно; глобальный config и уже открытые сессии не меняются. codex4 остаётся резервным профилем без автоматического назначения.
CLI launcher может работать под своим установленным Node 22; приложения проекта и их проверки используют Node 24.20.0. Это разные среды, не менять launcher ради продуктового Node.

## Когда делегировать

Подходят: отдельный дефект с воспроизводимым тестом, изолированный модуль, подготовка негативных тестов, независимое ревью diff, исследование конкретного сбоя.
Чат сам принимает архитектурные решения, разбирает неоднозначность, согласует контракты и проверяет результат. Не передавать Codex «закончи весь проект» и не считать его отчёт доказательством без read-back кода/логов.

Одновременно разрешено до одного Codex на поток. Это не обязанность загружать все три: общие лимиты подписки/память могут снизить полезную конкуренцию. Платный API автоматически не подключать.
Если лимит/авторизация препятствуют запуску, записать blocker, запросить конкретное действие и продолжить непосредственно через RDC.

## Изоляция задания

1. Родитель делает clean checkpoint и записывает task ID/base SHA/scope.
2. Для записи создать отдельный git worktree под /root/octoport-control/worktrees/ROLE/TASK и отдельную ветку exec/ROLE/TASK. Родитель и ребёнок не пишут одни и те же файлы в одной копии.
3. Дочерний task prompt: одна цель, разрешённые пути, необходимые контракты, критерии/команды, явные запреты на push, production, чужие процессы, секреты, новые агенты и расширение scope. Результат: exact diff/коммит, тесты и ограничения.
4. Новый exec, не чужая открытая интерактивная сессия. resume допускается только по сохранённому ID этого задания. Никогда resume --last.
5. Для read-only review достаточно -s read-only в рабочей копии роли. Для правок -s workspace-write в отдельной копии. Не включать bypass approvals/sandbox. Если sandbox ограничивает нужное действие, ребёнок сообщает родителю; родитель выполняет только уже разрешённую конкретную операцию.
6. Тяжёлые проверки ребёнка используют тот же общий lock. Можно запускать из родителя: control.py ROLE heavy --db -- pnpm --dir <own-child-worktree> test:integration. БД остаётся своей тестовой; родитель не использует её параллельно.
7. Родитель проверяет scope, смысл diff, тесты и отсутствие секретов, применяет принятый результат в свою ветку, затем обычный submit C. Не переносить весь чужой worktree или node_modules.
8. STOP родителя запрещает новые дочерние задачи и требует безопасной остановки/сохранения текущего Codex. Записать PID/session/task; чужие процессы не останавливать.

## Пример запуска

Сначала сохранить конкретный task prompt в своём logs/ROLE/TASK.md. Пример для A; B/C подставляют свой launcher, ROLE и путь:

```sh
flock -n /root/octoport-control/codex-A.lock \
  codex exec -m gpt-6-luna -s workspace-write \
  -C /root/octoport-control/worktrees/A/TASK \
  -o /root/octoport-control/logs/A/TASK-result.md \
  - < /root/octoport-control/logs/A/TASK.md
```

Это схема команды, TASK должен быть реальным идентификатором подготовленного worktree, не буквальным незаполненным placeholder.
Запускать через RDC с ограниченным ожиданием и сохранением логов; проверять завершение/exit code, не висеть в одном блокирующем вызове на часы.

## Git-публикация

Для трёх новых рабочих копий настроен существующий project deploy key через SSH host alias github-seller-agents (ssh.github.com:443). Fetch может идти по публичному HTTPS; push использует SSH.
Обычный HTTPS git push на сервере не авторизован и ждёт ввод. Не объявлять это отсутствием проектного ключа и не просить владельца новый токен.
core.sshCommand включает BatchMode и ограничение времени соединения. Ключ не копируется в репозиторий, отчёты или Codex task prompt.
Публикует родительский поток; A/B только свои ветки, C — проверенный main. Контроль доступа ключа и локальные Git hooks не являются полной OS-изоляцией.
