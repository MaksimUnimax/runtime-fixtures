# Исполнение Octoport на сервере

## Назначение и пределы
Постоянные управляющие промпты [A](PROMPT_A.md), [B](PROMPT_B.md), [C](PROMPT_C.md) задают всю согласованную область SPEC/PLAN. Короткие START восстанавливают эту ответственность. Завершение процесса, задачи, очереди или ответа чата не завершает проект.
Доверенный серверный цикл выбирает ограниченные задания, сохраняет состояние, запускает существующие профили codex/codex2/codex3 и продолжает после результата. Только gpt-6-luna через существующую подписку; платный API и автоматическая замена модели запрещены.
Первый контракт runtime принимает только SOURCE с фактически исполненными проверками из фиксированного каталога. Проверка пакета в VM остаётся SOURCE/PACKAGE; INSTALLED_SYNTHETIC, LIVE_OWNER, DEPLOYMENT и PRODUCTION не получаются из текста модели. Для них нужны отдельные действующие сборщики доказательств и разрешения. Отсутствующая возможность блокирует конкретную границу, а не всю разработку.
Код runtime и этот документ сами по себе не доказывают развёртывание. Источник фактического включения: /root/octoport-control/runtime/deployment.json, установленный systemd unit, marker, SQLite-задания и реальные receipts. Если receipt отсутствует или имеет статус NOT_ACTIVATED, фоновая работа не подтверждена.

## Ответственность и параллельность
A ведёт расширение и клиентские сценарии; B — backend и данные, единолично DB/schema/migrations; C — интеграцию, выпуск и мониторинг. Точные области остаются в [OWNERSHIP.json](OWNERSHIP.json) и [PLAN.md](PLAN.md).
Профиль не занят бесконечным чатом: ограниченный процесс завершает один проверяемый результат. Планирование и независимый review используют свободные профили; один профиль не исполняет две Codex-сессии одновременно.
Planner и reviewer read-only. Author пишет только назначенные файлы собственной рабочей копии. Git, очередь, commit, проверки, receipts и публикация принадлежат доверенной стороне. Авторский результат всегда сначала NOT_ACCEPTED; другой профиль проверяет точные SHA/tree/diff, входы, потребителей и доказательства.
Контроллер вправе разрабатывать код в отдельной claimed-копии. Общие обязанности и права находятся в [CONTROLLER_GUIDE.md](CONTROLLER_GUIDE.md). Отсутствие контроллера не является обязательным шлюзом обычной работы.
Claim/lease и файловые guards предотвращают согласованные конкурирующие операции; они не являются изоляцией от злонамеренного процесса с правами root.

## Файлы и реальная конфигурация
Конфигурация: /root/octoport-control/runtime/config.json; marker: /root/octoport-control/controllers/runtime-mode.json.
Требования: /root/octoport-control/runtime/requirements.json; общая очередь: /root/octoport-control/controllers/work-board.json. Манифест требований — индекс незакрытой области, а не замена полной SPEC и не доказательство приёмки.
Состояние запуска: /root/octoport-control/controllers/runtime/<epoch>/state.sqlite; отдельные jobs, tokens, logs, check receipts и integration receipts находятся в том же каталоге.
Обязательные config-поля: version=1, epoch, control_root, repo, requirements, enabled_roles, migration_board_sha256. Каталог check_catalog содержит только заранее проверенные argv, environment и timeout_seconds. Параметры не берутся из произвольной команды модели.
Ориентиры конфигурации: poll_seconds=10, planner_interval_seconds=1800, job_timeout_seconds=1200. Планировщик выбирает следующую готовую работу после результата; периодический пересмотр незакрытых требований — не команда повторять пройденные тесты.
Срочные задачи получают приоритет на свободной границе, обычные защищены от бесконечного вытеснения. Уже выполняющееся задание не прерывается небезопасно ради обещания фиксированного срока патча. Измеряются реальные времена поступления, диагностики, кандидата, review и выдачи.

## Команды
Путь RUNTIME берётся из фактического ExecStart установленного unit или точного принятого deployment receipt; нельзя подменять его непроверенным WIP. Во всех командах ниже CONFIG — /root/octoport-control/runtime/config.json.
- python3 RUNTIME --config CONFIG check --login — проверить предпосылки и существующие профили; не читать credentials в вывод.
- python3 RUNTIME --config CONFIG status — фактические задания, блокировки и режим; systemctl status octoport-continuous-runtime.service отдельно подтверждает процесс.
- python3 RUNTIME --config CONFIG add --task-file /absolute/task.json — добавить конкретный незакрытый результат с точными путями, requirement_id, basis, acceptance, required_checks и привязкой входов.
- python3 RUNTIME --config CONFIG inspect --job ID — сохранённые сведения конкретного задания.
- python3 RUNTIME --config CONFIG claim --role A --owner controller --base SHA --paths-file /absolute/paths.json — взять отдельное назначение перед ручной записью; использовать выданный token-file, не угадывать его.
- python3 RUNTIME --config CONFIG release --token-file /absolute/claim.json — закончить подтверждённую ручную работу.
- python3 RUNTIME --config CONFIG reconcile --job ID --receipt /absolute/receipt.json — документированное разрешение неопределённого исхода по фактам; не команда UNKNOWN→PASS.
Команды once/serve выполняют цикл. Не запускай второй serve рядом с установленной службой. Внутренние worker/entry предназначены только для доверенного supervisor и не используются как обходной запуск.

## Проверки, доказательства и ресурсы
check_catalog исполняется supervisor, фиксирует настоящий exit, argv, среду и хеш журнала. Текст автора «PASS» и exit Codex=0 не заменяют продуктовую проверку. Изменение исходников во время проверки отвергается.
SNAPSHOT связывает точный кандидат, входы, каталог проверок и среду. Неизменное доказательство не истекает просто по времени. CURRENT_STATE имеет срок, поскольку утверждает текущее состояние внешней системы. Изменившиеся условия требуют соответствующей проверки, а не автоматического повтора всего набора.
continuous_checks.py предоставляет extension-support и extension-lifecycle: один DEV-пакет в личном каталоге задания, проверка фактических байтов ZIP и распакованных файлов при каждом повторном использовании. Ключ учитывает настоящие исходники, включая изменения, скрытые Git index hints. Общий изменяемый кеш пакетов между заданиями не используется.
Среда подготавливается по необходимой capability. Python-only не требует установки Node workspace. Node 24.20.0/pnpm 10.34.5, frozen lockfile, собственные зависимости; ссылки на изменяемые node_modules другой копии запрещены. Нет кеша/места/нужного браузера — отдельная причина среды, а не «ошибка продукта».
Тяжёлые процессы выполняются через существующий resource_runner с собственной ограниченной cgroup, временем жизни и подтверждённой очисткой. Продуктовый DATABASE_URL не используется. Нельзя создавать второй Telegram poller либо переключать продуктовые API/worker/portal вместе с разработкой.
Старые DONE без точной независимой привязки переводятся в UNVERIFIED с сохранением исторических receipts. Новая очередь не признаёт их доказанной зависимостью по одному названию файла. Перенос не означает удаление сделанного или повторное написание принятого кода.

## Восстановление, STOP и интеграция
Supervisor сохраняет намерение и идентификатор попытки до запуска. Проверяются token, PID и время рождения процесса, job lock и ресурсная группа. Рестарт coordinator принимает живую попытку под наблюдение, не создаёт вторую.
Неопределённая операция записи сохраняется как UNKNOWN; слепой повтор запрещён. Независимая read-only сверка сохраняет diff и факты. Независимые задания продолжаются. Отсутствие новых данных не оправдывает бесконечные одинаковые повторные попытки.
Прямой STOP владельца сильнее текущего задания, старого разрешения и START. Штатный control.py ROLE pause остаётся доступным; не редактируй JSON вручную ради обхода. Останавливаются собственные тестовые группы разработки, не продуктовые службы. Рестарт systemd не снимает STOPPED.
Возобновление требует нового прямого указания владельца и его действующей квитанции. Остановка только coordinator через systemctl сама по себе не является STOP всех выполняющихся заданий: самостоятельные job supervisors могут продолжить уже назначенную работу.
Только C публикует main. Runtime готовит отдельную C integration-копию, проверяет точный scope, новый общий контекст другим профилем и пять обязательных workflow точного HEAD. Затем применяется существующий ready-main/pre-push и non-force push с readback.
Конфликт и красный CI сохраняют исходный кандидат и ограничивают зависимую интеграцию; не оставляют каноническую C-копию в незавершённом merge. Изменившийся main требует новой интеграции и проверки изменившегося контекста, а не подмены уже принятого diff.
Принятые конечные записи архивируются только после завершённой интеграции и отсутствия зависимых заданий/leases/review/CI. Исторические доказательства сохраняются; bounded active board не является пределом числа задач проекта.

## Проверка фактического включения
Перед cutover: сохранить прежнюю очередь и WIP; завершить независимое review runtime; выполнить явную миграцию доказательств; проверить точный config/marker/разрешение; убедиться в отсутствии дублирующих исполнителей.
После запуска: подтвердить фактический процесс, хотя бы один настоящий job, его проверенный результат и переход к следующему; отдельно проверить рестарт и STOP. Model/unit/fake-adapter проверки не заменяют эту проверку.
Записывай deployment receipt с кодом, конфигурацией, временем, процессами, задачами, точными границами доказательства и оставшимися ограничениями. Пока нет этих фактов, статус — подготовлено или проверяется, а не «полная автономия работает».
