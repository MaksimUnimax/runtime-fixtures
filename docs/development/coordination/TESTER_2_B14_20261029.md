## Общий пакет исправлений

### Операции и сессии

`AdminProvider` применяет только результат актуального обновления авторизации. Начало logout инвалидирует прежние `/me`; общий незавершённый logout не порождает повторный DELETE и не позволяет refresh вернуть прежний контекст. Неуспешный transport/CSRF logout не объявляется успешным. Loading снимает только актуальное чтение.

`useData` связывает выдачу не только с URL, но и с principal, expiry и permissions. При смене этой границы старые данные скрываются до нового эффекта, прежние ответы/ошибки/refresh callbacks не заменяют новую выдачу. Сохранены request generation и abort semantics.

Новая защита подтверждения и результата `Mutation` включается явным `reviewScope` только для 12 B14 controls. Подтверждённые path/body фиксируются, причина остаётся видимой и редактируемой до Confirm; при отправке причина и Cancel блокируются. Уже отправленный POST не называется отменённым. После навигации прежний B14 результат не обновляет новую цель.

Principals имеют общий busy на все строки, создание и Next до окончания authoritative reload. В AccountWorkspace блокируются связанные Devices/Overrides Cursor. Независимая пагинация платежей и billing events не блокируется. Существующие unscoped commercial/AI consumers сохраняют прежние callbacks при общем reload: новая защита B14 не теряет поздние исходы соседних операций.

### API и защита Owner

Admin subscription route передаёт существующий optional `accessBasis`, не придумывая его при отсутствии. Пять principal/device методов сервиса проверяют действующий строгий domain reason schema до repository; INVALID становится HTTP400. Это локальная защита своего участка, не утверждение, что общий внешний reason contract уже исправлен.

При revoke Owner и suspend Owner repository под существующим management lock проверяет наличие **другого** ACTIVE principal с ACTIVE user и активным Owner grant. Удаление последнего пригодного Owner запрещено, удаление непригодного Owner при сохранённом пригодном — разрешено. Старые count-проверки ошибочно учитывали Owner при suspended user. Новые DB cases проверяют также неизменность principal/session/audit при отказе. Это защита штатного management пути, не обещание против произвольных внешних SQL-записей в users.

### Подготовленные магазины — ещё без подключения

`b14-store-projection.ts` принимает только явные скаляры принятого ACTIVE `STORE_UPSERT`, проверяет account/entity/store identity, enum, revisions и timestamp. Raw sync state, receipts, credentials, credentialRevision, installation/binding/dialogue identifiers не входят в output. Лишние поля отвергаются.

Provider ID должен соответствовать существующему alphabet `confirmProviderIdentity`; ошибочное значение даёт `null`/`UNCONFIRMED`, идентичность не нормализуется для прохождения проверки. Нормальное Unicode-название сохраняется как plain text. Контрольные символы и узнаваемые credential assignments, включая quoted keys и NFKC-совместимые варианты, приводят к скрытию целого названия. Это ограниченное распознавание явных credential записей, не универсальный детектор произвольного секрета в пользовательском имени.

Native Date читается через intrinsic slot в узком preprocess. Отклонённый Date-shaped объект не передаётся даже в formatter Zod: последующая проверка получает только epoch/undefined. Положительные и отрицательные Date/Proxy cases проверены вместе со всем store набором.

Cursor — canonical unpadded base64url ровно `{v:1,accountId,entityId}`: есть предел размера, строгий UTF-8, отказ от BOM/duplicate/extra keys/альтернативных представлений и чужого account. Cursor не является подписью или разрешением. Будущий repository обязан проверить его принадлежность текущему ACTIVE набору в SQL.

**Дополнительный независимый source-шаг выполнен:** `b14-store-read-projection.ts` соединяет scalar mapper/cursor с реальным параметризованным SQL. Один statement проверяет существование account, наличие cursor в его текущем ACTIVE STORE_UPSERT наборе и получает `limit+1` строк через LATERAL; проверка и страница используют один MVCC snapshot. Размер страницы 1…100, по умолчанию50; порядок и сравнение используют одну DB collation. Не возвращаются whole state, installation, binding, credential или receipts. Неправильная выбранная строка, включая lookahead, отменяет всю страницу; отказ БД не превращается в пустой успех. Authoritative admin authorization обязан выполнить будущий caller — один account ID не является полномочием.

JSON `metadataRevision` проверяется как точный decimal text до Number(): строка, дробная точная величина и значение вне safe integer не превращаются в допустимую ревизию. Существующий пустой account отличается от отсутствующего. Свежесть относится к принятому sync; состояние ключа/устройства не выводится. Live keyset не обещает неизменяемый snapshot между разными запросами. Полный собственный набор reader **75/75 PASS**, narrow TypeScript и ESLint PASS; это fake-query transport + настоящий mapper, не выполненный PostgreSQL. Первый полный набор74 PASS/1 FAIL выявил ошибку таблицы самого теста (`it.each` разворачивал массив); исправлена вся таблица, первый отрицательный JSON сохранён.

Будущий read endpoint предложен как `/v1/admin/accounts/{account_id}/stores` с существующим `device.read` (Owner/Ops/Support). Предложенный DTO имеет nullable name, метаданные и время последнего принятого sync. Это не серверная проверка ключей: credential presence и verification не синхронизируются, их состояние остаётся неизвестным. HTTP DTO и permission choice требуют согласования общего автора.

## Журнал: все 15 действий текущих B14 экранов

`b14-audit-summary.ts` — внутренний mapper, доступный через обычный export domain package и используемый подготовленным `b14-audit-read-projection.ts`. **Действующий repository endpoint, HTTP и UI ещё не подключены**. Существующий audit envelope по ADR0027 по-прежнему не раскрывает freeform reason/safeMetadata. Предлагается opt-in `includeSummary=true`, чтобы default ответ оставался прежним для строгих клиентов.

Для любой подробной сводки обязательны `admin.audit.read` и соответствующее object read. Поля собираются явно, unknown/malformed существенные данные не превращаются в объяснение. ## Реальные тесты и точные полномочия

Новый HTTP test file запускает настоящий Fastify route validation/serialization, но использует fake auth и repository. Он показывает, в частности, что для существующего Beta principal вызов mutation repository может завершиться, а сериализация ответа даёт500. Это не исполненная транзакция PostgreSQL и не доказательство реального login/RBAC.

Новые 7 integration cases включают last-usable-Owner revoke/suspend/удаление непригодного Owner, три непустых private-column canary projections и полный Beta repository/auth lifecycle. Новые 13 real E2E cases используют штатные OTP/elevation/BFF/API, Owner/Ops/Support/Beta, lifecycle, CSRF, stale two-owner, permission loss, expiry, last Owner, invalid reasons, audit и два account/device scope. Они не используют `page.route` или подделанную admin cookie.

Ещё31 real-PG case в `b14-admin-read-projections.integration.test.ts` проверяет внутренние SQL readers:7 store cases и24 audit cases, включая все15 действий, account/cursor membership, JSON number/string/missing/null, точные дробные numeric до driver округления, непустые private canaries, object permissions и повторение envelope filters. Это проверка read projection на реальных таблицах, а не мутация через публичный API или installed/RBAC acceptance. Вместе написано38 новых integration +13 real E2E.

**Они пока NOT_RUN.** Локальной разрешённой T2 DB нет. `resetTransferProtectedTestFixture` разрешает C-owned `octoport_c_test` либо `product_control_plane_test` в настоящем GitHub Actions точного репозитория. T2 не использует чужую БД и не создаёт собственную под чужим именем; CI/GITHUB_ACTIONS не подделываются, epoch fence/triggers не отключаются. Миграции тоже пишут в БД, поэтому произвольный DATABASE_URL не является допустимой попыткой проверки.

Действующий доступный путь — штатный Server CI. Его unit gate сейчас остановят девять Beta cases до новой DB-проверки; удалять, пропускать или ослаблять эти tests ради зелёного CI нельзя. Если нужна другая T2 среда, отдельно согласуются конкретная disposable DB/порт/владелец и разрешённая граница fixture harness. Для installed проверки нужны отдельно разрешённый target и нормальные test identities/elevation. Глобальный admin token, production DB и чужой R3 browser/profile не используются.

Дополнительная отдельная TypeScript-проверка новых integration/E2E файлов ранее показала только существующую ошибку `tests/e2e/server/support/fixtures.ts:372`: несогласованные union-поля snapshot publish input. Этот общий helper не менялся. Результат той проверки не назван PASS и не подменяет выполнение новых реальных тестов.
