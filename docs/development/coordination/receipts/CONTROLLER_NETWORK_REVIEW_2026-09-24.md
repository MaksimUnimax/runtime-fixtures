Шесть ключевых файлов проверены на отсутствие отличий от A `144551fdb8d9d67b2988162592b27716b9c2e42d` и main `7e3e781491d42e366d60d3b3976cdd5bf179f840`. Runtime и live-конфигурация не менялись.

## Вывод для владельца

Обычное переключение диалога синхронизирует страницу с расширением локально. Наш сервер для этого не требуется. Дополнительный серверный запрос при нажатии Start/Resume проверяет состояние поддержки ИИ; он не выбирает главную вкладку и не согласует квоту Ozon/WB.

В одном профиле браузера уже есть общий исполнитель диалога, защита от повторного исполнения и часть общих ограничителей магазина. Между разными браузерами общей очереди API нет — это прямо записано в SPEC. При этом редкая сверка привязок между браузерами реализована не полностью и содержит дефекты. Нельзя обещать пользователю уже готовую автоматическую передачу управления «по последнему сообщению».

Есть полезная оптимизация без роста нашего сервера: убрать пустые локальные пробуждения, объединить служебные обращения и исправить область действия квот. Сначала исправить ошибки; произвольно увеличивать все интервалы или отключать проверки нельзя.

## Полная карта типов обращений

| Механизм | Когда и куда обращается | Оценка |
|---|---|---|
| Вход в аккаунт | Наш сервер: создать device authorization, ограниченный опрос результата, затем bootstrap | Нужен только в открытой попытке входа. Single-flight уже есть. Опрос завершается при успехе/сроке/отмене. Нет постоянного опроса для каждого пользователя |
| Обновление короткого токена | Наш `/v1/auth/refresh`; bootstrap умеет обновлять по необходимости | Сохранить. Распространить корректную работу с истёкшим access token на остальные защищённые служебные пути; не опрашивать каждые 15 минут |
| Подтверждение доступа/config/profile | `/v1/bootstrap`: вход, отсутствующий/неподходящий локальный контекст, Start/Resume через `ensureForIdentity` | Нет запроса подписки на каждую бизнес-команду. Отдельный регулярный цикл обновления лицензии ещё не подключён; согласованная политика 24h является требованием, не готовой реализацией |
| Состояние поддержки ИИ | `/v1/health-authority` на каждом допуске Start/Resume | Это совместимость/состояние AI-профиля, не передача вкладки. Нельзя просто удалить: подписанный DENY имеет смысл. Кандидат на общий single-flight и ограниченный кэш по полному контексту; TTL определить отдельно по требованию к скорости реакции на неисправность ИИ |
| Изменения магазина/привязки | Локальный журнал → `/v1/sync`, до 32 изменений в пачке | Нужен для редкой сверки. Сейчас есть ошибка планирования, проблема общей идентичности и отсутствие полноценного чтения удалённого состояния |
| Отметка о доставленном отчёте | Сохраняется локально; затем ставится собственная задача sync | Сам отчёт не отправляется нашему серверу. Намерение кода — отправка примерно через 5 секунд, а не только вместе с редкой служебной проверкой. Исправление планировщика нельзя выпускать без разделения срочных изменений и несрочных маркеров |
| Перенос ключей | Наш сервер: создание/обнаружение/получение/ACK ограниченной передачи | Отдельный редкий пользовательский сценарий. Постоянного WebSocket нет. В текущем UI источник обнаруживает запрос отдельной кнопкой; автоматический ответ без второго действия, описанный в SYNC, полностью не подключён |
| Проверка ключа магазина | Прямой запрос к Ozon/WB по явной кнопке | Сохранить; не превращать в постоянный ping. Изменение ключа инвалидирует старый контекст |
| Получение данных Ozon/WB | Прямо браузер → площадка, для разрешённых команд | Сохранить локальные проверки перед отправкой, последовательность пакета и no-replay UNKNOWN. HELP не требует сети; полученный локальный результат можно доставлять без нового скачивания |
| Ozon Performance OAuth | Прямо в Ozon, по необходимости перед Performance API | Токен кэшируется в памяти до срока, с запасом 30 секунд. После остановки worker кэш теряется. Нет отдельного таймера обновления; возможная следующая оптимизация — single-flight по кабинету, без обязательного нового постоянного хранилища секретов |
| Получение большого отчёта/файла | Прямо с разрешённого источника по явной команде | Не проксировать через наш сервер. Продолжения отчёта должны оставаться явными, без скрытого polling/pagination |
| Переключение диалога | Content script смотрит локальную идентичность раз в 1 секунду; при изменении посылает `OZ_CONTENT_READY` своему worker | Это не HTTP и не нагрузка нашего сервера. Сохранить правильное отсечение старого диалога. Event-driven замена возможна после проверки SPA-навигации, не является первоочередной экономией |
| Ожидание первого ответа ИИ | Локальное наблюдение/сообщение worker каждые 500 ms максимум 120 секунд | Ограниченный сценарий, не общий серверный опрос. Не трогать задержки вслепую: они влияют на отзывчивость |
| Поиск команд/доставка | DOM observers, ограниченные ожидания готовности кнопок/подтверждений; локальные messages и Port | Нужны для безопасности доставки. Повторять чтение DOM не равно повторять бизнес-запрос |
| Отображение ожидания квоты | Локальный секундный обратный отсчёт; probe каждые 250 ms максимум 5 секунд | Наш сервер не участвует. Можно заменить probe событием позднее; это ограниченная, не бесконечная работа |
| Восстановление вложения | Port открывается сразу; reconnect через 250 ms; локальная проверка recovery раз в минуту даже без активной доставки | Главный кандидат на устранение пустой работы. Уже есть push по изменению записи доставки. Переходить к соединению по потребности и ограниченному recovery, сохранив wake/restart/route-change сценарии |
| Popup/диагностика | Текущий popup читает локальное состояние, обновляется по storage event с debounce 100 ms | Сохранить. Старый diagnostics interval 1500 ms находится в заменённом popup и не считается активным циклом текущей сборки |
| Старый refresh Swagger Ozon | Историческая функция содержит fetch, но соответствующая legacy-команда отключена в текущем runtime | Не считать постоянным трафиком и не «оптимизировать» отсутствующий вызов |
| Technical scheduler | Один alarm ближайшей известной задачи: sync/квота/результат/очистка буфера/recovery | Правильная общая идея; нет нужды в отдельных постоянно работающих таймерах. Реализация требует исправлений ниже |

## Вкладки и браузеры: фактические границы

| Ситуация | Как устроено сейчас | Что требуется |
|---|---|---|
| Один диалог в двух вкладках одного профиля | Одна запись операции по conversation key, сериализованные изменения; владелец операции — tab ID. Другая вкладка не получает незавершённую операцию, пока прежняя ещё владеет диалогом. После исчезновения прежней возможен локальный rebind | Сохранить. Не выбирать владельца по клиентским часам или каждому новому сообщению. Проверять одновременный клик, закрытие вкладки, навигацию и worker restart |
| Разные диалоги, один кабинет Ozon в одном профиле | Для `analytics_data` и `stock_turnover_analytics` общий сохранённый ограничитель по хешу Seller Client-Id и семейству API. Версия ключа не создаёт отдельный счётчик кабинета. Текущая локальная настройка — 60 секунд + 5 секунд запаса | Сохранить область кабинет+семейство. Не выдавать её за покрытие всех методов Seller/Performance. Исправить автоматическое продолжение допустимого ожидания до первого запроса |
| Разные диалоги/карточки одного WB | Учитывается уже наблюдённый Retry-After, но ключ счётчика содержит credentialRevision и host | Привязать известный кабинет к корректной группе лимитов; не обещать общий лимит при неподтверждённой идентичности. Добавить реальный WB header и покрытие проверенных лимитов без миллионов таймеров |
| Разные браузеры/профили/компьютеры | Разные установки: общая квота API не согласуется. Редкая серверная сверка не является глобальной блокировкой | Сохранить принятую автономность. Если нужен строгий запрет параллельной работы во всех браузерах, это отдельное изменение продукта с сетевой зависимостью, а не бесплатная оптимизация |

«Последний отчёт» уже ограничен в документации: это только компактная отметка доставки текущей привязки, не текст переписки и не команда передавать управление после каждого сообщения. `preferredExecutorDecision` сохраняет пригодную текущую установку и выбирает по маркерам лишь при отсутствии/замене предпочтения. Клиентский `allowsFutureAction` учитывает Finish/newer binding, но не превращает preferredExecutor в эксклюзивную блокировку. Ни время получения сервером, ни произвольный AI message ID не доказывают глобальный порядок сообщений.

## Подтверждённые проблемы и задания

### N1 — фоновая синхронизация бесконечно переносит первую попытку

`technical-scheduler.js:reconstruct` для `nextAttemptAt=0` каждый раз назначает `now+1000` **перед** отбором уже наступивших задач. При каждом alarm задача вновь оказывается в будущем. Воспроизведение: 10 пробуждений за искусственные 300 секунд → 0 отправок, запись остаётся PENDING; явный вызов того же `syncNow` отправляет её успешно. Одновременно это создаёт бессмысленные пробуждения/записи storage.

**A, P1:** сохранять первоначальный deadline, не сдвигать уже наступивший; тестировать полный путь record → alarm → ACK после restart, а не только прямой `syncNow`. Отдельно несрочный delivery marker не должен создавать самостоятельную сетевую задачу через 5 секунд. В текущем retry-массиве последняя реальная задержка остаётся около 120 секунд, хотя MAX_RETRY_MS=300000; проверить backoff и Retry-After после устранения starvation. Не добавлять новый scheduler.

### N2 — межбраузерная сверка не находит один и тот же диалог

`sync-journal.js:metadata` выбирает entityId из локального bindingId. `bindConversation` создаёт bindingId случайным UUID; новая установка получит другой UUID. Server repository блокирует/читает сущность по `(accountId, entityId)`, не по conversation digest. Воспроизведено: одинаковый conversation digest, но две разные entity keys. Клиент вызывает POST `/v1/sync` только с локальными изменениями; полноценный read/pull чужой привязки при открытии не найден. Поэтому сам алгоритм reconciliation ещё не доказывает рабочую межбраузерную передачу.

**C назначает общий контракт; A+B реализуют, P1 для заявления multi-browser sync:** общий account-scoped opaque conversation identity, способ редкого чтения конкретной привязки/изменений и принятия её canonical bindingId; одна согласованная миграционная граница. Без per-command server lease, постоянного polling и хранения отчётов. До закрытия не заявлять мгновенную передачу по последнему сообщению. Ограниченный честно описанный первый магазинный срез может иметь отдельную границу поддержки.

### N3 — истёкший короткий токен может ошибочно завершить вход

`bootstrapOnline` обновляет access token перед запросом. `synchronizeMetadata`, `acquireSignedHealthAuthority`, `transferAuth` только проверяют владельца сохранённого контекста и используют текущий access token; `ensureAuthOwnership` не проверяет свежесть и не обновляет токен. При ответе 401/403 журнал sync вызывает `localReset`. Это статически подтверждённая цепочка риска, не живой тест с аккаунтом: обычное истечение токена может выглядеть как выход, хотя refresh ещё пригоден.

**A, P1; B проверяет error semantics:** общий authenticated request с on-demand refresh и одним повтором допустимого служебного запроса, сохранение idempotency и поколения. Подтверждённый revoke/invalid refresh не маскировать как offline. Проверить sync/health/transfer после срока access token без повторного входа. Исправлять вместе с N1, иначе ожившая отправка может проявить этот дефект.

### N4 — WB: общая пауза недостаточно общая и пропускает заголовок площадки

`batch-adapter.js:createPorts` использует `[wildberries, accountId, credentialRevision, host]`; credentialRevision создаётся локально. Воспроизведено: после 60-секундного cooldown для одной версии ключа другая версия сразу допускается. Две карточки одного кабинета также не обязаны делить эту revision. Ограничитель хранит только наблюдённую паузу, заранее разрешённые квоты всех методов не планирует.

В официальной документации WB указан `X-Ratelimit-Retry`. Подключённый transport сохраняет только `Retry-After`; воспроизведён ответ 429 с `X-Ratelimit-Retry: 60`, результат `retry_after=null`. Следующие независимые команды могут вновь попадать в лимит. Это не исправляется редким обращением к нашему серверу.

**A, P1 для WB quota:** корректно сохранять header площадки, одинаковый подтверждённый кабинет объединять по документированной группе методов; замена ключа не обнуляет паузу. Не вводить один грубый запрет на весь WB host, если реальные группы независимы. Непроверенную идентичность обозначать явно. После уже полученной ошибки автоматический повтор бизнес-команды остаётся запрещён.

### N5 — пробуждение после квоты не продолжает работу нового runtime

Композиция добавляет в `resumeProviderQuotaWaits` ранний `if (await saEnabled()) return`. Scheduler QUOTA вызывает именно эту функцию. Воспроизведено с наступившим сроком: 0 запусков, задача снова остаётся в scheduler. Явная кнопка `SA_RESUME_QUOTA` и некоторые content-recovery события имеют другие пути; они не доказывают автоматический alarm resume.

**A, P1:** подключить существующее безопасное продолжение только уже разрешённого пакета до первого provider dispatch. Сохранить проверку контекста, Finish, worker generation и запрет повторять неизвестно завершившийся запрос. Тестировать установленный alarm без кликов/переключения вкладки.

### N6 — ненужные локальные recovery и неограниченное ожидание служебного HTTP

Attachment script сразу открывает Port, восстанавливает соединение через 250 ms после разрыва и раз в 60 секунд запрашивает recovery даже без активной доставки. Это локальный трафик, но может будить worker и потреблять ресурсы компьютера. Точный CPU/RAM эффект и возможный цикл reconnect требуют browser trace; цифры ускорения не выдумываются. Уже есть storage-change wake конкретной доставки.

`control-client.js:request` ограничивает тело 1 MiB, но не имеет собственного полного deadline на fetch+body. Медленный ответ на Health стоит в цепочке Start/Resume. Собственные ограничения браузера не заменяют понятный bounded timeout приложения.

**A, P2:** Port по потребности, single-flight recovery, ограниченные попытки при активной доставке, проверка на reconnect/route change вместо безусловного idle polling. Общий deadline control request с правильной классификацией ошибки. Для Health — совместное получение совпадающих запросов; TTL-кэш только после определения допустимой задержки DENY. Не переносить суточную политику лицензии на совместимость ИИ автоматически.

## Порядок работы и что сохранить

1. A закрывает N1+N3 и N5 короткими совместимыми кандидатами с проверками; N4 — отдельный кандидат WB. Эти исправления входят в существующий A04, без остановки B/C.
2. C назначает одного автора общего контракта N2; B единолично делает необходимые DB/migrations. До этого не менять entity IDs наугад и не создавать две конкурирующие схемы.
3. N6 выполнять по отдельной ограниченной проверке, сохраняя надёжность доставки. Одно idle-подключение не объявляется доказанным OOM или причиной серверного инцидента.
4. Не запрещать параллельные диалоги разных магазинов, не сериализовать всё расширение, не удалять локальные guards и no-replay, не добавлять серверный координатор квот. Не удалять старые файлы/процессы в рамках аудита.

Согласованная подписка сохранена отдельно в `docs/architecture/SUBSCRIPTION_ACCESS_POLICY.md`: 24h обновление при использовании, paidThrough+72h offline, немедленный актуальный deny, изменения подписки сразу, существующий общий серверный lifecycle worker остаётся 30 секунд. Документ содержит различия с прежней реализацией; runtime ещё не переведён на эту политику.

## Доказательства и пределы

Семь воспроизведений: pending starvation; успешная явная отправка того же pending; отдельная 5-секундная задача маркера; разные server entity keys одного диалога; разделение WB cooldown по credentialRevision; потеря WB rate header; пустое quota wake в композиции. Скрипт и JSON сохраняются с аудитом в `/root/octoport-control/incidents/subscription-authority-audit-20260924/`. Названия PASS предыдущих тестов не отменяются задним числом: там проверялись другие границы (например, прямой syncNow и отсутствие немедленного HTTP, но не будущее срабатывание alarm).

Источник Chrome подтверждает: worker может завершаться после простоя, глобальная память теряется; сообщения/extension API могут продлевать его жизнь. Открытый Port сам по себе не гарантирует бессрочной работы. Chrome alarms допускают задержки и в установленной сборке не гарантируют срабатывание раньше 30 секунд; unpacked ведёт себя иначе. Поэтому 1/5-секундные значения в коде нельзя обещать пользователю как реальное расписание магазина.

Ресурсы проверки: сервер 15988 MiB RAM, около 13229 MiB доступно; swap занят 2 MiB, PSI memory 0, диск свободен 25 GiB, inode около 3.68 млн. Для этого аудита дополнительные серверы/браузеры не запускались, мусор не удалялся. Основания рекомендовать увеличение RAM сейчас нет; оптимизация пустых клиентских пробуждений не требует покупки серверной памяти.

Публикация: A-кандидат имеет проверенные пакеты, но пакетный PASS не равен store/live acceptance. По состоянию потоков ещё нужны согласованная live config-release цепочка, публичные privacy/support/install страницы, реальная карточка Opera и установленный обычным путём login/import/read-only proof. Новые дефекты нужно учитывать по достижимым функциям минимального публикуемого среза; не ждать всей коммерции и всего roadmap, но не рекламировать непроверенную межбраузерную синхронизацию. Новых действий владельца при этой проверке не требуется.
