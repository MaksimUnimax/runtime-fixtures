# Учёт места до создания временных данных и при завершении задачи

Основание: поручение владельца 2 октября 2026 исправить организацию накопления и удалять доказанно ненужные временные данные. Ответственность за механизм — контроллер; за каждый созданный ресурс — его автор. Это дополнение к TEMP_WORKTREE_LIFECYCLE и RESOURCE_POLICY. STOP, независимая приёмка, сохранение исходников и секретов, exact-head CI и правила публикации остаются обязательными.

## Что меняется в работе

1. Не создавать новое дерево ради чтения исходников или повторного чтения документов: использовать `git show`, существующие файлы и сохранённые точные результаты. Отдельная рабочая копия нужна только для независимых правок либо изолированной проверки. Зависимости устанавливать только если конкретная проверка их использует.
2. До новой временной копии, профиля, распаковки, установки зависимостей или тестовой БД вызвать `begin` операционного `/root/octoport-control/controllers/organization/tools/disk_lifecycle.py`. Указать роль, задачу, точные будущие пути/имена томов, назначение, ожидаемый максимальный прирост и срок до 72 часов. Не делать установку перед этим шагом. Регистрация не создаёт сами файлы и не запускает процессы.
3. Новый временный корень размещать непосредственным дочерним каталогом `/root/octoport-control/worktrees/ROLE` или `/root/octoport-control/temporary/ROLE`; для контроллера имя каталога `controller`. `logs/ROLE` предназначен для компактных постоянных квитанций/evidence и не является временным корнем: временную распаковку, dependency/cache/profile/test data там не регистрировать и не создавать. Один зарегистрированный верхнеуровневый task-root должен содержать все свои вложенные временные данные; отдельный зарегистрированный descendant не может скрывать незарегистрированных соседей. Не создавать новые `/root/runtime-fixtures-*`, `/root/Seller_Agents-*` или безымянные каталоги в /tmp. Исторические и канонические рабочие пути не перемещать этой инструкцией.
   Все новые кэши установки также направлять внутрь объявленного временного корня: `pnpm install --store-dir /EXACT_DECLARED_ROOT/task-cache/pnpm`, `npm_config_cache=/EXACT_DECLARED_ROOT/task-cache/npm`, `PIP_CACHE_DIR=/EXACT_DECLARED_ROOT/task-cache/pip`, `TMPDIR=/EXACT_DECLARED_ROOT/task-cache/tmp` (папки создать после begin). Для инструмента с XDG-кэшем аналогично задать `XDG_CACHE_HOME`. Значения относятся только к конкретной временной команде, не менять глобальную конфигурацию. Использование общего pnpm/npm/pip store для НОВОЙ установки под такой квитанцией запрещено: иначе удаление рабочей копии не удалит результат установки. Уже установленные общие браузеры и зависимости можно читать/использовать, не обновляя их. Обновление общей установки — отдельная явно учитываемая операция, этот временный маршрут её не разрешает. Не скачивать браузеры заново для каждого теста.
4. Технический допуск оставляет 5120 МиБ свободного резерва сверх всех заявленных открытых бюджетов и нового бюджета; требуется минимум 200000 свободных inode. Проверка и запись резерва выполняются под существующим коротким resource-admission.lock. Бюджеты не исчезают от смерти процесса или истечения срока. Это консервативный допуск, а не файловая квота: сохраняется весь заявленный резерв даже после частичной записи.
5. При нескольких независимых проверках одной задачи допустимы несколько зарегистрированных ресурсов. Нет общего ограничения «один процесс/один браузер». Старый незакрытый ресурс другой задачи той же роли нужно сначала удалить либо обоснованно оставить. Отказ относится к новому расходу диска: чтение, диагностика, исправление и безопасное сохранение работы продолжаются.
6. Браузеры/серверы/worker-пулы и тяжёлые проверки по-прежнему запускаются через существующий `control.py ROLE heavy`. Новый CLI не заменяет supervision, DB authority, память или finite runtime; не запускать дополнительный daemon/cron/исполнитель. Простая shell-команда не перехватывается на уровне ОС: обязательный маршрут применяется исполнителями и проверяется контроллером. Не заявлять абсолютную защиту от произвольной записи/превышения оценки.

### Запечатанный baseline управляемых временных корней

При первом включении fail-closed guard контроллер один раз выполняет `seed-baseline` после фактического аудита существующих `worktrees/ROLE` и `temporary/ROLE`. Baseline фиксирует уже существующие legacy-корни и их filesystem identity; повторный `seed-baseline` запрещён. Его нельзя пересоздавать, чтобы задним числом узаконить новый незарегистрированный каталог.

После baseline любой новый верхнеуровневый корень в этих каталогах должен быть покрыт действующим `begin`. `status`, `audit_check.py alerts`, новый `begin`, `declare-none` и `check-complete` показывают либо блокируют `UNREGISTERED_MANAGED_PATHS`. Удалённое и созданное заново старое имя также не считается старым baseline-объектом. Если filesystem не даёт проверяемое birth-time, baseline/guard считается непроверенным и работа не объявляется чистой.

## Завершение означает разбор файлов, а не только остановку процесса

7. До DONE/READY_FOR_OPERATOR и перехода к другой задаче разобрать все созданные временные ресурсы. Сначала сохранить уникальные исходники, точные Git refs, нужный пакет и компактные доказательства. После проверок потребителей удалить подтверждённо временное по действующей процедуре. Не сохранять полную установленную среду лишь для доказательства PASS.
8. Для удаления сохранить JSON-квитанцию с `cleanup_verified: true`, точными массивами `managed_paths` и `managed_volumes`, а также проверками потребителей и сохранённых результатов. Выполнить `close --reason /absolute/receipt.json`: CLI проверит отсутствие каждого пути (включая висячие ссылки) и каждого Docker-тома, соответствие перечня и хеш квитанции. Удаление выполняет проверенная процедура, не сам CLI. Исчезновение контейнера не означает исчезновение его тома.
9. Если объект ещё нужен, выполнить `hold` с конкретным потребителем, причиной и следующим сроком проверки максимум 72 часа. «На всякий случай», «старый тест», просто DIRTY или возраст не являются достаточным объяснением. HELD явно означает сохранённый ресурс, а не успешное удаление. Его бюджет остаётся учтённым. При истечении срока нужен новый фактический разбор; ничего не удаляется по одному таймеру.
10. `check-complete --role ROLE --task TASK` должен подтвердить отсутствие незакрытых или просроченных ресурсов этой задачи. Штатный `control.py ROLE queue-task --task TASK --task-state DONE` держит общий короткий disk-admission lock от этой проверки до записи work-board, ставит fail-closed `SEALING`, затем `SEALED`: DONE отклоняется при отсутствующем inventory, OPEN, просроченном HELD либо новом незарегистрированном managed path, а после DONE новый `begin/declare-none` для той же задачи запрещён. Если строгая запись DONE вернула ошибку, печать возвращается в `REOPENED` только после readback, который доказывает, что задача не стала DONE; при DONE или непроверяемом readback остаётся fail-closed `SEALING`. Если DONE-задача штатно переоткрыта в IN_PROGRESS по существующим правилам rework-receipt, печать снимается под тем же lock. Переход BLOCKED сам по себе этой финальной проверкой не блокируется. Задачи, создававшие временные данные, не завершаются одним сообщением PASS: в результате указываются квитанция удаления либо перечень действующих HELD с потребителями. Отсутствие регистрации не считается доказательством очистки. Для чисто read-only задачи выполнить `declare-none --role ROLE --task TASK --purpose 'Чтение существующих файлов; временные ресурсы не создавались'`; это нулевая декларация без фиктивного каталога или бюджета. Она запрещена, если для задачи уже зарегистрирован ресурс, и проверяется reviewer по фактической работе.

## Что не является мусором и как снять удержание

- Текущий рабочий каталог автора нужен для его незавершённых изменений. Уникальность устанавливается сравнением содержимого, не словом «копия». Контроллер должен отделить уникальные правки от восстановимых зависимостей; последние можно очистить отдельно после проверки потребителей.
- Изменённая историческая копия не хранится бессрочно только из-за DIRTY: определить владельца/задачу, сохранить реально отсутствующие в принятой версии изменения и нужные входы с readback, затем применить проверенную процедуру завершения. Не применять force/reset/clean к чужой работе ради уменьшения счётчика.
- Профиль с необходимым входом нужен конкретной разрешённой проверке. Куки, ключи и сессии не публиковать. Повторные установленные файлы расширения и восстанавливаемые кэши анализировать отдельно от уникального состояния входа.
- История проверок: сохранять точный SHA/хеш пакета, результат, существенную ошибку и минимальное доказательство. Полная копия исходников и установленного расширения для каждого повторения не обязательна. Файлы уже выданного пакета и воспроизводимость принятой ошибки сохраняются до конкретного срока/условия.
- Новая тестовая БД получает явное имя тома `octoport-ROLE-*`, запись `--volume`, владельца и условие удаления. Не плодить анонимные тома. Существующие постоянные БД и три штатные БД A/B/C не пересоздавать этой инструкцией. Исторические 43 тома классифицируются отдельно; общий prune или удаление WAL запрещены.
- Сервисные релизы и резервные копии нужны для работающего сервиса и конкретного восстановления. Контроллер проверяет фактическую ссылку службы, актуальный резерв восстановления и отличие содержимого; неизвестное назначение обозначается как незавершённая проверка, а не как доказанная необходимость.

## Примеры для исполнителя, не для владельца

```bash
python3 /root/octoport-control/controllers/organization/tools/disk_lifecycle.py begin --role A --task EXAMPLE-REVIEW --purpose 'Изолированная проверка конкретного исправления' --path /root/octoport-control/worktrees/A/example-review --reserve-mib 128 --hours 4
python3 /root/octoport-control/controllers/organization/tools/disk_lifecycle.py hold --role A --id ID_FROM_BEGIN --consumer 'Независимый reviewer задачи EXAMPLE-REVIEW' --reason 'Проверка ещё идёт; изменения и каталог использует указанный reviewer' --hours 4
python3 /root/octoport-control/controllers/organization/tools/disk_lifecycle.py close --role A --id ID_FROM_BEGIN --reason /absolute/cleanup-receipt.json
python3 /root/octoport-control/controllers/organization/tools/disk_lifecycle.py check-complete --role A --task EXAMPLE-REVIEW
```

Размер бюджета оценивается по конкретному измеренному действию: рабочая копия без зависимостей — порядка 128 МиБ с запасом; установка зависимостей/сборка/браузерный прогон требуют своего измеренного пика и запаса, а не универсальных 128 МиБ. Не занижать бюджет ради прохождения допуска. Сигнал о нехватке места устраняется очисткой доказанного лишнего, изменением объёма необходимой работы либо обоснованным изменением ёмкости, а не слепым повтором команды.

## Проверка контроллером

При каждом ресурсном контроле читать `status`, просроченные HELD и ресурсы завершённых задач; сверять регистрацию с фактически созданными крупными каталогами/томами. Результат без учёта созданных временных ресурсов вернуть автору на исправление. Историческую очередь разбора и выполненные удаления вести в текущем аудите, не создавать ещё один набор полных копий для самой проверки. Применённый маршрут и реальные квитанции отличать от лишь опубликованного документа. ORG-015 закрывается только после независимой проверки применения и рабочего цикла без прежнего накопления.
