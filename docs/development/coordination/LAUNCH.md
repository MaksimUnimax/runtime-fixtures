# Запуск и продолжение Octoport A/B/C

## Что получает каждый диалог
Постоянный чат отвечает за всю свою область согласованного проекта: архитектурные решения, полноту SPEC/PLAN, исполнение, качество, evidence и самостоятельную следующую работу до прямого STOP владельца.
Полные [PROMPT_A.md](PROMPT_A.md), [PROMPT_B.md](PROMPT_B.md), [PROMPT_C.md](PROMPT_C.md) — постоянные управляющие контракты. Короткие [START_A.md](START_A.md), [START_B.md](START_B.md), [START_C.md](START_C.md) загружают их и восстанавливают работу. Короткий START не заменяет полный контракт одной карточкой или командой запуска.
[EXECUTION_RUNTIME.md](EXECUTION_RUNTIME.md) — единый источник действующих runtime-команд, claim/lease, lock, процесса, восстановления, STOP и фактического deployment. [CODEX.md](CODEX.md) описывает полномочия исполнителей. Взаимодействие с контроллером — [CONTROLLER_GUIDE.md](CONTROLLER_GUIDE.md).
Промпты и JSON-состояние сами не запускают процессы. Завершённый ответ чата не должен быть единственным способом перехода к следующей задаче: непрерывный исполняемый цикл принадлежит проверенному runtime. Чат продолжает вести область и может сам выполнять claimed-задачу через RDC.

## Фактический статус внедрения
Эта инструкция не является receipt о развёртывании или доказательством фоновой работы. Перед объявлением «работает» прочитай актуальный раздел deployment в EXECUTION_RUNTIME.md и проверь названные там доказательства.
Нужны реальные процесс/service status, task ID и claim, свежая квитанция исполнения/результата, подтверждённый переход к следующей задаче, независимое review и обработка STOP. Свежий heartbeat, RUNNING, запись назначения или успешный вызов start по отдельности этого не доказывают.
Если действующего подтверждения нет, статус фонового исполнения — НЕ ПОДТВЕРЖДЁН. Не называй подготовленные документы внедрённым runtime. Сохраняй доступную работу активного чата только по безопасному отдельному claim, не запускай обходной daemon и не скрывай конкретную неисправность.

## Порядок начала и обновления
1. Сохрани существующие ветки, кандидаты, незакоммиченное, открытые запросы и receipts. Новый текст не начинает A01/B01/C01 заново и не требует новых диалогов либо сброса прогресса.
2. В соответствующем диалоге подключи GitHub и Remote Desktop Commander. Для C используй START_C.md; C восстанавливает состояние, проверяет базу и runtime по действующему контракту. Короткая проверка готовности A/B не означает завершение release-задач.
3. Для A/B используй START_A.md и START_B.md. Каждый читает свой полный промпт, текущие зависимости и фактическое состояние, а не ждёт нового поручения для каждой следующей работы.
4. Перед запуском executor либо собственной записью чат проверяет claim/lease, per-profile lock и process receipt. Нельзя дублировать уже активную задачу, захватывать чужую интерактивную сессию или писать поверх активного автора.
5. Реальные команды запуска, наблюдения и восстановления бери только из EXECUTION_RUNTIME.md. Не угадывай CLI по старому ограниченному codex-runner примеру; не меняй модель или глобальную авторизацию.
6. Проверь фактическое исполнение по безопасному receipt и конкретному результату. Если доступна следующая независимая работа, продолжение не требует отдельного сообщения владельца или контроллера.
7. STOPPED не возобновляется обычным START, заменой текста или рестартом сервиса. Нужно новое прямое указание владельца; ранее использованный receipt не годится после нового STOP.

## Если используется автоотправка
Возможная автоотправка коротких START — дополнительное средство обращения к диалогам, не единственный двигатель runtime.
Сохраняй разные текстовые блоки OCTOPORT_A, OCTOPORT_B, OCTOPORT_C и правильные URL соответствующих диалогов; один общий редактируемый text ID нельзя использовать для разных ролей.
Не держи несколько активных копий одного диалога и не отправляй сообщение в незавершённый ответ. Частота автоотправки не доказывает скорость или непрерывность разработки.
Если чат/браузер/подписка приостановлены, сообщай фактический статус. Живая работа runtime подтверждается отдельно; одна автоотправка либо текстовая декларация не дают такой гарантии.

## Как идёт работа
Постоянный цикл области: восстановление → готовый результат из незакрытых SPEC/PLAN → claim → авторская работа → checkpoint NOT_ACCEPTED → независимое exact review → интеграция C → следующая задача.
Планировщик и ревьюер read-only; автор пишет в отдельной назначенной workspace-write копии. Доверенный supervisor проверяет scope, сохраняет diff и выполняет Git. Автор не публикует и не принимает себя.
Другой профиль проверяет точный SHA/tree/diff. Исправленный кандидат проходит новое review. Только C выполняет интеграцию main с прежними hook/CI/ready-main/readback; только B автор DB/schema/migrations до явно внедрённой замены.
Чат вправе работать сам через RDC после отдельного claim той же области/профиля. Работа чата и runtime не создаёт двух авторов одних файлов или одной задачи. Занятый профиль блокирует конкретный запуск, а не всю независимую очередь.
Модель серверного Codex — только gpt-6-luna, существующая ChatGPT-подписка; без платного API, другой модели и fallback. До одной активной Codex-сессии на профиль; существующие интерактивные сессии не захватываются.

## Приоритет результата и полный проект
Ближайший результат — проверяемая ручная версия по R0–R4: точный пакет, конечная матрица доступных элементов, обычный серверный путь, честная инструкция и проверенные ограничения. A/C ведут ручную выдачу; B параллельно выполняет мониторинговое хранение и конкретные серверные блокеры.
Ранние STORE-0…STORE-4 идут параллельно. C подаёт каждый выбранный канал, как только достигнут рабочий безопасный минимум и доступ ревьюера в пределах уже выданного разрешения. Не ждать полного roadmap, всех браузеров, C06 или Safari.
S0–S3 сохраняются: ограничение данных/честные сообщения; один доказанный мониторинговый цикл; проверенное исправление с ручной приёмкой; надёжность и расширение покрытия. Они не становятся искусственным gate ручной выдачи или магазинного минимума.
Весь A01–A06, B01–B07, C00–C07, SPEC и readiness остаются обязательны. Пустая локальная очередь, DONE, зелёные тесты, ZIP или Submit не означают готовность всего сервиса. Потоки сами добавляют следующие незакрытые результаты в общую очередь.
Замороженные ручные/store байты сохраняются отдельно от развивающегося main. Новая версия не подменяет ранее проверенный пакет и не превращает SOURCE/SYNTHETIC в LIVE/PRODUCTION.

## Когда нужно участие владельца или контроллера
Через четыре часа после старта/последнего подтверждённого контроля либо раньше при существенном блоке, риске или повторной проблеме появляется «НУЖЕН КОНТРОЛЬ [A/B/C]». Для конкретного внешнего действия — «НУЖНО ДЕЙСТВИЕ ВЛАДЕЛЬЦА [A/B/C]».
Обычная проверка состояния, diff, CI и процессов не требует STOP. Запрос контроля не останавливает независимую работу; замечание ограничивает конкретное действие до указанного условия.
Вход/OTP/ключ/магазинный кабинет/ручная смысловая приёмка не обходятся. Подготовь всё доступное, сохрани точный blocker и сразу продолжай другую задачу. Уже выданное разрешение на ограниченный пилот, owner-test и ранний Submit не запрашивай заново без изменения области.
Состояние читается из notices и receipts; контроллер не наблюдает диалоги автоматически. Нельзя считать обновлённый JSON или доставленный текст доказательством исполненного действия.
Если все разрешённые результаты действительно заблокированы, нужен свежий полный queue-scan с отдельным доказательством каждого остатка, корневой зависимостью и условием возврата. Нельзя оформлять общее ожидание при READY/IN_PROGRESS или незавершённом Git.

## STOP, ресурсы и защита
Прямой STOP владельца сильнее непрерывного цикла. Он запрещает новые задачи/запуски; сохраняются безопасный checkpoint и STOPPED, завершаются собственные тестовые группы. Рабочие продуктовые сервисы из-за остановки разработки не выключаются.
Соблюдай RESOURCE_POLICY.md: тяжёлые проверки через supervised cgroup и бюджет; полезная параллельность сохраняется. RESOURCE_WAIT — блокировка запуска, не всей роли. Не занижай бюджет после OOM и не очищай старые процессы/файлы/БД без отдельного разрешения.
Проверки различают SOURCE, PACKAGE, INSTALLED_SYNTHETIC, LIVE_OWNER, DEPLOYMENT, PRODUCTION. Релиз, live DB и необратимые действия требуют своих действующих конкретных полномочий и evidence.
Секреты, приватные сессии и клиентские данные не попадают в Git/логи/скриншоты; public VNC и обход platform/auth gates запрещены. Сайт/SEO, Safari до релиза, новая коммерция/платные провайдеры, новая аудитория и массовый refactor не включены.
Локальные hooks и broad RDC доступ не равны полной OS-изоляции или серверной защите GitHub. Соблюдение claim, scope, exact review и доверенной интеграции остаётся обязательным.
