# Как запустить три диалога Octoport

## Порядок запуска

1. Отключи автопромпт в старых рабочих диалогах. Их ветки и файлы сохранены; продолжать работу будем в трёх новых копиях.
2. Создай новый диалог **Octoport C — интеграция и выпуск**, подключи GitHub и Remote Desktop Commander, вставь целиком PROMPT_C.md.
3. C проведёт короткую проверку базы и напишет **«A И B МОЖНО ЗАПУСКАТЬ»**. Это проверка начала работы, а не ожидание полного исправления проекта.
4. Создай **Octoport A — расширение** и **Octoport B — backend**, с теми же инструментами, вставь в каждый его полный промпт.
5. В расширении автоотправки создай **три разных текстовых блока**: OCTOPORT_A, OCTOPORT_B, OCTOPORT_C. Закрепи каждый за URL соответствующего диалога. Не выбирай один общий text ID для трёх ролей: его редактирование изменит текст сразу в нескольких диалогах.
6. Включи автоотправку для этих трёх URL. Для первого запуска разумный интервал повторения — 3–5 минут; это рабочая настройка, не гарантия производительности. Не открывай несколько активных копий одного диалога. Проверяй, что расширение не отправляет сообщения во время незавершённого ответа и сохраняет правильный выбранный блок.

Текущий auto-sender проверен по исходникам и локальным тестам. Живую одновременную работу трёх ваших вкладок эта подготовка не подтверждает. Если чат/браузер/подписка приостановили выполнение, один промпт не может обеспечить фоновую работу.

## Почему C работает с начала

C сразу проверяет общую базу, CI и безопасность выпуска; затем устраняет release-preflight и другие задачи своей очереди.
Как только A или B закончили небольшой проверенный кусок, они кладут его точный SHA и доказательства в общую очередь на сервере. C читает её между задачами и объединяет изменения по одному.
Нет необходимости запускать C вручную два раза в день. При активной автоотправке он работает рядом с A/B; при отсутствии кандидатов занимается своей очередью. Интеграция происходит постепенно, а не после завершения больших модулей.

## Когда потребуется моё участие

Потоки сохраняют состояние и запрашивают проверку:
- через 4 часа после старта/последнего подтверждённого контроля, при ближайшей границе работы;
- раньше при существенном блоке, риске безопасности или повторяющейся нерешённой проблеме.

Видимый сигнал: **НУЖЕН КОНТРОЛЬ [A/B/C]**.
Другой сигнал: **НУЖНО ДЕЙСТВИЕ ВЛАДЕЛЬЦА [A/B/C]**.
До вашего появления поток продолжает только независимую разрешённую работу. Опасное или требующее ваших действий действие остаётся заблокированным.

Когда увидишь сигнал:
1. Выключи автоотправку именно этого диалога.
2. Напиши ему: **«STOP. Сохрани состояние, текущие процессы и checkpoint для проверки контроллером. Новые задачи не начинай».**
3. Дождись подтверждения безопасной остановки и напиши мне: **«Проверь поток A/B/C, он запросил контроль и остановлен».** Технический отчёт вручную переносить не обязательно: состояние, ветку и очередь я проверю на сервере.
4. После проверки я исправлю найденное/план и дам конкретное указание на возобновление. Менять постоянный промпт понадобится только при изменении метода или границ, а не после каждой задачи.
5. Перед включением автоотправки явно возобнови поток по результату проверки. Сам повтор промпта STOP не отменит.

Два остальных диалога могут продолжать независимую работу. Если вопрос затрагивает общий контракт или данные, мы отдельно ограничим нужные участки.
Я не наблюдаю эти диалоги автоматически и не получаю их сообщения в фоне. Сигнал рассчитан на то, что ты его заметишь и вернёшься ко мне.

## Что уже организовано

Одна общая main; рабочие ветки A/B/C не являются тремя независимыми версиями продукта.
Раздельные копии, тестовые БД, порты, браузерные профили, очередь кандидатов и общий слот тяжёлых проверок.
Контроль потери контекста опирается на постоянный промпт и файлы состояния. Текст промпта сам по себе не гарантирует, что модель никогда не ошибётся.
Локальные Git hooks ограничивают случайные записи вне роли и публикацию main из A/B. Это не защищённая сервером GitHub политика и не отдельные права ОС; RDC всё ещё обладает широким доступом.

## Границы готовности

Подготовлена база разработки. Выпуск продукта пока заблокирован незакрытыми браузерными/live/recovery/release проверками из PLAN.md.
Старая проверка выпуска, способная принять неверный ZIP, отключена с явной ошибкой; задача C01 — заменить её настоящим валидатором, а не просто вернуть PASS.
Production, почтовые/внешние публикации и live БД в этой подготовке не изменялись.
