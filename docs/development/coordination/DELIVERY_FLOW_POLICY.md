# Работа по общему результату и исполняемой очереди
Решение владельца 2026-10-01: устранить ночной простой A/B/C, изменить неработающий метод. Это уточняет существующие PLAN A04/A06, B04 и C05/C06; продуктовый scope, STOP и границы полномочий сохранены.

## Что изменено
Основная единица работы — проверяемый пользовательский результат с явными зависимостями. A/B/C остаются владельцами файлов, но не ведут три изолированные очереди «исходник готов — жду».
Оперативная очередь конкретных результатов: /root/octoport-control/controllers/work-board.json. Это единственный текущий список этих назначений. PLAN остаётся границей разрешённого объёма; исторические receipts остаются доказательствами. Не копировать определения задач в отдельные notices: сообщение содержит ID и ссылку на очередь.
Каждый поток сам добавляет собственные следующие задачи из незакрытых требований SPEC/PLAN, с путями, результатом и приёмкой, согласовав занятые пути. Не ждать назначения от контроллера или C. Новая архитектура/продуктовые полномочия этим не выдаются.
У задачи есть role, plan, state, requires, result, paths, acceptance. Завершение требует completion_receipt. DONE означает завершение указанной задачи, а не автоматически main, LIVE или принятие собственного кода.
Запись общей очереди только под коротким controllers/coordination.lock с перечитыванием и atomic replace. Не держать lock при проверках. Свои статусы менять командой queue-task; чужие задачи не закрывать.
Зависимая задача становится доступной, когда необходимые результаты DONE. Новый приказ контроллера для этого не нужен.

## Конечная цель и самостоятельное продолжение
«Сервис готов» означает готовность и приёмку всего согласованного объёма. Это рубеж, а не автоматическая остановка команды. Непрерывная работа продолжается до прямого STOP владельца: после приёмки — следующий разрешённый этап, реальные дефекты и сопровождение. DONE локальной задачи, зелёные тесты, исчерпание назначений и собранный ZIP не означают эту приёмку. Ранний полезный выпуск остаётся промежуточным рубежом, а не концом разработки.
После каждого результата поток без нового запуска контроллера сверяет незакрытые требования SPEC, PLAN и общей приёмки. Берёт следующее доступное требование; крупное раскладывает на проверяемые части. Если собственная очередь пуста, сам создаёт следующую задачу через queue-add --task-file FILE.json: id, role, plan, state=READY, requires, result, paths, acceptance, basis (конкретное незакрытое требование). queue-add сверяет конкретные пути с OWNERSHIP, запрещает самоназначение чужих путей/масок и сохраняет точный пункт действующего PLAN. basis объясняет оставшийся пробел. Семантическую связь работы с требованием проверяет принимающий поток; CLI не умеет доказать её по свободному тексту. Очередь не выдаёт права на чужие файлы или новую функциональность.
Блокируется конкретное действие. Проверить независимую подготовку, потребителей, негативные сценарии, незакрытые требования и прямую помощь соседнему потоку по согласованным путям. Повторять неизменные тесты, штамповать документацию или выдумывать функции ради активности запрещено. Отсутствие задания от контроллера не является внешней блокировкой.
Приёмка сервиса фиксируется отдельным фактом C06/C07 и владельцем; не выводится из пустой очереди и не отменяет непрерывное продолжение. До неё любой отчёт об исчерпании работы обязан явно указывать незакрытые критерии, а не объявлять сервис завершённым.

## Обычный цикл
1. В своей роли выполнить control.py ROLE status --compact; читать work_queue, новые адресные сообщения и фактический Git. Полный state сохранён по указанному пути.
2. При доступном результате: start, если роль WAITING_INPUT; затем собственный checkpoint по реальной задаче. STOPPED так не возобновлять.
3. Отметить начало: control.py ROLE queue-task --task ID --task-state IN_PROGRESS.
4. Выполнить ограниченный результат, проверить и передать exact candidate по обычному протоколу. Нужен соседний результат — отправить прямой peer request, не ждать запроса, который никто не создавал.
5. Зафиксировать результат: queue-task --task ID --task-state DONE --receipt /root/octoport-control/logs/ROLE/result.json. Получатель всё равно проверяет границы этого evidence.
6. Конкретная внешняя блокировка: queue-task --task ID --task-state BLOCKED --summary "действие и причина" --receipt "evidence". После реального изменения условия IN_PROGRESS требует существующего unblock receipt. Не использовать его как новое разрешение обойти запрет.
До интеграции CLI-кандидата соблюдать те же правила через очередь и адресные сообщения, не править чужую рабочую копию.

## Ожидание и честное состояние
waiting отклоняется, если есть READY/IN_PROGRESS в общей очереди или незакоммиченная работа. Незавершённое сохранить отдельным честным checkpoint-коммитом, не выдавая его за принятую версию.
Старый полный список PLAN не закрывает новое назначение. Каждый waiting receipt содержит work_board — точную копию work_queue.input_snapshot из свежего status: факт существования и SHA256. Изменение или удаление очереди отклоняет прежнее обоснование; status также показывает его недействительность. BLOCKED, DONE и снятие BLOCKED требуют существующий receipt в logs/controllers/artifacts внутри control.
status обновляет heartbeat_at; только checkpoint обновляет last_checkpoint_at. RUNNING означает разрешённое состояние роли, не доказательство активного исполнителя. В аудите нужны реальные commits/diffs/process/evidence, а не свежий heartbeat.
review_pending не останавливает работу. Пустой polling и повтор одинаковых тестов не являются прогрессом.
Если все разрешённые результаты реально заблокированы, фиксируется общий PROJECT_BLOCKED: корневая внешняя зависимость, её владелец, готовая передача и одно действие для возврата. Не обещать бесконечную работу и не создавать фиктивные задачи.
На выпускном рубеже C и контроллер проверяют доступность следующего результата до ухода, а не только факт RUNNING. Отсутствующий внешний доступ обнаруживать ранним безопасным preflight и отделять от подготовки кода.

## Независимая проверочная среда
Разрешённый следующий результат — установленный клиент плюс настоящий изолированный API/worker/portal и disposable PostgreSQL с обычным OTP/device flow через локальный тестовый почтовый приёмник. Переиспользовать уже принятые C05 и p2-auth компоненты.
B владеет helper обычного входа/сроков/отзыва; C — жизненным циклом loopback-контура; A — установленным браузерным потребителем. Пути назначены в очереди до правок.
Тестовые аккаунты и ключи генерируются только внутри изолированной LOCAL_DEVELOPMENT среды. Не переносить их в STORE/живой сервер, не подменять authenticated/workAllowed, подписи, CSRF или сроки.
При необходимости иного endpoint/trust создаётся отдельно обозначенный DEV-артефакт. Замороженные STORE-пакеты не меняются. Проверка DEV не выдаётся за выпускной пакет или настоящий ответ ИИ.
Это новая сквозная граница, а не повтор C05: C05 ранее доказал запуск/restore и чтение уже созданных сессий, но не обычный OTP->portal->device->установленный клиент.
Подготовка не зависит от live admin cookie и не требует настоящих аккаунтов владельца. SMTP/provider/TG ограничены loopback/явными тестовыми двойниками. Все процессы через existing heavy и конечный cleanup.
Платформенный отказ технического входа и прежний C07 сохраняются отдельными ограничениями. Запрещены retry через иной исполнитель, увеличение TTL/выдача admin роли ради обхода, доступ к секретам или изменение live БД.

## Постоянные промпты и отчёты
Постоянный промпт хранит правила и указатели, а не утверждение, что давняя сессия ещё действительна или давняя задача ещё не выполнена. Состояние восстанавливается из текущих receipts без вывода секретов.
При изменении метода выдаются полные PROMPT_A/B/C; новую задачу и SHA в них не вшивать.
Контроллер сравнивает исполнение с предыдущим аудитом и базой ошибок. Назначение/код/тест/применение/эффект отмечаются отдельно. Собственное изменение контроллера принимает другой участник.
