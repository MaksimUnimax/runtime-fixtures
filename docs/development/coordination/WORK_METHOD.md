# Работа Octoport через диалоги MCP

Действующий метод от 2026-10-01. Репозиторий MaksimUnimax/runtime-fixtures, сервер Easyscript. Это изменение организации существующего проекта, а не новый roadmap. SPEC, MINIMUM_SPEC, PLAN, продуктовые контракты и принятые результаты сохраняются.

## Участники и результат
| Диалог | Ответственность |
|---|---|
| A, B, C | Три основных исполнителя. Каждый берёт законченный результат из общего PLAN и ведёт его через код, необходимые проверки, включение и подготовку пригодного пакета. Буква обозначает рабочую копию, а не исключительное право на компонент. |
| OPERATOR | Отдельный обычный диалог по обращениям: выдать проверенный пакет, принять замечания ручной проверки, организовать исправление, затем выдать исправленный пакет. Без автопромпта и бесконечного ожидания. |
| Контроллер | Весь проект: цель, roadmap, архитектура, качество, организационные ошибки, разрешённые исправления, готовность ручной версии и магазинов. Не обязательная пересылочная инстанция. |

Работают существующие чаты через MCP/Remote Desktop Commander и GitHub. Продолжение между ходами обеспечивает только уже используемый владельцем механизм повторения управляющего промпта. Сервер хранит код, состояния и доказательства; нового планировщика, постоянного Codex-исполнителя или фонового сервиса этот метод не создаёт. Не обещать работу неактивного чата без нового запуска/действующего повтора.

## Сквозная задача и общая работа
Одна задача — проверяемый полезный результат, связанный с существующим пунктом SPEC/PLAN. Исполнитель не заканчивает её словами «мой слой готов, передал C». Он отвечает за нужные клиентские и серверные изменения, совместимость, проверки, готовый артефакт и запись результата.
Существующие знания A об extension, B о backend и C о выпуске полезны как консультация, но не исключительные права. Каждый может выполнять любой раздел утверждённого PLAN. DB/schema/migrations имеют одного автора конкретного изменения, а не постоянного владельца B. Продвинуть main может любой A/B/C по прежним проверкам.
Общий учёт — /root/octoport-control/controllers/work-board.json. Это список результатов и зависимостей, не очередь передачи A→B→C. Задачи имеют одного текущего автора и конкретные пути. До правки закрепить scope атомарно штатными командами; чужую незавершённую работу не захватывать. Общий контракт/lockfile/миграцию включить в scope и проверить всех затронутых потребителей.
Одновременно не вести несколько несохранённых изменений одного автора. Появившееся срочное замечание переключает одного подходящего исполнителя после безопасного checkpoint; остальная разработка продолжается. При конфликте файлов сохранить точную зависимость или согласовать передачу на безопасной границе; не ждать завершения всего чужого модуля.
Не создавать дубли задач по одному замечанию. Недоступность владельца, проверки магазина или внешнего аккаунта блокирует только соответствующее действие. Доступные части и другие утверждённые результаты выполняются дальше. Не придумывать работу ради активности.

## Замечание ручной проверки → исправленный пакет
1. OPERATOR сохраняет слова оператора, фактически проверенную версию и воспроизведение в operator/feedback. Недостающий номер версии не повод отложить всю диагностику.
2. OPERATOR связывает замечание с одной технической задачей. Может сам исправить в согласованном изолированном scope или направить конкретному исполнителю. Не требуется разрешение контроллера на обычное исправление.
3. Автор воспроизводит причину и ведёт исправление до конца. Проверка другим участником или ограниченным помощником начинается, когда есть проверяемый diff; это не постоянный отдельный поток и не передача ответственности за выпуск.
4. Автор проверяет затронутое поведение и потребителей, собирает пакет, проверяет его в требуемом установленном сценарии и сохраняет точные байты плюс READY_FOR_OPERATOR. Прямая ссылка на замечание обязательна.
5. Сразу после сохранения результата автор продолжает следующий доступный пункт roadmap. Запуск OPERATOR, ACK, скачивание и ручная приёмка не являются условием продолжения.
6. OPERATOR по обращению или контроллер при аудите выдаёт уже подготовленный пакет. Результат ручной проверки и новые замечания централизуются через OPERATOR и общие записи. Техническая готовность, выдача и ручная приёмка — разные факты.

Полный формат кандидатов/выдач/замечаний — OPERATOR_TESTING_POLICY.md. Не заменять файл уже выданного пакета новой сборкой. Замечание к старой выданной версии не приписывать самой новой. При отклонении версии сохраняется точное замечание; прежний PASS не закрывает его.

## Проверки и включение
Автор обязан получить независимую проверку собственного изменения. Для неё доступен ограниченный Codex по CODEX.md либо другой свободный участник. Проверяющий читает diff и доказательства в отдельном контексте; самоподтверждение автора не считается. Проверка не закреплена за C или контроллером.
Не передавать одному диалогу обязательную очередь всех проверок и выпусков. При недоступном проверяющем конкретное изменение сохраняется; автор продолжает независимую работу, а проверку может выполнить другой разрешённый участник.
Сначала точное воспроизведение и быстрые проверки изменённой границы, затем потребители/регрессии по риску. Не собирать расширение и не гонять весь продукт ради правки документации. Совместимые исправления одного дефекта проверять целиком, не выпускать отдельный ZIP после каждой внутренней мелочи.
Перед main сохраняются пять обязательных CI точного кандидата: Server CI; Extension CI; Extension I1-C1 client; Documentation CI; Coordination and release safety. Не ослаблять их под видом ускорения. Публикуется своя ветка, затем ready-main с текущей origin/main базой, non-force push и readback.
Короткая конкуренция за main разрешается актуальной базой и non-force push: если main продвинулся, сверить изменение базы и совместимость, обновить exact evidence. Не держать общий lock во время тестов или ожидания CI. Проигравший гонку не перезаписывает чужой результат.
Evidence относится к точным входам: commit/tree, зависимостям, конфигурации, окружению, пакету и сценарию. Не переносить PASS с другого пакета. Не повторять неизменную проверку без причины; обязательный exact-head CI этим правилом не отменяется.
SOURCE, PACKAGE, INSTALLED_SYNTHETIC, LIVE_OWNER, DEPLOYMENT и PRODUCTION отдельно. READY_FOR_OPERATOR требует проверок точного установленного пакета для заявленного сценария; оператор проверяет реальную полезность. Количество тестов, зелёная сборка и RUNNING не доказывают работающий сервис.

## Roadmap и выпуск идут параллельно
Срочное исправление готовится от подходящей проверенной базы, пока остальные продолжают основную разработку. Пакет не должен каждый раз догонять случайные новые изменения main. Замороженная версия и развивающаяся линия различаются; исправление переносится в нужные линии с проверкой совместимости, без потери выполненного.
Ближайшая ручная цель: точный пакет → обновлённый совместимый тестовый сервер → обычный вход → установленный полезный сценарий и все доступные кнопки → ручная проверка. Не объявлять авторизацию проверенной подменой authenticated/workAllowed.
Ранний Submit разрешён после полезного безопасного минимума и рабочего пути ревьюера по STORE_POLICY.md. Он не ждёт всего roadmap, мониторинга всех ИИ или Safari. Весь утверждённый SPEC/PLAN и сопровождение продолжаются после ручного пакета/магазина.
Мониторинг: эталон и ограниченная история → значимое изменение DOM/API → проверка поведения расширения → исправленный проверенный кандидат → ручная приёмка → разрешённый канал обновления. Эталон не менять до принятия исправления. Не добавлять второй Telegram poller или незаметно переключать продуктовые сервисы.

## Рабочие границы и паузы
Входящие, feedback, готовые общие задачи и изменения назначений проверяются при входе, перед взятием задачи, после ограниченной операции и перед длительным запуском. Во время активной работы ориентир — не более 10 минут до следующей проверки, если атомарная операция позволяет. Долгую проверку запускать с сохранённым состоянием; не прерывать её бессмысленно ради часов.
Checkpoint содержит фактический результат, SHA, evidence, текущий scope и следующее доступное действие. Он нужен при переключении/перед долгой операцией и переносе в новый диалог, а не вместо результата.
Ожидание конкретного пакета, review, CI, owner-login или магазина не переводит всю команду в ожидание. Перед общим WAITING_INPUT проверить весь общий утверждённый PLAN и доступные задачи, а не только исторический раздел своей буквы.
Если действительно нет ни одного доступного безопасного результата, сохранить фактические внешние блокировки. Не изображать бесконечную работу, не обходить отказ платформы/доступа и не придумывать новые функции.
Более поздний прямой STOP немедленно сильнее любого повторяемого/стартового промпта. Сохранить WIP; новых задач, дочерних запусков и публикаций не начинать. Возобновление — только по новому явному указанию владельца. Продуктовые службы из-за STOP разработки не выключать.

## Общие границы
Один ограниченный Codex на A/B/C, только gpt-6-luna, существующие профили и подписка; без fallback/копирования авторизаций. Chat остаётся ответственным исполнителем. Если помощник недоступен, продолжать доступную работу через MCP.
Браузеры/серверы/тяжёлые проверки через существующий heavy и per-role disposable DB; ограничивать собственные процессы и завершать их. Не вводить общий лимит одного процесса и не очищать исторические данные самовольно.
Работа с исходником миграции не даёт права менять live БД. Прежние конкретные разрешения, backup/restore, совместимость, подпись, no-replay, privacy и production gates сохраняются. Уже данное разрешение не запрашивать повторно.
Никаких секретов, личных сессий и клиентских бизнес-данных в Git, отчётах или скриншотах. Marketplace payload остаётся локальным с принятой TTL; account/store/dialogue isolation не ослаблять.

## Контроль эффекта
Каждый контроллер проверяет фактические результаты, организацию и базу ошибок. Исправимую организационную причину устраняет сам в текущем запуске, не ограничивается назначением.
Замерять путь от получения замечания до доступного проверенного пакета: начало/конец диагностики и кода, ожидания, review, сборка, установленная проверка, готовность и выдача. Нельзя объяснять весь срок временем последней сборки.
Отдельно проверять прошлые причины: ночной простой при незакрытом roadmap, очередь через C, повторная приёмка неизменного пакета, потерянный REWORK, ожидание человека всем проектом, подмена MCP серверным исполнителем.
Статусы исправления: причина установлена, изменение подготовлено, проверено, применено, эффект наблюдался. Успешный модельный/CLI тест не доказывает суточную автономную работу чатов.
Организационная база /root/octoport-control/controllers/organization/errors.json, история events.jsonl. Не закрывать запись лишь потому, что выпущен новый текст. При повторе назвать, какой механизм не был применён/не сработал, и устранить причину.

## Основания метода
- Feature Teams: https://less.works/less/structure/feature-teams — владение результатом поперёк компонентов и уменьшение передач.
- DORA: https://dora.dev/capabilities/streamlining-change-approval/ — независимая проверка и автоматические проверки вместо обязательного внешнего согласования каждой правки.
- Короткие ветки/выпуск: https://trunkbaseddevelopment.com/short-lived-feature-branches/ и https://trunkbaseddevelopment.com/branch-for-release/.
- Работа агентов: https://www.anthropic.com/engineering/building-effective-agents и https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents — ограниченные задачи, независимая оценка, сохранённое состояние, проверка реального поведения.
Это инженерные основания выбора, а не доказательство уже достигнутой скорости Octoport. Применение к нашим чатам проверяется отдельно.

## Один ответственный за выдачу; независимое продолжение roadmap
Для конкретного замечания/ручной версии в work-board сохраняется один сквозной автор до READY_FOR_OPERATOR: исправление, необходимые проверки, точный пакет, совместимость серверного пути и передача OPERATOR. Закрытая вспомогательная проверка не закрывает этот результат. Автор не передаёт обязательную сверку готовности другому основному потоку.
Два остальных основных диалога имеют доступные независимые продуктовые результаты утверждённого SPEC/PLAN без зависимости от этой ручной выдачи. Независимое review обязательно, но не превращается в постоянную занятость второго/третьего потока одной сборкой. Начатая ограниченная операция завершается безопасно; следующая задача не ждёт нового контроллера.
Это распределение на текущий результат, не постоянные компонентные роли. C не становится сборщиком всех будущих версий. Внешняя блокировка сохраняет точный предмет и ответственного, но не останавливает независимую работу проекта.
Локальный установленный тест, STORE-пакет, ручная выдача и Submit имеют отдельные доказательства. Проверка нужного сценария обязательна; будущие этапы roadmap не добавляются к ней. Принятые проверки неизменённых байтов сохраняются при переносе карточки/изменении документации.
