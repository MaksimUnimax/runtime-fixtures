Точная внутренняя граница: readSnapshots({principal: ExtensionPrincipal, entityIds: readonly string[]}) -> Promise<readonly {entityId: string; serverRevision: number; serverState: SellerAgentsSyncEntryV1['payload'] | null}[]>.

Внутренний интерфейс может быть отдельным additive export, чтобы не ломать существующие mutation-only doubles. Реализация использует настоящую disposable DB, а не только тестовый двойник. Один bounded SELECT после транзакционной перепроверки/блокировки полномочий session/device/account/user; accountId только из principal. Ключи только канонические conversation:<digest> и store:<storeId>, до 32 уникальных, с существующей грамматикой storeId. Проверить ограничения и на границе reader. Ответ строго в порядке запроса, отсутствующий объект revision=0/state=null. Никаких INSERT/UPDATE/receipts/updated_at на read-only пути, никаких новых таблиц/миграций.

Один SELECT даёт согласованные пары revision/state для списка. При совместном запросе сервис завершает последовательность mutations, затем делает bounded read: snapshot отражает актуальное зафиксированное состояние на момент SELECT, включая разрешённые конкурентные записи. Не обещать атомарность всего batch, которой прежняя реализация не предоставляла. C задаёт wire bounds: entries+unique reads<=32, обязательна хотя бы одна операция, snapshots<=32, state<=4096 UTF-8 bytes, общий JSON response<=256 KiB. Не обрезать state молча.

Проверки: account isolation; revoked authority до транзакции; отсутствие побочных записей и изменений timestamps; порядок; missing; границы; одновременная mutation/read; сохранность historical replay. S2/0050 и включение новых сетевых полей остаются отдельным server-first шагом.

### Разрешённая Firefox архитектурная работа

Подтверждён настоящий общий блокер: Mozilla относит device/browser/usage/error сведения к technicalAndInteraction, разрешает эту категорию только как optional и требует уважать отказ. Косметическая запись optional без прекращения отправки не исправляет проблему.

C разрешено спроектировать и реализовать additive режим без передачи необязательных технических сведений: авторизация не должна зависеть от наличия browser/version metadata; совместимость должна оставаться проверяемой по подписанным данным и локальным сведениям. Не подставлять вымышленные версии/семейства, не разрешать неподдерживаемые профили и не ослаблять подпись, отзыв, account/device isolation. Сначала C фиксирует точный совместимый wire/compatibility контракт в Git; B единолично делает необходимые серверные/DB изменения, A — реальную проверку разрешения, отказ и отзыв перед отправкой. Это разрешённая задача внутри store readiness, отдельного разрешения владельца на обычную реализацию не требуется. До проверки обеих веток Firefox остаётся NOT_READY_FOR_AMO; Opera продолжает отдельно.
