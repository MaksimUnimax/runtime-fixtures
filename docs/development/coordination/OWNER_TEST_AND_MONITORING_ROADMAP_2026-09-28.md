## Главный ближайший результат

Владелец получает конкретную устанавливаемую версию, инструкцию обычного входа и проверенный рабочий путь от кнопки «Начать работу» до результата и «Завершить».
Перед передачей принимается конечный перечень всех доступных пользователю элементов этой версии: окно расширения, кнопки в диалоге и необходимые страницы портала.
Для каждой кнопки фиксируются ожидаемый результат, положительная проверка, существенная ошибка/отмена, браузер, точный пакет и уровень доказательства.
Результат SOURCE, пакет на диске и проверка с подставными ответами не превращаются в проверку настоящего магазина/ИИ.
Нельзя объявлять «все кнопки проверены» по числу тестов или по одному открывшемуся окну.
Нельзя молча сокращать существующий функционал, скрывать непроверенные кнопки или обещать владельцу непроверенную работоспособность.
Окончание всего мониторинга, всех браузеров, полного C06 и будущего канала исправлений не являются условием выдачи ручной версии и ранней подачи.

## Почему ручная версия задержалась

1. Был реальный дефект распознавания Copy в ChatGPT, затем в прежнем пакете остались удалённые операции WB. Принимать такие пакеты было нельзя; старые ZIP сохранили как историю, подготовили новый.
2. Выпуск 0.2.6 вскрыл разрозненные привязки к 0.2.5. Их исправляли последовательно после падений проверок: store contract, core route/import, I1, browser config, release safety и теперь runtime authority. Это инженерный долг процесса выпуска; количество проходящих тестов не оправдывает повторяющуюся задержку.
3. Проверенные компоненты не были доведены до одного принятого комплекта «этот ZIP + этот сервер + обычный вход + полезный результат». Обновление сервера подготовлено на изолированной БД, но не выполнено в owner-test; приёмка настоящего входа/провайдера остаётся открытой.
4. Отдельно развивались сервер, магазины, браузеры и мониторинг. Контроллер закрепляет приоритет выдачи ручной версии перед расширением мониторинга, без остановки независимой работы B и без отмены полного roadmap.
5. Устаревшие state/receipt создавали путаницу. A/C должны обновлять текущие статусы и точные ссылки, не переписывая историческую приёмку 0.2.5 как будто она относится к 0.2.6.

Внешнее ожидание не переводит весь поток в WAITING_INPUT: независимые разрешённые задачи продолжаются до прямого STOP владельца.

Пакет для личной установки нельзя называть принятым магазином. Проверка на серверном Linux не выдаётся за проверку Windows или обновления через магазин.

## Что получится после внедрения мониторинга

S0 даст работающий ограничитель накопления данных и понятные сообщения. Он ещё не даст автоматическое исправление расширения.
S1 даст рабочий обнаружитель поломки на одном заявленном сценарии ChatGPT, с отдельно показанными непроверенными участками.
S2 даст полный управляемый цикл подготовки, тестирования, ручного одобрения и выпуска исправления для поддерживаемых случаев.
Это готовый функционал в названных границах, а не обещание самостоятельно чинить любые сайты и любые API без участия человека.
Доставляемые настройки могут выбирать только заранее упакованную разрешённую логику. Изменение исполняемого кода требует новой версии расширения и обычного канала обновления; удалённый произвольный JS не добавляется.
До рабочего S2 один автор готовит, независимо проверяет и выпускает исправление обычным обновлением; независимое review не создаёт постоянную цепочку основных потоков. Отсутствие нового механизма исправлений не блокирует текущую ручную версию.

## Уведомления и хранение

Норма: один принятый эталон для совместимого набора версий + до трёх компактных последних наблюдений с объединением одинаковых результатов.
Активный инцидент, доказательства ручного одобрения/выпуска и квитанции защиты от повтора хранятся отдельно по ограниченной политике архитектуры. Их нельзя удалить вместе с обычной историей.
Сообщение человеку отвечает: что проверено; что не проверено и почему; найдена ли поломка; что будет сделано; требуется ли действие владельца.
Пример целевого текста: «ChatGPT: ответ и копирование кода проверены, ошибок нет. Алиса: проверена только открытая страница, вход не настроен. Ozon: документацию получить не удалось; изменения API пока не проверены. Исправления пользователям не отправлялись».
Это пример будущего формата, а не результат текущего запуска.
Одна поломка создаёт один инцидент; повтор того же сбоя не создаёт лавину сообщений. Отсутствие доступа означает «не проверено», а не «всё работает».
Получение официальных документов Ozon/WB должно иметь понятный статус источника/давности; отказ/защита сайта не обходятся и не заменяются выдуманной актуальностью.

## Границы выполнения и передачи

- Один автор конкретной ручной версии отвечает за R0–R3 целиком. Два других основных диалога продолжают независимые продуктовые результаты. Любой A/B/C включает свой принятый код в main по действующим проверкам. Конкретная live-authority сохраняется в исходных границах; нового разрешения здесь нет.
- Текущий roadmap даёт приоритет работам и проверкам, не является разрешением на ещё не одобренное переключение продуктовых API/worker/portal или использование личных секретов.
- Ограниченный пилот мониторинга уже разрешён владельцем; повторное общее разрешение на него не требуется. Второй Telegram poller не создаётся.
- Перед единственным необходимым действием владельца автор версии сначала полностью готовит доступные проверки, точный пакет и короткую инструкцию. Не запрашивает логин «на всякий случай» и не просит токены в чат.
- Все авторы исправляют отставшие state/result/next, сохраняют точные SHA и виды доказательства. Новый notice приоритетнее старого next; более поздний STOP всегда сильнее.
- Проверяется фактическая ревизия документа в main; применение оперативного назначения не выдаётся за завершённую интеграцию исходника.
