# Единый технический план Octoport

Это разрешённый объём существенной части проекта: довести расширение, backend, мониторинг и выпуск до проверяемой бесплатной беты, затем исправления по её результатам. Сайт/SEO разрабатываются отдельно. Монетизация и платные провайдеры не включаются автоматически.
Уже написанное не переписывать заново; проверять незакрытые критерии SPEC и выявленные риски. Старое слово ACCEPTED относится только к указанной версии и уровню доказательства.

## A — расширение и браузер

| ID | Очерёдность и задача | Условие завершения |
|---|---|---|
| A01 | Восстановить R5 browser-family candidate; расследовать Opera WORK_START_PENDING_COMMIT_READBACK_FAILED и таймаут поиска account | Минимальная воспроизводимая причина, исправление, исходная и извлечённая package проверки; явно различать продукт и окружение |
| A02 | MV3: перенос секретов при остановке/перезапуске service worker; recipientKeyMap сейчас живёт только в памяти | Проверенный безопасный resume либо явная отмена/повтор с новым ключом; нет ложного успеха, утечки, повторного применения, потери подтверждённого результата; reload/restart/timeout tests |
| A03 | Матрица браузеров и идентичности: Chrome, Opera, Yandex, Firefox, Safari | Каждому — собственная реальная версия, профиль, пакет и доказательство; Chromium не засчитывается за branded Chrome, отсутствие macOS не считается PASS |
| A04 | Закрыть остаток Q1-A/B и клиентской Q1-C по SPEC: multi-store, Ozon/WB, AI scopes, delivery/recovery/sync/revocation | Сквозные сценарии с единым подтверждением, no-replay UNKNOWN, изоляцией account/store/dialogue и сбросом поздних callbacks; требования связаны с evidence |
| A05 | Упростить наиболее изменяемые текстовые build patches постепенно | Извлечён один модуль там, где есть повторные дефекты/правки; сохранены hash guards и differential tests. Нет массовой переписи 60 патчей ради эстетики |
| A06 | UX установки/обновления/диагностики и исправления beta feedback | Понятные владельцу ограничения/ошибки; privacy-safe diagnostics; нет ложной рекламы неподтверждённых браузеров |

Можно переставлять независимые A02/A03, если A01 заблокирована окружением; блокировка остаётся видимой. У A нет права самостоятельно ослабить product browser contract.

## B — backend и данные

| ID | Очерёдность и задача | Условие завершения |
|---|---|---|
| B01 | Проверить совместимость объединённых миграций и подготовить безопасный путь для legacy Stream-2 DB | Fresh + canonical-prefix upgrade уже проверяются базой; инвентаризация реальных applied hashes только read-only; отдельный согласованный план для иной линии, backup/restore proof; не переписывать applied journal и не сбрасывать live БД |
| B02 | Bootstrap/config/profile catalog: ранее в preprod release/browsers/contracts/profiles/assignments было по 0 записей | Идемпотентное создание опубликованной согласованной v2 цепочки из версионированного input; неизвестные/пустые/несовместимые записи fail closed; подпись проверяет реальное установленное расширение; live mutation отдельно разрешается |
| B03 | ServerEphemeralTransferRelay: ограничить память и время жизни | Активная TTL-очистка, общий и account quota/byte cap, bounded payload, отзыв/ack/delete; flood/expiry/race tests; process restart не выдаёт фиктивный SUCCESS |
| B04 | Q1-C OTP/SMTP/auth/bootstrap/sync/revocation + перенос с A | Mail/job/idempotency/refresh race tests и доступные реальные подтверждения; owner mailbox/доступ — запрос владельцу без остановки остальных работ; секреты не в отчётах |
| B05 | Эксплуатация сервера и настоящий recovery | Вместе с C: выделенный service user, resource limits, чистый pinned artifact/SHA, staging rollback, восстановление реального disposable PostgreSQL из backup и приложение после восстановления |
| B06 | Остаток server/admin/support/beta admission по SPEC и негативным сценариям | Межаккаунтная изоляция, серверная авторизация каждой мутации, аудит без секретов, квота бесплатной беты, revocation и сроки хранения; UI/API согласованы |
| B07 | Исправления после контролируемой беты | Измеримые проблемы пользователей, тест регрессии по риску, прежние product/privacy invariants сохранены |

B — единственный автор DB/schema/migrations. Входящие запросы C на monitoring DB обрабатывать небольшими совместимыми порциями; не задерживать их до конца B-модуля.

## C — интеграция, выпуск и мониторинг

| ID | Очерёдность и задача | Условие завершения |
|---|---|---|
| C00 | Проверить общую базу/CI, очередь, часы review, места работы и test lock | A/B можно начинать сразу после короткой проверки готовности; не ждать завершения C01 |
| C01 | Заменить заблокированные legacy B1 prepare/preflight на достоверную проверку выпуска | Неверный ZIP с NOT_AN_EXTENSION, произвольный trust key, traversal/duplicate ZIP entry, missing runtime, private material, stale SHA/tree/version/contract/migration/endpoint получают FAIL. Правильный пакет проходит. Доверенные ключи и endpoints берутся из отдельного авторитетного input; проверяется содержимое ZIP, не только декларация RC manifest |
| C02 | Постоянно интегрировать готовые A/B кандидаты и общий контракт | Один exact candidate за раз, проверка свежего main, потребителей и CI, без force; локальная/удалённая версия и evidence совпадают |
| C03 | API-watch semantic diff: required/type/enum/security/request/response changes | Негативные fixtures на реальные breaking changes; изменение количества endpoints не единственный детектор. Отчёт содержит источник/версию/неопределённость; проверить общий deadline на чтение body/redirects, сейчас timeout снимается после headers |
| C04 | Monitoring/TG/health: runtime wiring, permissions, lanes, browser matrix | Уведомления без утечки, dedup/retry/caps, независимые расписания и работающий real service wiring. Создание функции/тестового stub не значит запуск сервиса. Изменения DB заказывает B |
| C05 | Q1-D: заменить доказательство JSON/symlink harness реальной rehearsal | Запуск приложения exact artifact + реальная disposable PostgreSQL migration/backup/restore/rollback с чтением сохранённых данных; старый harness остаётся только симуляцией |
| C06 | Общая готовность Q1/B1 и приёмка контроллером | SPEC→код→тест→evidence, все release blockers закрыты; browser-specific ограничения явные, verified upgrade/rollback, support/privacy/security; подготовлен точный deployment plan без самовольной публикации |
| C07 | Выпуск по отдельному разрешению владельца и сопровождение | Exact artifact, backup, health/smoke, наблюдение, проверяемый rollback; после запуска собран реальный feedback. Сайт/магазин браузера/действия владельца отдельными gates |

C приоритетно разбирает кандидаты A/B; собственный monitoring блок ограничен примерно 60–90 минутами до следующей проверки очереди. Если мониторинг регулярно задерживает интеграцию — запрос контроллеру на перераспределение, а не четвёртый бесконтрольный поток.

## Ранний магазинный путь — параллельно разработке

[STORE-0…STORE-4](../../product/readiness/PUBLICATION.md) — обязательный путь от подготовки издателя до открытой беты. STORE-0 начинается сейчас; C01/A03 и готовая безопасная основная цепочка дают кандидата для ограниченной магазинной проверки. STORE-2/STORE-3 выполняются до C06: реальная установка и обновление N→N+1 — входные доказательства общей приёмки. Ранее подразумеваемое «первый Submit только после C06» отменено. Внешняя подача и распространение требуют конкретного разрешения владельца.

A проверяет данные/UX при обновлении, B совместимость старого и нового клиента с backend, C отвечает за точный пакет, store ID, канал, reviewer flow и evidence. Владелец выполняет подтверждения аккаунтов, первую Windows установку/обновление и смысловую приёмку. Программистские операции ему не перекладываются. Ограниченная магазинная версия не означает разрешение открытого набора; полная бета остаётся C06→C07.

## Общие зависимости и контроль качества

- Общие Zod/OpenAPI/BrowserFamilies/lockfile меняет один назначенный автор C с тестами потребителей A/B. B владеет миграциями; номера и timestamps выдаются из актуального main.
- C01 необходим до любой release acceptance. Его блокировка не мешает обычной разработке.
- A02+B03 принимаются совместно как протокол переноса; отдельно зелёные стороны не означают надёжный перенос.
- A04+B02+B04 дают реальную Q1-C цепочку. Нельзя закрыть её synthetic fixture.
- B05+C05 дают эксплуатационную готовность. Сам JSON harness её не даёт.
- Для каждого browser-release нужен A03; отсутствие среды оформляется как незакрытый release gate этого браузера.
- Небольшие backward-compatible куски интегрируются по мере готовности. «Соединим всё в самом конце» не является методом этой программы.

## Отложенное и стоп-факторы

Коммерция/оплата, сайт/SEO, redesign API, смена модели безопасности, массовый refactor и удаление исторических серверных копий не входят автоматически.
Production publication, irreversible data changes и получение/использование чужих личных сессий не разрешены этим планом.
Временные обходы и незакрытые review requests не стираются после compaction; входят в runtime state и checkpoint receipt.
