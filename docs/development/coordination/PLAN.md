# Единый технический план Octoport

Это разрешённый объём существенной части проекта: довести расширение, backend, мониторинг и выпуск до проверяемой бесплатной беты, затем исправления по её результатам. Сайт/SEO разрабатываются отдельно. Монетизация и платные провайдеры не включаются автоматически.
Уже написанное не переписывать заново; проверять незакрытые критерии SPEC и выявленные риски. Старое слово ACCEPTED относится только к указанной версии и уровню доказательства.

Действует WORK_METHOD.md: ID A/B/C ниже обозначают сохранённые требования, а не исключительные права диалогов. OPERATOR встроен как отдельный интерфейс ручной проверки; после готовности пакета автор продолжает общий roadmap. Критерии продукта не сброшены.

## Ранний магазинный путь — параллельно разработке

[STORE-0…STORE-4](../../product/readiness/PUBLICATION.md) — приоритетный параллельный путь. Аккаунты зарегистрированы по подтверждению владельца; ранняя подача/публикация при минимальной готовности уже разрешена. По [STORE_POLICY.md](STORE_POLICY.md) каждый канал подаётся сразу после готовности полезного безопасного среза, без ожидания всех A03/A04/B02/B04/B05/C05, других браузеров или C06. STORE-2/STORE-3 выполняются до C06: магазинные установка и N→N+1 входят в последующую общую приёмку. Нужный конкретному срезу backend/recovery проверяется; независимые будущие работы не становятся искусственным gate.

Автор конкретного выпуска отвечает за данные/UX при обновлении, совместимость клиента/backend, точный пакет, store ID, канал, reviewer flow и evidence с независимым review. Владелец выполняет подтверждения аккаунтов, первую Windows установку/обновление и смысловую приёмку. Программистские операции ему не перекладываются. Ограниченная магазинная версия не означает разрешение открытого набора; полная бета остаётся C06→C07.

## Общие зависимости и контроль качества

- Общие Zod/OpenAPI/BrowserFamilies/lockfile меняет один автор конкретной сквозной задачи с тестами всех потребителей. Этот же принцип действует для миграций; номера и timestamps выдаются из актуального main.
- C01 необходим до любой release acceptance. Его блокировка не мешает обычной разработке.
- A02+B03 принимаются совместно как протокол переноса; отдельно зелёные стороны не означают надёжный перенос.
- A04+B02+B04 дают реальную Q1-C цепочку. Нельзя закрыть её synthetic fixture.
- B05+C05 дают эксплуатационную готовность. Сам JSON harness её не даёт.
- Для каждого browser-release нужен A03; отсутствие среды оформляется как незакрытый release gate этого браузера.
- Небольшие backward-compatible куски интегрируются по мере готовности. «Соединим всё в самом конце» не является методом этой программы.

## Отложенное и стоп-факторы

Коммерция/оплата, сайт/SEO, redesign API, смена модели безопасности, массовый refactor и удаление исторических серверных копий не входят автоматически.
Production publication, irreversible data changes и получение/использование чужих личных сессий не разрешены этим планом.
Временные обходы и незакрытые review requests не стираются после compaction; входят в runtime state и checkpoint receipt.

## Переход к согласованному методу — 1 ноября 2026

Владелец согласовал метод и начало работы. Переход продолжает существующую программу: все таблицы, зависимости, 21 технический ID и принятые результаты выше сохранены. Продуктовая программа сохраняет 33 блока и 216 уникальных случаев; 45 основных и 8 резервных бизнес-вопросов не объединяются в один принятый перечень. Технический ID B02 в таблице PLAN и продуктовые блоки B02/B14 сохраняют разные пространства идентификаторов.

Описание ролей и ответственности находится в [WORK_METHOD](WORK_METHOD.md#method-description-20261101), отдельно от рабочих правил и полномочий. Переход выполняется существующими участниками и существующими checkpoint/handoff.

1. **Сохранить фактическую границу продолжения.** dot сверяет текущий HEAD, WIP, исходы операций, автора каждого общего изменения, готовые кандидаты, уровни доказательств, следующий потребитель и весь незавершённый остаток. Исторические ACCEPTED сохраняются для своей версии; публикация этого раздела не закрывает открытые результаты.
2. **Назначить целую доступную функцию.** Один автор принимает требования, необходимые зависимости, интеграцию и будущий продуктовый пакет исправлений. Текущее распределение и передача сверяются по фактическому состоянию. Готовая независимая разработка продолжается при занятости QA, если есть реальный маршрут проверки и контролируется непроверенный остаток.
3. **Подготовить пригодный вход на QA.** Автор передаёт неизменную сборку с exact source/candidate, размером и хешем пакета, конфигурацией, требованиями и полным проверочным scope, потребителями, воспроизводимым способом запуска, исходными доказательствами и явными ограничениями. Карта проверочной мощности показывает реальных исполнителей, их независимость, доступ к среде, время полного прогона и занятые общие ресурсы. Без измерений точный срок и экономия остаются неизвестными.
4. **Пройти полный цикл функции.** QA проверяет готовую версию по полному доступному объёму, сохраняет непроверенные сценарии и возвращает автору единый пакет замечаний. Автор выполняет причинный общий патч; новая точная версия проходит необходимые проверки и независимую оценку. Полный цикл блока не сокращается до одного удачного пути, раннего исправления первого дефекта или переноса PASS со старой сборки. Пока проверяется сохранённая версия, автор ведёт независимую готовую работу с сохранением WIP.
5. **Сохранить переходные обязательства Тестеров.** Весь открытый B02 и B14 Тестера-2 остаётся в его фактическом остатке до подтверждённой передачи; B14 не подменяет B02. После полного технического блока Тестер-1 продолжает B03 и далее по действующему порядку, без ожидания ownerAccepted, отменённого владельцем 28.10.2026. Ручная приёмка записывается отдельно. Собственная реализация Тестера получает отдельную независимую проверку.
6. **Проверять только относящиеся зависимости назначения.** B/C сохраняют возможность вести любую подходящую независимую функцию; restore/installed-проверки планируются там, где они нужны конкретному результату, а не как допуск ко всей работе. Исходники доноров, общий контракт и каждый потребитель сохраняют происхождение и одного согласованного автора.
7. **Сверить фактический переход.** Контроллер выполняет полный независимый аудит перехода и последующих согласованных контрольных событий; dot сначала исключает дублирующий аудит того же вопроса. Контроль охватывает требования, готовность передач, возраст непроверенного остатка, пропущенные контрольные точки и системные повторы. Самоаудит dot остаётся отдельной обязанностью и включает своевременность запуска Контроллера.

В существующих рабочих отчётах, аудитах и самоаудитах по каждому A/B/C и действующему Тестеру сохраняется понятная владельцу цепочка: конкретная пользовательская функция → что можно будет делать на выходе → фактически сделанное → остаток до выдачи → источник/время. Соблюдение метода оценивается по этой цепочке как «соблюдается», «нарушен» или «недостаточно доказательств».

Прогноз полной разработки, порученный Astra, ещё не получен. После передачи полного проверенного итога он станет checkpoint существующего журнала docs/project-audits/AUDITS.md и серверного /root/octoport-control/project-audits/AUDITS.md, с исходной датой, предпосылками и ограничениями; число и завершение до получения итога не проставлены.

Переход не перезапускает roadmap и не объявляет B02, B14 или другие блоки готовыми. Полный перечень фактически непроверенных сценариев и незавершённых зависимостей остаётся в существующих рабочих записях соответствующей функции.

### 2. Четыре разных порядка

### 9. SITE, выпуск и сопровождение

SITE — отдельный действующий scope, но его нужные страницы/OTP/install/privacy/support/reviewer route являются зависимостями продукта до B12/B19/B31/B32. Существующий holder передаёт нужный законченный результат; C не присваивается исключённый apps/site. SEO не добавляется автоматически.

Store имеет ранний собственный полезный slice и полный итоговый channel route. Сохранены submission/moderation/install/N→N+1/data preservation/rollback. Модерация может идти одновременно с независимой работой, не заменяет beta admission и не требует всех поздних блоков для первого безопасного slice.

Бесплатная beta включает контролируемое admission/capacity, наблюдение, реальные feedback/support и остановку/возврат при проблеме. Рост 100→200/300 не автоматический таймер. SUSTAIN сохраняет реальные исправления/регрессии и работу с обратной связью как конечные результаты общей программы. Инциденту назначается автор, независимая проверка и выпускной outcome; отдельный бесконечный поток автора/аудитора не создаётся.

Коммерция B33 остаётся отдельно: тариф/provider/checkout/webhook/reconcile/refund/expiry/grace/idempotency/уведомления. Simulated P4/P5 и source 303 сохраняются с происхождением; R2 review/45 PG открыты. Общая безопасность подписочного lifecycle проверяется раньше по нынешнему worker consumer, не ждёт real-money решения.

### Условный прогноз всей программы

Первый условный прогноз всей бесплатной программы — выход T3–T4, **до первого полного frozen QA handoff новой композиции**, не «после B02». Авторы/QA/reviewer дают в существующем PLAN по каждому результату полной программы:

| Величина | Как получить конкретно | Граница |
|---|---|---|
| Остаток реализации/стыковки | Имеющиеся source/diff/consumers и остаток по каждому из 216 случаев в исходной аналитической матрице; ограниченная экспертная оценка автора | Не измеренное время, если аналога нет; фактический source-review всех 59 не заявлен |
| Review/QA мощность | Именованные доступные участники и whole scope/groups; provenance/tool/env route; existing receipts start/end | Свободный чат не capacity; отсутствующий native доступ — открытый вход |
| Возвраты/rework | Истории нескольких exact candidates, common-cause findings, исправления/повтор | Не сумма всего календарного возраста; интервалы не выдумываются |
| Общие ресурсы | Existing env/DB/browser/profile/custodian/CI availability и фактический пик | Checkout не отдельная среда; CPU/wall/agent effort различаются |
| Внешние окна | Actual AI/login/SMTP/store/moderation/cohort/owner необходимые действия | Если срок не ограничен, верхний календарный bound открыт, а не ноль |
| Стоимость | Только доступные billing/token/CI/resource records | Меньше текста не cache hit; elapsed не денежный счёт |

dot сводит optimistic/рабочий/неблагоприятный сценарии с условиями и всей сетью зависимостей. Календарь ограничивается и critical path, и суммарной нагрузкой каждого дефицитного ресурса. Первоначальный диапазон может быть экспертным, но его состав/источник видимы. Неоценённая существенная строка имеет named input и этап получения оценки в T3–T4; её нельзя спрятать общим «позже».

Далее actual D39/полный B02 уточняют runtime/AI класс; Health/repair — свой; RBAC/DB/data/gold/browser/store/restore — свои. После каждого контрольного события пересчитывается весь остаток до beta/SUSTAIN, не только следующий номер. B31 день/внешняя модерация/beta-наблюдение не исчезают от дополнительных авторов. B33 оценивается после отдельного коммерческого решения, общая lifecycle safety — раньше.

Известные обязательные цепочки для расчёта критического пути:

T3–T4 дают первый ресурсно ограниченный расчёт, в котором перечисленные ветви сходятся; при смене assumptions пересчитывается весь прогноз. Owner acceptance и защищённые release решения отображаются отдельными ожиданиями, а не скрываются в active разработке.

### Ресурсное завершение и проверка эффекта

В существующей записи результата сохраняются создавший ресурс автор, точные входы, потребитель, исходное/пиковое/конечное место и условие завершения. Совместимые неизменные артефакты используются по применимости; fault/restore имеет реальную изоляцию. Сохраняются уникальные source/patch/oracles, отрицательные доказательства, пакеты и нужный rollback. После последнего потребителя завершение своих временных ресурсов подтверждается фактическим исходом в действующих границах. Уже материализованное и будущий резерв не вычитаются из доступного дважды.

В существующих checkpoint/feedback/PLAN отражаются scope, source ready, review/CI/QA start/end/block, полный пакет замечаний, исправление, квалифицированный состав, выдача, отдельная ручная приёмка и завершение ресурсов. Источник, часовой пояс и точность времени сохраняются; неизвестные интервалы и перекрытия не превращаются в выдуманную сумму.

Эффект оценивается по времени до сопоставимой пригодной функции и независимого installed verdict, возрасту очереди, причине возвратов, регрессиям/пропускам, пригодности QA-входа и ресурсному хвосту. Полнота — 21 техническое обязательство, 33 блока, 216 случаев и 45+8 вопросов. Фактическая денежная экономия требует доступных измерений. Смена текста, число коммитов и RUNNING не доказывают успех.

Полный независимый аудит Контроллера требуется по уже согласованным событиям: переход, перед B22/B31/B32, сорванная контрольная точка, существенное старение/рост очереди, повтор системной ошибки или существенное расхождение. dot исключает дубль покрывающего аудит вопроса. Остальные продуктовые milestones служат контрольными событиями программы, а не создают постоянный второй диспетчерский цикл. Самоаудит dot каждый час включает своевременность запуска Контроллера за прошедший интервал.
