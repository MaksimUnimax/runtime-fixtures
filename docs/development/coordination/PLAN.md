# Единый технический план Octoport

Это разрешённый объём существенной части проекта: довести расширение, backend, мониторинг и выпуск до проверяемой бесплатной беты, затем исправления по её результатам. Сайт/SEO разрабатываются отдельно. Монетизация и платные провайдеры не включаются автоматически.
Уже написанное не переписывать заново; проверять незакрытые критерии SPEC и выявленные риски. Старое слово ACCEPTED относится только к указанной версии и уровню доказательства.

Действует WORK_METHOD.md: ID A/B/C ниже обозначают сохранённые требования, а не исключительные права диалогов. OPERATOR встроен как отдельный интерфейс ручной проверки; после готовности пакета автор продолжает общий roadmap. Критерии продукта не сброшены.

## Приоритет ручной версии и мониторинга — 2026-09-28

[Roadmap R0–R4 / S0–S3](OWNER_TEST_AND_MONITORING_ROADMAP_2026-09-28.md) уточняет ближайшую очередь по прямому запросу владельца: Автор ближайшего сквозного результата сначала доводит точный пакет до проверяемой ручной выдачи, включая конечную матрицу всех доступных кнопок установленного расширения и обычный серверный путь. Другой доступный автор параллельно выполняет ограничение хранения мониторинга; состав определяется общей очередью без постоянной компонентной монополии. Уже начатое ограниченное доказательство завершается на безопасной границе; это не общий STOP и не перезапуск плана.

[Архитектура мониторинга](MONITORING_REPAIR_ARCHITECTURE_2026-09-28.md) связывает эталон, ограниченную историю, реальное поведение расширения, проверенный кандидат, ручную приёмку и существующие каналы выпуска. S0–S3 не становятся новым условием ранней ручной выдачи или магазинного минимума. Исторические ACCEPTED и текущие SHA сверяются по свежим receipts/notices; поздний STOP сохраняет приоритет.

DB/schema/migrations имеют одного автора конкретной сквозной задачи из любого A/B/C. Live authority, безопасная совместимость и backup/restore сохраняются; чужой активный scope не пересекать.

## Ранний магазинный путь — параллельно разработке

[STORE-0…STORE-4](../../product/readiness/PUBLICATION.md) — приоритетный параллельный путь. Аккаунты зарегистрированы по подтверждению владельца; ранняя подача/публикация при минимальной готовности уже разрешена. По [STORE_POLICY.md](STORE_POLICY.md) каждый канал подаётся сразу после готовности полезного безопасного среза, без ожидания всех A03/A04/B02/B04/B05/C05, других браузеров или C06. STORE-2/STORE-3 выполняются до C06: магазинные установка и N→N+1 входят в последующую общую приёмку. Нужный конкретному срезу backend/recovery проверяется; независимые будущие работы не становятся искусственным gate.

Автор конкретного выпуска отвечает за данные/UX при обновлении, совместимость клиента/backend, точный пакет, store ID, канал, reviewer flow и evidence с независимым review. Владелец выполняет подтверждения аккаунтов, первую Windows установку/обновление и смысловую приёмку. Программистские операции ему не перекладываются. Ограниченная магазинная версия не означает разрешение открытого набора; полная бета остаётся C06→C07.

## Продолжение после готовности store-кандидата

По [решению владельца о непрерывной работе](CONTINUOUS_ROADMAP_POLICY.md) ранняя подача не завершает этот план. A/B/C самостоятельно переходят к следующему незакрытому требованию общего PLAN, включая автоматизируемые части docs/product/readiness. Store-кандидат фиксируется отдельно; дальнейшие изменения не подменяют проверенные байты. До общего WAITING_INPUT требуется проверить всю разрешённую очередь и объяснить блокировку каждого остатка. Текущие назначения и две ближайшие работы хранятся в состоянии/notice, а не переписывают историческую приёмку таблиц выше.

## Общие зависимости и контроль качества

- Общие Zod/OpenAPI/BrowserFamilies/lockfile меняет один автор конкретной сквозной задачи с тестами всех потребителей. Этот же принцип действует для миграций; номера и timestamps выдаются из актуального main.
- C01 необходим до любой release acceptance. Его блокировка не мешает обычной разработке.
- A02+B03 принимаются совместно как протокол переноса; отдельно зелёные стороны не означают надёжный перенос.
- A04+B02+B04 дают реальную Q1-C цепочку. Нельзя закрыть её synthetic fixture.
- B05+C05 дают эксплуатационную готовность. Сам JSON harness её не даёт.
- Для каждого browser-release нужен A03; отсутствие среды оформляется как незакрытый release gate этого браузера.
- Небольшие backward-compatible куски интегрируются по мере готовности. «Соединим всё в самом конце» не является методом этой программы.

## Отложенное и стоп-факторы

Коммерция/оплата, сайт/SEO, redesign API, смена модели безопасности, массовый refactor и удаление исторических серверных копий не входят автоматически.
Production publication, irreversible data changes и получение/использование чужих личных сессий не разрешены этим планом.
Временные обходы и незакрытые review requests не стираются после compaction; входят в runtime state и checkpoint receipt.
