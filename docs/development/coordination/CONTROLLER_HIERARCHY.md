# Два уровня контроля Octoport
Основание: прямое решение владельца 2026-09-29 09:14 +05 и уточнение09:28+05: новый контроллер имеет те же функции и полномочия, что прежний; единственная разница — дополнительный периодический аудит. Это дополнение действующего метода, не новая разработка и не отмена PLAN/SPEC. При расхождении со старым описанием единственного контроллера действует эта политика. Прямые указания владельца и более поздний STOP сохраняют приоритет.

## Иерархия и цель
| Участник | Ответственность |
|---|---|
| Владелец | Продуктовые цели, приоритеты, прямые разрешения/STOP, необходимые человеческие действия. Не выполняет обычную техническую диагностику. |
| L2 — старший контроллер в прежнем Work-диалоге | Периодически проверяет A/B/C и L1: качество решений, реальный прогресс, архитектуру, риски, достаточность доказательств. Может вмешаться в конкретный проблемный участок. |
| L1 — промежуточный контроллер в отдельном обычном чате | Полноценный контроль всего проекта: цели и roadmap, архитектура в рамках задачи владельца, зависимости, код и приёмка, ресурсы, ручная версия, магазины и мониторинг. Сам принимает технические решения, управляет потоками и при необходимости пишет код на тех же условиях, что прежний контроллер. |
| A/B/C | Автономно проектируют и пишут код в своих прежних областях. C один интегрирует main и выполняет разрешённые live операции; B один пишет DB/schema/migrations. |
| Серверный Codex | Не более одного ограниченного ребёнка на A/B/C; только gpt-6-luna; без нового четвёртого профиля, платного API и fallback. |

Цель — уменьшить расход ресурса старшего контроллера, сохранив инженерную проверку. У L1 нет дополнительного требования согласовывать свои действия с L2. Не добавлять обязательную подпись L2 на какую-либо обычную уже разрешённую работу и не превращать L1 в пересказчика состояний. L1 должен читать код, проверять доказательства и доводить доступные действия до результата.
Чаты не наблюдают друг друга автоматически. Работа возможна во время активного диалога/действующего автопромпта с доступными инструментами. Эта политика не устанавливает нового daemon, расписания, Telegram poller или автоматической фоновой сессии.

## Полномочия L1
L1 имеет те же контроллерские возможности и обязанности, что L2. Обозначения уровней нужны для учёта последующих аудитов, а не для урезания полномочий. Новому диалогу не требуется учитывать своё положение в иерархии при выборе разрешённой работы.
L1 самостоятельно проводит обычный controller review, проверяет exact diff/HEAD/CI/окружение, пишет адресные замечания с владельцем и критерием закрытия, проверяет исчерпание очередей и согласует независимые задания внутри принятого roadmap.
L1 вправе закрывать обычный review_pending A/B/C через существующий control.py ROLE reviewed --receipt после фактической проверки. Четырёхчасовой сигнал обрабатывается L1; L2 не требуется на каждом таком сигнале. review_pending не равен STOP.
L1 сверяет и сопровождает уже выданные разрешения на технический Octoport вход, отдельный пилот и ранний магазинный минимум. Исполняет соответствующий поток по прежнему разделению. Не запрашивать заново то, что разрешено; не расширять область разрешения.
L1 может исправить небольшой независимый дефект кода/документации в отдельной назначенной ветке/копии. Сначала проверить активные пути, записать scope/base/потребителей. Прочесть изменённый код и проверить по риску. Передать exact кандидат C; собственный код L1 принимает другой участник, не сам L1.
L1 не переписывает активные файлы потоков, не автор DB/schema/migrations, не продвигает main, не подменяет ручную приёмку и не снимает явный STOP. Права ОС/инструмента не расширяют организационные полномочия.
Действующие product/privacy/no-replay/trust/browser-contract требования сохраняются. Ограничения владельца действуют одинаково для обоих контроллеров: нельзя самовольно расширить продуктовый scope, отменить модель безопасности, изменить публичные обещания/оплату/лимиты набора. Архитектурные и технические решения внутри порученного проекта L1 принимает самостоятельно, обосновывает, проверяет и документирует; дополнительное разрешение L2 для этого не нужно.
L1 может проверять и закрывать замечания прежнего контроллера после выполнения их объективных условий, оставляя отдельный resolution receipt с автором и evidence. Исторический исходник замечания не стирать. Только реально заданные владельцем или техническим протоколом специальные границы сохраняют свои условия; сама новая иерархия не создаёт L2-only запрета. Не объявлять чужую ручную/внешнюю приёмку состоявшейся.

## Взаимодействие и защита от двух противоречащих контроллеров
Оперативные файлы: /root/octoport-control/controllers/hierarchy.json и controllers/L1/state.json. L1 пишет свои audits/<UTC-ID>/, decisions.jsonl и escalations/. L2 пишет отдельные controllers/L2/**. У сообщений разные ID: ROLE-L1-... и ROLE-L2-....
Перед новым назначением читать свежие входящие и более новые решения L2. Не выдавать вторую задачу на тот же результат, если действующая уже есть: обновить её зависимость/приёмку отдельной связанной записью.
Не править чужой request/notice. Ответ писать отдельно с reference на исходный ID. L2 может пересмотреть решение L1, сохраняя прежнее evidence и причину; L1 применяет это на безопасной границе, не откатывает автоматически коммиты/данные.
Для короткого изменения общих controller метаданных использовать flock controllers/coordination.lock. Для A/B/C state — только control.py или их ROLE.lock с атомарной записью и повторным чтением перед изменением. Не держать lock на время чтения, браузера, CI или ожидания человека.
Для общей правки кода/документации использовать явное назначение путей и единственного автора. При одновременной работе L2 резервирует только нужный scope; остальная работа L1/A/B/C продолжается.
Не запускать control.py с ролью L1: существующая CLI принимает только A/B/C. Для независимого тяжёлого прогона L1 заранее согласует с C изолированный тестовый scope и существующий supervisor; не создаёт четвёртую DB/не обходит cgroup/не занимает чужую активную БД. Малые проверки без серверов разрешены по RESOURCE_POLICY.

## Периодический внешний контроль
L1 не ждёт старшего диалога для архитектуры, координации или проверки, которые прежний контроллер выполнил бы самостоятельно в порученных пределах. Сложную задачу исследовать инженерно, сохранять гипотезы и принимать обоснованное решение.
Если не хватает именно решения/действия владельца, полномочий, доступа либо после обоснованных попыток остаётся опасная неопределённость, сохранить конкретный запрос контроля с воспроизводителем и предложением. Блокировать только зависимое опасное действие, продолжать независимую работу. Это прежний порядок контроллера, не новая лестница одобрений.
Владелец периодически запускает L2, который независимо проверяет и потоки, и L1, помогает/исправляет по результатам. Его отсутствие не останавливает полномочия L1. Новую обязательную стадию L2 перед main, пилотом, пакетом или Submit не вводить.
После существенной вехи сохранить сравнение «было/стало», доказательства и открытые ограничения, чтобы внешний аудит не требовал пересказа всей переписки. Это отчётность, а не ожидание разрешения.
Недоступный инструмент даёт UNVERIFIED/ACCESS_BLOCKED и точное объяснение; нельзя выдавать память/старый отчёт за новый аудит.

## Журнал L1 и приёмка его работы
В каждом цикле сохранить: UTC время; цель; фактический main и A/B/C HEAD/dirty/status; читаемые источники; выводы с уровнем доказательства; решения/замечания и их исполнителей; проведённые проверки с exit/log; live изменения с разрешением; незакрытые риски; следующий результат.
Отдельно хранить последнюю baseline L2 и агрегат изменений после неё: принятые кандидаты, реально закрытые требования, новые дефекты, действия L1, изменения работающего сервера, ручной/store статус. Не измерять успех количеством коммитов/тестов.
decisions.jsonl только дополняется. Исторические FAIL и отменённые решения сохраняются. Не подменять отчётом с новым временем неизменённые старые измерения.
state.json — короткий указатель, а не бесконечная история: текущая задача, до двух готовых следующих, last_audit, last_reviewed_main, open_findings, pending_owner_actions, L2_baseline, L2_requests, STOP/resume сведения.
L2 при возвращении сначала сравнивает baseline со свежим состоянием и читает журнал L1; проверяет наиболее рискованные изменения/часть закрытых замечаний независимо, а не повторяет весь suite без причины.

## Экономный рабочий цикл
Первый запуск читает обязательные правила полностью. Потом сравнивать SHA/hash правил и перечень изменённых файлов, перечитывать изменённое и относящиеся к задаче контракты.
Проверять новые кандидаты и реальные блокеры; переиспользовать точное неизменившееся evidence. Не запускать повторные сборки/браузеры/CI ради занятости. Не увеличивать документацию без проверяемого решения.
Общий WAITING_INPUT требует свежего полного scan PLAN своей роли/контроля. Если доступной работы действительно нет, честно зафиксировать это, а не выдумывать задачу. После внешнего блокера перейти к следующей доступной работе.
Обязательны ресурсы и готовность ранней публикации при каждом аудите; критерии RESOURCE_POLICY/STORE_POLICY сохранены.

## Первый запуск и STOP
Промпт нового L1: PROMPT_CONTROLLER_L1.md; runtime entry /root/octoport-control/controllers/L1/START_HERE.md. Первое прямое вставление владельцем разрешает запуск L1 и записывается одноразовым receipt OWNER_L1_DELEGATION_20260929T041408Z.
Повтор того же стартового receipt не снимает последующий STOP L1. Запуск L1 не снимает STOP A/B/C и не выдаёт новые live полномочия. Владелец указывает область STOP; если область общей остановки неясна, прекратить новые рискованные действия, сохранить состояния и уточнить.

## Обязательный аудит организации — решение владельца 2026-09-29 12:54 +05

Оба контроллера при каждом аудите и в каждом итоговом отчёте проверяют организацию работы, свои решения и повторение старых ошибок. Применять [ORGANIZATION_AUDIT_POLICY.md](ORGANIZATION_AUDIT_POLICY.md) и [шаблон отчёта](ORGANIZATION_AUDIT_REPORT_TEMPLATE.md).
Единая текущая база: /root/octoport-control/controllers/organization/errors.json; история: events.jsonl в той же директории. Датированный seed в Git — исторический снимок, не второй живой реестр.
Обязательны сравнение со старой записью, установленная причина повтора, фактический статус прежнего исправления, ответственный и проверка предотвращения. Костыли, скрывающие симптом вместо устранения причины, запрещены; неизвестную причину нельзя выдумывать.
Назначение задачи, написание кода и запись политики не доказывают исправление: нужны применение и подтверждённый эффект. Владелец получает понятное объяснение организации, новых ошибок, реально исправленного, повторов и оставшегося.
Это не дополнительное согласование с L2 и не барьер текущей выдачи. Поздний STOP и прежние владельцы main/DB сохраняются.
