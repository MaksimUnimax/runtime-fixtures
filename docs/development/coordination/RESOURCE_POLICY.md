# Ресурсы и скорость разработки

Прямое правило владельца от 2026-09-23: сохранять качество и увеличивать полезную скорость. Стоимость дополнительной ОЗУ менее важна, чем время разработки. Контроллер при каждой проверке оценивает, позволит ли увеличение памяти ускорить нужную параллельную работу, и сообщает об этом владельцу с замерами и рекомендуемым объёмом. Не ждать аварии или отдельного вопроса о покупке памяти.

## При каждом контроле Work

Снять свежие показатели: MemAvailable, swap, memory pressure, свободный диск и inode; проверить OOM, активные тестовые группы, их возраст, назначение, владельца, текущую память и пик. Для общего расхода учитывать cgroup/PSS; сумму RSS не выдавать за физическую память.

Отдельно определить:

1. Нужная активная работа. Сохранить параллельность; если ОЗУ ограничивает её, предложить увеличение памяти. Не подменять развитие сервера постоянной очередью тестов.
2. Обоснованное ожидание. У каждого оставленного стенда есть владелец, потребитель, цель и срок; процессы не оставляются на неопределённое время «могут понадобиться».
3. Остатки законченной работы. Сначала объяснить владельцу точные процессы/каталоги, происхождение, объём и доказательство ненужности. До этого не очищать. Перед отдельной очисткой получить подтверждение конкретного перечня; при необходимости дать полный ограниченный промпт серверному Codex. Не перекладывать диагностику на владельца.
4. Неизвестное назначение. Сохранить и расследовать; возраст и размер не являются разрешением удалить.

В отчёте контроллера обязательны состояние ресурсов и вывод об ускорении: есть ли польза от добавления ОЗУ сейчас, какие задания смогут перекрываться, исходные замеры, необходимый резерв и рекомендуемый объём. Если измерений недостаточно, назвать недостающие данные, а не обещать коэффициент ускорения. При повторных отказах допуска `RESOURCE_WAIT` не продолжать бесконечные повторы: вынести владельцу очистку установленного мусора либо увеличение ОЗУ для нужной нагрузки. Покупку/изменение тарифа выполняет владелец.

## Жизненный цикл нового тестового запуска

Все создающие браузеры, серверы, worker-пулы или значительную нагрузку команды, включая одиночные диагностические пробы, выполнять через `control.py ROLE heavy`. Обычное редактирование, чтение, Git и ограниченные небольшие unit-проверки продолжаются параллельно. A/B/C и их разрешённые Codex не сериализуются в одного исполнителя.

Каждый новый запуск получает собственную transient systemd service/cgroup, отдельную квитанцию и конечное время жизни. `KillMode=control-group` закрывает всю созданную группу после успеха, ошибки, сигнала, тайм-аута или потери управляющего runner, включая `setsid`/daemon-потомков. Это штатное завершение собственных новых процессов, заранее разрешённое запуском; оно не является очисткой старых файлов, контейнеров или чужих процессов.

Нельзя запускать `nohup`, `&`, `setsid`, отдельный `systemd-run` или Docker-задачу вне управляющей группы ради обхода жизненного цикла. Существующие постоянные сервисы и disposable DB отдельно учтены; runner не останавливает их. Новые контейнеры/долгоживущие стенды требуют отдельного учёта владельца и явного завершения, поскольку Docker daemon не является потомком тестового процесса. Не удалять старые профили/логи вместе с процессами: evidence сохраняется.

## Допуск по ёмкости вместо одного общего слота

Admission lock удерживается только на время решения о запуске. Несколько тестовых групп работают одновременно, если хватает доступной памяти с учётом ещё не использованной части их бюджетов. Нет лимита «один процесс», «один браузер» или «один тест на сервер». Общий старый `heavy.lock` используется в shared-режиме только для совместимости: старый exclusive-wrapper не может наложиться на новую схему.

Резерв: 1024 МиБ сверх текущей фоновой нагрузки, которая уже учтена MemAvailable. У каждой группы MemoryMax по её бюджету и MemorySwapMax=0: ошибочный тест не должен увести сервер в swap thrashing. CPU quota не вводится; доступные ядра можно использовать полностью. TasksMax=1024 защищает от неконтролируемого размножения в одной группе, не ограничивая нормальный набор подпроцессов.

Начальные профили — оценки для допуска, а не доказанные максимумы всех тестов:

| Профиль | Начальный бюджет, МиБ | Назначение |
|---|---:|---|
| focused | 512 | небольшая ограниченная проверка |
| browser | 1536 | браузерная проба без двух Next dev |
| integration | 2048 | интеграционный прогон |
| build | 3072 | сборка |
| e2e | 4096 | полный серверный браузерный набор с API и двумя Next dev |
| general | 2048 | совместимость старых команд без профиля |

Без явного профиля `test:e2e`/`playwright test` выбирает e2e, `test:integration` — integration, иначе general. Предпочтительно указывать профиль явно. Фактические cgroup peaks сохраняются; следующие бюджеты автоматически увеличиваются при приближении к пределу или OOM. ООМ внутри тестовой группы — ENVIRONMENT_RESOURCE_LIMIT, не доказанный дефект продукта и не PASS. После исчерпания бюджета сначала пересмотреть оценку/нагрузку, не ослаблять тест.

`--memory-mib` допускается для конкретной обоснованной более узкой/крупной задачи. Значение и признак ручной оценки сохраняются. Нельзя уменьшать оценку того же упавшего прогона ради обхода допуска. После увеличения ОЗУ параллельная ёмкость растёт автоматически, глобальный лимит «один heavy» возвращать нельзя.

Примеры:

```bash
python3 tooling/coordination/control.py A resources
python3 tooling/coordination/control.py A heavy --profile browser -- python3 path/to/browser_probe.py
python3 tooling/coordination/control.py B heavy --db --profile e2e --timeout-seconds 3600 -- pnpm test:e2e
python3 tooling/coordination/control.py C heavy --profile focused -- node --test path/to/focused.test.mjs
```

Команды проверки продукта берутся из действительного package.json/тестового плана; примеры не создают новую обязанность прогнать полный набор. Код 75 означает, что конкретная новая задача не допущена; остальные работы не останавливаются. Одновременные DB-прогоны одной роли не допускаются, поскольку разрушают одну disposable schema; разные роли имеют разные DB.

Реестр: `/root/octoport-control/resource-jobs/<id>/receipt.json`. Он содержит назначение по профилю, роль, память/пик, время, результат и доказательство завершения группы, без argv/environment/секретов. Приватный payload для передачи окружения имеет права 0600, читается только новым worker и сразу удаляется. Payload не является пользовательским артефактом. Не выводить среду в логи.

Отказ systemd/cgroup проверки запрещает только новый ресурсный запуск. Небезопасного fallback с обычным Popen нет. Исправность подтверждается отдельными live-тестами: три одновременно работающие роли, detached child, ошибка, тайм-аут, SIGKILL runner, ограниченный cgroup OOM и сохранность постороннего контрольного процесса. Они не заменяют продуктовую приёмку.
