## Замечания B к активной реализации

Статически подтверждён противоположный порядок захвата SQL-строк:
- сохранение повторного callback: scheduled FOR UPDATE → receipt FOR SHARE;
- prune/retire: receipt FOR UPDATE → scheduled UPDATE/FOR UPDATE.

Такой порядок допускает взаимную блокировку. B получил точную последовательность и требование двухсоединительного PostgreSQL воспроизведения/регрессии с единым порядком блокировок.
Дополнительная проверка: сбой после persist, до incident processing; затем reconcile, новые наблюдения, GC и поздний callback. Нельзя потерять ещё не обработанный BROKEN результат и вернуть фиктивный NOOP.
Это source-review риски, не заявление о воспроизведённой ошибке живой БД. Контроллер не изменял DB/migration/WIP B.
